## P01〜P04・P06：反復実践の参照判断

以下は演習の期待値と採点時の着眼点です。学習者が実行した記録ではありません。本人が予測・変更・実行し、実際の出力とRunを提出したかは別に検証します。

### P01：配列の要素参照とコピー

`first = items[0]`は要素オブジェクトを参照します。`first.qty = 4`の後は`items[0].qty = 4`、`items[1].qty = 2`です。さらに`copy = { ...items[0] }`とし`copy.qty = 5`に変更しても、`items[0].qty`は4のままです。ここでのスプレッド構文は浅いコピーです。入れ子のオブジェクトまで独立するとは説明しません。予測と実行出力が一致するか、添字とプロパティの意味を区別できるか確認します。

### P02：上限判定の境界

次は数量上限**のみ**を判定する関数例です。実Shopの数量更新APIを呼んでいるわけではありません。

```ts
function canAdd(current: number, add: number, stock: number, limit: number): boolean {
  return current + add <= Math.min(stock, limit, 99);
}
```

| 入力 `(current, add, stock, limit)` | 計算 | 上限判定 |
| --- | --- | --- |
| `(1, 1, 3, 5)` | `2 <= 3` | `true` |
| `(2, 2, 3, 5)` | `4 > 3` | `false` |
| `(0, 3, 3, 5)` | `3 <= 3` | `true` |
| `(2, 0, 3, 5)` | `2 <= 3` | `true`（上限内という意味のみ） |

最後の`add = 0`は上限超過でないことを示すだけです。実際の「0点追加」を業務操作として許すか、既存の1点を0点へ更新・削除できるかは、この関数だけでは証明できません。負数や整数以外の入力も別の入力検証の責務です。本人が書いた条件分岐と実出力を必ず照合します。

### P03：構文・型・実行時の失敗

括弧の不足は構文解析時の失敗です。`number`引数へ文字列を渡した例は、課題で指定された`workspace/M05/p03-type-error.ts`を対象に`tsc --noEmit`で検出し、非0終了と診断内容、修正後の0終了を保存する必要があります。`tsx`による実行成功は型検査の成功を意味しません。

未定義の変数をJavaScriptとして実行すると`ReferenceError`となりますが、TypeScriptのソースであれば実行前に未定義名の型診断も発生し得ます。型・構文の診断と実行時例外を一つの失敗にまとめず、各ファイル・コマンド・終了コードを対応付けます。ここに挙げた診断は参照例であり、本人の実行結果の代わりにはなりません。

### P04：Promiseと`await`後の値

`Promise.resolve("ready")`を返す`async`関数の戻り値はPromiseです。戻り値そのものを記録した場合はPromiseを扱い、`await`した場合は解決後の文字列`"ready"`を扱います。ConsoleがPromiseをどう表示するかは実行環境によって異なるため、出力表示の文面だけで型を断定しません。`await`は結果の待機と後続処理の順序を規定しますが、固定の`waitForTimeout`を入れる根拠にはなりません。予測、実行コード、実際の順序を対比します。

### P06：弱いAI修正の採否

`expect`を削除すると、商品詳細への正しい遷移先を確認するAssertionが消えるため棄却します。`waitForTimeout(5000)`の追加も、Locator不一致や業務結果の誤りを解決した証拠にはならず棄却します。Locatorを対象商品とrole/nameから特定し、実在する`/products/product-mug`へのリンクを業務Assertionとして残します。修正前後の異なるRun・spec SHA・JSON report・終了コード・Traceの該当箇所を提出させ、未実行をPASSとしません。

## P05：複数明細のLocator境界を確認する参照spec

[Cart Locatorのread-only参照spec](../playwright/M05/cart-locator-inspection.spec.ts)は既存の`resetScenario(default)`を使い、guestの`product-mug`（セラミックマグ）と`product-low-stock`（コンパクトタオル）を画面から追加して2明細にします。Cart全体の`combobox[name=数量]`と`button[name=削除]`はそれぞれ2件となり、グローバルなLocatorの一意性は保証されません。`article.cart-item`を商品名リンクで絞った後、数量の値と削除buttonの一意性を検査します。**削除はクリックしません**。同一商品に複数SKUがある場合は商品名だけでは不十分なので、SKUと明細件数を追加確認する必要があります。CSSクラスは現実装への依存であり、学習者はrole/name・label・表示文字列の候補と保守性を比較して採否を判断します。

専用Webサーバーを利用できる環境では`PLAYWRIGHT_TEST_ROOT=training/ai-assisted-qa-course/assessment/playwright/M05 pnpm exec playwright test --config playwright.ai-assisted-qa.config.ts cart-locator-inspection.spec.ts --project=ai-assisted-qa-chromium`で独立実行できます。新課程専用Configは`PLAYWRIGHT_TEST_ROOT`を許可されたassessment領域へ解決し、`output/training/ai-assisted-qa/playwright-result.json`へJSON reportを出力します。旧`playwright.training.config.ts`の`training-chromium`は別のreporter/出力先を持つため、P05の新課程実行証拠には混用しません。この直接実行は`course:run`のRun receiptを生成しないため、HEAD・spec SHA・JSON report・終了コードを別途対応付けて保存します。参照specの存在や静的構文検査は実ブラウザPASSではなく、実行したHEAD・report・証拠を別途照合します。本人のP05提出は参照specの転記だけでLevel 2と判定しません。
