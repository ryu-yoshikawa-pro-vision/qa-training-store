# M04 模範成果物と判断根拠

> publicなqa-training-storeに置く通常Markdownです。学習用配布からの除外は秘密保持ではありません。文面一致ではなく意味・出典・判断・証拠を評価します。

## 成果物の標準例

公開のレビュー入力で根拠のない期待結果、Case重複、条件・境界の欠落をBR/ACと照合し、重大度、影響、修正を返す最も早い責任工程を記録する。不明な仕様は質問として残し製品バグと断定しない。Unit/Integration/Component/E2Eの観測範囲・フィードバック速度・費用を比べ、再実行価値が高く安定した項目をAutomate、判断待ちをLater、費用に見合わないものをDo not automateとする。公開資料には固定された公開例の分析を載せる。実際の本人判断は評価時に新しい具体条件を提示して確認し、その条件文・値は公開資料に事前保存しない。

## 公開レビュー候補への完成回答

ここでは[`public-review-cases.md`](../../inputs/M04/public-review-cases.md)に記載された候補だけを判定します。正式な評価で初めて提示する条件はこの模範・採点資料へ含めません。資料内にはseverityの数値尺度が定義されていないため、重大度は高/中/低の根拠を文章で示し、未定義の数値を割り当てません。

### `CASE-CART-CANDIDATE-01`：自動補正の期待値

| 項目 | レビュー結果 |
|---|---|
| 問題箇所 | 操作前数量2から絶対数量6へ変更しようとしたとき、期待値を上限5へ自動補正するとしている。提案の根拠欄も空欄 |
| 仕様根拠 | `BR-CART-001`は同一SKU合計が在庫・購入上限・99の最小値を超えないこと、超過操作は全体を拒否して操作前数量を保つことを規定する。`AC-CART-001`も自動補正しないことと現在数量維持を受け入れ条件にする |
| 正しい期待結果 | 状態`default`では在庫20、購入上限5、上限99のため有効上限5。絶対数量6の指定全体が拒否され、自動で5へ変わらず、カート数量は2のまま |
| 修正対象 | Caseの期待結果と根拠欄。必要なら上限5と操作前数量2の観測欄を明記する |
| 影響・重大度 | 高。誤ったオラクルが自動補正不具合を正しい結果として通し、購入数量・在庫・金額の不変条件違反を隠す。根拠は`RISK-CART-001`およびBR/AC |
| 検証層 | Integrationを第一候補にする。上限拒否と永続状態の不変条件を安定したSeedで反復検証でき、Web E2Eより準備・実行費用が低い。画面の拒否表示自体が対象なら、その表示だけをComponent/Web E2Eで補う |
| 既存Caseとの関係 | 訂正後の条件・操作・期待結果は`CASE-CART-BASE-01`と同じ。正規Caseは`BASE-01`を使い、この候補から別の実行Caseを追加しない |
| 自動化 | Candidate-01単独では **Do not automate**。同じ検証を行う正規Case`CASE-CART-BASE-01`をIntegrationで一件だけAutomateする |

### `CASE-CART-CANDIDATE-02A / 02B`：重複Case

両者はID以外のRole、State、商品、操作前数量1、絶対数量2、成功期待値、根拠が一致するため、同じ振る舞いを測る完全重複です。`BR-CART-001`の上限内変更を代表する`02A`を正規Caseとして残し、`02B`は実行対象から除きます。既存のCoverage表、Risk→Condition→Case参照、Test IDリンクがある場合は`02B`から`02A`へ更新し、どの参照も切れたまま削除しません。`02A`が同条件を実際に実行し、上限内の許容動作へのリンクを保持することを確認すれば、`02B`を除いても対象条件のcoverageは失われません。

| Case | 影響・判断 | 自動化 |
|---|---|---|
| `02A` | 正規Caseとして残す。高頻度の基本操作を一件で表せる。 | **Automate**。同じIntegration suiteに一件だけ置く |
| `02B` | 重複Caseとして参照を移した後に除く。重複は保守・実行費を増やすが、独立した製品条件を追加しない。重大度は低 | **Do not automate**。`02A`があるため2つ目を実装しない |

### `CASE-CART-CANDIDATE-03`：操作前数量の欠落

操作前数量がないので、拒否後に同じ数量が保たれたかを比較できません。Seed名から現在数量を推測したり、更新結果だけでACを満たしたと判定したりしません。修正Caseではdefault Seed、`variant-basic-shirt-01`、操作前数量2をセットし、数量2を表示/データで観測した後、**絶対数量6**への変更を試みます。期待結果は操作全体の拒否と数量2の維持です。実行前数量が観測できなければ、結果は未確認のままにしてデータ準備または観測方法を確認事項として残します。これは入力の欠落であり、それだけを製品不具合とは判定しません。

未修正の候補は自動化を**Later**とします。前提値のないままテストを登録すると、失敗・成功のどちらも不変条件を証明できません。操作前数量を明示してReset後に観測できるようにします。値を2とするなら、Candidate-01および`CASE-CART-BASE-01`と同じ検証になるため、正規Case`BASE-01`へ統合し、新しい自動テストは追加しません。別の操作前数量など、仕様上異なる条件を確認する必要がある場合だけ、その根拠とcoverage上の便益を示して別Caseの要否を判断します。

### 自動化対象のまとめ

| 対象 | 層と判断 | 費用・リスク・安定性 |
|---|---|---|
| `CASE-CART-BASE-01`（Candidate-01の正規Case） | Integration / Automate | 在庫・数量整合性の影響が高く、固定Seedの再現性が高い。Candidate-01と同じ検証は既存Case一件で確認し、重複を追加しない |
| Candidate-01 | Do not automate as a separate test | 期待結果を仕様どおり訂正した後は`CASE-CART-BASE-01`と同じ検証責務になるため、既存Caseへ統合 |
| Candidate-02A上限内変更 | Integration / Automate | 基本操作の安定した回帰確認として一件残す |
| Candidate-02B重複 | Do not automate | 02Aと同じため、自動化すると結果を増やさず実行・保守費だけ増える |
| Candidate-03未修正入力 | Later | 操作前数量を確定・観測できるようにするまで、期待値を実証できない。値が2なら`CASE-CART-BASE-01`へ統合し、別テストを増やさない |

ここでの判断は公開された4候補に対する模範です。提出者の新しい未提示条件への反応を代替せず、実製品の実行結果やCI成功を主張しません。

## 評価時に確認する観点

1. 欠落・重複・根拠なし期待結果を公開入力で検出する
2. 指摘に重大度・仕様根拠・影響・修正先がある
3. 自動化判断に再実行価値と費用を含む
4. 仕様不明と再現確認済みの製品欠陥を分ける
