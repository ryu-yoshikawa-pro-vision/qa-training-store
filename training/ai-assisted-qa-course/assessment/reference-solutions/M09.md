# M09 模範成果物と判断根拠

> publicなqa-training-storeに置く通常Markdownです。学習用配布からの除外は秘密保持ではありません。文面一致ではなく意味・出典・判断・証拠を評価します。

## 成果物の標準例

Workflowはevent/trigger、Jobは依存と実行環境、Runnerは実行機、stepはbuild/test等、ArtifactはRunに保存するファイルである。対象commit SHAとRun/Check/Artifactを対応付け、install/build/test/uploadのどこで失敗したかに応じたlogを調べる。公開標準Runnerとprivate/larger runnerの料金条件を混同しない。最小権限を使い、Secretをlog/Artifactへ出さず、Training CIに正式deploy権限を加えない。遅さを理由に品質ゲートを無効化せず、必要な検証範囲と実行費用を比較する。

## 評価時に確認する観点

1. Trigger/Workflow/Job/Runner/Step/Artifactの責務を説明する
2. PR HEADとArtifactのtarget SHAを照合し、Run・Check・Artifactが同じ実行に属することを確認する。Run/Checkにmerge SHAが記録される場合はPR headと区別する
3. 失敗段階から調査ログを選ぶ
4. 料金・権限・Secret・deploy境界を示す

## P01〜P06：別条件のCI設計・証拠判定の参照判断

以下は提出物の採点用の判断例です。学習者の実CI実行やGitHub上のRunの存在を示すものではありません。

### P01：手動起動だけに変えた案

基準の`pull_request` triggerと違い、`workflow_dispatch`では`github.event.pull_request.head.sha`が利用できません。別案では、実行時に選んだref・checkout後の`git rev-parse HEAD`・PR最新HEADを別々に照合します。選択refがPR HEADと一致することをAPIやPR画面で確認できなければ、「PR最新HEADの検証」は未確認です。triggerだけを差し替えて`EXPECTED_HEAD_SHA`を残す修正は不採用とします。手動案は実行されない期間が生じるため、その間の新commitは未検証です。元の基準案と別名`.disabled`案の両方を残し、実workflowへ配置しません。

### P02：PR HEADとmerge SHA、Run/attemptの区別

`pull_request` workflowの`github.sha`はPRの検証用merge commitを指す場合があり、現在のPR head SHAと同一と推定しません。基準案は`github.event.pull_request.head.sha`をcheckoutし、実際の`git rev-parse HEAD`を`EXPECTED_HEAD_SHA`と比較し、`target-sha.txt`に記録します。PR更新後の旧Runは対象HEADが異なるため最新検証へ流用できません。同じRun IDでもattemptが違えばCheck/Artifactを混用しません。`if: always()`のArtifactはテスト失敗時にも生成され得ますが、アップロード成功だけでテスト成功にはなりません。Run ID、attempt、Check結論、checkout SHA、Artifact内SHA、実行spec、JSON結果を対応付けて判断します。

### P03：合成ログA/B/Cと別条件X/Y/Zの分類

| 条件 | 最初に失敗したstep・実行範囲 | 評価時に確認する根拠 |
| --- | --- | --- |
| A | Buildでfailure。Playwright testsと`if: success()` uploadはskipped | Buildのunresolved import、step conclusion。テスト未実行 |
| B | Playwright testsでfailure。後続`if: always()` uploadはsuccess | 期待数量3に対し実際2のAssertion、JSON結果、ArtifactはテストPASSの証拠にならない |
| C | Playwright testsはsuccess、`if-no-files-found: error`のuploadでfailure | Artifact対象pathと実ファイル、upload設定。証拠を保存できたとしない |
| X（架空） | Browser導入でfailureなら後続テストは未実行の可能性 | 導入stepの結論と後続stepの実際の結論を確認 |
| Y（架空） | テストPASS後にuploadがfailure | test結果とArtifact保存の結果を別々に報告 |
| Z（架空） | checkoutが成功しても期待SHAと不一致なら証拠不採用 | `git rev-parse HEAD`、対象PR HEAD、SHA照合stepとその結論 |

A/B/Cは`failure-cases.md`の合成例、X/Y/Zも架空の追加条件です。実Runの実行済み・skipped・不明はGitHub Actionsのstep記録を見ずに確定しません。

### P04：頻度変更、費用、未検証期間

「PR更新ごとに1回起動し、再実行・重複イベントなし」という設問の仮定では、A「1日3回×7日」は自動Run **21回**、B「週2回×7日」は自動Run **2回**です。手動案の回数は本人が決め、0回なら対象期間は未検証です。Run数だけで費用は確定しません。各行でRunner OS、対象1 spec、除外する他テスト、品質ゲート、ジョブ実行分、Artifact保存量、非公開repoのBilling・支払主体・残枠を確認します。未検証期間、失敗時の再実行、PR HEAD変更で旧Runが無効になる条件も比較し、料金または権限が未確認なら有効化を`BLOCKED`にします。

### P05：権限拡大・Secretを要求する提案

Artifactを保存するためだけの`permissions: write-all`、deploy用Secretは不要なので拒否します。基準案の`contents: read`、checkoutの`persist-credentials: false`、依存導入、Browser導入、対象spec、`actions/upload-artifact`について必要な権限と出力先を個別に説明します。`persist-credentials: false`は依存スクリプト・外部通信の安全まで保証しません。外部PRコードを`pull_request_target`とdeploy Secretで実行する提案は、信頼できないコードに高権限を与えるため拒否します。未確認の第三者Action更新は採用せず、正式CIとdeployは対象外にします。

### P06：M10へ渡す基準workflow

学習用に修正した基準案を`.disabled`のまま引き継ぎます。対象は新課程の`workspace/M07/repaired-assertion.spec.ts`、`PLAYWRIGHT_TEST_ROOT=workspace/M07`、専用8082のShop Serve、Chromium、`target-sha.txt`、Playwright JSON結果、専用Artifactです。基準例の`contents: read`、Secret不要、deployなしを維持し、既存Web/Mobile CIを有効化・変更しません。

**CIのShop配布前提を別途確認します。** `course:sync`の`course/shop/`と`.course/distribution-manifest.json`は通常のcheckoutだけでは復元されません。現行`playwright.ai-assisted-qa.config.ts`は両方がない場合に`build:web`へ切り替わり、片方だけでは検証エラーになります。本人Private repoのRunnerで配布物を取得・配置・検証する手順と固定revisionの根拠がなければ、完成見本を有効化可能な事前ビルド済みCIとは評価しません。誤ってフルビルドになったRunを学習用軽量CIのPASSに数えません。

本人Private repoのevent、fork入力、依存Action、料金、権限、配布物の取得方法とPR HEAD照合が未確認ならM10での有効化は`BLOCKED`です。実行前の設計検査を実Run成功と報告しません。
