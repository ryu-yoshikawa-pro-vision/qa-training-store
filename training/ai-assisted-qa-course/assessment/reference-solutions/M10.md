# M10 模範成果物と判断根拠

> publicなqa-training-storeに置く通常Markdownです。学習用配布からの除外は秘密保持ではありません。文面一致ではなく意味・出典・判断・証拠を評価します。

## 成果物の標準例

Phase 2成果物を受け取る前にrepository、branch、diff、権限、Secretを確かめる。対象テストを動かす最小workflowを作り、ローカルとrunnerの差をOS・依存・環境変数・browser・権限で比較する。CIだけの失敗は最初の異常ログから調べ、テストを弱めず原因を分類する。PR APIから最新head SHAを確認し、pull_request Run、同じRunに属する成功Check、Artifact digest、Artifact内target-shaとPlaywright JSONを照合する。GitHubがRun/Checkへmerge SHAを記録する場合はPR headと区別する。AIの変更案は仕様・差分・検証結果で採否する。Phase 3は受講者の選択制でも今回の教材・評価・自動検証から除外しない。公開模範には評価者が実地で提示する具体条件を含めない。

## 評価時に確認する観点

1. 対象repository・branch・差分・権限を確認する
2. 最小workflowと実行環境差を説明する
3. PR head・Run・Check・Artifactを突合し、merge SHAとArtifact内の実行対象SHAを区別する
4. 成功/失敗/未実行とAI提案の採否を根拠付ける

## 学習目標・知識ノードとの対応

### M10-01: Phase 2の成果物をGitHubへ安全に持ち込み、対象と権限・変更範囲を確認する

- K-M10-01 実技資産の選択とGit公開範囲: Phase 2のspecだけを安全にcommitする

### M10-02: 受講者のテストを実行する最小のGitHub Actions workflowを構築し、ローカルとの差を説明する

- K-M10-02 CIの再現環境とテスト実行: 手元とRunnerの差を確認する

### M10-03: 対象SHA、Run/Check/Artifactを対応付け、成功・失敗・未実行を正しく報告する

- K-M10-03 現行PR HEADと検証証拠: 最新SHAのRun/Artifactを示す

### M10-04: CI環境だけの失敗とテスト自体の問題を区別し、必要な改善・再実行を判断する

- K-M10-04 CI障害の再現と原因切分け: 環境・テスト・アプリの失敗を区別する

### M10-05: AIの変更・レビュー提案の採否と、CIで確認した品質・未確認事項を説明する

- K-M10-05 AIによる修正・判断と残リスク報告: 保証されたことと未確認事項を説明する
