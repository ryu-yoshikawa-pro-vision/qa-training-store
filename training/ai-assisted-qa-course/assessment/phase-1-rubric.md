# Phase 1 公開評価基準（M00〜M04）

この基準は提出物を評価する観点を公開します。模範解答と採点用データはpublicなリポジトリ内の別ファイルとして公開し、学習者向けTemplate、同期、ロード、Web Buildから除外します。この配布除外は秘密保持ではありません。評価担当者名は個人情報としてこの公開基準に記載しません。教材の形式検証と人による意味の確認を区別します。

## 到達水準

| 判定 | 公開定義 |
|---|---|
| 0：未確認 | 必要な根拠や提出物が見つからない、または未実行。未実行を失敗や合格に読み替えない。 |
| 1：支援あり | 手順を促されると進められるが、根拠の誤読、欠落、説明できない判断が残る。 |
| 2：独立して説明 | 条件の異なる課題で本人が資料を選び、根拠・判断・限界・未決事項を自分で説明できる。 |
| BLOCKED | 必要な環境・参照・権限が利用できない。能力の合格/不合格とは別に記録する。 |

## 目標別の公開証拠

| 目標 | 確認する証拠 | 到達しない例 |
|---|---|---|
| M00-01 | 指定ファイルを保存し、現在位置・相対パス・実行結果を説明する | ロード成功だけで修了とする |
| M00-02 | エージェントの実行権限、Skill補助物、認証・Secretの境界を説明する | Skill名やAIの自己申告を実行証拠とする |
| M00-03 | 目的・参照・権限・成果物・完了条件を含む自作依頼 | 例文の転記だけで判断を示さない |
| M00-04 | Secret、差分、ポート、費用条件の安全な判断 | 未指定条件を推測し危険操作を行う |
| M01-01 | テスト目的と期待結果を説明する | 画面表示だけで品質保証を主張する |
| M01-02 | 探索・自動化・回帰の役割と限界を比較する | 方法を費用や目的なしで選ぶ |
| M01-03 | 工程ごとのAIと人の責務を分類する | 人間のレビューを省略する |
| M01-04 | すべてをE2Eにしない理由を費用・層で示す | E2E件数を網羅性と同一視する |
| M02-01 | BR/AC、実装、観測、AI推測を別々に参照する | AI出力や既存テストを正本とする |
| M02-02 | Role/State/Data/Journeyと操作前後の前提を整理する | 欠けた値を推測する |
| M02-03 | Seed/Resetの保証と保証外を実装根拠で示す | Seed名からカート状態等を推測する |
| M02-04 | ImpactとLikelihoodの根拠を分けて優先度を説明する | 測定のない発生率を事実とする |
| M02-05 | AI案の欠落・誤読を仕様根拠から修正する | 採否理由や未決事項がない |
| M03-01 | `BR-CART-002`の統合対象を同じ結果になる入力群に分け、異なる除外理由を混同しない | 根拠なしに異なる除外条件を同じ同値クラスへ入れる |
| M03-02 | `variant-basic-shirt-02`の在庫3・購入上限5から有効上限3を導き、上限3と超過4を比較して変更前数量の維持を確かめる | default variantの上限5を流用する、または仕様にない自動補正を期待する |
| M03-03 | `BR-CART-003` / `AC-CART-003`の条件を表にし、各checkout判断を仕様根拠へ結び付ける | 仕様にない条件組合せを実行可能・成功とみなす |
| M03-04 | `BR-CART-002`のゲスト・会員カート統合について、事前状態・操作・統合後状態・除外理由を追跡する | 統合元カートの状態や除外理由が未定義のまま期待結果を作る |
| M03-05 | Risk→Condition→Case→BR/ACの根拠を追う | IDだけ並べ期待結果の根拠がない |
| M04-01 | 欠落・重複・矛盾と修正版の理由 | 指摘を仕様根拠に結び付けない |
| M04-02 | 検証層をリスク、フィードバック、費用から選ぶ | 全条件を高価なE2Eに集める |
| M04-03 | Automate/Later/Do not automateを比較する | 再実行価値・保守負荷を示さない |
| M04-04 | 仕様不明と再現した不具合を分け未決を残す | 未確認を仕様または障害と断定する |

## Phase 1修了の読み方

各目標の必要証拠がそろい、本人が初見の別条件で判断を説明できた後に評価します。公開教材と自動テストだけでは人の理解を認定できません。正式な評価担当者は未指定のままです。
