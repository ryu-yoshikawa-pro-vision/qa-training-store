# AIエージェント活用演習のテスト対象

## 位置づけ

`qa-training-store` のScenario Shopを、[AIエージェント活用演習](../../docs/curriculum/test-automation/05_ai-agent-workflow.md)の共通テスト対象として使用します。新しい業務機能や、意図的な不具合を本番向けのアプリ実装へ追加する必要はありません。

この資料は演習対象と作業順序を示す補助資料です。期待動作の正本は[製品仕様](../../docs/spec/README.md)であり、Seed IDの具体値は`src/seeds/metadata.ts`を参照します。アプリの観測結果やAIの提案を理由に期待動作を変更してはいけません。

## 共通課程で使用するシナリオ

| 段階 | 対象 | 対応する既存Seed | 主な学習内容 |
| --- | --- | --- | --- |
| 仕様・リスク分析 | カートへの商品追加と購入可否 | `default`、`out-of-stock`、`low-stock` | 正常系・境界値・期待結果の根拠 |
| テスト設計 | 購入不可商品を含むカート | `cart-with-invalid-items` | ロール・在庫・SKU・商品状態の条件整理 |
| Playwright実装 | ゲスト・会員のカート操作 | `default`、`regular-member` | Locator・Assertion・Seed/Reset |
| 失敗分析 | 失敗と復旧の区別 | `payment-declined`、Trainingの診断演習 | 製品不具合とテスト不具合の切り分け |
| 最終比較 | チェックアウトの状態変化 | `cart-version-invalidates-checkout`、`checkout-resume` | 状態遷移、リスク、回帰影響 |

演習は最初から全シナリオを実行しません。最小のカートジャーニーから開始し、追加のリスクを説明できた場合に対象を広げます。決済・チェックアウトに関する追加シナリオは、対象機能の正式な仕様を確認してから使用します。

## モバイルアプリ自動化の選択課程

P1-7とP2-6を履修する場合は、既存の`training/maestro/exercises/`を利用します。WebとNativeで同じ業務条件を扱う場合でも、画面・要素識別・テスト制御の違いを確認します。Android実行環境の準備とMaestroの成功記録は選択課程の範囲であり、共通課程の必須条件に追加しません。

## 受講者が実施する一連の演習

1. [カートの正式仕様](../../docs/spec/features/cart.md)を読み、BR・AC・確認が必要な条件を抽出します。未確定事項は勝手に補いません。
2. AIを使う前に受講者自身が少なくとも1つのリスクと1つのテスト条件を記述します。
3. OpenCodeと`qa-workflow-skills`に同じ仕様を渡し、テスト分析・設計の案を作成します。
4. AIの案を仕様と照合し、採用・修正・不採用と判断理由を記録します。
5. 採用した条件のうちWebで検証すべきものを`training/playwright/exercises/`へ実装します。AIによるコード生成を使用してかまいません。
6. `pnpm run training:web:exercise`等の既存の入口から実行し、結果と証拠を確認します。実行できなかった場合も成功扱いにしません。
7. 誤った期待結果や重複テストをAIが提案した場合、何が誤りなのかを説明して却下します。
8. 最終演習では設計根拠、Playwrightコード、実行証拠、結果の評価を対応付けます。

## テスト対象の見直し結果

- **維持**: 現行のWeb / Nativeアプリ、正式な製品仕様、既存のSeed / Reset、Playwright・Maestroの入口。
- **変更**: 上表の既存シナリオを、受講者のテスト分析とAIの出力の比較、実装・検証の教材として明示します。
- **今回変更しない**: 製品のビジネスルール、商品・決済仕様、正式な回帰テスト、意図的な不具合の製品本体への投入。

学習を実際に通してみて、既存Seedでは再現できない必須テスト条件が確認された場合に限り、仕様・Seed・テストとその検証を揃えて追加します。学習のためだけにアプリへ根拠のない仕様変更を加えません。
