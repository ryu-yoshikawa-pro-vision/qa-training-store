# 人間向け文章の表現規約

## 目的

この文書は、Scenario Shopリポジトリで人間が読む文章を書くときの、言語と表現の判断基準を定めます。目的は英語をすべて日本語へ置き換えることではなく、一般的な説明は自然な日本語で統一し、正式名称・技術用語・識別子・機械契約は正確に保つことです。

## 適用対象

README、仕様書、設計文書、カリキュラム、運用文書、Skill、reference、Issue / Pull Request template、Plan、調査文書、レビュー手順など、人間が読む文章を原則として対象とします。

一方、次のものは文章規約による日本語化の対象としません。

- ソースコード上の識別子、package名、設定値、コマンド、ログ、エラー文字列
- テスト用fixture、snapshot、機械処理用のschema、YAML、JSON、CSVのkeyや固定値
- validator、contract test、E2E、外部仕様、UIが直接参照する固定文字列

機械的な値を説明する本文やリンク表示名は、値を変えずに日本語化できます。たとえば、ファイル名を維持したまま、リンク表示を `[習熟度評価基準](02_competency-rubric.md)` とすることができます。

## 基本言語

人間が読む説明文、見出し、表、箇条書きは原則として日本語で記述します。日本語で自然に表現できる一般語を、理由なく英語のまま残しません。

次の対応は判断の出発点です。固定の検索置換ルールではなく、実際の文脈に合う自然な表現を選びます。

| 英語表現 | 基本的な日本語 |
|---|---|
| `Summary` | 概要 |
| `Findings` | 確認結果、指摘 |
| `Evidence` | 根拠、確認材料、成果物 |
| `Scope` | 対象範囲 |
| `Validation` | 検証 |
| `Risks` | リスク |
| `Next Actions` | 次の対応 |
| `Required` | 必須 |
| `Optional` | 任意 |
| `Recommended` | 推奨 |
| `rationale` | 理由、変更理由 |
| `review record` | レビュー記録 |
| `learner-facing` | 受講者向け |
| `Learner Required` | 受講者必須 |
| `Rubric` | 評価基準 |
| `Competency Rubric` | 習熟度評価基準 |
| `classification token` | 分類用の識別値 |
| `Failure Evidence` | 失敗の根拠、失敗時の記録 |
| `Environment block` | 環境上の問題 |
| `Expected Product Behavior` | 期待する製品動作 |
| `Normative Specification` | 規範仕様、正式仕様 |
| `Current Repository` | 現在のリポジトリ |
| `Current Workflow` | 現在のワークフロー |
| `Executable Source` | 実行可能な正本 |

運用上の出力項目名、schema key、固定見出しなどが既存契約で指定されている場合は、その契約を優先します。たとえば、既存のRun報告や評価出力で`Summary`、`Progress`、`Evidence`が項目名として固定されている場合、項目名は維持し、説明文を日本語にします。

## 技術用語

日本のエンジニア同士の通常の会話でそのまま使われる技術用語は、無理に日本語化しません。たとえば、次は維持して構いません。

```text
API
SDK
CI
PR
workflow
framework
middleware
interface
runtime
lint
typecheck
GitHub Actions
```

次の製品・ツール・技術の正式名称も維持します。

```text
Playwright
Maestro
GitHub
React
Expo
TypeScript
JavaScript
Cloudflare
SQLite
```

英語であるという理由だけで残すのではなく、正式名称または一般に定着した技術用語であることを基準にします。`Build`、`Deploy`、`Route`、`Session`、`Seed`、`Scenario`、`Test`なども、技術上の概念として使う場合は文脈に応じて維持できますが、一般説明の中で不自然に連結しないようにします。

## 固有名詞・正式名称・固定文字列

次は原則として変更しません。

```text
ファイル名
ディレクトリ名
branch名
package名
関数名
クラス名
型名
変数名
API名
SDK名
コマンド
path
URL
Test Case ID
BR / AC ID
設定値
コード
ログ
エラーメッセージ
UI上の正式名称
GitHub Actionsの正式なjob名
validatorやcontract testが直接参照する固定文字列
外部仕様で定義されている正式表記
```

正式な値が英語でも、それを説明するリンク表示名や本文まで英語にする必要はありません。formal specの見出し、表の列名、UI正式名称などを変更する場合は、参照元と契約を確認してから判断します。

## リポジトリ内で使われているだけの用語

「既存文書で繰り返し使われている」「大文字で始まる」「過去に分類名として定義された」という理由だけでは、正式名称や固有名詞とはみなしません。コード、validator、外部仕様、UI、schema、設定などの契約として本当に必要かを確認します。

単に過去の文章で使われてきただけの表現は、自然な日本語へ変更します。PR #151で確認済みの表現は、特別な理由がない限り次のとおり継続します。

| 概念 | 使用する表現 |
|---|---|
| `Competency Rubric` | 習熟度評価基準 |
| `Native specialization` | モバイルアプリ自動化の選択課程 |
| `Common Core` | 共通課程 |
| `learner-facing` | 受講者向け |
| `Common route` | 共通課程 |
| `Minimum Evidence` | 最低限必要な成果物、最低限必要な確認材料 |
| `Completion contract` | 修了条件 |
| `Common completion` | 共通課程の修了 |
| `bounded Level 2` | 対象範囲を限定したレベル2 |

文脈に合わない場合は、表現を機械的に当てはめず、元の意味を確認したうえで自然な日本語を選びます。

## 造語・独自用語

説明を整理する目的だけで、新しい造語、分類名、略称、ラベルを作りません。一般的な日本語や既存の技術用語で説明できるものには、新しい名前を付けないでください。

## 要件の強さ

文章を日本語化するときも、仕様上の強さを変えません。元の文脈を確認し、次のように対応します。

```text
must / required      → 必須
should / recommended → 推奨
may / optional       → 任意、可能
```

「必須」を「推奨」に弱めたり、「可能」を「必須」に強めたりしません。`required`、`optional`などがschema、設定値、固定enumの一部である場合は、値を変更せず、必要なら本文で日本語の意味を説明します。

## 見出し

人間向けの見出しは原則として日本語にします。ただし、validatorやcontract testが見出し文字列自体を機械的に参照している場合、外部仕様として固定されている場合、または正式なUI名称・schemaとして扱う場合は維持します。固定見出しを維持する必要があるときは、日本語の説明を併記できるかを検討します。

見出しを変更するとMarkdownのanchorや参照リンクが変わることがあるため、変更前に参照関係を確認します。

## 文体

普通の日本語の技術文書として読みやすい文章にします。

- 不要に長い一文は分割し、主語・述語・修飾関係を明確にする。
- 単なる直訳調、日本語の途中へ一般的な英単語を挟む表現、意味の薄い抽象語を避ける。
- 同じ概念は、文書をまたいでも同じ表現を基本とする。
- 助詞だけの変更、語順だけの変更、同義語への置換、個人の好みだけを理由に差分を作らない。
- 仕様、要件、学習内容、条件、数値、順序、参照関係を文章改善の都合で変更しない。

## 機械契約と過去記録の扱い

検索は修正漏れを探すために使いますが、単純な一括置換は行いません。検索結果を、一般語、定着した技術用語、正式名称、識別子、コード、固定値、機械契約、過去記録に分類してから修正します。

過去の`.codex/runs/`、過去の`docs/plans/`、`docs/reports/`、調査結果、リリース記録、既存ADR、完了した作業履歴、生成済みartifact、eval dataset、fixture、snapshot、ログは、文章表現を統一するだけの理由では書き換えません。今回新しく作成・更新するPlanやRun Artifactは、この規約に従います。

`CHANGELOG.md`など履歴と現在の運用説明が同居する場合は、履歴を変更せず、現在運用される説明部分だけを対象にします。
