# 業務ルール

本ドキュメントはPhase 1の正本仕様書です。キャンセル・返品・返金、および高度な決済復旧処理については、Phase 2以降であらためて詳細化します。

## 1. 商品・マスタ

### 1.1 商品状態

| 状態 | 顧客表示 | 購入 | 変更先 |
|---|---:|---:|---|
| draft | × | × | published / 物理削除 |
| published | ○ | ○ | unpublished / discontinued |
| unpublished | × | × | published / discontinued |
| discontinued | × | × | なし |

- カートアイテム（Cart Item）、注文明細（Order Item）、レビュー（Review）のいずれからも参照されておらず、かつ所属SKUに `INITIAL_STOCK` 以外の在庫履歴が存在しないdraft（下書き）商品のみ物理削除が可能です。削除時は、SKU、商品画像関連付け、および削除対象SKUのみに紐づく `INITIAL_STOCK` 履歴も同一トランザクション内で削除します。なお、GitHub上に配置されている画像アセットバイナリは削除しません。
- 商品を公開（published）するには、有効（active）なカテゴリー、有効なブランド、1件以上の有効なSKU、1件以上の商品画像関連付け、およびちょうど1件のメイン画像（Primary画像）が設定されている必要があります。
- 公開中の商品が紐づいているカテゴリーおよびブランドは無効化できません。
- 商品は1つのカテゴリーを直接参照します。なお、カテゴリーはPhase 1の段階では階層構造を持ちません。
- ストアフロントでカテゴリーを選択した場合は、指定された有効な単一階層カテゴリーをOR条件として商品を検索します。
- カテゴリーおよびブランドは作成時に有効（active）とします。カテゴリー名・表示順、ブランド名の通常更新処理では有効状態を変更せず、状態変更専用のユースケース（Use Case）を使用します。
- 新規カテゴリーの追加時、既存カテゴリーが0件の場合は `sortOrder=10` とし、既存カテゴリーが存在する場合は `max(sortOrder) + 10` として末尾に追加します。最大値の取得と新規作成は同一トランザクション内で実行し、任意の位置への変更は作成後の並べ替え操作によって行います。

### 1.2 商品Aggregate編集

- Product、Variant、ProductImageの関連付け情報は、`ProductAggregate` として同一トランザクション内で保存します。
- Product Aggregateの更新処理では既存Variantの在庫数を変更しません。既存在庫の変更は在庫調整ユースケースのみが実行します。
- Product Aggregateは、draft状態を含めて1件以上の有効なVariant（active Variant）を常に保持します。バリエーション（Variation）なし商品の場合は有効なVariantをちょうど1件、バリエーションあり商品の場合は有効なVariantを1件以上保持します。これにより、管理画面一覧における価格と在庫の表示を一意に決定できるようにします。
- `productCode` は、商品がdraftであり、かつカート・注文・レビューからの参照がない場合にのみ変更可能です。保存済みのSKUコードも、親商品がdraftかつVariantへの参照がない場合にのみ変更できます。公開後は商品コードおよびSKUコードの値を維持し、新規SKUの追加と旧SKUの無効化によって対応します。
- `productCode` およびSKUは、前後の空白除去（Trim）、Unicode NFKC正規化、ASCII大文字化の順で正規化を行い、`[A-Z0-9_-]+` に合致する文字列のみを保存します。画面表示、検索、一意性判定、並べ替え（Sort）には、この正規化後の値を使用します。
- 新規Variantは常に有効（active）な状態で作成します。作成時には初期在庫を入力可能とし、保存時に `INITIAL_STOCK` の在庫履歴を作成します。無効状態での新規作成は許可せず、作成後の無効化は更新（Update）契約を通じて行います。
- draft状態のVariantであっても、カート・注文・レビューからの参照がある場合、または `INITIAL_STOCK` 以外の在庫履歴が存在する場合は物理削除せず、`isActive=false`（論理無効化）に設定します。各所からの参照がなく、在庫履歴が `INITIAL_STOCK` のみの場合は、その履歴を同一トランザクション内で削除した上でVariantを物理削除できます。
- 公開中（published）の商品は、常に1件以上の有効なVariantを保持する必要があります。そのため、最後に残った有効なVariantを無効化または削除する操作は拒否されます。
- 商品Aggregateの新規作成時は、常にステータスを `draft` とし、`publishedAt=null` を設定します。商品Aggregateの編集処理内でステータスを変更することはできず、公開・非公開・販売終了への変更は専用の状態変更ユースケースのみが実行します。
- バリエーションなしの商品は、`variationName=null` かつ `optionValue=null` である有効なVariantを1件のみ保持します。
- バリエーションありの商品は、バリエーション軸名を1〜30文字で保持し、同一商品内で有効な `optionValue`（選択肢名）の重複を禁止します。
- 商品の複製操作ではデータベースへ直接保存せず、新規登録フォームへ初期値を事前入力します。説明文、カテゴリー、ブランド、価格、有効なVariant構成、有効な画像関連付けのみを転記し、商品コード（`productCode`）および各SKUコードは空欄、初期在庫は0とします。利用者がコードおよびSKUを入力して保存を実行した時点で、通常の新規作成（CreateProductAggregate）処理が走り、`INITIAL_STOCK` 履歴と0件のレビューサマリーを作成します。複製元商品の注文履歴、レビュー、過去の在庫履歴は一切引き継ぎません。
- プレビュー（Preview）機能は未保存のフォームデータを表示するものであり、データベースや在庫履歴を変更しません。商品名、カテゴリー、ブランド、1件以上の有効なVariantなど、draft保存に必要な最小限のバリデーションを満たしている場合のみ実行でき、画像が未登録の場合はプレースホルダー画像として表示します。

### 1.3 GitHub画像Asset

- 画像バイナリの実体（正本）は、GitHubリポジトリ内の `public/images/products/` に配置します。Cloudflare Pagesからは同一オリジンの静的アセット（Asset）として配信します。
- ビルド前に画像マニフェストとなるTypeScriptモジュールと診断用JSONを生成し、アプリケーションはこのモジュールを静的にインポート（import）して、`assetId` からファイルパス、形式、寸法、ファイルサイズ、有効状態を取得します。実行時（Runtime）の外部フェッチは行いません。
- 管理UIでは、アセットカタログから画像を選択し、商品との関連付け、解除、メイン画像（Primary）の指定、並び順、および代替テキスト（Alt Text）の変更のみを行います。商品に最初に画像を関連付けた際は自動的にメイン画像に設定されます。メイン画像の関連付けを解除した際に他の画像が残っている場合は、`sortOrder` が先頭の画像を同一トランザクション内で自動的にメイン画像に昇格させます。また、デフォルトのAlt Textを初期値として、商品固有のAlt Textを編集できます。
- ブラウザからGitHub APIへ直接書き込みを行うことはありません。また、GitHubのアクセストークンをフロントエンド側に保存することも禁止します。
- 画像バイナリの新規追加や差し替えを行う際は、リポジトリにコンテンツハッシュ付きの新しいファイルを追加し、Pull Request・コミットおよび再デプロイによって反映します。既存のファイルを直接上書きすることはありません。
- GitHub CI側では各ブラウザのIndexedDB内での参照状況を把握できないため、一度リリースされたアセットは、使用状態にかかわらずマニフェストやファイルから物理削除しません。選択候補から外す場合は `isActive=false` と設定し、すでに設定済みの既存商品においては画像の表示を継続します。
- 画像アセットの新規関連付けは、有効（active）なアセットに対してのみ許可されます。すでに無効（inactive）となったアセットの既存の関連付けは維持されますが、一度解除した後は再関連付けできません。

### 1.4 一覧価格・Facet

- SKUごとに、現在時刻においてセール適用後の価格へ閲覧者（Viewer）の会員ランク割引を適用し、表示単価（`viewerUnitPrice`）を算出します。
- 商品一覧の表示では、有効なVariantにおける最小表示単価（`minimumViewerUnitPrice`）と最大表示単価（`maximumViewerUnitPrice`）を返却します。両者が同額の場合は単一の価格を表示し、異なる場合は「最小価格〜最大価格」の形式で表示します。
- 価格フィルターでは、有効なVariantのいずれかの `viewerUnitPrice` が指定範囲内であれば、その商品を検索結果に含めます。
- 価格の昇順・降順ソートはいずれも `minimumViewerUnitPrice` を第1キー（主キー）とし、同額時のタイブレーク（最終キー）には `productCode` の昇順を使用します。
- `hasPurchasableStock`（購入可能在庫あり）は有効かつ在庫数が1以上のVariantが1件以上存在する場合にtrueとし、`hasActiveSale`（セール開催中）は現在セール対象となっている有効なVariantが1件以上存在する場合にtrueとします。
- 管理画面の商品一覧における在庫ステータスは、その商品に属する有効なVariantの在庫合計（`activeTotalStock`）に基づいて判定します。`in_stock`（在庫あり）は1以上、`low_stock`（残少）は1〜5、`out_of_stock`（在庫切れ）は0と判定します。なお、SKU単位の詳細な在庫状態は在庫一覧画面で扱います。

### 1.5 商品探索

- ホーム画面では、主要カテゴリー、新着商品、セール商品、会員ランク案内を固定の順序で表示します。新着商品は `publishedAt`（公開日時）の降順、同日時の場合は `productCode` の昇順で並べます。なお、`publishedAt` は初回公開時にのみ設定され、再公開時に更新されることはありません。
- ホーム画面の商品セクションには閲覧者条件を適用し、新着・セールそれぞれ最大8件まで表示します。
- カテゴリーおよびブランドのナビゲーションでは、閲覧者条件を適用した後の該当商品件数が1件以上ある有効（active）な項目のみを返却します。カテゴリーに表示される商品件数は、そのカテゴリーに直接属している閲覧可能な商品数とします。
- 検索の対象フィールドは、商品名、短い説明（キャッチコピー）、ブランド名、カテゴリー名です。
- 検索サジェスト（Search Suggestion）は入力文字数が2文字以上の場合に最大8件表示し、商品、カテゴリー、ブランドの順にグループ化して提示します。
- 検索および絞り込み（Search / Filter）では、閲覧者条件、キーワード、カテゴリー、ブランド、価格、在庫、セール、最低評価の各条件をすべて適用した上で、総件数（total）とページネーション（Page）を算出します。カテゴリーやブランドの絞り込み条件は、同一ファセット内ではOR条件、異なるファセット間ではAND条件として結合します。
- ファセット（Facet）の件数カウントは、閲覧者条件および現在適用中の他の絞り込み条件を適用しつつ、対象ファセット自身の選択条件のみを除外した状態で算出します。
- カテゴリーファセットでは、単一階層カテゴリーのID、表示名、および該当件数を返却します。
- レビュー公開件数 `publishedCount=0` の場合は `ratingAverage=0` とし、それ以外の場合は `ratingAverage = ratingTotal / publishedCount` の計算結果を端数処理（丸め）を行わずに保持します。
- 評価フィルター（Rating Filter）は、端数処理を行っていない厳密な値で `ratingAverage >= minimumRating` かつ `publishedCount > 0` を満たす商品を抽出対象とします。
- セールフィルター（Sale Filter）は、現在時刻においてセール価格が有効なSKUを1件以上保持している商品を抽出対象とします。
- 並べ替え（Sort）で同順位が発生した場合は、`productCode` の昇順によって並び順を一意に確定させます。
- 商品詳細画面から一覧へ戻る際のスクロール位置はUI状態（UI State）として扱い、業務データとしてデータベースへ永続化しません。

### 1.6 価格・Sale

- 金額はすべて日本円の整数値（小数なし）で扱います。
- `saleStartAt <= now < saleEndAt`（開始日時以上・終了日時未満）の期間内である場合にセール価格を適用します。
- セール価格は、通常価格よりも小さい正の整数値とします。
- 商品詳細画面では、通常価格、セール価格、会員ランク適用後価格を、内容の重複なくわかりやすく表示します。
- ストアフロント向けのVariant DTOに含める `activeSalePrice` は、現在時刻においてセールが有効な場合にのみ値を設定し、セール期間外に設定されている `salePrice` を画面側へ返却しません。

### 1.7 Variation

- バリエーション（Variation）は1軸のみを扱い、バリエーション軸名と選択肢名を明示します。
- 選択肢が12件以下の場合はボタン群として並べ、13件以上の場合はセレクトボックス（ドロップダウン）形式で表示します。
- 在庫切れとなったバリエーションの選択肢も非表示にはせず、選択不可（disabled）とした上で、その理由（在庫切れ）を表示します。
- バリエーションが未選択の状態では、購入数量の変更および「カートに追加」ボタンを無効化します。
- ストアフロントへ返却するVariantは有効（active）なものだけに限定し、返却用DTOには `isActive` フィールドを含めません。在庫切れは有効状態を保ったまま `stockQuantity=0` として表現します。

### 1.8 Review集計

`product_review_summaries` テーブルに、公開レビュー件数、評価合計、平均評価、星1〜5の評価別件数を保持します。これらはレビューの新規作成、評価の変更、削除、非公開化、再公開化と同一のトランザクション内で更新します。

- 商品の新規作成時には、すべての集計値が0のレビューサマリー（Summary）を同一トランザクション内で作成します。削除可能なdraft商品を物理削除する際は、レビューが存在しないことを再確認した上で、サマリーも同一トランザクション内で一緒に削除します。
- 商品Aggregateの作成（Create）および更新（Update）処理では、ユースケースがシステム時計（Clock）から現在時刻を1回だけ取得し、Product、Variant、ProductImage、および `INITIAL_STOCK` 履歴にまったく同一のタイムスタンプを使用します。新規作成時は0件のレビューサマリーにも同じ時刻を使用します。更新処理では既存のレビューサマリーを変更せず、レビューサマリーの再集計はレビュー変更専用ユースケースのみが担当します。リポジトリ層がシステムの実時計を直接取得してはいけません。
- 星1〜5の評価別件数の合計値は、常に公開件数 `publishedCount` と一致します。
- 評価順による商品並べ替え（Sort）は、端数処理を行っていない `ratingAverage` の降順、`publishedCount` の降順、`productCode` の昇順の優先度で確定します。
- 平均評価は画面表示時にのみ小数第1位に丸めて表示し、データベースへの永続化、並べ替え、フィルター処理では丸めを行いません。
- レビュー一覧では、新着順、評価の高い順、評価の低い順の並べ替えを提供します。
- 顧客は自身が投稿した `published` または `hidden` 状態のレビューを編集できますが、編集によってステータスが自動的に変わることはありません。`hidden`（非公開）状態のレビューを顧客が編集しても自動的に再公開されることはなく、管理者による再公開操作が必要です。なお、`published` や `hidden` のレビューは論理削除によって `deleted` へ移行でき、削除後は再編集や同一注文明細への再投稿はできません。

## 2. 価格計算

```text
1. SKU有効単価 = Sale適用後・会員割引前単価
2. 単価割引 = floor(SKU有効単価 × 会員割引率)
3. 会員単価 = SKU有効単価 - 単価割引
4. 明細小計 = SKU有効単価 × 数量
5. 明細割引 = 単価割引 × 数量
6. 明細合計 = 会員単価 × 数量
7. 商品小計 = 全明細小計の合計
8. 会員割引 = 全明細割引の合計
9. 合計 = 商品小計 - 会員割引 + 送料
```

- 会員ランクに応じた割引率は、レギュラー（regular）0%、ゴールド（gold）5%、プラチナ（platinum）10%とします。
- 端数処理（切り捨て）はSKU単価ごとに1回のみ行います。商品小計の全体に対して割引率を掛け直すような計算は行いません。
- 商品一覧、商品詳細、カート、購入手続き（Checkout）、注文履歴の各画面において、すべて同一の単価割引ルールを適用します。
- レギュラーおよびゴールド会員は、割引前の商品小計が5,000円（税込）以上の場合に送料無料となります。
- プラチナ会員は、購入金額にかかわらず常時送料無料とします。
- 基本送料は全国一律500円とし、すべて税込で表示します。
- レギュラーおよびゴールド会員に対しては、送料無料までの残り金額を `max(0, 5000 - 割引前小計)` で算出して表示します。
- 注文明細（Order Item）には、有効単価、単価割引額、明細小計、明細割引額、明細合計をスナップショットとして保存し、注文（Order）には、商品小計、会員割引合計、注文時の会員ランク、送料、最終請求合計をスナップショットとして保存します。

## 2.1 配送先

- ユーザー1人あたり最大5件まで登録可能とし、デフォルト（Default）配送先は最大1件とします。
- 最初に登録された配送先は、登録時に `makeDefault=false` が指定されていても自動的にデフォルト配送先となります。すでにデフォルトに設定されている配送先を更新する際に `makeDefault=false` を指定してもデフォルト状態は維持され、デフォルト配送先を0件にするような更新操作は許可しません。
- 別の配送先を新たにデフォルトに設定する場合は、対象の配送先をデフォルトに変更すると同時に、旧デフォルト配送先の設定を同一トランザクション内で解除します。
- デフォルト配送先を削除した際に他の配送先が残っている場合は、`createdAt`（登録日時）の昇順、同日時の場合は `id` の昇順で先頭となる配送先を、同一トランザクション内で新しいデフォルト配送先に昇格させます。
- 登録されている最後の配送先を削除した場合は、デフォルト配送先も0件となります。

## 3. Cart

- `/cart` は、ゲスト（guest）および一般顧客（customer）が利用可能な公開ストアフロントルートとし、運用者（operator）および管理者（admin）の利用は不可とします。
- 同一SKUが追加された場合は数量を合算します。追加後の数量が、現在在庫数、上限値99、SKUごとの購入上限数のうちの最小値を超える場合は、数値を自動補正することなく操作全体をエラーとして拒否し、カート内の現在の数量を維持します。
- 商品詳細画面の「カートに追加」ボタンは追加する相対数量を受け取り、カート画面での数量変更は変更後の絶対数量を受け取る別々の契約として扱います。数量に0が指定された場合は、カート明細（Cart Item）を保存せず削除します。
- 商品詳細画面からのカート追加操作では、Cart Version（楽観排他用バージョン）の指定を要求しません。ユースケース側でユーザーまたはゲストの所有権を解決し、有効なカート（active Cart）の取得または新規作成、既存SKUの数量加算または新規明細の作成を単一トランザクション内で実行します。一方、カート画面での数量変更や明細削除は、画面に表示されている既存状態に対する更新操作となるため、CartおよびItemのVersionを要求します。
- カート表示時および購入手続き（Checkout）の開始時には、商品の公開状態、購入権限、最新価格、在庫状況を再検証します。
- カート投入後に商品の価格改定が発生した場合は、顧客が新価格を承認するまで購入手続きに進むことはできません。
- 注文（Order）作成が完了した時点で、カートのステータスを `consumed`（利用済み）に変更し、カート明細を注文明細（Order Item）へと変換します。
- ゲストID（`guestId`）はローカルストレージ（Local Storage）に保存し、同一ブラウザからの再訪時にゲストカートを再取得できるようにします。
- カート明細の追加、数量変更、削除、価格変更の承認処理では、親カートの `updatedAt` と `version` を同一トランザクション内で更新します。ゲストカートの統合処理においても、ユーザーカートの `version` をインクリメントします。
- カート画面および購入手続き画面における明細の表示順は、カート明細の `createdAt`（作成日時）の昇順、同日時の場合は `itemId` の昇順とします。注文明細の行番号（`lineNumber`）も、この表示順と同じ順序に従って1から採番します。
- ログイン時は、ユーザーアカウントのカートを基準として、ゲストカートの内容をSKU単位で統合します。合算数量は購入許容上限まで取り込み、上限を超過した数量分は切り捨ててその旨を画面に通知します。非公開化された商品、会員ランク条件を満たさない商品、無効化されたSKU、在庫が0の明細は統合対象から除外し、除外理由を表示します。統合元のゲストカートは、同一トランザクション内でステータスを `abandoned`（破棄）に変更します。
- 決済（Payment）が失敗した場合でも、使用済みの元カートを復活させることはせず、注文詳細画面から再決済を試行します。

### 3.1 名称の正規化

カテゴリー名、ブランド名、およびバリエーション選択肢名の重複判定では、以下の共通処理によって比較用キー（比較Key）を生成します。

1. 前後の空白文字を除去（Trim）する。
2. Unicode NFKCで正規化する。
3. ロケール非依存の方式で小文字化する。
4. 連続する空白文字を半角スペース1文字に集約する。

画面表示用の元文字列はそのまま保持し、重複判定処理や検索用インデックスにはこの比較用キーを使用します。

## 4. Checkout Session

- チェックアウトセッション（Checkout Session）のステータスとして、`active`、`converted`、`abandoned`、`expired` を持ちます。
- セッション情報として、対象顧客（customer）、対象カート（Cart）、カートのバージョン（Cart version）、配送先スナップショット、支払い方法、現在の進行ステップを保持します。
- 決済ゲートウェイキー（Gateway Key）はセッション内に保持しません。Gateway Keyは決済試行（Payment Attempt）の作成時にその都度生成します。
- 有効なセッション（active Session）は、ユーザー1人につき最大1件のみ存在します。購入手続き開始時に対象カートのIDおよびバージョンが完全に一致する既存セッションが存在する場合は、そのセッションを再開します。カートIDやバージョンが異なる場合は、既存セッションを `abandoned`（破棄）に変更した上で、新規セッションを作成します。
- ログアウト操作によってチェックアウトセッションが削除されることはありません。再ログイン後に所有権とカートの状態を検証した上で、中断したセッションを再開できます。
- チェックアウトセッションの有効期限は作成日時から24時間後とし、再開や更新によって延長しません。期限判定時に、期限切れの有効なセッションを `expired` に変更します。
- 購入手続きの途中でカートのバージョンが変化した場合、カート変更処理のトランザクション内ではチェックアウトセッションを更新しません。ルートガード（Route Guard）、注文確認画面の取得時、または注文確定処理のタイミングでバージョンの不一致を検知してカート画面へとリダイレクトさせ、次回チェックアウト開始時に以前の有効セッションを `abandoned` に変更します。
- URLの直接入力などによって不正なステップへアクセスされた場合は、入力情報が不足している前段のステップへ押し戻します。
- 注文作成が正常に完了した時点で、セッションのステータスを `converted`（成約完了）に変更します。
- 決済結果の表示ルートは `/checkout/complete?orderId=...` または `/checkout/failed?orderId=...` とし、画面表示前に注文の所有権または管理者権限を厳密に検証します。
- 郵便番号からの住所自動補完機能は外部APIに依存せず、システム内に同梱された学習用郵便番号辞書から住所候補を返却します。候補の適用は利用者の任意とし、辞書に一致する候補がない場合でも手動入力をそのまま継続できます。

## 5. 在庫

- SKUの在庫数量は0以上の整数で管理します。`out` は在庫数量0、`low` は1〜5、`available` は1以上を表します。`low` と `available` は重なり得る状態です。状態に該当するSKUの件数と在庫数量を区別し、表示する低在庫SKU件数には在庫数量0のSKUを含めません。
- カートへの商品追加時や、注文データの作成時点では在庫の減算を行いません。
- 決済（Payment）の成功が確定したトランザクション内で、最終的な在庫の再検証と減算処理を実行します。
- 決済モックが成功レスポンスを返した場合であっても、トランザクション内の最終在庫再検証で在庫不足が判明した場合は、決済失敗（Payment failed: errorCode=`OUT_OF_STOCK`）、注文ステータス `payment_failed` として確定処理を行い、在庫数および在庫履歴（Inventory History）は変更しません。ローカルのモック決済であるため、実課金が発生したまま在庫不足になるような不整合は生じません。
- 管理画面からの手動在庫調整および購入に伴う在庫減算は、すべて在庫履歴テーブルへ記録します。

## 6. 模擬Payment

| Code | 結果 | Error表示 |
|---|---|---|
| TEST-SUCCESS | succeeded | なし |
| TEST-DECLINED | failed | 支払いが拒否されました |
| TEST-INSUFFICIENT | failed | 残高不足として処理できませんでした |
| TEST-AUTH-FAILED | failed | 本人確認に失敗しました |

- 模擬決済（Mock）は外部ネットワークへの通信を行わず、テスト用コード（Code）と試行キー（Attempt Key）の組み合わせから常に決定論的な結果を返却します。
- 同一のAttempt Keyに対しては、何度呼び出しても常に同一の結果を返します。
- 決済処理の通常遅延時間（Delay）は初期値を500msとし、テスト管理画面（Test Control）から変更可能です。
- 決済ゲートウェイ（Gateway）の呼び出し処理中は、アプリケーションのデータベーストランザクションを保持したままにしません（コネクションを長時間占有しない設計）。
- 結果が明確に失敗（failed）となった注文に限り、再決済の試行を許可します。
- 決済処理中（processing）の状態では、注文のキャンセルや重複した再試行はできません。`/checkout/processing?orderId=...` へのアクセス時は、注文の所有権、注文ステータスが `pending_payment` であること、および最新の決済が `processing` であることを検証した上で、画面の表示およびポーリング処理を再開します。
- サーバー再起動やデータベースの確定書き込み失敗によってステータスが `processing` のまま残存している場合は、同一のAttempt Keyを用いて再実行します。ローカルモックは決定論的に動作するため、結果が変わることはありません。最新の試行がすでに `succeeded` または `failed` に達している場合は、ゲートウェイ処理を再実行せず既存の結果を返します。処理が競合した場合は最新状態を再取得し、別プロセスで確定済みであればその完了結果を返却します。
- タイムアウト、結果不明（Unknown）、および残高照合（Reconciliation）への対応はPhase 3で実装します。

## 7. Order・採番

- 注文番号の採番フォーマットは `ORD-YYYYMMDD-NNNN` とします。日付部分はシステム時計（Clock）における日本標準時（Asia/Tokyo）を基準とします。
- 日次シーケンス管理用の `daily_sequences` テーブルは、注文作成の同一トランザクション内で排他的に更新します。
- 注文作成の確定時点で、商品情報、適用価格、配送先住所の内容をスナップショットとして注文データ内に保存します。
- 注文明細（Order Item）は、カート明細の `createdAt` 昇順、同日時の場合は `itemId` の昇順に従って、行番号（`lineNumber`）を1から連番で採番します。注文詳細画面ではこの `lineNumber` 順に明細を表示し、注文一覧画面の代表商品画像には `lineNumber=1` の画像を採用します。
- 注文データ（Order）は理由を問わず物理削除しません。

### Phase 1の状態

```text
pending_payment
├─ payment_failed ── retry ──> pending_payment
└─ paid → preparing → shipped → delivered
```

- `paid → preparing`（支払い完了から準備中）への遷移は、運用者（operator）または管理者（admin）による発送準備開始操作によって行います。
- 定義されたステータスフローを飛び越えて遷移させたり、過去のステータスへ逆戻りさせたりすることはできません。
- 顧客向け画面ではシステムの内部ステータス名をそのまま表示せず、現在の状況、次に予定されている対応、および顧客自身が実行可能なアクション（再決済など）をわかりやすい表現で表示します。

## 8. 配送

- 発送準備の開始時に、ステータスが `pending` の配送データ（Shipment）を作成します。
- 商品の発送時には、配送業者名（`carrierName`）、追跡番号（`trackingNumber`）、発送日時（`shippedAt`）の入力を必須とします。
- 注文ステータスの `preparing → shipped`（準備中から発送済み）への更新と、配送ステータスの `pending → shipped` への更新は、同一トランザクション内で実行します。
- 配送完了時には、注文ステータスの `shipped → delivered`（発送済みから配送完了）への更新と、配送ステータスの `shipped → delivered` への更新を、同一トランザクション内で実行します。

## 9. Review

- レビュー（Review）は、購入者（customer）本人の配送完了（delivered）となった注文明細に対してのみ投稿できます。
- レビューの投稿は注文明細1件につき最大1件までに制限されます。投稿後に論理削除された場合でも同一 `orderItemId` のレコードがデータベース上に保持されるため、同一明細に対する再投稿はできません。
- 商品ごとのレビュー集計値には、公開中（published）のレビューのみを集計対象として含めます。
- レビューのステータス変更処理と、商品レビューサマリー（Summary）の更新は、同一トランザクション内で実行します。
- 星評価の入力UIコンポーネントは、アクセシビリティに配慮したラジオボタングループ（Radio Group）として実装します。

## 10. Admin操作

- 運用者（operator）および管理者（admin）のアカウントでは、商品の購入手続きを行うことはできません。
- 管理者（admin）権限を持つユーザーのみが、会員ランク（Rank）、ロール（Role）、アカウント状態（Account Status）を変更できます。Phase 1では、Rankの変更は一般顧客（customer）の範囲内、Roleの変更は運用者と管理者（operator / admin）の間、Statusの変更は有効と利用停止（active / suspended）の間のみを許可し、変更理由の入力や保存は行いません。RoleまたはStatusを変更した際は、対象ユーザーのすべての有効セッションを同一トランザクション内で即座に無効化します。customerのアカウントを `suspended`（利用停止）に変更する場合は、進行中のチェックアウトセッションも `abandoned` に変更しますが、カート内の明細は保持します。
- システム内に最後1人だけ残った有効な管理者（active admin）アカウントを、停止または降格させる操作は禁止します。
- 管理画面のダッシュボード（Overview）には、発送準備待ち件数、低在庫警告、非公開レビュー件数、および直近の注文一覧を表示します。売上集計機能はPhase 1では提供しません。
- 一括操作（Bulk Action）の対象は、商品の公開・非公開の切り替え、およびレビューの非公開・再公開の切り替えに限定します。
- 一括操作時は、対象となる各リソースに対して通常の更新ルールを個別に検証し、一部のデータのみが成功する部分成功（Partial Success）を許可します。処理結果には、成功件数およびエラーが発生した対象リソースの情報を明示します。
- パスワード変更や退会手続きの詳細な業務ルールはPhase 2で定義します。

## 11. Test Control

- テスト管理（Test Control）機能としては、データベースリセット（Reset）、初期データ投入（Seed）、仮想現在時刻変更（Clock）、決済遅延シミュレーション（Payment Delay）のみを提供します。
- リセット操作を実行すると、アプリケーションデータベースの内容と全セッションを完全に消去し、指定されたシードデータを再投入します。
- 任意のデータベース直接書き換え、データのインポート／エクスポート、および任意の障害注入スクリプト（Fault Script）の実行機能は、Phase 1のスコープには含めません。

## 12. 将来の業務ルール

- Phase 2予定: ゲスト購入（Guest Checkout）の再検討、未発送商品のキャンセル、キャンセル申請フロー、返品受付（Return）、全額返金（Refund）、ユーザー退会処理。
- Phase 3予定: 決済結果不明（Payment Unknown）ハンドリング、決済ゲートウェイ元帳（Gateway Ledger）、残高・売上照合（Reconciliation）、データ移行およびインポート／エクスポート機能。

## 11. 実装境界の補足

- ログインおよび新規登録におけるパスワードのハッシュ照合は、データベーストランザクションの外部で実行します。認証に成功した後、ユースケースはセッションIDを生成してクライアントの `CurrentSessionStore` へ先行して設定し、その保存に成功した場合に限り、DBセッション作成とゲストカート統合を行う単一トランザクションを開始します。トランザクションが失敗した場合は `CurrentSessionStore` をクリアし、DBセッションを作成せずにゲストカートを維持します。ローカルストレージへの設定自体に失敗した場合はトランザクションを開始しません。アプリケーション起動時に `CurrentSessionStore` が存在するものの対応するDBセッションが存在しない場合は、セッションポインタをクリアして未ログイン状態に初期化します。
- 有効なカート（active Cart）の取得または新規作成は単一トランザクション内で実行し、一意制約（Unique）の競合が発生した場合は既存のカートを再取得して処理を継続します。
- 管理画面からの手動在庫調整は、在庫数量の更新と在庫履歴（Inventory History）の作成を同一トランザクション内で不可分に実行します。
- チェックアウトセッションの有効期限は、アプリケーション起動時、チェックアウトルートガードの通過時、およびチェックアウト開始処理のタイミングで判定します。
- 検索サジェストは、リクエストシーケンスIDまたは `AbortController` による通信キャンセル制御を用い、ユーザーによる最新の入力に対応する結果のみを表示します。
