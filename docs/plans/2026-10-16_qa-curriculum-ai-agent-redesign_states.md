# 全モジュールの開始・終了基準状態

## 目的と適用範囲

M00〜M10の**各モジュールについて開始時と終了時の正しい状態を実際に作成し、検証できること**をカリキュラムの完成条件にする。受講者の現在の状態が課題を始められるかを判定し、先行モジュールの成果物を紛失・利用できなくなった場合にも、**当該モジュールに必要な正しい入力状態を参照できる**ようにする。

**復旧方法・自動復元コマンド・学習者データの復元処理は作らない。** 状態の基準データを揃えることが今回の要件である。学習者が作った過去の成果物を勝手に置換しない。基準状態を使用したことと、先行モジュールを本人が修了したことは別の事実として管理する。

このPlanは[学習順序と習熟基準](./2026-10-16_qa-curriculum-ai-agent-redesign_progression.md)、[モジュール単位ロード](./2026-10-16_qa-curriculum-ai-agent-redesign_distribution.md)、[評価](./2026-10-16_qa-curriculum-ai-agent-redesign_assessment.md)、[知識グラフ](./2026-10-16_qa-curriculum-ai-agent-redesign_knowledge-graph.md)に従う。M00〜M10以外の新規必須モジュールは追加しない。

## 状態として作成するもの

各モジュールは、**開始基準状態**と**終了基準状態**の2つを持つ。どちらも説明だけでなく、必要な実ファイル・設定・サンプル成果物・実行データと、その照合条件を揃える。

| 対象 | 内容 |
| --- | --- |
| **開始基準状態** | 正しい配布元revision、必要な前提成果物、設定、入力仕様・Seed、既知の課題状態、実行に必要な環境条件。**意図的な未完成コードや失敗状態も、課題の開始条件として正しければ含める** |
| **終了基準状態** | そのモジュールで完成した状態の模範成果物、仕様ID・Case ID・実行証拠への対応、許容する別解、確認すべき不変条件、Level 2で要求する本人の説明・判断 |
| **機械で確認できる条件** | ファイル配置、ID・参照関係、設定値、スキーマ、依存の存在、許可した実行コマンド、Seed/Reset、期待するPASS/FAIL/未実行の区別など |
| **人が確認する条件** | AIの出力の意味的な正しさ、仕様に対するテスト設計の妥当性、判断理由、失敗原因の切分け、代替設計の可否 |
| **revisionと出典** | モジュールID、基準状態の版、配布元commit、正式仕様/Skillの参照revision、入力として使う前モジュールの終了基準状態、評価に用いる条件 |

状態の一致は「ファイルが模範と完全一致すること」を原則にしない。テスト分析・設計・AI判断には**正しい別解**があり得るため、仕様上の必須条件・不変条件・評価根拠に照らす。Playwright・Git/CI等の機械的な部分は実際の動作証拠で確認する。

**開始状態の整合**（学習を開始できるか）と**終了状態の習熟判定**（本人が理解して到達したか）は独立して判定する。模範成果物を参照した、または状態の整合チェックに合格しただけでLevel 2を認定しない。

## 基準データの保存と公開範囲

完成時の配置を次のように定義する。

```text
qa-training-store/                               # 教材の公開正本
  training/ai-assisted-qa-course/
    states/
      M00/ ... M10/
        start.json                              # 開始時の判定契約。機密データを含めない
        end.json                                # 終了時の判定契約。解答内容は含めない
    ...                                         # 配布する課題・入力テンプレート

学習用リポジトリ/                               # 公開Template、別の個人作業環境
  course/modules/M00/ ... M10/                 # 各モジュールの公開教材と開始判定
  workspace/M00/ ... M10/                      # 受講者の成果物（勝手に置換しない）

非公開の評価資料保存先/                          # 公開Git履歴にも含めない
  reference-states/
    M00/ ... M10/
      start/                                    # 先行成果物を含む正しい開始データ
      end/                                      # 正しい完成データ・模範成果物
      reference.json                            # 確定revision、照合結果・出典
```

- 公開する`start.json`/`end.json`は**開始条件・出力契約・検証できる範囲**を記述する。模範コード、修了課題の答え、非公開評価用テスト、設計・分析の完成済み回答は書かない。
- **開始・終了の完成データそのもの**はアクセス制限された保存先で管理する。先行モジュールの終了基準データを次モジュールの開始基準データへ使う場合も、同じID・revisionを参照し、手動コピーによる不整合を防ぐ。
- 受講者用の開始状態には、**そのモジュールの受講に必要で公開できる入力**を配置する。過去モジュールの正解を先取りできる完成データは公開同期しない。
- 公開の判定契約と非公開の完成データは**同じモジュールID・基準revision**で対応させる。公開チェックで出せる判定は、模範解答を知らずに確認できる内容に限る。
- 先行成果物が利用できない場合に参照すべき開始基準状態を定義しておき、本人の成果物がある場合はそれを優先する。ただし**基準データを使った事実を先行学習の修了とみなさない**。基準データの配布・差替えや特別な復旧操作の実装は本件の要件に含めない。
- 公開の`qa-training-store`、公開Template、公開branch、Git履歴、学習用の全モジュール配布に**非公開の完成回答を混入させない**。教材と修了解答の境界は[同期・ロードPlan](./2026-10-16_qa-curriculum-ai-agent-redesign_distribution.md)を優先する。

## モジュール別の開始・終了基準状態

以下は**各モジュールで必要な基準データの完成仕様**。記載された内容を実際のファイルや、必要に応じて短い検証データ・実行証拠として用意する。

| モジュール | 正しい開始状態 | 正しい終了状態と照合する内容 |
| --- | --- | --- |
| **M00：開発環境・AIの安全な利用** | 本人の2コアCodespaces、モジュールロード済みの未編集教材と練習用ファイル、許可したAI/Skill実行範囲、Secretを含まない設定。**ターミナル知識は前提にしない** | 指定された練習用ファイルだけに妥当な変更があり、保存・操作記録・AIの許可判断と結果照合が説明できる。Secret漏えい・範囲外編集なし。模範の変更例と許容差分を持つ |
| **M01：QA・自動化の基礎** | M00の安全なAI利用条件、製品の簡単な機能説明と未記入の確認対象表、既知の期待結果を示す仕様断片 | 期待/観測の区別、手動/自動の選択、テスト層の比較、人間/AIの責任の説明。正しい判断例と誤判定の基準を持つ |
| **M02：仕様とリスク分析** | M01の用語・判断の前提、Cart等の確定BR/AC、Role/State/Data/Journeyの入力資料、未完成の分析表 | 仕様IDに紐付いた条件・状態・Seedの意味・優先度・未決事項。根拠がない動作を断定しない完成分析データと照合規則を持つ |
| **M03：テスト設計** | **仕様ID・条件・初期状態・リスクが揃ったM02相当の承認済み分析**、未完成の同値/境界/条件表/状態遷移/Caseテンプレート | 各技法の適用根拠と有効なケース、BR/AC→条件→Caseの対応、実行できる初期条件と観測可能な期待結果。許容ケース集合と過不足の確認条件を持つ |
| **M04：設計レビュー・自動化対象選定** | **M03相当の承認済みCase**と、意図した欠落・誤りを含むレビュー素材、自動化候補と評価基準 | 誤りを根拠で採否判断したレビュー記録、修正済みCase、自動化採否・保留理由、未決事項。**Phase 1修了成果とPhase 2へ渡す正しい分析・Case・前提・期待結果**を確定する |
| **M05：Node.js/TypeScript/Playwright基礎** | **M04終了状態に対応する承認済みCaseとテストデータ・仕様根拠**、動作するScenario Shop、Node/pnpm/Chromium、修正可能な短い練習用spec | TypeScriptの最低限の読解・部分修正が反映されたspec、正しいLocator/Assertion、設定・実行コマンド・対象URLと実行結果。**Phase 1の本人成果物が使えない場合でも、M05の基準入力は定義済み** |
| **M06：CaseからE2E実装** | **M05の最小specが実行できる環境**と承認済みCase、Seed/Reset、未完成の新課程専用spec、対象テストデータ | Case ID→Locator/Action/Assertionの対応、独立実行できるspec、Reset後の複数回の結果、Run/Trace/Reportの根拠。無意味なAssertionや状態依存を除外する完成specを持つ |
| **M07：失敗分析・保守** | **M06相当の動作するspecと基準Run**、再現できる**意図的な失敗**を含む診断課題、Trace/ログ、正式期待結果 | 原因の切分け、AI差分の採否、必要最小限の修正、修正前後の別Runと未解決事項。**Phase 2修了成果とPhase 3へ渡す正しいspec・Config・Reset・実行証拠**を確定する |
| **M08：Git・GitHub・レビュー** | **M07終了状態に対応する動作確認済みspec・設定・必要な実行手順**、個人学習用Gitリポジトリ、commit前の安全な練習変更 | 公開対象を絞ったdiff、適切なcommit/branch、レビュー可能なPR、AIレビューの採否根拠。ログ・Secret・未承認成果物を混入させない |
| **M09：GitHub Actions/CIの理解** | **M08相当の変更履歴・PR**、新課程専用の未完成workflow、必要なRunner・Test実行条件、既知の失敗ログ | 起動条件/Job/Step/権限を説明できる有効な専用workflow、Run/SHA/Artifactの対応と失敗箇所の判断。**CIが成功すべき課題と失敗を分析する課題を分ける** |
| **M10：CI統合・修了** | **M09相当の専用CI構成とM07の承認済みspec**、確認対象のPR HEADと検証データ、修了課題の入力条件 | 新課程の対象specを実際に実行したworkflow、対象SHAに一致するRun/Check/Artifact、失敗時の調査・判断、未確認事項の報告。**Phase 3修了基準と一致**する完成状態 |

### フェーズ間の一致条件

- **M04終了 ≒ M05開始**：M04の承認済みCase、仕様ID、初期データ、操作・期待結果、自動化対象の採否を**同一の基準成果物ID・revision**で参照する。M05に追加するNode/Playwrightの環境だけは別の開始条件であり、M04の能力評価に含めない。
- **M07終了 ≒ M08開始**：M07の承認済みspec・Config・依存・Reset・動作証拠の基準ID・revisionを維持する。M08で必要なGitの準備はM07の合格条件に含めない。
- そのほかも**Mxx終了の必要成果物とM(x+1)開始の前提を同一の出典・版へ紐付ける**。後続課題のために追加する未完成テンプレートや意図的な失敗素材は、前モジュールの終了成果物と混同しない。
- フェーズ修了課題は学習者の**初見の別条件**で評価する。保存している模範の終了成果物を閲覧したことによって修了したとみなさない。

## 開始前と終了時の判定

- **開始時**：学習者の配布元SHA、ロードしたモジュールID・revision、必要な依存ファイル、前モジュールの引継ぎ成果物、仕様・Seed、実行環境を確認する。結果は「開始可能／不足・不整合／確認不能」に区別し、具体的な欠落項目を表示する。
- **終了時**：提出物の必須構造・ID・仕様根拠・動作結果を確認し、**内容が妥当であるかの人による判断**を別に行う。PASSの自己申告や模範と同じ文字列があることだけで合格させない。
- **前工程の成果物がない場合**：前モジュールの本人評価と切り離し、**当該モジュールの開始基準状態を照合することで、何が不足しているか／どの正しい入力が必要かが分かる**ようにする。自動復元・別モジュールの無断ロード・本人ファイルの自動上書きはしない。
- **開始状態に意図した失敗がある場合**：M07の故障spec、M09の誤ったworkflow等は、正常な課題開始状態として明示する。修了状態のPASS条件と混同しない。
- **基準の改訂**：正式仕様、`qa-workflow-skills`、テストデータ、問題、モジュールの学習目標を改訂した場合、開始/終了の両方と隣接モジュールの引継ぎ条件を確認する。古いrevisionの基準に対するPASSを新版へ自動流用しない。

## 知識グラフとの対応

[知識グラフ完成仕様](./2026-10-16_qa-curriculum-ai-agent-redesign_knowledge-graph.md)には、各モジュールの**開始・終了基準状態を識別できるIDと参照関係**を追加する。必要条件は次のとおり。

- 各`module`→開始基準状態・終了基準状態を辿れる。
- 状態から必要な知識・製品仕様・利用Skill・教材・実技・評価基準・revisionへ辿れる。
- 前モジュールの終了と次モジュールの開始が共有する成果物IDを検索でき、仕様やSkill変更時の再確認候補となる。
- 機械で確認する条件と、意味・判断を確認する条件は混同しない。
- 公開グラフは**基準状態の識別子・公開可能な判定契約のみ**を持ち、非公開の模範内容や受講者成績を含めない。

## 受入試験

| 検証 | 合格条件 |
| --- | --- |
| モジュール網羅 | **11モジュールすべて**に開始・終了の基準データと判定条件があり、実在ファイルに紐付く |
| 前提整合 | M00には未学習知識の要求がない。隣接モジュールとフェーズ境界の成果物ID・版に矛盾がない |
| 完成データ | **開始と終了の状態を実際に用意**し、コード・設定・Seed・Case・Run・評価根拠がある項目では動作・意味の両面を確認済み |
| 開始判定 | 正常、前提ファイル欠落、revision不一致、状態不一致、意図的な失敗素材、確認不能を区別できる |
| 終了判定 | 模範の機械チェックと、仕様・理由・別解を含む意味的な確認方法が揃っている |
| 前成果物の欠落 | M04の本人成果物がなくてもM05開始に必要な**正しい基準入力**が存在し、どの条件が必要か判断できる。M07→M08も同様 |
| 情報保護 | 完成した模範解答・評価用テストが公開リポジトリ、Template、同期対象、Git履歴に混入しない |
| 非破壊 | 基準照合で学習者の編集済み成果物を変更せず、別モジュールを無断ロードしない |
| 改訂追従 | 仕様・Skill・教材を変更した場合、開始・終了双方と隣接モジュールの再確認対象を検出できる |
| 習熟との分離 | 正しい基準入力を使用しても、当該受講者の先行モジュールのLevel 2・フェーズ修了を自動認定しない |

**今回の対象はPlanへの追記のみ**。基準状態の実データ、照合スクリプト、非公開の模範成果物や学習用リポジトリは作成しない。これらは本Planに定義した最終的な実装・受入条件に含める。
