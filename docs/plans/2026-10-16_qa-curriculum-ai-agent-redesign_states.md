# 全モジュールの開始・終了基準状態

## 22状態と講師不要のAI達成判定の分離

既存11モジュール×開始/終了の22状態は**準備条件・提出ファイル/ID/revision・参照の検査**を担当し、AI意味評価による本人の習熟Levelとは区別する。現状の`course:check`はRunやコードの意味を実行・評価しない。旧`end.json`の`human-review`に相当する意味判定は、正規の独立AI評価器に置き換え、構造チェックだけでLevel 2としない。各モジュールの終了状態は本人の回答・実証拠があるかまで参照できるようにし、M04/M07/M10の全必須IDの正式修了は別の評価結果で判定する。

評価には教材/状態/仕様/固定Skill/公開rubricのrevisionを固定し、本人の`workspace/`に個人の履歴を保全する。再評価で旧結果を上書きせず差分と再確認したIDを記録する。モジュール単位のロードは自動進行・個人ファイル復元・先行Phaseの修了認定を行わない。AIが使えない場合は評価をBLOCKEDとするが、講師への対面採点を必須の代替手段にはしない。

### 実行証拠の取得・検証と信頼限界

全Phase共通の証拠には`evidence_id`・module/phase・対象spec/test/Case/BR/AC・入力元・教材/製品/Skillのrevision・コード/設定/証拠のSHA-256・実行条件・開始/終了時刻・実行コマンド・exit・実際の結果・必要なTrace/Artifactへの参照を**取得可能な範囲で**記録する。全学習項目へRunを要求するのではなく、**実行する技能の必須条件**を評価器の機械的検証へ接続する。本人が任意に書いた`PASS`文章・手入力のRun ID・AIの「実行済み」報告だけを真正な実行証拠としない。

- **M03**：固定Skill commitとTCN/Model、技法runtime、Coverage/CI、Case、最終`verify_runtime_evidence`の`valid=true`およびcurrent/freshness/closure参照をSkill契約で検証。単なるexit 0や過去結果、意味的に不当な期待結果ではLevel 2不可。
- **M06**：採点器が受入済みのPlaywright専用Config・許可されたspec/依存を通じて必要な新規実行を起動し、ResetとCase/Assertionの対応、test ID、コードハッシュ、結果を照合する。古いログ/別spec、固定TODOのみ、失敗を勝手にPASSとした結果は拒否。
- **M07**：修正/保守前後の差分と**別Run**を照合。POM/fixtureのimport先と実際の使用、業務Assertionが弱くなっていないことを検証し、別Runを同一IDで流用できないようにする。意図的失敗specの期待FAILと、修正後の実PASSを混同しない。
- **M10**：本人の非公開リポジトリの**実際のGitHub API**から最新PR head SHA、workflow path、Run ID/attempt、Check、ArtifactのSHA/結果を取得し、対象specと本人成果物の同一性を確認する。`pull_request`のmerge refとPR headを区別し、旧SHA・別workflow・偽ログ・無効workflowのみ・取得不能なArtifactは非達成扱いにする。Tokenは安全に取り扱いAI送信しない。

Node.jsの限定した証拠取得/実行処理と、権限のないAI意味評価を分離する。自分のCodespaceのローカルログを自分で書換えられる以上、完全な改ざん防止は保証できない。**必要なRunを評価処理から新たに実行して証拠を採取**するか、GitHub等の照合可能な取得元で確認し、過剰な署名基盤や中央監査サーバーは追加しない。取得条件が成立しない場合は`not_run`/`ungradable`/`blocked`を理由で区別し、正式PASSにしない。

## 追加する終了証拠と拒否条件

M06の`end.json`と提出物では、固定3 Caseとは別の新規spec、そのCaseの仕様・期待結果、Reset後の単独/再実行への参照がない限り修了証拠にしない。M07はPage ObjectとPlaywright標準fixtureの実装・参照import・保守差分・別Runを追跡可能にし、名称が違っても妥当な実装を拒否しない。M10は対象spec/依存コードと専用workflowの有効化差分、現PR HEADのRun/Check/Artifact・費用/権限・変更条件の判断が必要で、旧Runや合成証拠では完了しない。終了状態の構造チェックとLevel 2の人間による意味判断は分離する。

変更時は`states/Mxx/end.json`、`exercises/Mxx`、提出テンプレート、公開ルーブリック、`assessment/scoring-tests/Mxx.json`、`training/course-sync/manifest.json`、関連Validator/契約テストを同じ要件に更新する。22状態の数は増やさない。

## 追加実技と22開始・終了状態の関係

開始/終了状態の機械判定は受講者の習熟判定ではない。M04の未知仕様・保留・引継ぎ、M06の別Case新規specと単独/再実行、M07のPage Object/fixture保守改善と前後Run、M10の有効化済み専用CIと現HEADの実Run/Artifactを、対応する終了時の成果物・実行証拠へ紐付ける。既存fallbackで前のPhaseが修了したと誤認定しない。未実行/BLOCKED/未達/PASSとLevel 2を別に記録する。

## 学習証拠と開始・終了状態の区別（2026-10-25）

22状態の構造的な準備完了はLevel 2の習熟ではない。全モジュールの本人の成果物・変更条件への判断・短い質疑/操作証拠と固定版を追跡し、M04/M07/M10にて**本人が開始した独立AI意味評価と決定論的な検証**でPhaseの全必須IDを正式採点する。人間の正式評価者の承認待ちを設けず、判定不能/未実行/BLOCKEDは修了にしない。

## 目的と適用範囲

M00〜M10の**各モジュールについて開始時と終了時の正しい状態を実際に作成し、検証できること**をカリキュラムの完成条件にする。受講者の現在の状態が課題を始められるかを判定し、先行モジュールの成果物を紛失・利用できなくなった場合にも、**当該モジュールに必要な正しい入力状態を参照できる**ようにする。

**復旧方法・自動復元コマンド・学習者データの復元処理は作らない。** 代わりに、各モジュールに前工程の本人提出物に依存しない、**公開可能な正しい学習用開始入力**を用意する。本人の成果物がある場合はそれを使える。学習者が作った過去の成果物を勝手に置換しない。基準状態を使用したことと、先行モジュールを本人が修了したことは別の事実として管理する。

このPlanは[学習順序と習熟基準](./2026-10-16_qa-curriculum-ai-agent-redesign_progression.md)、[モジュール単位ロード](./2026-10-16_qa-curriculum-ai-agent-redesign_distribution.md)、[評価](./2026-10-16_qa-curriculum-ai-agent-redesign_assessment.md)、[知識グラフ](./2026-10-16_qa-curriculum-ai-agent-redesign_knowledge-graph.md)に従う。M00〜M10以外の新規必須モジュールは追加しない。

## 状態として作成するもの

各モジュールは、**開始基準状態**と**終了基準状態**の2つを持つ。どちらも説明だけでなく、必要な実ファイル・設定・サンプル成果物・実行データと、その照合条件を揃える。

| 対象 | 内容 |
| --- | --- |
| **開始基準状態** | 正しい配布元revision、必要な前提成果物、設定、入力仕様・Seed、既知の課題状態、実行に必要な環境条件。**意図的な未完成コードや失敗状態も、課題の開始条件として正しければ含める** |
| **終了基準状態** | そのモジュールで完成した状態の模範成果物、仕様ID・Case ID・実行証拠への対応、許容する別解、確認すべき不変条件、Level 2で要求する本人の説明・判断 |
| **機械で確認できる条件** | ファイル配置、ID・参照関係、設定値、スキーマ、依存の存在、許可した実行コマンド、Seed/Reset、期待するPASS/FAIL/未実行の区別など |
| **AIが意味評価する条件** | 本人の判断理由、仕様とテスト設計の整合、失敗原因・代替案の妥当性。決定論的な証拠照合と校正に合格した評価器のみ使用し、判定不能やBLOCKEDを合格へ変換しない |
| **revisionと出典** | モジュールID、基準状態の版、配布元commit、正式仕様/Skillの参照revision、入力として使う前モジュールの終了基準状態、評価に用いる条件 |

状態の一致は「ファイルが模範と完全一致すること」を原則にしない。テスト分析・設計・AI判断には**正しい別解**があり得るため、仕様上の必須条件・不変条件・評価根拠に照らす。Playwright・Git/CI等の機械的な部分は実際の動作証拠で確認する。

**開始状態の整合**（学習を開始できるか）と**終了状態の習熟判定**（本人が理解して到達したか）は独立して判定する。模範成果物を参照した、または状態の整合チェックに合格しただけでLevel 2を認定しない。

## 基準データの保存と公開範囲

完成時の配置を次のように定義する。

```text
qa-training-store/                               # 教材の公開正本
  training/ai-assisted-qa-course/
    states/
      M00/ ... M10/
        start.json                              # 開始時の公開判定契約
        end.json                                # 終了時の公開判定契約
    ...                                         # 配布する課題・入力テンプレート
  assessment/
    reference-solutions/M00.md ... M10.md       # 公開の模範解答
    scoring-tests/M00.json ... M10.json         # 公開の採点用テスト
    completed-states/M00.json ... M10.json       # 公開の完成状態データ

学習用リポジトリ/                               # 公開Template、別の個人作業環境
  course/modules/M00/ ... M10/                 # 各モジュールの公開教材と開始判定
    inputs/                                    # そのモジュール専用の検証済み開始入力
  workspace/M00/ ... M10/                      # 受講者の成果物（勝手に置換しない）

```

- 公開する`start.json`/`end.json`は**開始条件・出力契約・学習者配布時に照合できる範囲**を記述する。完成回答・採点テストの本文は別の`assessment/`資料へ置き、状態契約へ複製しない。
- **終了模範データ**は`assessment/completed-states/Mxx.json`等の通常ファイルとして公開リポジトリに作成・検証する。内容はGit差分・PRレビューで確認できる。公開可能な設定・Seed・入力契約など**同一の確定データは、参照元ID・revisionで共通参照**してよい。モジュール別の22状態の定義と照合は独立して維持し、**22組の物理コピーは要求しない**。本人成果物を後続で使う場合は同一成果物ID・revisionを引き継ぎ、別条件の公開開始サンプルを使う場合は別IDとして同じ入力契約に適合させる。練習用開始サンプルと完成状態は用途別ファイルに置き、学習用配布物には完成状態を含めない。
- 受講者用の開始状態には、**そのモジュールの受講に必要で公開できる検証済み入力**を配置する。先行成果物を紛失した場合も、当該モジュールに同梱した開始入力で演習を進められる。先行モジュールの**修了課題とは異なる条件・テストデータの例**を用い、完成状態資料は学習者向け配布から除外する。
- 公開の判定契約と公開の完成データは**同じモジュールID・基準revision**で対応させる。学習者向けの照合で公開する判定は、配布契約上認められた内容に限る。
- **入力の選択**：受講者の先行成果物が存在し、開始契約に適合すれば優先して参照する。欠落・不適合なら、当該モジュールに同梱された公開可能な基準入力を選べるよう教材手順と照合条件を定義する。どちらを使ったか記録し、**先行モジュールの本人修了を認定しない**。既存成果物の書換え・復元コマンド・特別な復旧処理は追加しない。
- 模範解答・採点用テスト・完成状態は`training/ai-assisted-qa-course/assessment/`の公開通常ファイルとして置く。これらの配布除外は秘密保持ではない。許可リストで学習用Template、Web Build、ロード対象、公開Artifactから除き、該当する同期/ロード/build契約テストで確認する。教材と評価資料の配布境界は[同期・ロードPlan](./2026-10-16_qa-curriculum-ai-agent-redesign_distribution.md)を優先する。

## 基準データの重複を避ける条件

- **状態の定義は22件のまま**：各Mxxの開始・終了の公開契約、実在する参照先、個別の検査は残す。同じ設定・Seed・仕様断片を状態ごとに複製する必要はない。
- **実データの再利用**：同じ内容が必要で公開区分も一致する場合だけ、確定済みの共通データをID・revision参照で使う。参照先が存在し、版が一致し、後続モジュールの契約を満たすことを独立に確認する。共有元を更新したら参照する全状態を再確認する。
- **用途別に分けるもの**：各モジュール固有の未完成素材・意図したFAIL・検証する差分、および**公開の完成状態資料と学習用の開始サンプル**。同じ入力契約を使っても、別ファイルとして追跡し、完成状態資料は学習者向け配布から除外する。
- **受入条件**：共通参照してもM00〜M10の各開始判定と各終了判定が実行でき、参照欠落・revision違い・公開範囲違反を検出できる。共通化のために新しい保存DBや復旧機能は設けない。

## 判定契約の共通項目

`start.json`と`end.json`は同じ構造の項目を使う。公開するのは必要条件と検査の定義だけで、**完成回答本文は別の評価資料へ置く**。

| 項目 | 内容 |
| --- | --- |
| `module_id` / `state` | `M00`〜`M10`と`start`または`end`。1モジュールにつき各1件 |
| `revision` / `source_sha` | 状態定義の版と教材正本の確定commit |
| `inputs` | 必須成果物のID、作成元モジュール、必要な版、入力場所、公開可能な欠落時の説明。M00のみ先行成果物なし |
| `environment` | 必要なツール、設定、Seed/Reset、起動対象。対象モジュールで実際に必要なものだけ |
| `expected` | 開始/終了として満たすべきファイル構造、ID、仕様ID、正当な状態・許容差分など**公開可能な範囲** |
| `checks` | 自動確認可能な条件・期待結果、検証手順の参照、意味判断が必要な場合のAI独立評価・本人証拠。既存`human-review`は学習者の正式修了要件として採用せず、状態データ・Validatorの実装で適切な役割を置換する |
| `references` | 対象の仕様/Skill revision、公開教材・評価観点の参照、後続で必要な成果物ID |

**入力のIDとrevisionの扱い**：本人の先行成果物を使う場合は、先行モジュールの`end.json`に対応する同一成果物ID・revisionを維持する。後続モジュール同梱の公開サンプルを使う場合は**別の成果物ID・revisionを保持し、先行終了状態と同じ入力契約（必須項目・型・参照する仕様revision）に適合することを検証**する。共通の設定・Seedなど同一の確定ファイルは参照ID・revisionで共有できる。**後続での入力要件が増える場合は、前モジュールの終了条件を勝手に増やさず、当該モジュールの配布する課題・環境条件として追加**する。

公開の`assessment/completed-states/Mxx.json`は同じ`module_id`・`state revision`と、実際の模範成果物のファイル一覧・検証に使う期待結果・実行証拠の種類・許容別解の根拠を対応付ける。評価時に初めて提示する具体的条件、学習者の名前・回答・成績やSecretは記録しない。

開始状態と終了状態の検査は**読み取り専用**。`ready`は配布・構造・ファイル参照の一致だけを表し、実行可能な環境であることを意味しない。`course:check`は状態ファイル、必須path、revision、参照を照合し、`execution.status: unverified`と未確認の環境要件を出力する。Node.js、pnpm、Python/Skill runtime、Playwright、Seed/Reset等を実際に実行した証拠は別の開発/実地検証で確認する。未確認を実行成功扱いしない。実技の模範と受講者の提出物が同じ内容になっても、それを本人のLevel 2の根拠として自動採用しない。

## M02→M03の開始入力と終了状態の照合

- **開始入力の2種類を区別**：受講者がM02で作った人間可読の検証責務と、M03同梱の別条件の検証済み開始サンプルは、**同じ入力契約・別の成果物ID**を持つ。どちらを使用したか記録する。公開模範は修了課題の条件を先行モジュールの練習素材へ転記せず、評価時に初めて提示する具体的条件は公開しない。
- **意味上の入力契約**：検証責務ID/文章、根拠BR/AC、対象Scope、Risk・優先度、状態/Seed、期待する成立条件・不変条件、仕様とSkillの確定revision、未決事項を参照できること。BR/ACと`spec-analysis`のAuthority Entity IDは同一だと推定しない。
- **機械的な入力契約**：M03で作成する`metadata`（**17キー**）と`condition_structure.py`の`input`（**15キー**）、`test_requirements[]`各行（**5キー**）は固定Skillの検証契約に一致する。実際の`spec-analysis` Authority、`test-analysis` Product Risk、Scope IDの参照元・current性を入力前に確認する。`test_requirements[]`にない説明文はM02の成果物で管理し、未知フィールドを挿入しない。
- **入力とTCNの差分検査**：`test_requirements[]`から`test_conditions[]`へ引き継ぐTR/Authority/Risk/Scopeを比較し、生成されたTCNの参照とM02の仕様根拠へ追跡する。**`direct`で`ready`になっても未解決参照が省略された場合は開始・終了の成功判定に使わない**。ScopeはID形式だけでなく実際の参照先・版も確認する。
- **未決・Disposition**：current TR Entityを持たない初回directの`requirement_dispositions[]`は空配列とし、未確定の責務はM02の未決として扱う。Dispositionを使用するときは、対象のcurrent TR Entityを固定Skillの実行結果で確かめる。
- **終了状態**：`condition_structure(direct)`でTCN/Model、技法runtimeで適用結果、`materialize_coverage(artifact)`でCI、適切なmodeの`case_structure`でCaseを生成し、最終の`verify_runtime_evidence`が`valid=true`であること。さらに、期待結果の仕様整合・技法の選択理由・正しい別解を確認する。終了コード0のみ、単独の`ready`、AIの成功報告のみでは修了としない。
- **失敗時**：未知の参照、誤mode、未解決TCN、古いEntity、未実行の技法結果、fingerprint不一致、終了コード0の`invalid_input`を区別し、どの契約を満たさなかったか記録する。自動復元や新しいruntimeの実装を必須としない。

## 公開評価資料と学習用開始入力を分ける条件

モジュールの**通常演習用の開始入力**と、修了課題を照合するための**公開模範**は、用途別の別ファイルとして管理する。公開模範を見られることを前提に、本人の判断は評価時に初めて提示する条件と根拠の説明で確認する。

1. 教材管理者は、各モジュールの`inputs/`に、そのモジュールの操作・設計に必要な**公開してよい承認済みサンプル**を用意する。M05ではM04の本人成果物に代えて利用できる仕様ID付きCase、M08ではM07相当の安全なサンプルspec・Config・実行手順が該当する。
2. サンプルの入力仕様・期待結果は**当該モジュールの学習用条件**として検証する。**先行モジュールの修了課題・その模範成果物と同じ条件、設問、採点データを使わない**。学習用入力と完成状態資料は用途別に管理する。
3. モジュールロードは、先行提出物を参照するか、そのモジュールに同梱した開始サンプルを使うかを学習者に明示する。**どちらの場合もロードするのは指定1モジュールだけ**。本人の過去成果物を補完・書換え・復元しない。
4. 終了基準状態の**公開契約**と公開の**模範実データ**は同一revisionに対応させ、Gitで通常レビューする。配布許可リストでは評価資料を学習者へ渡さず、Web Build・公開Artifactにも含めない。これは秘密保持を意味しない。
5. **公開サンプルの機械的な開始判定**は開始可能性を示すだけでLevel 2の修了ではない。本人の独立した判断・短い条件変更の回答・実証拠を、校正済みAI評価器と決定論的な検査で確認する。模範の閲覧自体を不合格理由とせず、無根拠な転記だけで合格にもならない。

### フェーズ間の一致条件

- **M04終了 ≒ M05開始**：M04の承認済みCase、仕様ID、初期データ、操作・期待結果、自動化対象の採否を**同じ入力契約（必須項目・スキーマ・仕様revision）**で引き継ぐ。本人のM04成果物を利用する場合はその固有ID・revisionを記録し、M05同梱サンプルを利用する場合は**別の成果物ID・同等の入力契約**として記録する。先行修了課題の模範と同一内容にはしない。M05に追加するNode/Playwrightの環境だけは別の開始条件であり、M04の能力評価に含めない。
- **M07終了 ≒ M08開始**：M07の承認済みspec・Config・依存・Reset・動作証拠の**入力契約**を維持する。本人成果物のID・revisionとM08同梱サンプルのID・revisionは区別し、どちらも同じ契約に適合することを確かめる。M08で必要なGitの準備はM07の合格条件に含めない。
- そのほかも**Mxx終了の必要成果物とM(x+1)開始の前提を同じ入力契約に紐付ける**。本人提出物と公開サンプルは別の成果物ID・版を持ち、同一ファイルであることを要求しない。後続課題のために追加する未完成テンプレートや意図的な失敗素材は、前モジュールの終了成果物と混同しない。
- フェーズ修了課題は学習者の**初見の別条件**で評価する。保存している模範の終了成果物を閲覧したことによって修了したとみなさない。

## 開始前と終了時の判定

- **開始時**：学習者の配布元SHA、ロードしたモジュールID・revision、必要な依存ファイル、**本人の先行成果物または同梱の公開サンプル**、仕様・Seed、実行に必要な環境要件を照合する。構造結果は`ready`/`insufficient`/`mismatch`/`unverifiable`に分類し、具体的な欠落項目を表示する。`ready`を開始可能やruntime成功とは表示しない。環境要件は`unverified`と明記し、実行結果が必要な課題では独立した開発/実地検証で確認する。
- **終了時**：提出物の必須構造・ID・仕様根拠・動作結果を確認し、**内容が妥当であるかの人による判断**を別に行う。PASSの自己申告や模範と同じ文字列があることだけで合格させない。
- **前工程の成果物がない場合**：前モジュールの本人評価と切り離し、**当該モジュールに同梱された検証済み開始入力を使って学習を開始できる**ことを確認する。これを先行修了と記録しない。自動復元・別モジュールの無断ロード・本人ファイルの自動上書きはしない。
- **開始状態に意図した失敗がある場合**：M07の故障spec、M09の誤ったworkflow等は、正常な課題開始状態として明示する。修了状態のPASS条件と混同しない。
- **基準の改訂**：公開サンプル・公開模範・入力契約を同じrevisionで追跡する。正式仕様、`qa-workflow-skills`、テストデータ、問題、モジュールの学習目標を改訂した場合、開始/終了の両方と隣接モジュールの引継ぎ条件を確認する。古いrevisionの基準に対するPASSを新版へ自動流用しない。

## 知識グラフとの対応

[知識グラフ完成仕様](./2026-10-16_qa-curriculum-ai-agent-redesign_knowledge-graph.md)には、各モジュールの**開始・終了基準状態を識別できるIDと参照関係**を追加する。必要条件は次のとおり。

- 各`module`→開始基準状態・終了基準状態を辿れる。
- 状態から必要な知識・製品仕様・利用Skill・教材・実技・評価基準・revisionへ辿れる。
- 前モジュールの終了と次モジュールの開始が共有する**入力契約ID・参照revision**を検索できる。本人成果物を使う場合は成果物IDを維持し、公開サンプルの場合は**別IDが同じ入力契約へ適合**することを確認できる。仕様やSkill変更時の再確認候補も特定できる。
- 機械で確認する条件と、意味・判断を確認する条件は混同しない。
- 公開グラフは**基準状態の識別子・公開可能な判定契約と評価ファイルへの参照**を持ち、模範本文や受講者成績を複製しない。

| 終了判定 | 模範の機械チェックと、仕様・理由・別解を含む意味的な確認方法が揃っている |

| 配布境界 | 公開の模範・採点・完成状態資料が学習者Template、Web Build、同期/ロード、公開Artifactへ含まれないことを契約テストで確認する。配布除外は秘密保持ではない |
