### 学習・提出・評価

1. 全11モジュールの各学習目標に、**説明例を1つ以上、別条件の本人判断を測る演習、短い質疑への回答、操作・実行証拠、自己確認、公開評価基準、復習先**を対応させる。技法・演習の複雑さに応じて例と課題は追加する。
2. 各モジュールでは本人が自己確認とクイズを行って次へ進める。一定の低得点には復習を案内するが、自動進行禁止や正式修了とはしない。評価者による各モジュールの承認待ちは設けない。
3. 専任研修担当者はM04/M07/M10の終了時に、そのPhaseの**全モジュールの証拠をまとめて**正式評価する。採点は目標ID別のLevel 0/1/2/3・BLOCKED・未評価を区別し、全必須目標Level 2以上で修了とする。不足時は対応目標の追加練習と再評価を行う。

5. 画面操作証拠は、必要な画面・安全に取得した操作記録・ログ・実行条件・成果物を組み合わせて、第三者が実際の作業と判断を確認できる形とする。大量の動画を形式目的で必須にしない。本人の質疑回答と再評価履歴は既存の`workspace/Mxx/submission.md`などへ追記し、非公開の正式評価結果は別管理する。

## 3. 改善後の受講者像と学習の流れ

### 3.1 受講者の前提

- PC基本操作とテスト実施または設計の経験を前提とする。プログラミング・Git・AIの経験は不要とする。
- 日本語の説明を読むことはできるが、BR、AC、Case、Seed、Reset、CLI、SHA等の技術用語は初登場時に未習得とみなす。
- 環境や権限・費用上の問題は技能の不合格とは区別する。
- モジュールの終了時には、AIが成果物を生成しただけではなく、本人が根拠・操作・結果・限界を説明できる必要がある。

### 3.2 全モジュールで一貫させる進行経路

1. 学習トップで「何を学ぶか」「何を準備するか」「Phase 1〜3の違い」を理解する。
2. 環境準備ページを開き、個人の学習用リポジトリ、GitHubアカウント、Codespacesの作成・費用条件・停止方法を確認する。
3. M00から選び、「学ぶ理由」「事前に必要な知識」「今回の到達目標」「必要な時間・環境は何か」を確認する。所要時間は未計測なら推測値を断定せず、実試行後に記録する。
4. 初登場する用語を日本語と身近な具体例で理解する。識別子は意味を教えた後で正式仕様に結び付ける。
5. 教材内の完成した説明例を、最初の条件・途中判断・最終結果まで追う。
6. Codespacesを開き、指定された場所で本人が pnpm course:load Mxx を実行する。実際のコマンド・引数・フォルダ配置は現在の学習用Template/loader実装と照合する。
7. 対象モジュールの入力ファイル、作業場所、編集してよい場所、提出テンプレートを確認する。
8. 手順付き練習→条件変更練習→本人が判断する演習を行う。SkillやAIを使用した場合も根拠を照合する。
9. 成果物を保存し、コマンド・結果・スクリーンショット・Runなど必要な証拠を対応付ける。秘密情報は記録しない。
10. 自己確認表で、できたこと・未確認・BLOCKEDを区別する。
11. Webクイズに回答し、誤答を該当する本文節で復習する。クイズの得点を正式修了としない。
12. 必要な本人評価・提出・再提出の案内を確認する。担当者が未指定ならその旨と暫定的にできる自己確認を分ける。
13. 次モジュールへ本人の操作で進む。前の成果物を自動ロード・自動上書きしない。

Webは説明・閲覧・クイズの入口であり、WebからCodespaces・OpenCode・Skill・Playwrightを自動操作する機能は現在の要求に含めない。

## 4. すべての教材と演習に必要な内容

### 4.1 教材本文の共通要件

各モジュールの本文に、必要に応じて節を分けて以下を記載する。

- このモジュールが必要な理由と、QA業務・身近な操作における例。
- 今までに学んだ知識と、まだ学んでいない知識。未習得の技術用語を前提にしない。
- 初出用語の日本語説明、具体例、正式な識別子との対応。本文に略語だけを置かない。
- 操作・判断の対象となる実在のScenario Shop仕様、画面、Seed、データ、Case。
- 「何を考え、どの情報を調べ、どう判断し、結果をどう確認するか」を省かない逐次説明。
- 条件表、コード、画面操作などの完成例と、誤った例・ありがちな勘違い・その修正理由。
- 初めて触れる画面・操作・ファイル・コマンドについて、開始位置と操作後の目印。
- 手順通りの練習から、条件を変えた本人判断へつなぐ演習。
- 学習項目IDと「受講者が何をできれば到達といえるか」の日本語説明。
- 演習へのリンク、提出物の場所、自己確認、クイズ、復習、次へ進む条件。
- 詰まったときの原因の見分け方と、危険な操作を避けた対処。

BR/AC、Role/State/Data/Journey、Scope、Skill、TCNなどの識別子は保持するが、用語や背景を説明する前に暗記を要求しない。コード・コマンド・API名は正式名称を維持する。

### 4.2 演習資料の共通要件

training/ai-assisted-qa-course/exercises/M00〜M10 のすべてについて：

1. 何のための練習か。どの学習目標を確認するか。
2. Codespacesへの入り方。どのリポジトリ・フォルダ・ターミナルを使うか。
3. 開始前に確認すること。権限・費用・環境・必要ファイル・前モジュール成果物または公開fallback。
4. コマンドをどこで実行し、成功した場合に何が現れ、失敗した場合に何を確認するか。
5. 入力の内容と、編集を許すファイル・許さないファイル。
6. 最初の一例を実際に手を動かして追う手順。
7. 条件を変えて考える練習と、AIの出力をそのまま採用してはいけない例。
8. 最終的な提出物、ファイル名、記載欄、完成例または記入例。正式評価の基本条件は公開してよい。評価時の条件変更・追加質問で本人判断を測る。
9. 自己確認の観点と、評価担当者が確認する本人の判断・証拠。
10. PASS、FAIL、未実行、BLOCKED、仕様未決を混同しない記録方法。
11. 提出・評価・再学習・次へ進むための導線。運用上の未決事項を明示。
12. 再ロード・環境停止時に過去成果物を失わないための注意。

Webに掲載する演習説明と、Codespacesに配るexercise.mdが食い違わないよう同じMarkdown正本を再利用する。Web用に内容を手動複製した第二正本は作らない。

### 4.3 本人による理解の確認

各学習目標について、単に答えの提示・クイズ正答・ファイル存在を確認するのではなく、本人が以下を説明できるかを明示する。

- 何を検証したか、なぜそれを検証したか。
- どの仕様・コード・実行証拠が判断を支えるか。
- AIが出した候補のうち何を採用・修正・保留したか。
- 変更した条件ではどう考えるか。
- できていないこと、仕様で分からないことは何か。

公開の模範解答を全文コピーしただけではLevel 2としない。公開fallbackから独立実習を始めても、前Phaseを修了したことにはしない。

## 10. 確認方法と回帰テスト

### 10.1 必要な自動検証

リポジトリで定義されているコマンドを優先し、変更対象に応じて少なくとも以下を確認する。

- pnpm run validate:ai-assisted-qa
- pnpm run validate:curriculum
- pnpm run validate:skills
- pnpm run validate:spec
- node scripts/training/knowledge-graph.mjs validate
- pnpm run build:docs
- pnpm run build:web
- 関連の契約テスト、unit/component/integration/repositoryテスト
- 新課程クイズのPlaywright E2Eと旧課程・Scenario Shopの必要な回帰
- lint、typecheck、format、security check
- 配布許可リスト、loadの非破壊性、評価資料のWeb/Template混入防止

Windowsローカルの保護対象未追跡ファイルによる既知の全verify停止は、今回の変更による失敗と区別する。別SHAの成功や実行していない検証を今回のPASSとして報告しない。

### 10.2 追加・更新する検証

- サイドバーから学習トップ・環境準備・仕様書一覧・学習目標・各モジュールへ移動できる。
- Webの学習目標、公開演習、公開評価基準をサイト内で読める。学習者向けの文書が意図せずGitHub blob/mainへ移動しない。
- 旧課程・仕様ページ・M00〜M10・クイズ53問のリンクとAnchorに欠落がない。
- 教材・クイズに可視SHA-256値を表示しないが、クイズの版変更時に旧回答を流用しない。
- 教材・クイズが共通の外観・ナビゲーションを持つ。
- リテラル \n や不正なエスケープ文字が本文に表示されない。
- 画像がビルドに含まれ、altテキストがあり、デスクトップ・小画面で読める。
- 教材本文と演習ファイルの参照・記述が食い違わない。
- 模範解答、採点用テスト、完成状態、個人Secret・評価記録を配布/Web Buildへ混入させない。
- 既存の22状態、固定Skill revision、source SHA、上書き防止、M06公開fallback、Phase 3選択制が維持される。

### 10.3 人による教材レビュー

全11モジュールの各学習目標について、最低限次を実際の本文・演習で確認する。

| 観点 | 確認内容 |
| --- | --- |
| 前提 | 新しく出てくる言葉と操作に必要な説明が先にあるか |
| 理解 | 身近な例→Scenario Shopの正式な例へ移れるか |
| 実技 | どの画面・ファイル・コマンドから始めるかを本文だけで分かるか |
| 判断 | 完成回答を写す以外に、条件変更・根拠確認の練習があるか |
| 自己確認 | 成功・失敗・未実行・BLOCKEDが分かるか |
| 評価 | 提出する物とLevel 2の判断が明確か |
| 復習 | 誤答や詰まりに対応した説明箇所へ戻れるか |
| 継続 | 次へ進める条件と前工程からの引継ぎが正しいか |

字数、チェック欄の存在、CI成功だけで「学習可能」と判定しない。

### 10.4 実際の受講者で行う検証

外部Template・Codespacesの実地確認に加え、テスト実施・設計経験者に口頭補足なしで（今回PR外の後続改善として）、学習トップ→環境準備→M00→演習→成果物→自己確認→クイズ→復習→次への進行を試してもらう。Phase 1/2/3の性質の異なる代表モジュールも確認する。迷った位置、分からない用語、操作できない画面、教材にない判断、BLOCKEDを記録して改善する。

この実試行は現時点で未実施。試行せず「初学者が学べることを実証済み」と報告してはいけない。

## 11. 完了条件

**教材・Web・演習の実装完了**を判断するための条件：

1. 受講対象が「テスト実施または設計の経験者で、AI・開発ツールは未経験でもよい」としてPlan・教材で一致している。
2. M00〜M10の全11教材が4章・5章の要件に沿って充実し、初出の前提知識と用語を説明している。
3. 各モジュールに、操作の入口、作業手順、期待される結果、失敗時の確認、本人判断を要する練習、提出物、評価、復習、次へ進む方法がある。
4. 学習トップ、Codespaces環境準備、全仕様の入口、51学習項目、Webで読める演習・公開評価基準へ迷わず辿れる。
5. 教材・クイズの外観が統一され、現在地・トップ・前後移動が分かる。
6. 受講者画面にSHA-256を表示せず、内部版管理と保存回答の整合性を維持する。
7. 文字列の \n、リンク切れ、画像欠落、モバイルでのレイアウト崩れがない。
8. 必要な図・実画面例が入り、仕様と実装が一致し、本文からも内容を理解できる。
9. 全53問・51学習項目・58知識ノード・11モジュールの演習・公開ルーブリック・模範との意味上の整合が確認される。
10. 学習用Template、同期・ロード、既存Playwright・Scenario Shop、旧課程、評価資料の配布除外、安全境界に回帰がない。
11. 自動検証・ブラウザ操作検証を実施し、未実行・BLOCKEDを隠していない。
12. 未確定の評価担当者・提出先・運用URL・費用条件は、架空の決定事項に置き換えていない。

**運用開始を判断する追加条件**：

- 外部Template/Codespacesで、M02→M03のOpenCodeモデル依存の統合を含む必要な実地動作が確認されている。
- 実際の対象となるテスト経験受講者が教材と操作手順を追えるか試行し、実際に問題となった迷い・欠落を修正した。
- 正式評価担当者、提出先、非公開評価記録の保存先・権限、再提出・BLOCKED対応が決定・共有されている。
- 評価担当者が同じ証拠を見て、正しい別解と不足・未確認を一貫して判断できる。
- これらの確認が終わらない間、教材の実装完了と運用開始可能性を混同しない。

## 12. 想定されるリスクと対処

| リスク | 対処 |
| --- | --- |
| 文章量を増やしただけで理解しやすくならない | 学習項目ごとの前提・具体例・実操作・判断・評価を実物でレビュー |
| 技術用語を全部消して正式仕様と結び付かなくなる | 最初に日本語で意味を教え、その後正式名称・識別子を導入 |
| WebとCodespacesで教材内容が二重管理になる | 既存Markdownを正本とし、Web生成・配布で共通利用 |
| 公開すべきでない採点・個人記録が混入する | 公開許可リストとビルド検証、秘密情報を扱わない例 |
| 実画面画像が古くなり手順と矛盾する | 更新元と確認対象を明示し、画面操作の回帰確認を追加 |
| Codespaces費用や権限を推測して受講できなくなる | 利用枠・請求主体・2コアを実地確認し、未確定はBLOCKED |
| 未完成のOpenCode統合を「実行できる」と説明する | 実環境受入まで未確認とし、決定論的runtimeの証拠と分離 |
| クイズの点数が本人の修了として扱われる | 公開ルーブリック、本人の成果物・判断、評価担当者を分離 |
| 改修が既存の旧課程や製品へ波及する | 共通コードの影響を確認し、旧課程/Shopの回帰を実行 |
| デザイン刷新が操作性を下げる | アクセシビリティと実際のナビゲーションを先に検証 |
