# 知識グラフの完成仕様と継続改訂

## 全機能分析・学習目標・AI判定の参照契約

全Web・管理・Nativeのサポート機能を公式仕様から棚卸しし、分類済み100%と分析対象の意味的設計済み100%を別々に算出する。対象外・未決・BLOCKEDと理由を追跡し、分析済みの分子に加えない。既存の目標IDと教材・演習・仕様・Skill・証拠・採点を紐付け、M02/M04未知仕様引継ぎ、M06新規E2E、M07保守設計、M10 CI運用判断で不足したら既存IDを壊さず追加する。AI意味レビューは既存のグラフと採点JSONを使い、実入力SHA・教材節・正式仕様を確認してpass/fail/ungradableを根拠付きで記録する。新DBは作らない。

## 改訂後の学習目標と追跡・判定（2026-10-25）

現行51学習目標・58理解事項・53問題は確認時点の基準値であり、固定上限ではない。Phase 1の未知仕様と設計引継ぎ、Phase 2のE2E本人構成・Page Object/fixtureの保守設計、Phase 3のCI設計・権限と運用判断を、教材・知識・仕様・Skill・クイズ・演習・質疑・操作証拠・評価基準へ追跡し、不足する学習目標には既存IDを壊さず追加する。

Scenario Shopの全対象機能について、仕様・Risk/TR/Condition/Caseまたは根拠付き対象外・未決・BLOCKEDの対応を追跡する。目標ごとの教材品質AIレビューは出典位置・判定規則・合格/不合格/判定不能・校正例とともに残し、構造Validatorや本人のLevel 2を代替させない。

## 目的・完成条件

知識グラフを、**カリキュラムの学習目標・必要知識・教材・確認問題・実技・評価基準・テスト対象・Agent Skillsを一貫して追跡し、変更時に必要な改訂と再検証を特定する仕組み**として完成させる。今後も追加・改訂があることを前提とするが、今回の実装を途中段階として成立させる計画にはしない。

完成条件は次のとおり。

1. 必修M00〜M07と選択M08〜M10の**全51学習項目**について、必要な知識・前提・教材節・クイズまたは実技・Level 2の評価基準を辿れる。クイズ不要の項目には実技で測る理由を記載する。
2. 既存の理解事項58件について、内容・粒度・重複・前提順序を精査し、必要な分割・統合・追加・削除を反映した**過不足のない知識体系**を確定する。件数を58に固定しない。根拠は各項目の学習目標と実際の教材・課題に置く。
3. 正式仕様・Seed/Reset・Scenario Shopの実装参照と、別リポジトリ`ryu-yoshikawa-pro-vision/qa-workflow-skills/skills/`の利用Skillについて、**参照元commit・関連する学習項目・演習を確認できる**。Skillと製品仕様の本文をグラフへ複製しない。
4. 教材・問題・実技の追加、更新、移動、削除、仕様・Skillの改訂に対し、影響する学習項目、理解事項、教材節、評価、モジュールを**根拠付きで抽出**できる。影響対象が未接続の場合は取りこぼしとして検出する。
5. **整合性の機械検証**と**教材・評価内容の独立した妥当性確認**を区別する。グラフが通過しただけで問題の正しさ、Skill実行、受講者の習熟を認定しない。
6. 学習者へ配布するファイルと公開評価資料の境界を維持し、グラフには評価資料の参照を記録できるが本文を複製しない。Secret、本人の成績は公開グラフへ含めない。既存の配布許可リストを変更権限の正本とする。

## 正本と保存形式

- **ID間の対応・依存関係の正本**：`docs/curriculum/ai-assisted-qa/knowledge-graph.json`（UTF-8 JSON）。リレーショナルDB・グラフDB・閲覧用Webアプリは追加しない。教材本文や正しい期待結果はJSONに複写しない。
- **学習目標・水準**：`..._learning-map.md`と`..._progression.md`が要求の正本。JSONへ必要なID・短い説明・参照先を持つが、長文教材を複写しない。
- **教材・クイズ・実技・評価**：教材本文はMarkdown、学習用クイズの問題・正答・公開解説は`quizzes/Mxx.json`、実技はspec等、評価基準は各実ファイルが内容の正本。**関係グラフJSONはクイズ内容を複製せず**、各問題のIDと当該JSON内の位置・参照先、必要なrevisionと関係のみを持つ。
- **製品仕様**：`docs/spec/`を正本とし、変更経路・元のGit SHAと必要な文書/BR/ACを参照する。
- **Skill**：`ryu-yoshikawa-pro-vision/qa-workflow-skills`の`skills/<skill>/SKILL.md`を正本とし、commit SHAとSkillで参照するhelperの存在・依存を確認する。`qa-training-store/.agents/skills/`の汎用Skillは対象に含めない。
- **公開評価資料**：模範解答・採点用テスト・完成状態データは`training/ai-assisted-qa-course/assessment/`の公開正本に保存する。公開グラフには評価資料のID・パス・revisionと評価観点を記録できるが、評価資料の本文や学習者個別の結果は複製しない。

## 対応表の生成と二重管理防止

- [学習項目対応表](./2026-10-16_qa-curriculum-ai-agent-redesign_learning-map.md)の学習項目ID・理解事項ID・教材節・問題ID・実技/評価IDなどの**関係情報はJSONグラフだけを手動で更新**する。対応表はグラフの関係と実際の教材・問題・実技・評価ファイルから生成する閲覧用データとし、手編集の正本にはしない。
- 学習目標・Level 2の文章は学習項目Planと学習順序Plan、各設問の問題文・選択肢・解説は問題ファイル、実技の課題内容と評価条件はそれぞれの実ファイルが正本。JSONにあるID・パス・revisionを実ファイルと照合し、**ファイルがあるだけ、関係が存在するだけでは内容の妥当性を保証しない**。
- 既存の`scripts/training/knowledge-graph.mjs`に、**対応表をMarkdown形式で出力する読取り専用経路**と、生成した表・グラフ・実ファイルの整合を検証する処理を完成仕様として追加する。表をリポジトリに保存する場合は同じ経路で再生成した差分を検査する。別の手動台帳や新DBを増やさない。
- 検証では全51学習目標の存在、必須関係の欠落、同一IDの重複、削除/改名による参照切れ、評価手段の不在、revisionのずれを検出する。意味上の評価妥当性は担当者のレビュー記録で確認し、グラフの構造チェックをその代わりに使わない。
- 22基準状態は**各モジュール別に独立した論理状態と判定契約**を保持し、同じ公開区分・同一revisionの設定やSeed等は共通IDで参照可能とする。学習用の開始サンプルと公開完成状態資料は用途別のファイルとし、完成状態は学習者配布から除外する。物理データを再利用しても各状態の参照整合を確認する。

## ノード契約

すべてのノードに不変の`id`、定義された`type`、短い`title`を持たせる。実在ファイルを指すノードには`repo`、`path`、必要な`revision`（Git commit SHA等）、参照が有効かを確認する方法を持たせる。IDは改訂後も可能な限り維持し、表示名・パスと同一視しない。

| type | 役割と必須対応 | 完成時の扱い |
| --- | --- | --- |
| `phase` | P1〜P3と必修/選択 | 3フェーズと修了の境界を保持 |
| `module` | M00〜M10と所属・順序 | 前提となるモジュールと学習者のロード単位を追う |
| `learning_objective` | `M00-01`等、Level 2基準 | 51項目の教材・評価への到達可能性を保証 |
| `knowledge` | 目標に必要な独立の理解事項と達成時の行動 | 粒度の妥当性、既習知識の再利用、先行依存を確認 |
| `lesson` | 実在する教材の節・例・演習前の説明 | 対象知識の説明位置、教材revisionを追う |
| `quiz` | 実在する問題ID・公開解説への参照 | 対象知識・要求認知水準・選択肢の根拠を検証 |
| `exercise` | 実在する模擬課題・実技と提出物 | 対象の能力、入力条件、評価証拠を対応させる |
| `assessment` | フェーズ末の修了基準、公開模範・採点資料への参照、評価観点 | 初見条件でLevel 2を測れるかを確認。評価時に提示する具体的条件は含めない |
| `module_state` | 各モジュールの開始/終了基準、revision、公開可能な照合契約 | 全11モジュールの開始と終了を対応付ける。公開の模範本文は複製せず、完成状態ファイルのパス・revisionを参照する |
| `artifact` | 実技により提出する成果物の識別子・保存先・公開可否 | 公開の模範解答は評価資料の参照から辿り、学習者個人の実データは保持しない |
| `test_target` | Scenario Shopの機能・BR/AC・必要な状態/Seed等の参照 | 教材/実技が参照する仕様の変更影響を追う |
| `skill` | 外部workflow Skillの入口・revision | 実際のSkill/補助ファイルに対応し、変更影響を追う |

まだ教材・問題・実技の実ファイルがない段階では**架空のパスや問題IDを実在するノードとして作成しない**。完成状態では必要な成果物を実際に作成し、上表のノードへ接続する。既存JSONの記録内容と完成条件の不足は実装作業として扱い、完成要件そのものを段階的・暫定的に縮小しない。

## 関係契約

`from`、`to`、`relation`は必須。関係の方向と、どちらを変更したらどこを見直すかを明示する。後続の関係を無秩序に増やさず、次のものを必要な範囲で使う。

| relation | 方向と意味 |
| --- | --- |
| `part_of` | 学習目標→モジュール、モジュール→フェーズ、教材節・問題・実技→モジュール |
| `requires` | 後で学ぶモジュール/知識→先に必要なモジュール/知識 |
| `requires_knowledge` | 学習目標→必要な知識 |
| `teaches` | 教材節→説明する知識 |
| `evaluates` | クイズ/実技/修了評価→**実際に測る**学習目標または知識 |
| `uses_target` | 教材節/実技/修了評価→参照する製品仕様・機能 |
| `uses_skill` | 教材節/実技→使用するworkflow Skill |
| `produces` | 実技→評価対象の成果物ID・説明（成果物が実在する場合） |
| `has_start_state` / `has_end_state` | モジュール→開始/終了の`module_state`。各モジュールにそれぞれ**1件**の基準状態を持つ |

`produces`の参照先は型`artifact`で、`id`・成果物の保存先・公開可否・所属する実技を明示する。成果物のない実技には関係を作らない。グラフに学習者の実際の提出物や評価成績は保存しない。

従来の`applies_to`・`may_use_skill`は**学習上の候補関係**であり、実施対象が確定した`uses_target`・`uses_skill`の代わりに使わない。移行時は関係の意味を検証し、候補を機械的に確定扱いへ変換しない。既存JSONの過去記録を利用する場合はスキーマ更新と一緒に移行・検証する。

## 評価の網羅と合格判定

1. **教材の網羅**：全必須`knowledge`に、当該知識を説明する`lesson`がある。単なる関連章のリンクでは不十分。また、11モジュールすべてに公開可能な判定契約と公開の模範実データがある。
2. **評価手段の網羅**：全必須`learning_objective`に`quiz`または`exercise`/`assessment`が対応する。技能・判断を四択のみで合格にしない。
3. **内容の妥当性**：問題の出典・正答・全選択肢の意味と理由・認知水準、実技の前提/操作/期待結果/証拠が**本当に対象能力を確認するか**独立レビューする。レビュー結果を公開可能な根拠で記録する。
4. **本人の習熟**：使用した教材・課題の版と本人の回答・操作・判断を、公開グラフではなく非公開の受講記録で確認する。環境BLOCKED、未実行、未達、達成を区別する。
5. 評価不能・教材欠落・知識分解の重複・前提順序の循環があれば**未達として報告**する。問題やノードを形式的に追加して件数だけ合わせない。

## 変更・改訂フロー

1. 改訂元を特定する（正式仕様のファイル/BR/AC、Seed/Reset、Skillのcommit、教材、問題、実技、Level 2基準）。
2. グラフから**直接の利用箇所と逆向きの関係を辿って**影響候補を抽出する。仕様ファイルの変更では該当する教材・実技・評価を、Skill更新では使用する教材・実技・関連モジュールと学習目標を示す。参照が欠ける場合は追加調査する。
3. 実際の変更差分と参照契約を読んで影響候補を採否判断し、教材・問題・実技・評価基準・モジュール順序の**必要な変更のみ**を行う。
4. JSONと実在ファイルを合わせ、既存IDの保持・改名/分割/統合・移動・削除の対応と、受講者用配布許可リストを点検する。
5. 参照整合・循環・実在ファイル・元commit・必須の対応範囲を機械検証し、影響範囲の教材/実技を意味的にレビューする。Skill実行経路・Playwright実行が変わった場合だけ必要な実行検証を行う。
6. 元の資料・Skillの更新とグラフの改訂は**別のリポジトリの別責務**。グラフから勝手に製品コード・Skillへcommit・pushしない。

## モジュールの開始・終了基準状態との関係

[状態設計](./2026-10-16_qa-curriculum-ai-agent-redesign_states.md)に従い、**全11モジュールそれぞれの開始・終了基準状態をグラフから参照可能**にする。

- `module_state`ノードを採用し、モジュールID、`start`/`end`、基準revision、公開可能な判定契約の実在パスを保持する。公開の完成状態データは`assessment/`に保存し、その本文を公開グラフへ複製しない。学習者個人のデータは公開グラフへ含めない。
- `module`から`has_start_state`・`has_end_state`で参照する。状態と、必要な教材・知識・仕様・Skill・評価を既存の関係で辿れるようにする。前モジュールの本人成果物はそのID・revisionを引き継ぎ、**同梱の公開サンプルを使用する場合は別ID・revisionのまま同じ入力契約へ接続**する。成果物のIDが異なることを不整合とみなさない。
- 基準の内容は「正常動作」だけを意味しない。M07の故障課題・M09の失敗Run等、**意図的な失敗を含む開始状態**も正しい状態として記録する。
- グラフ検証では**22個の開始/終了状態ノード**（11モジュール×2）の存在、関連契約ファイル、同じ入力契約に適合する前後の本人成果物または別IDの公開サンプル、共通データの参照先とrevision、変更時の影響追跡を確認する。**22組の重複した実データの複製は要求しない**。外部Skillの変更から状態の再確認対象へ辿れることを受入条件にする。
- 基準入力の参照だけで前モジュールの本人修了を認定しない。**自動復元は責務に含めない**。

## 未登録変更の検出と教材改訂の確認

- **変更ファイルの一覧を入力**できるようにする。既存の単一ノード向け`impact <node-id|path|repo:path>`に加え、実装時は`impact --changed-files <path-list-file>`でGit差分から得た複数ファイルを照合する。CLI自体が外部へpush・教材同期・Git履歴書換えを行わない。
- 変更ファイルがグラフに未登録の場合、**影響なしではなく`unmapped`としてFAILまたは要手動確認**を返す。ただし`node_modules/`、生成物、画像など対象外ファイルは固定された除外規則で区別する。Skill変更は`qa-workflow-skills`の**旧/新の確定commit間で差分**を取得してから比較する。
- `lesson`・`quiz`・`exercise`・`assessment`・`module_state`など、**教材を追加・移動・削除した場合**も実在するファイルとグラフ参照を照合する。削除対象のnode IDやrevisionを無断で使い回さず、分割・統合時は旧IDとの対応理由を更新内容として残す。
- 修了課題・通常演習と**公開の開始用サンプル入力**を区別して結び付ける。基本評価条件は公開してよい。評価時は追加条件・質問で本人判断を確認する。状態グラフは入力の契約IDと基準revision・実在する公開契約・公開評価資料のID/パスだけを保持し、資料本文は複製しない。
- グラフは**評価対象への対応を追跡するもの**で、評価者が提出物から本人の能力を認定する責務を代替しない。全必須目標・知識・教材・実技・終了状態の接続を検証し、意味的な妥当性は担当者が別にレビューする。

## 検証CLI・データ管理

- `node scripts/training/knowledge-graph.mjs validate`でスキーマ、ノード/関係、ID・型、参照切れ、モジュール/知識の前提循環、全学習目標の知識・教材・評価接続、参照ファイル・commitを検証する。
- `node scripts/training/knowledge-graph.mjs impact <node-id|path|repo:path>`と、完成時に追加する`impact --changed-files <path-list-file>`で影響する知識・学習目標・モジュール・教材・クイズ・実技・評価を理由とともに示す。未登録変更は**unmapped/要確認**とし「影響なし」へ分類しない。
- 同じ入力では同じ結果とし、Gitのコミット/差分で変更履歴を管理する。データを改訂しても存在しないSkillや問題を捏造しない。
- 正本の仕様とSkillのrevisionは、各学習用教材が参照した版を辿れるようにする。改訂後の過去の学習結果は無条件で新版の成功証拠としない。
- 検証CLIは読取り専用。ネットワーク更新、教材同期、受講者ロード、成績記録、外部Skillの実装変更を**兼務させない**。
