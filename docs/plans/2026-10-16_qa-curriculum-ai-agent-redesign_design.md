# QAカリキュラム再設計：学習目的・評価・レッスン設計

## 採用する学習目的

**卒業像**：手動テストの基礎を持つ初学者が、Scenario Shopの仕様とリスクを理解し、OpenCodeと必要なQA Skillを使ってテスト分析・設計・Playwright自動化・実行結果の評価・変更管理を進められる。AIが出した結論の根拠と変更差分を確認し、誤りや未実行を見抜いて適切に差し戻せる。

学習対象はテスト自動化の実務とAIエージェントの利用である。OpenCodeは無料利用可能なモデルがあるため実習に採用するが、特定モデルの性能評価、モデルID、料金枠、ツール設定の細部は評価対象にしない。Claude Codeなどへ移った場合にも共通する能力を重視する。

### 卒業時に実証する能力

| 能力 | 具体的な到達行動 | 完了の判断に使うもの |
| --- | --- | --- |
| 仕様・リスク分析 | BR/ACと観測結果を区別し、重要なリスク・未確定事項を抽出する | 正本参照、リスク、欠落と採否理由 |
| テスト設計 | 境界値・状態遷移などの技法を適用し、AIのケース案を評価する | 条件・ケース・期待結果・仕様の対応 |
| エージェント活用 | 目的、対象、参照資料、変更許可範囲、出力、完了条件を渡し、必要なSkillを利用する | 実際の依頼内容と結果、必要に応じた再依頼 |
| 自動テスト | PlaywrightコードをAIと協働して完成し、Locator・Assertion・Seed/Resetを確認する | 対象ケースと対応したコード、独立した実行結果 |
| 失敗分析 | エラーと実行証拠から製品・テスト・環境の原因を区別し、必要な修正を判断する | 根拠、初回結果、修正、再実行結果 |
| 変更管理 | 生成差分を自分で確認し、PR・CIの実行結果を根拠に合否を判断する | `git diff`、PRレビュー、Run / Check / Artifact |
| 安全性 | 認証情報・利用者情報を渡さず、AIの変更や実行を許可範囲に限定する | 意図しない差分なし、権限・実行対象の説明 |

コードをすべて手書きで再現すること、すべてのSkillを暗記することは求めない。一方で、AIに書かせたテストの検証内容を本人が説明できない場合は修了としない。

## 評価基準：C01〜C12の継続とC13の追加

既存のC01〜C12と評価レベル0〜3は継続する。**C13「AIエージェントを用いたQA作業と成果物の検証」** を新たな共通必須項目に追加する。AI活用はC02/C04/C07/C09/C11にも反映するが、C13があることで「AIを実際に使ったか」を見落とさない。

| レベル | C13で実証する行動 |
| --- | --- |
| Level 0 | エージェントに依頼できない、または未実行と成功を区別できない。AIの推測を仕様の根拠とする |
| Level 1 | 指示された入力とSkillで分析・設計またはコード作成を行い、ガイドに沿って確認できる |
| **Level 2（必須）** | 実際にOpenCodeへ範囲を指定して依頼し、返された設計・コード・結果を仕様や証拠で検証し、採用・修正・不採用を理由付きで判断して完了できる |
| Level 3 | 複数案やSkillの開始点を比較し、リスク・工数・結果の信頼性を踏まえて実行方法の改善を提案できる |

Part 1のC13 Level 2は「仕様分析→テスト条件/ケース→Playwright作成→ローカル実行→評価」が1件以上つながっていること。Part 2ではその変更について差分レビュー→PR→対象コミットのTraining CIのRun / Check / Artifactまで確認できること。**操作したという報告だけでは不足**。実際の依頼、成果物、受講者の採否判断と理由、証拠が必要。

現行の修了条件は、Part 1 = C01〜C07 + C09〜C10、最終 = C01〜C07 + C09〜C12、C08 = Native選択。これに**両課程でC13を加える**。既存の形式・IDの互換性を確認し、修了レシートの意味判定を自動で偽装しない。

既存項目の変更は最小限にする。
- C02/C04：AIが作った分析・設計も、受講者が正本と照合して確定した成果物として認める。
- C07：全手書き前提を外し、採用したAssertion、状態リセット、Test Case対応と実行成功を要求する。
- C09/C10：AIの原因仮説・改善案と、実行証拠で確定した結果を区別する。
- C11：AIが作ったGit差分も受講者が説明・レビューしたものを認める。
- C01/C03/C05/C06/C08/C12の業務上の修了要件は、理由がない限り維持する。

### 評価に残す証拠

既存 `handoff-root/self-check/P1-09.md`、`P2-08.md` と既存のワークブック・コード・実行証拠を使う。新しい必須CSVを作らない。各self-checkには少なくとも次を短く記す。

1. 対象と依頼した作業：正式仕様、条件、許可範囲、AIへの指示（全文または再現できる要約）。
2. エージェントの結果：使用したSkill、作成/提案されたテスト条件・コードの参照先。
3. 本人の判断：採用した点、修正または不採用の点、仕様・テスト技法・ログに基づく理由。
4. 実行確認：実行コマンド・対象Commit・成功/失敗/未実行・関連Receipt/Trace/Check/Artifact。
5. 未解決事項：不明点、環境障害、権限・モデルの制限を完了と混同しない。

会話ログ全部、モデルの内部推論、トークン使用量、料金の数値は必須証拠にしない。APIキー、シークレット、個人データは記録しない。採点に「AIが必ず間違えること」を要件としない。後述の**固定された誤りのある提案**を別途評価できるようにする。

`training:completion:check` が判定するのは機械的な整合・提出物の有無。C13の判断の正しさは受講者自身と講師の公開ルーブリックで判定する。講師による対面採点や外部LLM Judgeを必須にしないが、実際にAIを使ったことと根拠を示す必要はある。

## 教材の順序と17レッスンの変更設計

現在のファイルとLesson IDは維持する。`P1-07`、`P2-06`はNative選択課程。全レッスンへAI節を機械的に追加しない。元の学習目的と活動を比較し、**以下の置換・縮小・維持**を実施する。

### Part 1：テスト対象から自動化・結果評価まで

### レッスン移行と学習負担

- P1-02の分析とP1-03のケース設計を**毎回最初からやり直さない**。同一のCart課題を段階的に深め、必要な時だけ新しい条件を加える。
- P1-04で最小の手動Assertion修正を1件行い、生成コードを評価する前提を確保する。その後はAIに実装を任せてもよい。
- P1-06のC09演習、P1-08のC10演習は既存の決定的な教材を使う。自然に不具合が発生するまで待たせない。
- P1-09とP2-08は同じ成果物の追加検証。総合演習のために独立したテスト一式を二重実装しない。
- 現行の約80〜85時間は改訂前の計画値であり、改訂後の確定値として掲載しない。AI導入で省く手作業と、結果検証・差分確認に要する時間を実習で測ってから修正する。
- 既存Lesson IDを固定するのは回帰上の合理性による。必要性が確認できれば後に変更可能だが、今回の目的だけでは変更しない。

## 初回から最終までの共通演習

### P1の流れ

1. `docs/spec/features/cart.md` の `BR-CART-001`・`AC-CART-001`を確認。どの状態で数量上限を超える操作を拒否するか説明する。
2. OpenCodeに作業目的、参照すべき正式仕様、必要な出力、**製品コードを変更しないこと**、予期しない操作の確認を依頼する。必要なSkillを使ってリスク・条件・テストケースを作成する。
3. 生成したケースを仕様と照合し、重要度・テスト層・期待結果を受講者が確定する。AIの案が正しければ無理に誤りを見つけなくてよい。
4. `training/playwright/exercises/`にPlaywrightテストを生成し、実行前に差分をレビュー。Seed/Reset・Locator・Assertion・Case IDを確認する。
5. 既存Training入口で実行。失敗ならTraceと事実を取り、必要に応じてAIへ診断を依頼する。成功した場合もCaseが意図した条件を検証していることを確認する。
6. P1-06の`diagnostic-cart.spec.ts`で、仕様に反する期待結果を実際に検出・修正する。本人の診断根拠を残す。P1-08は別にC10の最小保守改善を扱う。
7. 4 CSV、コード、証拠、Receipt、self-checkに必要な情報をまとめる。C13の判断記録を追加する。

### P2の流れ

1. P1から引き継いだテストコードのGit差分と対応するTC IDを確認する。
2. OpenCodeにレビュー案を出させ、本人が正本と実装に基づいて判断する。不要な改変は採用しない。
3. 用意されたTraining CopyのPRへ反映し、対象commitのTraining CIを確認する。
4. Run/Check/ArtifactとローカルRunを区別する。AIの「PASSでした」という文章だけで成功扱いしない。
5. C11、C12、C13の評価記録を同じケースから提出する。

## C13の判断を安定させる演習

エージェントが常に誤った回答を出すとは限らない。C13の採否判断を偶然に依存させないため、講師用の既存決定的な診断素材を再利用する。

- P1-03：教材に「上限超過なら数量を自動補正して成功する」といった**誤ったテスト期待結果の案**を提示し、受講者が `BR-CART-001` と照合して不採用にできるか確認する。これは製品のバグ注入ではなく、レビュー演習の入力である。
- P1-06：`diagnostic-cart.spec.ts`の誤ったAssertionを特定し、仕様と実行証拠に基づいて修正する。
- P2-03：過剰な共通化・無意味なAssertion・未実行の成功報告などから、必要な指摘を選ぶ教材用のレビュー例を利用する。新たな評価基盤は作らない。

**採点の正解は正式仕様・既存テスト契約を根拠とする**。採点用に意図的なAI回答を公開教材の「生成結果」だと偽らない。教材上は「誤った提案例」と明記する。

## OpenCode実習に必要な最低限の安全条件

- 作業環境は個人のTraining Copyまたは隔離した学習用コピー。`qa-training-store`の本番用回帰スイート・デプロイ設定は変更しない。
- OpenCodeに利用するSkillは、`qa-workflow-skills` の実在するパス・依存ファイル・スクリプトを伴う。利用revisionを記録し、未知のモデルに依存する設定を教材へ固定しない。
- 仕様は `docs/spec/` を正本とし、UIやAI出力は観測・推論として区別する。
- 変更前は許可対象ファイルを限定。変更後は`git status`と`git diff`を確認してから採用する。
- Secret、トークン、個人情報、実案件の非公開データを無料モデルへ送らない。教材に必要な情報は模擬ECのデータだけを使う。
- 実行先・副作用・Reset/cleanupが確認できない場合はエージェントに本実行させず、未実行として扱う。
- 失敗をリトライ回数やタイムアウト増加で隠さない。ローカル・CI・診断Runを混同しない。

## Codex実装前の受入確認

1. P1-02からP2-08まで、レッスンごとの**実際に置き換える節・演習**と不要になる旧記述を決め、差分が既存内容の重複追加でないことを確認する。
2. Skillを読み込めるOpenCodeの現行環境を確保し、少なくともCartの小さな実習を行う。未実行なら教材上の動作保証を付けない。
3. 学習者が提出するC13の証拠を、既存のself-check・ワークブックと結び付け、テストコードの品質・実行結果・理解度がそれぞれ評価できることを確認する。
4. 契約テスト・必須レッスン・既存Workbook・正式テストの関係を整理してから書き換える。コード変更・PR・CI設定の変更はCodex実装段階でのみ行う。
