# テスト自動化・AIエージェント活用カリキュラム再設計Plan

## 結論

現行17レッスンを維持し、**学習目標・評価・演習の中身をAIエージェントとの協働へ再設計する**。既存課題へ「AIを使う」段落を追加するだけの改訂は行わない。

学習目的は、QAの分析・設計・Playwright自動化・結果評価・変更管理を、OpenCodeとqa-workflow-skillsを使って進め、AIの成果物の正確性・差分・実行証拠を本人が判断できることである。

- 既存のC01〜C12を維持し、AIの実利用と生成結果の検証を必須にするC13を追加する。
- Cartを共通の必須テスト対象とし、既存のSeed・診断・保守演習を再利用する。Checkout/Paymentの難しい状態遷移、Native、Scored Agentic QAは選択・発展に配置する。
- テストケース・コード・証拠・self-checkの既存提出形式を再利用し、意味判断まで機械PASSにしない。
- 現時点で新しい製品機能・意図的な本体バグ・新規QA基盤を追加する根拠はない。実動作で必須課題の不足が証明された場合だけ最小限の修正を検討する。
- 実装はCodexが担当する。**このブランチでは調査・再定義・設計文書以外の変更をしない。**

## 設計判断の理由

### 既存17レッスンを維持する

既存の教材は、仕様・リスク・テスト技法・Playwright・実行証拠・保守・Git・CIという必要分野をすでに扱っている。Lesson IDやCSV・修了判定の変更コストだけではなく、**AI協働に置き換えれば既存分野を活かせる**ため、数を削減・増加させる必要性が確認できない。

ただし、同じテストを手作業とAIで最初から二度作らせることは避ける。受講者が最小の理解を得た後、AIに設計・実装を委譲し、仕様と証拠から本人が検証する。

### C13を追加する

現行C01〜C12だけでは、AIを実際に利用して結果を検証した経験が共通課程の修了要件と明確に結び付かない。C13を設け、P1とP2の総合演習でその活動を確認する。C01〜C12の安全性・QA品質の要件は削らない。

### 製品本体の変更を先に決めない

`BR-CART-001`、`cart-with-invalid-items`、既存の診断・保守演習、Training Copyで初学者向けの一連の課題は設計可能。新機能や意図的な不具合をアプリへ入れるのは、既存の教材ではできないことを実動作で確認した場合に限る。

## Codexへの実装引継ぎ条件

**このPlanの変更・レビューが了承された後に**、Codexは設計文書と現在の実装を再確認し、次を順番に進める。

1. **最小実演**：隔離Training CopyでOpenCodeのSkill認識、必要スクリプト、Cartの設計成果物、Playwright受講者specと実行を確認。失敗時は現行の成果物形式・Skill機能・実行環境のどこが不足したかを区別する。未検証の部分を完成扱いしない。
2. **目標と評価**：`README.md`、`00_learning-design.md`、`02_competency-rubric.md`を設計通りに更新し、C13とAI生成コードの責任分担を明文化する。
3. **レッスンの置換**：17本の既存学習活動を設計文書の表と照合して修正する。内容が重複する既存演習・説明は整理し、末尾にAI節を足すだけで済ませない。
4. **Scenario Shop演習**：必須のE1〜E6を既存Seed・診断・保守素材で成立させる。必須課題を再現できない証拠がある場合だけ、Training教材→Seed→製品本体の順に最小修正する。正式な仕様・回帰テストへの影響を確認する。
5. **評価・提出・CI**：既存4 CSVとhandoff、`training:completion:check`、`tests/contracts/training-*.test.ts`の整合を取り、C13の提出物を検証する。意味上の正確さをファイル存在だけで機械的にPASSさせない。
6. **検証と報告**：変更範囲に対応する `pnpm run validate:curriculum`、`pnpm run test:contracts`、`pnpm run format:check`、Web Training実行、Training Copy・CIの実際の結果を記録。未実行とPASSを区別する。

「最小実演」でOpenCodeやSkillが動かない場合、学習目的や製品仕様を強引に変えて回避しない。環境・互換性・Skill側の不備を確定し、改修範囲がこの設計から外れるなら再検討する。
