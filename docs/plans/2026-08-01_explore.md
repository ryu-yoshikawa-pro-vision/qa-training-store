# qa-training-store UI・UX探索指示

## 目的

起動済みの `qa-training-store` をPlaywright MCPで実際に操作し、UI・UX上の不自然さ、分かりにくさ、操作上の問題を探索してください。

今回のタスクは、**探索とレポート作成のみ**です。

コード、設定、テスト、ドキュメントなどは一切修正しないでください。

---

## 最重要ルール

次の行為は禁止します。

* ソースコードの変更
* CSS、コンポーネント、文言の変更
* テストコードの追加・変更
* 設定ファイルの変更
* 依存関係の追加・更新
* `package.json` やロックファイルの変更
* アプリの起動、再起動、停止
* Git操作
* Commit、Push、Branch作成、PR作成
* 発見した問題の自動修正
* 修正案をコードとして実装すること
* Playwright TestのSpecを新規作成すること
* Playwright MCP以外のブラウザ自動操作手段への切り替え

ファイルを書き換えないでください。

成果物は、最終的なMarkdown形式の探索レポートだけにしてください。

---

## 前提

アプリはユーザー側で起動します。

アプリの起動コマンドは実行しないでください。

最初に、ユーザーから渡されたURL、または指示されたローカルURLへPlaywright MCPでアクセスしてください。

URLが明示されていない場合は、次の順で確認して構いません。

1. タスク内で指定されたURL
2. リポジトリのREADMEに記載されたローカルURL
3. 一般的なローカルURL候補

ただし、URLを推測して複数ポートを無制限に探索しないでください。

候補を確認してもアプリへ接続できない場合は、後述の終了条件に従って終了してください。

# 1. 開始前の必須確認

探索を開始する前に、次を順番に確認してください。

## 1.1 Playwright MCPの利用確認

Playwright MCPのブラウザ操作ツールが利用可能であることを確認してください。

最低限、次の操作が可能である必要があります。

* ページを開く
* URLへ移動する
* Accessibility Snapshotまたは同等のページ構造を取得する
* 要素をクリックする
* 文字を入力する
* Screenshotを取得する
* Viewportを変更する、またはDesktopとMobile相当で確認する

### Playwright MCPを利用できない場合

次のような状態では、探索を開始せず終了してください。

* Playwright MCPが登録されていない
* MCP Serverが起動しない
* Browser Toolが表示されない
* Playwright MCPの呼び出しが失敗する
* 必要なBrowser操作ができない
* Screenshotを取得できない
* Accessibility Snapshotだけでなく、画面の視覚確認もできない

この場合、CLI、通常のPlaywright Test、独自Script、curl、ブラウザ拡張、別のMCPなどへ切り替えてはいけません。

最終出力には、次だけを簡潔に記載して終了してください。

```markdown
# UI・UX探索結果

## 結果

探索を実施できませんでした。

## 終了理由

- Playwright MCPを利用できないため

## 確認した内容

- 実施した確認
- 発生したエラーまたは利用できなかった機能

## 対応が必要なこと

- Playwright MCPを利用可能な状態にする
- その後、同じ指示で再実行する
```

---

## 1.2 アプリへの接続確認

Playwright MCPで対象URLを開き、アプリの画面が表示されることを確認してください。

次の場合は探索を開始せず終了してください。

* 接続を拒否された
* 対象URLが開けない
* 404やサーバーエラーだけが表示される
* アプリではない別ページが表示される
* 画面が永久にLoading状態になる
* JavaScript Errorにより操作できない
* 認証や初期設定が必要だが、利用可能な情報がない
* 主要画面へ移動できず、探索が成立しない

アプリの起動や再起動は行わないでください。

接続できない場合、ポートを変更してアプリを起動したり、起動コマンドを実行したりしてはいけません。

最終出力には次を記載して終了してください。

```markdown
# UI・UX探索結果

## 結果

探索を実施できませんでした。

## 終了理由

- 起動済みアプリへ接続できないため

## 対象URL

- 確認したURL

## 確認した内容

- 表示された状態
- 発生したエラー
- Screenshotを取得できた場合はその保存先

## 対応が必要なこと

- 対象アプリを起動する
- 正しいURLを指定する
- その後、同じ指示で再実行する
```

---

## 1.3 独立したBrowser Contextの利用

ユーザーも同時にアプリを操作する可能性があります。

次を守ってください。

* ユーザーが使用中のChrome Profileへ接続しない
* 既存のChrome Tabを操作しない
* Playwright MCP専用の独立したBrowser Contextを使用する
* ユーザーの操作中のSession、Cart、注文、入力内容を変更しない
* ユーザーのブラウザデータを参照しない
* 永続Profileを使用しない
* 外部サイトや個人AccountへLoginしない

独立したContextを確保できない場合は、探索を終了してください。

# 4. 探索方法

単に画面を順番に開くだけではなく、実際の利用者の操作として確認してください。

各機能で、最低限次を実施してください。

1. 画面を表示する
2. Screenshotを取得する
3. Accessibility Snapshotを確認する
4. 主な操作を実行する
5. 操作後の結果を確認する
6. DesktopとMobileで比較する
7. 不自然さがあれば再現手順を確認する
8. 問題が一時的でないか再確認する
9. 同じ問題が他画面にも存在しないか確認する

Accessibility Snapshotだけで評価を完了しないでください。

必ずScreenshotを見て、視覚的な不自然さも確認してください。

# 6. 評価観点

## 6.1 操作性

* 次に何をすべきか分かるか
* 主操作が見つけやすいか
* Buttonの役割が明確か
* 戻る、キャンセル、保存の挙動が自然か
* 同じ操作が画面ごとに違う挙動になっていないか
* 操作後に何が起きたか分かるか
* 誤操作しやすい配置になっていないか
* 破壊的操作が通常操作と近すぎないか

## 6.2 情報設計

* 情報の優先順位が自然か
* 重要な情報が埋もれていないか
* 見出しと内容の対応が分かりやすいか
* 同じ情報が不必要に重複していないか
* 一覧で比較すべき情報が並んでいるか
* 詳細画面と一覧画面の役割が整理されているか

## 6.3 視覚的な自然さ

* 余白が広すぎないか、狭すぎないか
* Alignmentがずれていないか
* Cardの高さや幅が不自然にばらついていないか
* Border、Shadow、背景色が過剰でないか
* 文字Sizeと階層が自然か
* CTAが他の要素に埋もれていないか
* 画面全体の密度が不自然でないか
* ECサイトとして商品が主役になっているか
* 管理画面として一覧性が確保されているか

## 6.4 Responsive対応

* 横スクロールが発生していないか
* Textが途中で切れていないか
* Buttonが画面外へ出ていないか
* Fixed要素が内容を隠していないか
* HeaderとBottom Navigationが競合していないか
* TableがMobileで操作不能になっていないか
* DialogがViewportからはみ出していないか
* Keyboard表示を想定した操作領域になっているか

## 6.5 Form

* LabelとInputの対応が明確か
* 必須項目が分かるか
* Errorの場所と原因が分かるか
* 入力値が失われる可能性がないか
* 保存中、成功、失敗が分かるか
* Disabled状態の理由が分かるか
* Placeholderだけに説明を依存していないか

## 6.6 文言

* 機械的、不自然、曖昧な日本語がないか
* 同じ概念に異なる名称を使っていないか
* Buttonの文言から結果を予測できるか
* Error Messageから次の行動が分かるか
* 学習用アプリとして不要に専門的な表現がないか

## 6.7 状態表示

* Loading中であることが分かるか
* Empty Stateから次の操作へ進めるか
* Error発生時に復帰方法が示されるか
* 成功通知を見落とさないか
* 処理中に二重送信できないか
* 在庫切れや販売停止を購入直前まで見落とさないか

## 6.8 Accessibility

* Keyboardだけで主操作ができるか
* Focus位置が分かるか
* Dialogを閉じた後にFocusが戻るか
* 見出し構造が不自然でないか
* Accessible Nameが操作内容を表しているか
* 色だけで状態を表現していないか
* Touch Targetが小さすぎないか
* Skip Linkが機能するか

既存の自動Accessibility Testが通るかどうかだけで判断しないでください。

自動検査では見つからない、実際の使いにくさも確認してください。

# 7. 問題として扱わないもの

次を安易に問題として挙げないでください。

* 単なる個人的な好み
* 根拠のない配色変更案
* 「もっとモダンにする」だけの指摘
* ShadowやGradientを増やすだけの提案
* Animationを追加するだけの提案
* Card化すればよいという一律の提案
* Componentを抽象化すべきというコード都合の指摘
* 実際の操作に影響しない軽微なPixel差
* 学習用アプリであることを無視した本番サービス基準の要求
* Backendが存在しないこと自体への指摘
* 外部決済を使っていないことへの指摘
* 意図的なTest ControlやSeed Scenarioの存在

問題と判断する場合は、必ずユーザーへの影響を説明してください。

# 8. Severity基準

## Critical

* 操作を完了できない
* データ破損や重大な誤操作につながる
* 主要機能へ到達できない
* Mobileで主要操作が完全に不可能
* 別Roleの機能へ不正に到達できる

## High

* 主要操作をかなり迷う
* 誤操作する可能性が高い
* 重要情報を見落とす
* 回避方法を知らないと操作を完了できない
* 特定Viewportで主要機能が大きく崩れる

## Medium

* 操作はできるが分かりにくい
* 情報階層や導線が不自然
* 画面間の一貫性がない
* 一覧性や入力効率が明確に低い
* 一部の利用者が迷う可能性が高い

## Low

* 操作には大きく影響しない
* 視覚的な不自然さがある
* 文言や余白の軽微な不整合
* 改善すると理解しやすくなる

Severityを過大評価しないでください。

単なる見た目の違和感は、原則としてLowまたはMediumです。

# 10. Screenshot

問題を発見した場合は、可能な限りScreenshotを保存してください。

Screenshot名は、内容が分かる名前にしてください。

例：

```text
ux-001-home-mobile-header-overlap.png
ux-002-cart-desktop-primary-action.png
ux-003-admin-products-table-small-mobile.png
```

Screenshotは証拠として使用します。

ただし、Screenshotを保存するために既存ファイルを上書きしないでください。

リポジトリ内に保存する必要がある場合も、今回のタスクではファイル変更禁止のため、保存せずMCPのArtifactまたは一時領域を使用してください。

Screenshotを永続的に保存できない場合は、レポートにその旨を記載してください。

# 11. 探索中の判断

問題を発見しても、その場で修正しないでください。

改善方法を思いついても、コードを書かないでください。

修正によって改善するかを試す目的でも、CSSやDOMを一時変更しないでください。

Browser DevToolsなどでStyleを上書きして比較することも禁止します。

問題の確認と記録だけを行ってください。

---

# 12. 重複指摘の扱い

同じ原因によって複数画面で発生している問題は、可能な限り1件にまとめてください。

例：

* 複数画面のPrimary Buttonで同じContrast問題がある
* 共通HeaderがすべてのMobile画面で内容を隠す
* 共通Form ComponentのError表示が分かりにくい
* 共通Table ComponentがSmall Mobileで崩れる

ただし、影響や再現条件が異なる場合は分けても構いません。

件数を増やすために類似問題を細分化しないでください。

---

# 13. 探索不能になった場合

探索開始後に次の状態になった場合は、それ以上無理に続けず終了してください。

* Playwright MCPが途中から利用できなくなった
* Browserが繰り返しCrashする
* MCP Serverとの接続が失われた
* Screenshotが取得できなくなった
* Page操作が継続的にTimeoutする
* アプリが操作不能な状態になった
* 独立したBrowser Contextを維持できなくなった
* ユーザーの操作環境へ影響する可能性が生じた
* Login情報や前提データがなく、主要探索を続けられない
* Test ControlやScenario Resetが正常に動作せず、状態を保証できない

同じ失敗操作は、原因確認のため最大2回まで再試行して構いません。

2回失敗した場合は、別手段へ切り替えず終了してください。

終了時は、完了済みの探索結果だけをレポートし、未確認範囲を明示してください。

「おそらく問題ない」と推測で補完しないでください。
