# 新課程の達成・評価・修了基準

## 評価の基本設計

**新しい課程の独立した評価基準**を`docs/curriculum/ai-assisted-qa/assessment-rubric.md`に実装する。旧`docs/curriculum/test-automation/02_competency-rubric.md`のC01〜C12や`training:completion:check`は変更しない。

修了判定は、次の**別々の証拠**に基づく。クイズの正答率だけでは実務遂行能力は保証できず、既存PlaywrightのPASSだけでも仕様の理解を証明できない。

| 評価対象 | どの能力を見るか | 使う証拠 |
| --- | --- | --- |
| 知識・理解 | 用語・仕組み・制約を区別し、仕様やコードの意味を説明できる | 選択式クイズ、誤答時の理由説明・再確認 |
| テスト分析・設計 | BR/ACからリスク・条件・期待結果を正しく導き、AI案を評価できる | Scenario ShopのRisk・Condition・Caseとレビュー理由 |
| 実装・実行 | 受講者が確認したPlaywrightテストが対象の振る舞いを検証し、独立に実行できる | spec、Reset、Run、Receipt/Trace等の実際の証拠 |
| 失敗・保守 | 原因仮説と事実を区別し、仕様を変えずに修復・再実行する | 実行前後の別証拠、差分、判断記録 |
| 変更管理 | AIの変更を許可範囲で管理し、PRとCIの保証範囲を説明できる | Git差分、PR、対象SHAとRun/Check/Artifact |
| AIの安全な活用 | 目的・制約を与え、出力の採否を自分で判断できる | 実際の依頼・提案・採否理由・変更と結果の確認 |

## レベルと合格条件

新課程で用いる評価レベルは次のとおり。旧課程とレベル番号が同じでも、**別の課程の評価結果として管理**する。

| 水準 | 判定の意味 |
| --- | --- |
| Level 0 | 正しく説明・実行できず、未確認を成功と誤認する等の重要な誤りがある |
| Level 1 | 手順、ヒント、例題を参照して実行できるが、別条件での判断に支援が必要 |
| **Level 2** | 与えられた対象・制約について正しく適用し、仕様・証拠から結果と理由を説明できる |
| Level 3 | 複数の実施方法をリスク・費用・保守性から比較し、妥当な改善案を提案できる |

**共通課程の修了は、卒業能力に必要な項目をすべてLevel 2以上で満たすこと**。平均点で重大な不適合を相殺しない。Level 3や全Skillの習熟は必須ではない。

### 知識クイズの合格と再確認

初回の正答数・誤答した学習項目IDを記録する。全モジュールに単一の80%という閾値を先に設定しない。問題数・難易度と理解が必要な範囲は、[学習項目表](./2026-10-16_qa-curriculum-ai-agent-redesign_learning-map.md)と[クイズ設計](./2026-10-16_qa-curriculum-ai-agent-redesign_quizzes.md)で決める。

- **知識確認を完了できる条件**：必須の理解項目について、正答した問題、または誤答後の復習と**条件を変えた再確認**により、理解を確認できたこと。
- 初回誤答は消去しない。対応する教材節と解答・誤答解説へ戻り、同じ答えの暗記に依存しない事例または短い理由説明で再確認する。
- 多義的な選択肢、誤った解説、未習の前提が必要な問題は問題の欠陥として扱う。受講者の不合格理由にしない。
- クイズの結果のみで「Playwrightを実装できる」「AIを使えた」「CIを実行した」と判定しない。
- 合格率・初回正答率などの数値を掲載する場合は診断・学習改善用とし、必須の理解項目の取りこぼしを隠す修了基準にはしない。

### 実技の合格条件

各実技について事前に対象・変更権限・正本・実行環境・提出内容を公開する。評価者（受講者本人、または指導担当者）は**次の必須条件がすべて成立するか**判断する。

| 評価観点 | Level 2で必要なこと | 不合格となる具体例 |
| --- | --- | --- |
| 仕様適合 | BR/ACと観測を分け、正しい期待結果を記載 | 表示された結果を仕様より優先 |
| テスト分析・設計 | リスク→条件→Caseを対応させ、判断理由を示す | リスクや期待結果の根拠がない |
| 自動化コード | テストケースに対応した意味のあるAssertion、Reset、実行の独立性がある | 要素が見えるだけで業務結果をPASSとする |
| 証拠 | 実際に実行した対象ケースのログ・Run等が識別できる | AIが「成功」と述べただけ |
| 改善 | 初回失敗・原因・最小修正・再実行を区別できる | リトライ増加のみで根因解決と主張 |
| 安全性 | 許可範囲・Secret・正式コードとの境界を守り、差分を説明できる | 意図せず製品や正式CIへ変更 |
| 変更管理・CI | PRの対象commitと実際のCI実行が対応する | 古いSHAの成功Runを最新の合格に流用 |
| AIとの協働 | 実際の依頼・生成内容・本人の採否と根拠がある | AI案を仕様確認なしにそのまま正解とする |

**実演が必要な項目は説明文だけで合格にしない**。AIが最初から正しかった場合、却下すること自体を要求しない。受講者が正しさを照合・説明できたかを評価する。

## 各段階の修了

| 段階 | 修了に必要な条件 |
| --- | --- |
| M00 | 安全な作業範囲と基本操作を説明・確認できる。環境障害ならBLOCKEDであり能力不足と混同しない |
| M01〜M04 | 対象の知識確認と、必要な分析・設計・レビュー成果物を満たす |
| M05〜M07 | コードの意味を説明でき、実際のWeb実行・失敗診断・改善証拠が必要な課題を満たす |
| M08〜M09 | 受講者の変更をレビューし、対象SHAとTraining CI結果を確かめた |
| M10 最終 | **未演習の条件**で分析・設計→AI利用→Web実装→実行・検証→PR/CIまで進め、知識・実技・判断の必須観点が全てLevel 2以上 |
| Native選択 | Web共通課程と別の評価にする。共通修了の必須条件には含めない |

### 総合演習の独立性

M10では、M02〜M09で用いたCartの代表ケースそのものを提出させない。既存のCheckoutの未演習状態など、**別条件へ知識を転用しなければならない課題**を用意する。ただし本番仕様への改変・隠し問題・未知の製品挙動を正答として要求しない。題材が本当に未演習かは実装時に確認する。

不具合や実行環境の制約で一部を実行できなかった場合は、その部分を`BLOCKED`または未実施とする。実行できていない段階で総合修了とすることはない。

## 評価結果の記録と保護

新課程に必要な記録形式は、`docs/curriculum/ai-assisted-qa/assessments/`で公開する。受講者の実際の回答や個別の評価結果は、学習者の作業コピーまたは指定された提出先に保存し、公開リポジトリの教材ファイルへ混入させない。

最小記録項目：
- モジュール・学習項目ID、初回の問題IDと結果、復習・再確認の結果。
- 実技の対象（仕様ID、テストケースID等）、AIへの目的と許可範囲、生成物・本人の判断理由。
- 対応するコードのパス・差分、実行証拠（Run/Receipt/Artifact等）、未完了事項。
- 実技の評価観点別の達成/未達と、必要な再確認。

**APIキー、Token、個人情報、AIとの全会話、モデルの内部推論は要求しない**。参照する証拠にSecretが含まれないことを確認する。

## 新課程と既存の判定実装の境界

旧 `scripts/training/check-completion.ts` は旧課程の`P1-xx`/ `P2-xx`を判定し、`semantic_understanding: "NOT_EVALUATED"`と記録する。この意味や対象を変更しない。新課程の習熟度について自動判定する独立コードを最初から作る必要はない。まずは上記の公開基準と学習者の自己確認・指導担当者の確認で成立させる。

自動化するなら、問題ID/学習項目ID/提出先/実行結果の**構造的な整合**を対象とする。問題の意味上の正しさ、レビューの妥当性、受講者の理解度をファイル存在だけでPASSにしない。

## Codex実装時の検証

1. 新課程の全必須学習項目について、知識確認か実技評価、または両方があり、必要な水準を確認できる。
2. クイズの正答・誤答説明・復習先が存在し、回答前に正答を表示しない。
3. 具体的な誤答例で、根拠なくAI案を採用すると不合格になることが判定できる。
4. M10の総合演習は、新しい条件に知識を転用することを要求し、過去の結果を流用しただけでは合格しない。
5. 新課程の評価を追加しても、旧課程の習熟度表・Completion Receipt・validator・Training CIの結果に影響しない。
6. 未実行・環境障害・不合格を区別し、既存の成功結果で未実行を隠さない。
