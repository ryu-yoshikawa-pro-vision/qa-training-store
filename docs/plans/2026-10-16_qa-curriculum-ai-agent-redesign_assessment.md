# 新課程の評価・各フェーズの修了基準

## 評価する能力と共通原則

本Planでの「修了」は3つの別々の結果を表す。**Phase 1修了はテスト設計能力、Phase 2修了はPlaywright自動化能力、Phase 3修了はGitHub・CI運用能力**である。標準の学習環境はGitHub Codespacesだが、Gitコマンド・PR・CIの学習は選択Phase 3に限定する。

- Phase 1だけで修了可能。Phase 2はPhase 1の学習成果を前提に追加し、Phase 3は任意の追加受講である。
- 各フェーズの問題・解説・実技評価は別に用意し、**将来のフェーズで初めて学ぶ操作やツールを先行フェーズの合格条件にしない**。
- クイズは正答・誤答説明と復習先がある知識確認。実技はAIとの実作業と成果物、実行・判断の証拠で確認。クイズ得点だけで技能を認定しない。
- 初回クイズの正答率を一律80%等に固定しない。必須の学習項目で誤解が残っていないことを復習・別条件での再確認によって確かめる。
- **未実行、BLOCKED、未達、達成**を区別し、AIの自己申告や旧課程のPASSを新課程の証拠として使わない。

## 共通の受講開始条件（修了評価とは別）

- GitHubアカウントから**本人の無料枠を利用する2コアCodespace**を作成できることを確認する。現在のリポジトリは2コア固定設定ではない。所有者・支払主体、残りコア時間・ストレージ、課金停止条件を確認し、**無料利用が成立しなければ開始をBLOCKEDにする**。
- 既存devcontainerの起動・Node.js/pnpm/OpenCode CLI、受講範囲に応じてPlaywright/Chromiumの動作を確認する。OpenCodeは利用時点のFreeモデルだけを使い、個人Secretの登録・認証経路・補助モデルと自動課金設定を確認する。実機未検証のものは成功と認定しない。
- `qa-workflow-skills`の必要なSkillとPython helperを認識・実行でき、AIに与える権限を制限できることを確認する。個人情報・APIキーを教材や共有ログに保存しない。
- 各フェーズ終了時の成果物のダウンロード／保全とCodespace停止方法を示す。無料枠到達・容量不足・接続不能は**環境BLOCKED**として扱い、学習成果のLevelを推測で合格・不合格にしない。
- **環境の準備完了 ≠ 受講者の技能習得**。初期設定は受講できる状態かの確認であり、以下のPhase 1〜3の実技評価を代替しない。

## 習熟度の判定

| 水準 | 意味 |
| --- | --- |
| Level 0 | 対象の仕様・結果を正しく説明・判断できない |
| Level 1 | 教材の例や手順をなぞればできるが、新しい条件では支援が必要 |
| **Level 2** | 与えられた新しい条件に正しく適用し、仕様・証拠から自分で結果を説明できる |
| Level 3 | 複数の方法・費用・リスク・保守性を比較して改善策を説明できる |

各フェーズの必須観点を**すべてLevel 2以上**にしたとき修了とする。Level 3や全Skillの習熟は必須にしない。旧課程のC01〜C12やCompletion Receiptと結果を混ぜない。

## Phase 1の修了：AIエージェントを使ったテスト分析・設計

### 評価対象（M00〜M04）

| 観点 | Level 2の合格条件 | 主な証拠 |
| --- | --- | --- |
| AIの基本操作 | CodespacesでOpenCode CLIと必要なSkillを使い、手順例を経験したうえで本人が目的・資料・作業範囲・完了条件を指定できる | 実際の依頼内容、結果、本人による確認 |
| 安全・証拠 | 読取りとファイル変更を区別し、Secretを扱わず、AIの推測・未実行の成功宣言を見抜ける | ローカルの変更前後比較、採否理由 |
| 仕様とリスク | BR/ACと観測を区別し、Role/State/Data、リスク・優先度を根拠付けられる | 初見条件の仕様参照、Risk/Condition |
| テスト設計 | 適切な技法から条件・ケース・前提・期待結果を導ける | CaseとBR/ACの対応 |
| AI案のレビュー | 不足・重複・誤った期待結果を検出し、自動化候補の採否と理由を説明できる | 本人が確定させた設計、AI案の採否 |

**総合演習（M04終了時）**：Scenario Shopの未演習の仕様条件を配布し、OpenCode/Skillを使いながら分析・設計・自動化候補の判断を行う。教材に載っている完成例の転記では合格しない。AIから正しい提案が出た場合は根拠を示した採用を認め、無理に誤りを捏造させない。

**必要な環境**：GitHubログイン済みのCodespace、教材・仕様資料・成果物保存先、利用可能な無料モデルのAIエージェントと必要なSkill。**Gitコマンド、PR、Playwright、CI、実行中のScenario Shopは必須にしない**。製品の動作確認は参考にしてよいが、Phase 1では仕様に基づく分析・設計を判定する。

**修了の意味**：AIを活用して自動化に必要なテスト分析・設計成果物を作り、その妥当性を確認できる。Playwrightでの自動実装・実行は未認定。

### Phase 2への引継ぎ

確定したテストケース（識別子、仕様ID、前提状態、操作、期待結果）、選定理由、未確定事項を**Codespace内でMarkdown等へまとめ、Git操作なしでダウンロード**して保全・引継ぎできるようにする。GitHubのPRや旧Training Copyへの提出を前提としない。

## Phase 2の修了：Playwright構築・実装・実行・改善

### 評価対象（M05〜M07）

| 観点 | Level 2の合格条件 | 主な証拠 |
| --- | --- | --- |
| 自動化環境 | Codespaces既存のNode.js/pnpm/Playwrightを理解し、新課程用Config・テスト対象・実行コマンド・結果先を設定して実行できる | `package.json`、Config、Codespaces内の実行記録。devcontainer全体の再構築は不要 |
| コード理解 | TypeScriptの必要部分、Locator/Action/Assertion、待機と期待結果を理解し、AI生成コードの誤りを見つけられる | コード読解、本人の採否と変更前後 |
| テストの実装 | Phase 1のCaseから仕様に適合するPlaywright specを作り、Resetと独立性を確保する | 受講者spec、Seed/Reset、意味あるAssertion |
| 実行結果 | ローカルで対象テストを実行し、PASS/FAIL/BLOCKEDとRun・Trace等の証拠を対応付けられる | 実行コマンド、ログ、Report/Trace |
| 診断と保守 | Test/Product/Environment/Flakyの可能性を区別し、必要なら最小修正・別Runで検証できる | 初回と修正後の異なる証拠、差分、理由 |

**総合演習（M07終了時）**：Phase 1の承認済みケースからローカルE2Eを構築・実行し、さらに未演習の条件または故意に不適切なテストspecの診断・修正を行う。テストの不具合を直すために製品本体を変更しない。

**必要な環境**：同じCodespaceに導入済みのNode.js/pnpm/Playwright/Chromium、テスト対象と許可されたAIエージェント。**Git/PR/GitHub Actions/CI操作は不要**。Git CLIを使った差分確認は許可するが、必須にはしない。

**修了の意味**：Codespaces内で再現性のあるWeb自動化を構築・実装・実行・改善できる。GitHub/CI運用は未認定。環境が利用できない場合はその実行部分をBLOCKEDとし、架空の成功証拠で合格させない。

### Phase 3への引継ぎ

Phase 2でCodespaces内で動作確認したspec、環境設定、依存関係、Reset手順、実行コマンド、結果・未確認事項を**Git操作なしで保全**して引き継ぐ。**テストケース自体を再作成させない**。

## Phase 3の修了：GitHub・CIによる継続実行（選択）

### 評価対象（M08〜M10）

| 観点 | Level 2の合格条件 | 主な証拠 |
| --- | --- | --- |
| Git/GitHub | 許可された作業コピーでbranch、commit、PRを作り、AI変更を差分からレビューできる | Git差分、PR、本人の採否理由 |
| CI構築 | Phase 2のテストをCI用に起動し、依存導入・Build/Serve/Test・Artifactを適切に構成できる | 新課程用workflow、Run |
| 実行証拠 | 対象PR/commit SHAとRun/Check/Artifactが一致することを確認できる | GitHub Actionsの実際の結果 |
| 失敗調査 | CI環境差・対象のテスト不備・実行未完了を切り分け、必要な対応を示せる | 失敗ログ・変更内容・再実行 |
| 安全性・運用 | 権限・Secret・正式CIとの境界を守り、品質ゲートと未確認事項を説明できる | workflowレビュー・最終評価 |

**総合演習（M10終了時）**：Phase 2で成功したPlaywright specをGitHubの専用Training環境へ持ち込み、新課程専用のCIから実行して証拠を確認する。新たなテストケースの再実装を修了条件としない。既存CIの成功を、新しい対象SHAの成功として流用しない。

**必要な環境**：書込可能な学習用GitHubリポジトリと標準GitHub-hosted Runner・workflow権限等。**公開リポジトリでの標準Runnerの無料利用**を第一候補とし、private/larger runnerでの課金・公開内容の安全性を確認する。使えない場合はBLOCKEDとするが、Phase 2修了を取り消さない。

**修了の意味**：自動テストをGitHub/CIへ組み込んで検証・調査・管理できる。

## クイズと再確認

[クイズ仕様](./2026-10-16_qa-curriculum-ai-agent-redesign_quizzes.md)で各学習項目に問題または実技評価の根拠を付ける。初回回答、正誤、誤答した学習項目、復習、**条件を変えた再確認**をフェーズ別に記録する。問題の曖昧さや誤った解説は受講者の不合格とせず問題を修正する。

回答・評価記録は受講者のローカル作業コピー／指定提出先に保存し、教材・公開PR・旧`self-check/P1-xx.md`へ混入させない。APIキーや個人情報、AIの内部推論、AIとの全会話は保存を要求しない。

## 既存課程との境界と実装検証

旧`scripts/training/check-completion.ts`の`semantic_understanding: "NOT_EVALUATED"`と旧課程の対象Lesson IDはそのまま維持する。新課程の修了判定は別の公開基準を用い、少なくとも初版では**ファイル存在だけで意味的な理解をPASSとしない**。

受入検証：**新規2コアCodespace**でPhase 1・2の初期導入、OpenCodeの無料モデルとSkill、Playwright実行、成果物保全を検証する。Phase 1の修了判定にPlaywright・Git/PR/CI関連の必須証拠がないこと、Phase 2にGit/PR/CI関連がないこと、Phase 3を選択しない場合に旧・新のテストが失敗しないこと。各フェーズで学習目標・クイズ・実技・解説・修了条件の対応漏れを確認する。
