# Web / Native 20+ Full QA Cycle 実行計画

## 0. 依頼概要

- 依頼内容: Web / Native の全画面・全主要フローを、同じ品質基準と網羅性で確認し、問題の修正と再検証まで行う完全QAサイクルを最低20回実施する。
- 背景: 既存Repositoryには全Route UI Review、Web E2E、Accessibility、Native Component / Contract、Windows Android実機Runbook、Maestro Flowがある一方、Small Mobileの全Route coverage、毎Cycleの実ブラウザ探索、Mobile-MCPとMaestro-MCPを分離した反復証跡は未整備である。
- 期待成果: 最低20回の完全Cycle、発見した重要問題の最小かつ根本的な修正、関連Regression、最終品質ゲート、実行不能なEnvironment項目だけを明示した最終報告。

## 1. ゴール / 完了条件

- ゴール: Web Phase 1とNative Phase 2前半の現行Scopeを、実ユーザーの操作として継続的に再評価し、表示品質、Responsive、Navigation、Form UX、状態表示、Accessibility、EC / Adminとしての自然さ、機能完成度を実質的に改善する。
- 完了条件（DoD）:
  - Cycle 1〜20以上の各回で、Cycle開始時のRoute Inventoryを再確認する。
  - Web 38 route entriesを1440×1000、1024×900、390×844、320×700で確認する。Adminは小画面Boundary UIを確認する。
  - Browserプラグイン内のPlaywright操作で全画面を表示・Scroll・操作し、Guest / Customer / Admin主要Flowを最初から最後まで確認する。
  - Native正式実装10画面、Not Found、Automation Harness、明示的placeholder routeを実Androidで確認し、Mobile-MCP探索とMaestro-MCP回帰を別結果として残す。
  - Native主要Flowは起動、Home、Catalog / Search / Category、Product、Variation、Cart追加、数量変更、削除、Empty、再追加、再起動、状態復元を含む。
  - 各Cycleで発見した問題を原因調査し、必要最小限の根本修正、関連Test追加・更新、対象再確認、全Cycle残余の確認まで行う。
  - 不完全なCycleは完了数へ数えず、Cycle 20後も修正可能な重要問題があればCycle 21以降を続ける。
  - 最終品質ゲート、Strict evaluation、Run Artifact Sanitizer Write + Checkを完了する。
  - Git commit / push / branch作成 / PR作成その他のGit mutationを行わない。

## 2. Repo mapping

### Entry points

- Web: `app/_layout.web.tsx`、`src/presentation/root-layout.web.tsx`、`src/bootstrap/browser-runtime.web.ts`、`src/presentation/shells/app-frame.tsx`。
- Native: `app/_layout.tsx`、`src/presentation/root-layout.native.tsx`、`src/bootstrap/native-runtime.ts`、`src/presentation/native/native-runtime-provider.tsx`、`src/presentation/native/native-shell.tsx`。
- Route: `app/**/*.tsx`。Web / Nativeは`*.native.tsx`で38 route entriesずつ対になる。
- Visual contract: `src/presentation/design/tokens.ts`、`src/presentation/styles/global.css`、Web shell / shared components、`src/presentation/native/native-components.tsx`。
- Scenario: `src/seeds/metadata.ts`を正本とし、Web DexieとNative SQLiteのcomposition rootへ接続する。
- Test: `playwright.config.ts`、`e2e/web/**`、`tests/**`、`maestro/**`、`scripts/native/windows/android-local.ps1`。

### Main flow

- WebはBrowser Runtime → Application Services → AppFrame → Storefront / Admin Shell → Pageの順で表示し、RouteGuardがRoleと小画面Admin境界を制御する。
- NativeはSQLite / KV → shared Catalog / Cart Use Cases → Native Runtime Provider → Native Shell → Native Screenの順で表示する。
- Test ControlはWeb UI / Test APIとNative Deep Link / Harnessで責務を分離し、ProductionではAutomation surfaceを公開しない。

### Key abstractions

- Web shared UI: Button、ProductCard / Image、SearchCombobox、StatePanel、FormErrorSummary、ConfirmDialog、StatusBadge、AccountNavigation。
- Native shared UI: NativeButton、NativeTextField、NativeProductImage、NativeStatePanel、Native Shell / Bottom Navigation。
- Application / Domain / Repository契約はPresentationから分離し、UI問題だけで業務契約を変更しない。
- Android正式入口はRunbookと`android-local.ps1`、主要商品FlowとIME依存Search FlowはADR-0007どおり分離する。

### Existing tests

- Web: Phase 1 required 14 flow、UI/UX A〜J、Accessibility、Mobile boundary、Cross-role、Firefox / WebKit smoke、4 viewport UI Review。
- Native: Unit / Repository / Component / Contract、Production Bundle Guard、Maestro Runtime 5 Flow、Persistence / Boundary 5 Flow、Search 1 Flow。
- `pnpm run verify`はFormat / Lint / Typecheck / image / security / Vitest / Web Buildを含むが、Playwrightと実Nativeは別実行が必要である。

### Safe change surface

- 第一選択: `src/presentation/**`、既存の`e2e/web/**`、`tests/component/**`、`tests/contracts/**`、`maestro/**`。
- 業務契約の欠陥を実操作で再現した場合だけ、Application / Domain / Repository / Seedへ最小限に拡張する。
- 同じ問題が複数画面へ出る場合はshared component / token / layoutで修正する。

### Confirmed coverage gaps

- `e2e/web/ui-review.spec.ts`のSmall Mobileは主要10 routeだけで、全38 route / Boundaryを320×700で確認していない。
- `/guide`は現行core UI Review routeに含まれていない。
- 自動Screenshotは167枚の既存baselineを持つが、各Cycleの実ブラウザ操作そのものを代替しない。
- Windowsでは物理Android端末とMaestro 2.8.0が利用可能だが、iOS Simulator / Xcodeは利用できない。

## 3. 現状理解と前提

- Current understanding:
  - WebはPublic 14、Customer 11、Admin 13の計38 route entriesである。
  - Nativeは正式実装10画面、Not Found 1、Automation Harness 1、明示的placeholder 26の計38 route entriesである。
  - 旧Route Inventoryの`/admin/test-control` Native UIなしという記録は古く、現行コードは`NativeContractHarnessScreen`を表示する。
  - Native正式ScopeはGuest Home、Catalog、Search、Category、Product、Variation、Cart、Guide、Legalで、Login / Account / Checkout / Order / Review / Admin本実装は将来Phaseである。
  - 直近Android成功baselineはRelease Build、Install、Smoke、Control、Runtime 5/5、Boundary 5/5、制御IME条件Search 1/1、`verify` exit 0である。
- Assumptions:
  - 「Native Full QA」は、現ホストで正式実行可能な物理Androidを主対象とし、iOSは独立Workstreamとして静的契約確認と環境再探索を行う。iOSを実行できない事実をAndroid成功へ混ぜない。
  - 全Routeの4 viewport screenshot / DOM boundary確認は既存UI Reviewを拡張して再利用し、人間視点の探索はBrowserプラグイン内Playwrightで別途行う。
  - 各Cycleの画面数はRoute Inventoryのroute entry数、Flow数は開始から完了まで操作した独立Flow数として数える。
- Non-goals:
  - Native後半placeholderの機能前倒し、Guest Checkout、Coupon、Point、Wishlist、返品、返金、外部決済、Backend / Cloud Service、Store公開。
  - 大規模Architecture再設計、無関係な依存更新、UI問題に根拠のないDomain / DB変更。
  - EAS Cloud Build / Submit、GitHub Actions再実行、Git mutation。
  - 20という数を満たすための部分確認、代表画面だけの確認、自動Test PASSだけによるCycle完了。

## 6. 変更方針

- Change strategy:
  1. Cycle 1前に全Route Inventory、4 viewport coverage、Browser / Mobile-MCP / Maestro-MCP / Android preflightを確立する。
  2. 既存UI Reviewを全38 route × 4 viewportへ広げ、`/guide`と小画面Admin Boundaryを含める。既存Test基盤を置き換えない。
  3. 各Cycleは Inventory → Web全画面4 viewport → Native全画面 → 主要Flow → Issue修正 → focused regression → Cycle残余 → cycle regression の同じ順で実施する。
  4. Issue修正はFunctional / critical UX / layout / responsive / navigation / accessibility / information architecture / polishの順で優先する。
  5. 同一障害2回、同一工程3回、追加情報なしでは無目的再実行を止め、WorkstreamをBlockedとして他作業を継続し、後で再試行する。
  6. Cycle 20後に残Issueを再評価し、必要ならCycle 21以降を同じ契約で続行する。
- 実行タスク:
  - [x] Repo mapping、Strict Run、保存計画、Cycle台帳を作成する。
  - [ ] Baseline Inventory、coverage gap修正、Browser / Android / MCP preflightを完了する。
  - [ ] Cycle 1〜20以上を1件ずつ完全実施する。
  - [ ] 最終品質ゲート、evaluation、Sanitizer、最終報告を完了する。

## 8. リスクと未解決論点

- Risks:
  - 38 route × 4 viewport × 20回以上は長時間になるため、自動captureと実操作を別証跡として効率化しつつ、どちらも省略しない。
  - Web Scenario resetとNative device stateが相互に汚染しないよう、Cycle / Role / Flowの境界で正式resetを使う。
  - Native Build / device / IME / MCP failureは他Workstreamを止めず、最初の異常と派生エラーを分離する。
  - AndroidとiOSを混同しない。WindowsでiOS実機確認はできないため、静的契約を継続し、利用可能性を各Cycle開始時に再評価する。
  - Screenshot生成量が大きいため、一意Stageを使い既存証跡を上書きしない。
- Open questions:
  - Mobile-MCPの親tool surfaceはlazy-loadedであるため、Cycle 1前に正確なcall surfaceを親または専用read-only agentで固定する。
  - 具体的な実装修正対象はCycleごとの実観測から確定する。
