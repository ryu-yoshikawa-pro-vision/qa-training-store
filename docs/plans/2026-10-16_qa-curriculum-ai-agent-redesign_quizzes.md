# 新課程の確認クイズ・正答・解説の設計

## 目的

**3フェーズ別に独立して確認できる**構成とする。Phase 1はM00〜M04（AI基礎・テスト分析・設計）、Phase 2はM05〜M07（環境構築・Playwright・実行診断）、Phase 3はM08〜M10（GitHub・CI、選択）を対象とする。**先のフェーズで初めて教える知識を前のフェーズのクイズへ混ぜない**。それぞれのフェーズだけで知識確認・実技・修了が完結する。

[学習項目表](./2026-10-16_qa-curriculum-ai-agent-redesign_learning-map.md)の理解を確認するため、新課程**専用**の四択クイズを設ける。旧課程の記述式104問はそのまま残し、新課程へ移動・改変・一括変換しない。

- Phase 1はAIエージェントを触ったことがない人を想定し、**Codespacesの2コア選択、VS Code・ターミナル、OpenCode CLI、無料モデルとSecretの取り扱い、ポート公開・停止と保存**、エージェントの実行権限、Skillの使い方、指示の要件、AIの自己報告と実際の成果物の違いについても確認する。初回は手順を見て操作し、最後は自分で依頼・検証する。GitHub/Playwrightの知識をPhase 1の問題の前提にしない。
- Phase 2は**Node.jsの役割、pnpm/package.json、TypeScriptの変数・オブジェクト・配列・関数・型・import/export・async/await**を短いテストコードと結び付けて確認する。その上でCodespacesに導入済みのPlaywright構成、新課程Config・ポート8081/8082/6080・出力先、Locator/Assertion、Reset、Traceと失敗の分析を確認し、Git/PR/CI操作を知らなくても解ける問題にする。
- Phase 3はGit、GitHub Actions、SHAとCI Evidence、**公開リポジトリの標準Runnerとprivate/larger runnerの料金の違い**、権限・品質ゲートを確認する。Phase 1・2の修了点数にPhase 3の得点を加算しない。
- 知識・具体事例・判断を対象とする。**Playwrightの実装やAIの実利用をクイズだけで合格としない**。
- 問題数をあらかじめ65問などに固定しない。学習項目ごとに必要な確認を割り当て、目標に対する不足があれば増やす。
- **学習用クイズの正答・解説と実技・修了課題の模範解答・採点用テストは、用途別の通常ファイルで公開する**。学習用Templateへは教材・クイズ・課題文・未完成コードを配布し、修了課題の模範・採点用テストは配布しない。この除外は秘密保持ではない。静的配信したクイズJSONは回答前でも閲覧できるため、解答の秘匿を前提とした合否判定はしない。
- **新課程用の四択問題・正答・公開解説は、これから新規制作するモジュール別JSONを唯一の正本とする。** 旧課程の104問を変換・流用しない。教材本文は従来どおりMarkdownで管理する。**JSONからHTMLのクイズ画面を生成**し、全問回答後に正答数・正答率・問題別の正誤・全選択肢の意味と解説・復習先を表示する。結果確定前はUIで正答と解説を表示しない。
- **既存から再利用するのは静的Web公開基盤**であり、新しいDB・認証・採点サーバーは作らない。問題・正答をMarkdownとJSONの両方で手動管理しない。必要な場合のオフライン閲覧用MarkdownはJSONから生成する（編集用の第二正本にしない）。詳細なUI・ブラウザ内保存は[Web閲覧・学習体験Plan](./2026-10-16_qa-curriculum-ai-agent-redesign_web-learning.md)に従う。

## 保存場所とJSONの契約

```text
docs/curriculum/ai-assisted-qa/
  modules/
    M00/README.md                     # 新規：教材本文
    ...
    M10/README.md
  quizzes/
    M00.json                          # 新規：問題・正答・公開解説の共通正本
    ...
    M10.json
```

新課程の受講者用`start-here.md`に**Phase 1のみ／Phase 1＋2／全3フェーズ**の受講経路を示す。既存の`README.md`は知識グラフ管理用として維持する。Webでは一問ずつ回答・結果確認できる。実技は本人が学習用TemplateのCodespacesでモジュールIDを一つずつロードする。**Webクイズは正式なフェーズ修了を自動認定しない。**

### JSONの最小項目

| フィールド | 意味・検証条件 |
| --- | --- |
| `schema_version` | 定義した形式の版。未対応値を拒否 |
| `module_id` | `M00`〜`M10`の1件。ファイル名・問題IDのモジュールと一致 |
| `questions` | 問題の配列。**記述順を出題順**とする。0問を拒否 |
| `questions[].id` | `M03-Q01`等、全課程で一意な問題ID |
| `questions[].objective_ids` | 実際に問う学習項目IDの配列。知識グラフの実在IDへ対応 |
| `questions[].question` | 回答条件を含む設問本文。初学者が解釈できる情報を記載 |
| `questions[].options` | `A`〜`D`の4件。各要素の`value`・`label`・`meaning`・`reason`を必須とする。意味と正誤理由を別項目で管理 |
| `questions[].correct_value` | 正答の`value`1件。選択肢中に実在することを検証 |
| `questions[].source_refs` | 正答を裏付ける教材・BR/AC・仕様・正式API等の参照先 |
| `questions[].review_path` | 復習対象の**新課程Markdownの節**へのリンク。存在・アンカーを検証 |

問題文・選択肢・正答・各選択肢の意味・正誤理由・根拠・復習先は**同じ問題オブジェクトで一括管理**し、問題と解説のファイル間照合を不要にする。JSONを学習用の表現データとみなし、コードとして評価しない。既存のMarkdown/HTML表示へ渡す際も文字列はエスケープして描画し、任意のHTML/JavaScriptとして実行しない。

**問題の版**は`Mxx.json`のUTF-8バイト列に対するSHA-256をビルド時に算出し、クイズ画面とブラウザ保存状態へ共通で渡す。IDが同じでも設問・選択肢・正答・解説・参照先が変われば異なる版となり、旧回答を復元・採点しない。空白だけの修正で再回答になる場合も、誤った復元を避ける側へ倒す。変更時に人手でrevision番号を更新する管理は追加しない。

## 設問が確認する理解と誤答時の診断

同一JSONに保存した問題・解説を利用し、各問題を制作・レビューするときに、**なぜその設問が必要で、どの理解を確認できるか**を明確にする。追加の問題管理台帳や手編集のMarkdown解答ファイルは作らない。

- **確認対象**：対応学習項目のうち、実際に問いが確認する理解・適用・判断と、その根拠を言語化する。問題IDを対応させただけで項目全体を評価済みとしない。
- **正答の導出**：問題文に与えた条件から正答までを第三者が再現できることを確かめる。実際の仕様を題材にする場合は操作種別、BR/AC、例外・境界、期待結果を照合する。
- **誤答の意味**：A〜Dの既存の選択肢別解説で、各誤答につながる**具体的な概念の混同や条件の読み違い**を説明する。根拠のない心理的推測は書かず、誤答から一意に理解不足が確定しない場合はその限界も示す。
- **再確認**：既存の復習先へ戻った後、正答を暗記するだけでなく**別の数値・状態・条件**で説明または短い実技を行う。どの問題・実技で再確認するかを分かるようにする。
- **測定の限界**：Caseの設計、コード修正、本人による根拠判断など、四択では確認できない能力は[評価Plan](./2026-10-16_qa-curriculum-ai-agent-redesign_assessment.md)の実技へ渡す。同じ知識を測る問題を件数合わせで増やさない。

設問を作った人以外が、正答の妥当性、誤答に対応する理解不足、復習・別条件での確認先を説明できない場合は修正する。四択、全選択肢の意味・正誤理由、根拠、独立レビューの契約を満たす。

## 知識と設問の対応

[基準グラフ](../curriculum/ai-assisted-qa/README.md)から、学習項目を構成する理解事項とその前提を確認する。知識の名称だけを問う問題で、適用・判断まで評価済みと扱わない。

- **理解**は概念・制約・用語の区別を、**適用**は例と条件を変えたときの利用を、**判断**は根拠や代替案の採否を確認する。四択で検証可能な範囲と、本人の作業を観測すべき実技を分ける。
- 問題のIDがつながるだけでは評価網羅としない。**教材の説明・設問があること／正答と全選択肢の説明が正しいこと／実際に要求能力を測れること**を別に確認する。
- 誤答は**異なる概念の混同・条件の読み違い**を意図したものとし、選択肢ごとの意味と、その問題条件での正誤理由を両方確認する。無理に類似した誤答を捏造しない。
- 問題や正式仕様を改訂した場合は、その問題IDと使用した教材・実技の版、対応する理解事項を再確認する。**旧版の回答を新版の学習証拠へ自動的に引き継がない**。個人の評価記録や公開模範解答の本文を公開グラフへ複製しない。

### モジュール別の出題範囲と十分性の判定

教材の全量制作前に、各モジュールの学習項目・理解事項を**実際に確認すべき理解・適用・判断**へ分け、クイズで問う内容と実技で確認する能力を決める。次の問題数は**初期の制作目安**であり、固定の合格基準ではない。題材・問題文・選択肢を作成した後、評価観点の不足や重複に応じて調整する。

| モジュール | クイズで重点的に確認する内容 | 初期目安 | 本人の実技で確認する内容 |

| M03 | 同値分割、境界値、条件表のルール、状態遷移、Caseと技法の採否 | 13問 | 主要4技法の条件導出・Case設計、別条件への適用 |
| M04 | AI案の不足・誤期待、テスト層、自動化採否、未決事項 | 8問 | 初見条件の設計レビューとPhase 1総合判断 |

上表の合計は**106問程度の制作目安**であって、106問あれば学習項目を評価済みとする意味ではない。各モジュールの問題を実際に決める際は、対応学習項目・理解事項、問題が問う具体的な判断、問題ID、実技で代替する観点とその証拠、採用問題数の理由を[知識グラフと実在する教材・問題・実技の対応](./2026-10-16_qa-curriculum-ai-agent-redesign_learning-map.md)から確認する。独立した新しい管理台帳は作らない。

- **不足の拒否**：1〜2問などの少数設問でも、必要な理解・適用・判断を他の設問・実技で測れた具体的な根拠がなければ、そのモジュールのクイズ制作を完了としない。単に学習項目IDを付けたり「実技で確認」と書いたりするだけでは不足を解消できない。
- **目安からの増減**：問題数を減らす場合は、重複排除や実技で代替する観点・成果物・本人の判断を確認する。追加する場合も、従来の設問では測れない理解・条件判断があることを根拠にする。
- **完成の確認**：問題数、対応関係、正答の一意性、全選択肢の意味・正誤理由、正式根拠、復習先、別条件での再確認を点検し、**重要な評価観点に不足がないこと**を問題作成者以外が確認する。実技の作成・合格基準は[評価Plan](./2026-10-16_qa-curriculum-ai-agent-redesign_assessment.md)に従う。

## 問題の設計と独立レビュー

1. [学習項目表](./2026-10-16_qa-curriculum-ai-agent-redesign_learning-map.md)と[段階的習熟基準](./2026-10-16_qa-curriculum-ai-agent-redesign_progression.md)から、知識として理解すべきことを確認する。**フェーズ別に**必要な学習項目だけを選び、問題・正答の対応表を記録する。全項目に問題IDまたは**クイズ不要の根拠と対応する実技**を記録する。
2. 難易度の高い状態遷移や計算問題では、正答の根拠を問題文に先に明かさない。仕様の条件に基づき導ける問題にする。
3. 問題を作った後、**正解を独立に再計算・検証**する。数量、実行時間、日時、SHA、権限などの誤りは合否に直結する。
4. A〜Dを各々問題文の条件と照合する。2つ以上正解、正解なし、条件によって回答が変わる問題を不採用にする。
5. 誤答には、実際に起こり得る混同・読み違いを用いる。文法・選択肢の長さで正解が推測できる問題は修正する。
6. **全選択肢の説明**がその選択肢の実際の内容を説明し、正答欄と矛盾しないことを確認する。
7. 誤答時の復習先が存在し、問題が前のモジュールまたは当該モジュールまでに学んだ内容で解けることを確認する。
8. 単一の正答が成立しにくい設計判断は、実技・レビュー課題へ移す。
9. Codespaces作成のためGitHubアカウントは必要だが、Phase 1の問題をGitコマンド・PR・Playwright・CIログを知らないと解けない問題にしない。Phase 2の問題をGitHubのPR操作でしか正解を確認できない問題にしない。Phase 3のクイズ・回答・合格条件をPhase 1・2へ持ち込まない。判断に幅があることを採点者の独断で「不正解」としない。

### 自動検証と人による検証

**新課程のJSON検証をビルドに必須組込み**、形式・モジュール/問題ID一意性、4選択肢、正答の実在と一意性、全選択肢の意味と正誤理由、根拠、学習項目ID、復習先Markdownとアンカーの実在を確認する。既存の旧課程validatorは変更せず、新課程専用の最小検証処理を設ける。**同期先では配布された公開クイズJSONを同じ契約で検証**できるが、公開の修了課題模範や評価テストを学習者向け配布から除外する。これは秘密保持ではない。

それだけでは「問題の正解が本当に正しい」ことは証明できない。Specや技法に依存する問題の正答・誤答説明は独立レビューを実施する。旧 `scripts/validate-curriculum.ts` への追加や変更で済ませない。

## 完成形の設計例

以下は**新課程向け問題の例**。M02/M03の2問はPhase 1、M05の1問はPhase 2、M09の1問はPhase 3の例であり、先行フェーズの修了に後続の問題を含めない。すべての正式問題を作成したことにはならない。完成状態では、全学習項目について[知識グラフ完成仕様](./2026-10-16_qa-curriculum-ai-agent-redesign_knowledge-graph.md)に基づき必要な問題・全選択肢の説明・実技・評価方法まで揃え、対応の妥当性を検証する。

### M02-Q01：仕様と観測

対応：M02-01

問題：正式仕様は「購入上限を超える追加操作は拒否し、既存数量を維持する」と定めている。画面では追加成功に見え、AIも成功が正しいと報告した。テストの期待結果の根拠とすべきものはどれか。

- A. 実際の画面表示
- B. AIの最終報告
- C. 正式仕様のBR/AC
- D. 既存のE2Eテストの期待結果

正答：**C**。

- A：観測事実であり、仕様を上書きしない。
- B：AIの報告自体が妥当性の根拠にはならない。
- C：期待動作を定める正本である。
- D：既存のテストに誤ったAssertionがある可能性がある。

根拠：`docs/spec/README.md`、`docs/spec/features/cart.md`。復習：M02、正式仕様と観測の区別。

### M03-Q01：境界と追加拒否

対応：M03-02

問題：在庫3個、購入上限5個、システム上限99個の商品がある。カートに2個入った状態で追加2個を要求した。仕様が「上限超過の追加は丸ごと拒否し、元の数量を維持する」と定める場合、期待結果はどれか。

- A. 数量は4個になる
- B. 数量は3個に自動補正される
- C. 数量は2個を維持し、追加が拒否される
- D. 数量は0個に戻り、追加が拒否される

正答：**C**。

- A：在庫3個を超える。
- B：上限への自動補正を認める仕様ではない。
- C：追加後の4個は上限3個を超えるため操作を拒否し、元の2個を保持する。
- D：元のカート数量を消去する仕様ではない。

根拠：`BR-CART-001`。復習：M03の境界値分析と期待結果。

### M05-Q01：Assertionの保証範囲

対応：M05-03

問題：Playwrightで購入ボタンへの`toBeVisible`が通過した。これだけで実際に確認できた事実はどれか。

- A. 決済が完了した
- B. 購入ボタンが表示されていた
- C. ボタンのクリックが成功した
- D. 注文データが保存された

正答：**B**。

- A：決済結果は検証していない。
- B：可視性を直接検証している。
- C：クリック操作は実行していない。
- D：注文データを確認していない。

根拠：Playwrightの`toBeVisible`。復習：M05のAssertion。

### M09-Q01：CIとコミット

対応：M09-02

問題：あるPRの現在のHEADはcommit B、成功したGitHub Actions Runはcommit Aに紐付いている。Run Aだけを根拠として言えることはどれか。

- A. PR番号が同じためcommit Bも検証済み
- B. branchが同じためcommit Bも検証済み
- C. Run Aはcommit Aに対する証拠であり、commit Bは別途確認が必要
- D. Runが緑なので検証対象commitの照合は不要

正答：**C**。

- A：PR内でHEADは更新され得る。
- B：branchが同じでも内容は変化する。
- C：Runが検証したSHAと現在のSHAの一致を確認する必要がある。
