# 確認クイズ・正答・解説の設計

## 目的と対象

既存の各レッスンには記述式の`## 確認問題`と`## 自己確認`がある。PR #198 HEADでは総合演習2本を除く15レッスンに合計106問があり、最低回答要素による自己確認は可能だが、個々の問題に四択・正答・選択肢別解説は用意されていない。

**方針**：
- 既存106問は、理由を自分の言葉で説明する記述式問題として必要なものを残す。すべてを無条件でクイズに変換しない。
- 学習項目を短時間で確認するために、**4択・1正答**の確認クイズを新たに設ける。実務的な判断が必要な問題は、Scenario Shopの条件を問題文に明示する。
- **誤った選択肢ごとに、なぜ誤りかを説明する**。単に「正解はC」とするだけでは、自習教材として不十分。
- 理解を問う問題には唯一の正解が成立する条件を与える。設計上のトレードオフに複数解がある場合は四択に押し込まず、既存の記述式・実技ルーブリックへ移す。
- 確認クイズは**学習項目を確認する手段**。コード実装、AIとの協働、PR、CI実行の達成は実技で別に検証する。

## 問題と正答の保存先

既存教材の`## 確認問題`（記述式）を消さず、独立したクイズへリンクする。

```text
docs/curriculum/test-automation/
  quizzes/
    README.md
    P1-01.md
    ...
    P1-09.md
    P2-01.md
    ...
    P2-08.md
    answers/
      P1-01.md
      ...
      P1-09.md
      P2-01.md
      ...
      P2-08.md
```

この設計の理由：
- **単なるMarkdownファイル**であればGitHub上でもローカルでも読め、特別な新規依存、サーバー、DB、採点アプリを要求しない。
- 解答と解説は別ファイルに分け、受講者が一度回答してから開く導線を作る。**非公開の試験問題ではない**ので、ファイルを読めば正答が見えることは仕様上許容する。
- 各レッスンから`quizzes/P1-01.md`へ、クイズから`answers/P1-01.md`へ戻れるようにする。原則として演習を終えた後に解答を確認する。
- 問題形式が変更されても、レッスンのLesson ID・既存4 CSV・Completion Receipt schemaを必須要件なしに変更しない。後で対話的なアプリが必要になった場合、問題データの分離やJSON化は別途判断する。

### 各クイズファイルの必須構成

1. 対象レッスン、対象学習項目ID、回答時の参照ルール（オープンブック可否）、解答を見る順序。
2. 各問題に`P1-03-Q01`のような安定したIDを付け、どの`P1-03-K01`を測るか明記する。
3. 「問題文」「A〜Dの4選択肢」のみを問題ファイルに記載する。**受講者が答えを予測できる強調・誘導を入れない**。
4. 外部資料が必要な問題には仕様IDと必要条件を問題中に示す。正解コードや正本の結論を前提文で漏らさない。
5. レッスンごとの問題数、誤答した項目の復習先、解答ファイルへのリンク。

### 各解答ファイルの必須構成

| 欄 | 意味 |
| --- | --- |
| 問題ID / 学習項目ID | 問題と到達目標の一対一または根拠のある一対多 |
| 正答 | A〜Dの**1つだけ** |
| 正答の理由 | 前提と仕様から、なぜ成立するかを説明 |
| A〜Dの選択肢別解説 | 誤りも含めて**4選択肢すべて**に短い説明 |
| 根拠 | レッスンの該当節、正式仕様のBR/AC、実際のコードやGit/CI契約 |
| 誤答した場合の復習先 | 必要な学習項目・教材の見出しへのリンク |

回答を保存・集計する個人別DBは不要。受講者は既存の`self-check/P1-03.md`などに問題ID、選択した答え、正答数、誤答の理由と復習・再確認結果を記録する。元の確認問題に答えた場合は従来どおり記述式自己確認の記録も残せる。

## 内容検証の契約

Codexは**作問と検証を別の作業**として行う。AIが作ったクイズを無検証で正式解答と扱わない。

1. 学習項目表の65行を起点に、各問題がどの行を測るか列挙する。
2. 問題文を確定した後で、正本に基づいて正解を独立に解く。特に数量・状態遷移・Git/CIの時系列は手順を再計算する。
3. A〜Dの全選択肢について、条件を満たすか個別に判定する。**同時に複数が正解なら問題を修正する**。単に正答ラベルを1つに減らしてはいけない。
4. 誤答は明確に誤りと説明でき、かつ実務上ありそうな選択肢にする。明らかに不自然な選択肢で水増ししない。
5. 難易度が高すぎる、複数解になり得る、元の学習項目を測れていない問題は削除または再作問する。
6. 問題の正答・理由・選択肢別解説・根拠・復習先が対応していることを確認する。
7. 実装の契約テストはID一意性・リンク存在・A〜D存在・正答ラベルの一意性・各選択肢の説明有無・学習項目の参照完全性を検証する。**正答の意味的正しさは機械的な文字列検証だけでは保証されない**。少なくともBR/AC依存の問題は仕様との独立レビューを必要とする。

Markdownのため問題ファイルの入力形式を無理にJSON schemaで固定する必要はない。最低限の見出し・問題ID・選択肢と解説欄の定型は設け、Codexが迷わず契約テストを書けるようにする。コード用の汎用quiz engineは本件では作らない。

## 正解・誤答解説付きの作問例

以下は**設計用の完成例**。Codexはこれを全65問の代わりに使ってはならない。実際に教材へ採用する場合、既存仕様とIDの現行revisionを再確認する。

### 例1：正式仕様と観測（P1-02-K01 / Q01候補）

問題：ある機能について正式仕様のBR/ACは「追加できない場合は操作を拒否」と定義している。一方、画面では追加成功に見え、AIも「成功が正しい」と報告した。テストの期待結果の判断根拠にすべきものはどれか。

- A. 現在画面に表示されている成功結果
- B. AIが複数回述べた成功結果
- C. 正式仕様のBR/AC
- D. 既存のE2Eテストに記載された期待結果

**正答：C**。

- A：観測事実であり、正式仕様を上書きしない。
- B：AI出力には誤りがあり得る。仕様上の根拠の代わりにならない。
- C：受入基準を定める正本だから。
- D：既存テストのアサーションが仕様と食い違う可能性があるから。

根拠：`docs/spec/README.md`の優先順位、`docs/spec/features/cart.md`。復習：P1-02「教材」「正本の参照経路」。

### 例2：数量上限と保持（P1-03-K01 / Q01候補）

問題：ある商品の在庫が3個、購入上限が5個、システム上限が99個。カートにすでに2個あり、追加2個を操作する。正式仕様が「上限超過した操作は丸ごと拒否し、従前数量を維持」と定める場合、期待結果はどれか。

- A. カート数量は4個になり、追加成功する
- B. カート数量は3個に自動補正され、追加成功する
- C. カート数量は2個のまま、追加が拒否される
- D. カート数量は0個に戻り、追加が拒否される

**正答：C**。

- A：在庫3個を超過する。
- B：仕様は上限への自動補正を許可せず、追加全体を拒否する。
- C：2＋2は上限3を超えるため、元の数量2を維持する。
- D：拒否した操作によって元の数量を消す仕様ではない。

根拠：`docs/spec/features/cart.md`の`BR-CART-001`。復習：P1-03「同値分割と境界値分析」、Cartの期待結果。

### 例3：Assertionの保証範囲（P1-04-K03 / Q01候補）

問題：Playwrightで`await expect(page.getByRole("button", { name: "購入" })).toBeVisible()`が通過した。この結果から**確認済みと言えること**はどれか。

- A. 決済が正常に完了した
- B. 購入ボタンが表示されていた
- C. ボタンのクリックが成功した
- D. 残高が正しく更新された

**正答：B**。

- A：決済の状態は確認していない。
- B：このAssertionが直接検証するのは対象要素の可視性。
- C：クリック操作そのものを実行・検証していない。
- D：残高の読み取り・比較を行っていない。

根拠：P1-04「Assertion」、Playwright公式`toBeVisible`。復習：P1-04「操作と検証」。

### 例4：失敗原因の判断（P1-06-K01 / Q01候補）

問題：BRには「数量上限を超える追加は拒否する」とある。実際の画面も拒否したが、テストは「追加成功の通知が出る」とアサーションして失敗した。提示された証拠から最も妥当な一次判定はどれか。

- A. 製品コードの不具合
- B. テストの期待結果の誤り
- C. ブラウザのインストール不足
- D. Runnerの実行時間不足

**正答：B**。

- A：画面の拒否動作は提示された仕様に従っている。
- B：アサーションが仕様と逆の成功結果を期待している。
- C：ブラウザは動作し画面の応答まで観測できている。
- D：示された失敗はTimeoutではなく仕様に合わないAssertionである。

根拠：`BR-CART-001`、`training/playwright/diagnostic-exercises/diagnostic-cart.spec.ts`。復習：P1-06「失敗分類」「Trace」。

### 例5：CI結果の対象commit（P2-05-K02 / Q01候補）

問題：PRのHEADはコミットBだが、表示しているGitHub Actionsの成功RunはコミットAに紐付いている。この成功Runだけで**コミットBを検証済み**と判定できるか。

- A. できる。PR番号が同じだから
- B. できる。どちらも同じbranchだから
- C. できない。成功Runが検証したcommitを確認する必要があるから
- D. できる。最新のRunが緑であれば内容は同じだから

**正答：C**。

- A：PR内のcommitは更新され得る。
- B：同じbranchでも時点によってコードは異なる。
- C：対象SHAの一致は実際にその変更を検証した根拠となる。
- D：Runの状態だけでは検証対象が同一とは限らない。

根拠：P2-05のTraining CI、GitHub ActionsのRunとcommitの対応。復習：P2-05「Run/Artifact」。

### 例6：AIの成功報告（P1-09-K02 / Q01候補）

問題：AIは「テスト実行に成功」と報告しているが、実行コマンド・実行ログ・Receiptなどを確認できず、利用環境も未接続だった。学習者の完了報告として適切なのはどれか。

- A. AIが成功と答えたためPASSとする
- B. テストコードが存在するためPASSとする
- C. 未実行または未確認と記録して、実行できる環境で検証する
- D. 既存のbaselineのPASSを新しいテストの結果に使う

**正答：C**。

- A：AIの文章は実行証拠ではない。
- B：ファイルの存在だけではテストの実行を証明できない。
- C：確認できた事実と不足している証拠を区別している。
- D：baselineの成功は受講者自身のテストの成功を証明しない。

根拠：`scripts/training/check-completion.ts`、P1-09の完了条件。復習：P1-09「自己確認」。

## 合否と再確認

クイズの合否は[評価・修了設計](./2026-10-16_qa-curriculum-ai-agent-redesign_assessment.md)に従う。クイズだけでレッスン修了とはしない。受講者にとって何を間違え、どこを復習し、どの条件で再確認できるかを分かるようにする。
