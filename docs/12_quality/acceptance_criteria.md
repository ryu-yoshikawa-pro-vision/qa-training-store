# Phase 1受入基準

## 1. 基盤

- Expo WebがDomain／Application／Repositoryのレイヤー境界を遵守して動作すること。
- Web環境において、Dexie Repositoryの契約テスト（Contract Test）に合格すること。
- IndexedDBのインデックスキーにbooleanやnullを使用せず、isDefaultKey、isActiveKey、optionScopeKeyへのマッピング（プロジェクション）が契約テストをパスすること。
- Domain EntityおよびEnumが`domain_types.md`と、Core DTO、Input、Result、Errorの各型定義が`application_contracts.md`と完全に一致していること。
- ストアフロントのカタログおよび管理画面の全一覧クエリにおいて、検索・絞り込み・並べ替え・ページネーション（Search/Filter/Sort/Page）がRepository側で実行され、同順位時のタイブレーク用キー（最終Key）が仕様契約どおりに機能すること。
- UIコンポーネントからDexieを直接呼び出さないこと（必ずRepository層を経由すること）。
- Storefront ShellとAdmin Shellが明確に分離されていること。
- 未使用のRefund、Gateway Ledger、Import/Recoveryの各テーブルがPhase 1のスキーマに存在しないこと。

## 2. Auth・Permission

- guestおよびcustomerが`/cart`を閲覧・変更でき、チェックアウト（Checkout）はactiveなcustomerのみ利用できること。operatorおよびadminによるカートの利用は拒否されること。
- operatorおよびadminによる購入ルートへのアクセスおよび購入Use Caseの実行が拒否されること。
- 会員ランク（Rank）、アカウント状態（Account Status）、リソースの所有権（Ownership）、最後のadminの保護がUse Case層で厳格に強制されること。
- activeなcustomer、operator、adminがログインでき、ログイン時にcustomerのみゲストカートの統合が行われ、operatorおよびadminはセッションのみを作成すること。operatorおよびadminがストアフロントを閲覧する際の権限・表示条件はguest相当となること。
- suspended（利用停止）またはwithdrawn（退会済み）のアカウントはログインできないこと。
- プロフィール取得DTOが電話番号と`actionVersion`を返却し、プロフィール更新後にも更新後の新しい`actionVersion`を返却すること。
- 初めて登録された配送先住所が自動的にデフォルト（Default）となり、単なる更新操作だけでデフォルト住所が0件にならないこと。別の住所をデフォルトに指定する処理や、デフォルト住所削除時にcreatedAtおよびid順で後継のデフォルト住所を選定する処理が、同一トランザクション内で決定論的（確実）に実行されること。
- ログインおよび新規登録（Register）では、CurrentSessionStoreへの保存成功後にのみDBトランザクションを開始すること。customerはセッション作成とゲストカート統合を、operatorおよびadminはセッション作成のみを単一トランザクションで実行すること。トランザクション失敗時はポインタをクリアし、セッションを作成せずにゲストカートを保持すること。
- パスワードハッシュがPBKDF2の固定フォーマットで生成・照合され、平文のパスワードがDBやログに残らないこと。

## 3. Home・Search・Catalog

- ホーム、全商品一覧、検索結果、カテゴリー別一覧がそれぞれ独立したルートとして動作すること。
- 検索サジェストが最大8件表示され、キーボード操作、Enterキーでの検索実行、Escapeキーでの閉じる操作に対応していること。また、古いリクエストの結果が新しい入力内容を上書きしないこと。サジェストの遷移先として、商品候補は商品詳細へ、カテゴリー候補はカテゴリー一覧へ、ブランド候補は該当ブランドの絞り込みを適用した検索結果へ遷移し、候補未選択状態でのEnterキー入力時はキーワード検索へ遷移すること。
- 閲覧者（Viewer）の条件（会員ランクや公開状態など）を適用した後の総件数（total）、ページ情報（page）、ファセット集計（facet）が正確であること。
- カテゴリーファセットが第1階層カテゴリーの表示名と件数を返却し、閲覧者条件適用後の該当商品件数と一致すること。
- ホームカタログDTOが、閲覧者条件適用済みのカテゴリー・ブランド表示名および商品件数、新着商品（最大8件）、セール商品（最大8件）を返却すること。件数が0件のナビゲーション項目は除外され、新着商品は初回の`publishedAt`（公開日時）順で並び、再公開操作によって表示順が変動しないこと。在庫切れの公開商品も商品セクションに含まれ、購入不可である旨が表示されること。
- ホーム、ナビゲーション、商品検索・サジェスト候補・商品詳細、ならびに管理画面の商品一覧・詳細におけるセール判定が、テスト用クロック（Test Clock）の固定時刻と一致し、Repositoryがシステムの実時計を直接参照しないこと。
- 適用中フィルター（Applied Filter）の個別解除・一括解除、およびモバイル画面でのまとめて適用する操作が正常に動作すること。
- ソート順が同順位の場合、`productCode`によって安定した並び順が保たれること。
- 商品詳細画面から一覧画面へ戻った際、検索クエリ、ページ番号、スクロール位置が正しく復元されること。
- 商品等から参照されているカテゴリーやブランドの無効化を拒否すること。カテゴリー一覧、ファセット、ナビゲーションにおいて、第1階層カテゴリーとして同一の件数が表示されること。
- カテゴリーおよびブランドの通常編集では`isActive`を変更できず、専用のステータス変更Use Caseでのみ有効／無効を切り替えられること。新規作成時は`active`（有効）とすること。
- カテゴリー、ブランド、バリエーションの重複判定ロジックが共通の正規化キー（Normalization Key）へ集約されており、Webアプリケーション内のすべての登録・更新経路で同一の判定結果となること。
- 商品アグリゲートの作成・更新・削除が、定義されたトランザクション境界および参照整合性ルールに従うこと。新規作成時には0件のReview Summaryを作成し、更新トランザクションには必要な`INITIAL_STOCK`（初期在庫）履歴を含め、削除時には0件のReview Summaryの削除を含むこと。なお、商品更新トランザクションでは既存のReview Summaryを変更しないこと。
- 商品アグリゲートの作成（Create）および更新（Update）において、クロックから現在時刻を1回のみ取得し、Product、SKU、画像関連エンティティ、`INITIAL_STOCK`履歴に同一のタイムスタンプを保存すること。作成時は0件のReview Summaryにも同じ時刻を使用し、更新時は既存のReview Summaryを変更しないこと。
- 下書き（draft）を含むすべての商品アグリゲートはactiveなSKUを1件以上保持し、バリエーションなしの場合はactiveなSKUがちょうど1件、バリエーションありの場合は1件以上存在すること。管理画面一覧での最小価格・最大価格がnullにならないこと。
- 商品アグリゲートの新規作成時は必ずステータスが`draft`かつ`publishedAt`が未設定となり、アグリゲートの更新操作では`status`や`publishedAt`を変更できないこと。公開状態および初回の`publishedAt`の更新は、専用のステータス変更Use Caseのみが行うこと。
- 商品のステータス変更アクションは、「draft → published」「published → unpublished / discontinued」「unpublished → published / discontinued」の遷移のみを許可し、`discontinued`（廃止）は終端ステータスであること。未保存の編集内容の保存とステータス変更を同時に実行しないこと。
- 商品コード（Product Code）およびSKUの変更可否判定、ならびにメイン画像（Primary画像）の自動割り当てが、定義されたビジネスルールどおりに動作すること。
- `productCode`やSKUの入力時に小文字や全角文字が正規化され、正規化後の重複登録を拒否すること。また、DB、画面表示、検索処理のすべてで正規化された同一の大文字値を使用すること。
- 商品の複製操作では即座にDBを変更せず、新規登録フォームへactiveなSKU、画像、商品情報を転記し、商品コード（Code）およびSKUを空に、初期在庫を0にリセットすること。保存実行後は通常の商品作成契約が適用されること。
- 新規追加されるSKUは`active`固定で追加され、すでに保存されているSKUの価格変更、無効化、条件付き削除が正しく機能すること。`INITIAL_STOCK`以外の在庫変動履歴が存在するSKUは削除できず、既存の在庫数を商品編集画面から直接変更できないこと。
- GitHub画像アセットの選択、関連付け解除、メイン画像（Primary）の変更、表示順の並べ替えができること。画像が0件の状態で保存できるのは`draft`のみであり、画像が1件以上ある場合はPrimary画像がちょうど1件設定され、同一の`assetId`を重複して関連付けられないこと。ブラウザからGitHubへ直接書き込みを行わないこと。リリース済みのアセットは物理削除せず、既存のinactiveな関連付けは維持できるものの、再度関連付けることはできないこと。
- 商品詳細画面において、画像ギャラリー、会員ランクごとの価格階層、バリエーション選択、配送料条件、レビュー評価分布が正しく表示されること。
- レビューサマリー（Review Summary）は、`publishedCount = 0`のときは`ratingAverage = 0`とし、それ以外は`ratingTotal / publishedCount`の計算結果を丸めずに保持し、画面表示時のみ小数第1位へ丸め、評価順のソートや絞り込み（Sort/Filter）には丸め前の値を使用すること。
- バリエーションの選択UIにおいて、12件と13件の境界でボタン表示（Button）とドロップダウン選択（Select）の切り替えが正しく行われること。

## 4. Price・Stock・Cart

- regular、gold、platinumの各会員ランクにおける商品価格および配送料が、シードデータの期待値と一致すること。
- 送料無料までの不足額および送料無料達成のメッセージ表示が正確であること。
- 注文やチェックアウトの各ステップにおいて、価格、在庫数、公開ステータス、ユーザー権限、カートバージョン（Cart version）が再検証されること。
- 決済（Payment）が成功した場合にのみ在庫が1回減算され、決済失敗時には在庫数が変動しないこと。
- ログイン・新規登録、商品アグリゲート・公開ステータス変更・カテゴリー／ブランド無効化、在庫調整、ユーザーアクセス管理、注文（Order）作成、決済確定、出荷（Shipment）処理、レビュー集計といった複数Repositoryにまたがる更新処理が、ApplicationTransactionRunnerによって単一のトランザクションとして実行されること。
- カートへの商品追加、数量変更、購入上限数超過時の追加拒否、カート明細の削除が正しく機能し、いずれの変更操作でも親カートのバージョン（Cart version）が1回ずつインクリメントされること。
- 新規のゲスト（Guest）または顧客（customer）が、商品詳細画面からカートバージョンを指定せずに最初の商品を追加でき、activeなカートの取得または新規作成とカート明細の追加が、同一トランザクション内で完了すること。
- ゲストカートの統合処理が、会員カートを基準とし、購入許容上限や購入不可商品の除外ルールに従って実行され、統合結果がSKU単位で画面上にフィードバックとして保持・表示されること。
- 複数SKUを持つ商品の価格帯表示（価格幅）、価格フィルターによる絞り込み、価格ソートが、閲覧者の価格ルール（会員ランクに応じた実効価格）と一致すること。
- 管理画面の商品一覧における在庫フィルターは、activeなSKUの合計在庫数に基づいて判定され、「0 = 在庫切れ」「1〜5 = 低在庫」「1以上 = 在庫あり」となること。SKUごとの在庫状況の混在によって商品全体のステータス判定がブレないこと。
- カートアイテムの`unitEffectivePriceAtAdd`（追加時有効単価）はセール適用後かつ会員ランク割引前の価格を保持し、カート表示時および注文確定時に現在の会員ランクに基づいてSKU単価単位で割引額を再計算すること。単価割引額の端数は切り捨て（floor）処理とし、注文全体の割引額（`Order.discountAmount`）がすべての注文明細の割引合計（全`OrderItem.lineDiscountAmount`の合算）と完全に一致すること。
- カート画面が、`CartDto`の情報のみを用いて商品名、商品画像、追加時価格および現在価格、購入可能最大数量、明細に関する警告・エラー（在庫不足や販売停止など）を表示できること。

## 5. Checkout

- ユーザーごとのactiveなチェックアウトセッション（Checkout Session）は最大1件とし、同一のカートおよびバージョンである場合は既存セッションを復元すること。チェックアウト中にカートが変更された場合、セッションを即時更新するのではなく、ルートガード、注文確認画面、または注文確定処理の段階でバージョン不一致を検出してカート画面へ押し戻し、次回チェックアウト開始時に以前のセッションを`abandoned`（破棄）に変更すること。また、アプリ起動時、ルートガード通過時、チェックアウト開始時に24時間の有効期限切れを判定すること。
- 会員ランクが変更された場合、進行中のactiveなチェックアウトセッションが同一トランザクション内で`abandoned`に変更され、カート内容は保持されたまま新しい会員ランクの価格で再確認できること。
- 配送先住所（address）、決済方法（payment）、注文確認（confirm）の各画面へ直接URLでアクセスされた場合、前提条件を満たしていない不足段階のステップへリダイレクトされること。処理中（processing）、完了（complete）、失敗（failed）の各画面では、`orderId`の妥当性、注文の所有権、ならびにOrderおよびPaymentのステータスを厳格に検証すること。
- フォームの入力項目は1列レイアウトとし、必須／任意の区別および電話番号の利用目的を明記すること。
- 郵便番号からの住所候補提示は、シード辞書に一致した場合にのみ表示され、ユーザーが適用するかどうかを選択できること。
- バリデーションエラー発生時にエラーサマリー（Error Summary）へ自動でフォーカスが移動し、サマリー内のリンクから該当入力フィールドへ遷移・フォーカスできること。
- デスクトップ表示での追従型サマリー（Sticky Summary）およびモバイル表示での折りたたみ式サマリーが、それぞれ正常に操作・閲覧できること。
- 注文確定ボタンに支払い合計金額が表示され、`CheckoutConfirmationDto`の`checkoutActionVersion`を用いて注文確定リクエストを安全に構築できること。
- 注文作成トランザクションの内部で、カートアイテムの追加時単価と現在の実効単価を再照合し、価格に差異が生じている場合はOrderやPaymentを作成せずにカート画面へ戻すこと。
- 注文（Order）作成トランザクションの成功時に、該当カートのステータスが`consumed`（消費済み）に、チェックアウトセッションが`converted`（成約）に更新されること。
- 確定ボタンの連打や二重送信（二重Submit）によって、同一注文から複数のOrderが作成されないこと。

## 6. Payment・Order

- 外部決済ゲートウェイ（Gateway）の通信呼び出し処理を行っている間は、アプリケーションのDBトランザクションを保持（ロック）し続けないこと。
- 決済テスト用の成功トークン（TEST-SUCCESS）選択後、在庫が十分に確保されている場合にのみ、Paymentステータスが`succeeded`、Orderステータスが`paid`となり、在庫の減算および履歴の記録が重複なく1回だけ確定すること。
- 決済確定直前の最終在庫確認で在庫不足となった場合は、PaymentおよびOrderが`failed`となり、在庫数や履歴レコードは変更されないこと。
- 決済が明確に失敗した場合は、Paymentステータスが`failed`、Orderステータスが`payment_failed`となり、在庫数は変動しないこと。
- `payment_failed`状態となったOrderから、`OrderDetailDto`に含まれる`orderActionVersion`を使用して、新しい試行（Attempt）として再決済（再Payment）を実行できること。
- 決済処理中（`processing`）の間は再試行やキャンセル操作を受け付けず、`/checkout/processing?orderId=...`の画面を再読み込みした後に同一のAttempt処理を再開できること。すでに完了しているPaymentの結果については、Gatewayを再実行せずに既存の結果を返却すること。
- 決済ゲートウェイは処理時刻を返却せず、結果受領後にアプリケーションクロック（Application Clock）から取得した同一のタイムスタンプが、Paymentの`processedAt`ならびにOrder/Paymentの履歴レコードへ保存されること。
- 注文完了画面に、注文番号、支払い合計金額、配送先住所の概要、および次に案内すべきアクションが正しく表示されること。
- 注文詳細画面において、注文日時、商品情報、SKU有効単価、単価割引額、明細ごとの小計・割引額・合計額、商品合計小計、会員ランク割引額、配送料、総合計金額、注文時点の会員ランクスナップショット、配送先スナップショット、Payment情報、Shipment（出荷）情報、現在のステータス、次のプロセスの説明、利用可能なアクション、およびタイムラインが表示されること。
- 管理画面の注文詳細において、顧客のメールアドレス、表示名、および注文時点のスナップショット情報が表示されること。
- `paid → preparing`（支払い済みから出荷準備中）へのステータス変更を、`AdminOrderDetailDto`の`orderActionVersion`を用いて`StartOrderPreparationUseCase`へ渡して実行でき、更新後に返却されるDTOの新しいバージョンを用いて、続けて発送（shipped）や配送完了（delivered）の操作を行えること。
- OrderおよびShipmentのステータス更新（shipped / delivered）が、ApplicationTransactionRunnerによる同一トランザクション内で実行され、処理の途中で失敗した場合に一方のエンティティのみが更新された状態にならないこと。
- 日次で採番される注文番号（Order Number）が重複しないこと。

## 7. Review

- 配送完了（delivered）となった注文明細のうち、購入者本人のOrderItem 1件につき1回のみレビューを投稿でき、論理削除された後であっても再投稿はできないこと。
- 星による評価（レーティング）をキーボード操作で選択できること。
- `ReviewEligibilityDto`が既存レビューの評価点、タイトル、本文、ステータス、バージョンを返却し、公開中（published）または非公開（hidden）のレビューを初期表示して編集できること。
- レビューの新規作成、編集、削除、非公開化、再公開のいずれの操作においても、商品のレビューサマリー（Summary）と評価分布が同時に最新状態へ更新されること。
- 公開中（published）のレビューのみが、商品画面の評価集計対象となること。

## 8. Admin UX

- 管理画面のサイドナビゲーション、パンくずリスト（Breadcrumb）、ページヘッダーが、すべての管理画面において一貫した構成・デザインで提供されていること。
- ダッシュボード概要（Overview）に、発送準備待ち、低在庫、非公開レビュー、最近の注文、クイックアクションが表示されること。ここで低在庫はactiveなSKUのうち在庫数が1〜5のSKUのみをカウントし、在庫数0は「在庫切れ」として低在庫のカウントから除外すること。
- 管理画面の各一覧画面が、検索（Search）、絞り込み（Filter）、並べ替え（Sort）、適用中フィルター表示（Applied Filter）、データテーブル（Table）、ページネーション（Pagination）からなる共通構造を持つこと。
- データそのものが1件も存在しない場合（Data 0件）と、フィルター絞り込みの結果該当データがない場合（Filter 0件）とで、それぞれ適切な専用の空状態画面（Empty State）が表示されること。
- 一括操作（Bulk Action）の対象機能は、商品の公開／非公開の切り替え、およびレビューの非公開化／再公開の切り替えのみに限定されていること。
- 一括操作は現在表示中のページ内で選択された行のみを対象とし、一度に処理可能な件数は最大50件までとすること。検索結果の全ページ全件選択機能は提供せず、処理完了後は成功件数および失敗件数が画面に明示されること。
- 商品編集画面において、未保存の変更がある場合のみコンテキスト保存バー（Contextual Save Bar）が表示され、未保存プレビューを画面内のダイアログまたはオーバーレイで確認できること。また、保存、変更の破棄、画面離脱時の確認ダイアログが正しく動作すること。プレビューの表示は下書き（draft）保存に必要な最小限のバリデーションを満たしている場合にのみ実行でき、画像が0件の場合はプレースホルダー画像が表示されること。
- 会員ランク（Rank）はcustomer内でのみ、権限（Role）はoperatorとadminの間でのみ、アカウントステータス（Status）はactiveとsuspendedの間でのみ変更可能とし、変更理由の入力は要求しないこと。最後の管理者の保護、自分自身に対する権限変更の防止、およびステータス変更に伴う全セッションの無効化処理が正しく動作すること。customerのアカウント停止時は進行中のactiveなチェックアウトセッションを破棄し、カート内容はそのまま保持すること。なお、退会済み（withdrawn）ステータスおよびcustomerのRoleは編集不可（読み取り専用）とすること。
- カテゴリーおよび画像の並べ替え操作は、ドラッグ＆ドロップを行わずにキーボードやボタン操作だけでも完了できること。カテゴリーの並べ替えは専用の並べ替えモードで全件を表示して行い、`orderedIds`の指定不足があるリクエストは拒否し、10刻みの値で表示順を再採番すること。なお、ブランドの並び順は名称順固定とすること。
- 新規カテゴリー登録時、既存データが0件の場合は`sortOrder = 10`、既存データがある場合は`max(sortOrder) + 10`の値が割り当てられて末尾に追加されること。また、最大値の取得と新規保存処理は同一トランザクション内で実行されること。

## 8.1 Cross-roleシナリオ

- 同一のブラウザコンテキストにおいて、adminとして商品を登録・公開した後、customerとしてその商品を検索し、カートに追加・変更して購入を完了できること。
- adminが上記の注文ステータスを配送完了（delivered）まで進めた後、購入したcustomerがその注文明細に対してレビューを投稿できること。
- operatorとadminのロールを切り替えた際に、セッション、ナビゲーション表示、権限判定が正しく更新され、IndexedDBに格納された業務データが保持されること。

## 9. Testability

- シードカタログに定義された固定ID、金額、カート統合、チェックアウト、画像アセットに関する期待値と、実際のデータ内容が完全に一致していること。
- リセット操作によってDB、現在のセッション（Current Session）、ゲスト識別子（Guest Identity）が初期化され、指定されたシードデータが投入された上で、シード用Guest IDがローカルストレージに再設定されること。
- テスト用のクロック時刻および決済遅延時間（Payment Delay）を任意の値に固定、または固定解除できること。
- Test APIにおける書き込み操作がリセット、シナリオ用シード投入、クロック操作、決済遅延設定のみに限定され、読み取り操作がメタデータおよび固定の読み取り専用インスペクションDTO（Inspection DTO）のみに限定されていること。任意のテーブル操作、任意のクエリ実行、任意条件での検索、データの直接書き換え、スクリプト実行、外部へのFetch処理などの機能を提供しないこと。

## 10. UI・Accessibility

- 各主要画面において、読み込み中（Loading）、データなし（Empty）、エラー（Error）、競合（Conflict）、該当なし（Not Found）の各状態表示が漏れなく定義・実装されていること。
- UI上の文言・表示名がコンテンツ辞書（Content Dictionary）の定義と完全に一致し、システムの内部ステータス値やコード値がそのまま画面に露出しないこと。
- Web環境における主要な購入フロー（商品選択から注文確定まで）を、キーボード操作のみで完結できること。
- 検索コンボボックス、評価用ラジオグループ、エラーサマリー、ダイアログ、フィルターシートなどの主要UIコンポーネントが、キーボードおよびスクリーンリーダーで問題なく操作可能であること。
- エラー状態を色のみに依存して表現せず、テキストラベルやARIAロール（Role）を適切に付与して明示すること。
- 画面幅360pxのストアフロント環境において、2列の商品グリッド表示および主要なCTA（アクションボタン）が正常に視認・操作できること。
- 画面幅1024px以上の環境において、管理画面が操作可能であること。

## 11. Automation・Deployment

- 単体テスト（Unit）、アプリケーション結合テスト（Application Integration）、Dexieの契約テスト（Dexie Contract）のすべてに合格すること。
- `e2e-chromium` マトリクステストのすべてのレグ（leg）に合格すること。必須レグ（`required` leg）は `pnpm run test:e2e:chromium` により、`chromium` プロジェクト上で `e2e/web/phase1-required.spec.ts` および `e2e/web/ui-ux-improvements.spec.ts` を実行し、`e2e_design.md` に定義された WE-CORE-001 〜 WE-CORE-012 をビジネスフローマッピングとして追跡・検証すること。
- `pnpm run build:web` 実行時に画像マニフェストの生成・検証が必ず行われ、Image Manifestの検証、リリース済みアセットの追記限定（append-only）検証、およびGitHub Tokenの混入防止チェックがすべて成功すること。Cloudflare環境へのデプロイでも同一のコマンドを使用すること。
- Cloudflare本番環境へのデプロイ後に行われるスモークテストに合格すること。
- E2Eテスト失敗時に出力されるアーティファクトに、シナリオ名、クロック時刻、遅延設定値、バージョン情報が含まれていること。

## 12. Documentation

- Phase 1に関する未確定・未決定の事項が、Decision Logに残存していないこと。

## 13. Web Phase 1対象外

Web Phase 1の受入基準には、Native環境のランタイム動作およびMaestroによるテストフローを統合しません。Nativeコード変更時におけるNative CIは別個の契約として扱い、「Androidのビルドおよびランタイム検証」と「iOSのビルドのみ」を検証対象とします。iOSのランタイム動作、シミュレータ動作、Maestroテストの合格（PASS）は保証しません。また、ゲストによるチェックアウト（Guest Checkout）、キャンセル・返品・返金（Cancel/Return/Refund）、決済状態不明時の照合処理（Payment Unknown/Reconciliation）、インポート・エクスポート、マイグレーションリカバリー、パブリックデモの分離、お気に入り機能（Wishlist）、おすすめ機能（Recommendation）、クーポン、ポイント、売上チャートについては、Phase 1の受入基準には含めません。

## 実装境界Gate

- プレゼンテーション層からのリクエストパラメータに、Current User、Role、Rank、Actor、Guest ID、Clock、生成済みID、Manifest解決後の値が含まれていないこと（これらは内部コンテキスト等から解決すること）。
- ビルド時に生成されたManifestモジュールのみをランタイムで使用し、実行時にアセット情報を取得するための外部Fetch（Runtime Fetch）が発生しないこと。
- 注文詳細DTOに、決済Gateway Key、Repository Version、システム内部のActor IDが含まれていないこと。
- リセット処理は1つのBrowser Context内の1つのPageを対象とする条件で成功し、DBの削除処理がブロックされた場合には明示的に失敗すること。
