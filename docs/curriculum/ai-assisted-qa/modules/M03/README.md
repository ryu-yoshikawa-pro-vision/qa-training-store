# M03：テスト設計

## このモジュールで学ぶこと

- 仕様に合うテスト技法を選び、選択理由と限界を説明する。
- 同値分割、境界値、デシジョンテーブル、状態遷移を条件に応じて使う。
- Risk→Condition→Case→BR/ACを追跡し、期待結果の根拠を示す。
- AIが出した条件・ケースの穴、矛盾、実行不能な組合せを見つける。
- Skillの構造化出力と、Skillを実際に実行して得た証拠を区別する。

## 到達条件

初見の仕様条件から本人がケースを作り、前提、操作、期待結果、根拠を説明できます。完成した条件表を眺めるだけではなく、条件に漏れや仕様上の未決がある場合はそれを示します。

## 例：数量上限の境界値

`BR-CART-001`における有効上限は、在庫数、購入上限数、99の最小値です。演習で具体条件が与えられたときは、上限値と上限を1つ超える値を候補にします。超過操作の期待結果は、`AC-CART-001`に従って「拒否され、変更前の数量を維持する」です。

上限の全要因を比較せずに、常に99の直前・直後だけを選ぶのは不十分です。また、上限を超える値が必ず画面から入力できるとは限りません。画面で選択できない場合は、E2Eに適さない理由と、適切なテスト層を区別します。

## 例：検索条件のデシジョンテーブル

商品検索の`BR-STOREFRONT-002`は、同じ facet 内の条件がOR、異なる facet 間の条件がANDとなることを定めます。学習者は、条件の組合せ、期待される商品集合、仕様から導けない条件を表にします。製品の実在データにその組合せがない場合は「実行不能」と記録し、架空の商品や結果を追加しません。

## M02から引き継ぐもの

M02の`analysis.md`から、正式なBR/AC、Risk、Scope、検証責務、対象範囲、期待する成立条件、未決事項を引き継ぎます。人が読む検証責務と、Skillへ渡す機械入力は別に保存します。

初回の条件設計は、固定commit `7cc6cba7772de549841a39d71694cbafbc783324`の`test-condition-design` Skillを`direct` modeで開始します。実行の順序は次のとおりです。

1. 正式な仕様を参照してM02の実在するAuthority/Risk/Scope参照を確定します。未確定の参照を推測で作りません。
2. `condition_structure.py`の`direct`入力を作り、Skillのruntimeで検証します。M02の文章を`test_requirements[]`へ複製したり、契約にないキーを追加したりしません。
3. Skillが選んだ技法を確認し、その入力契約で実際のモデルruntimeを実行します。
4. 現行runtime結果と実行時metadataを`current_model_result_row(envelope, metadata)`で検証してから、`materialize_coverage.py`の`artifact`入力を作ります。
5. Case Skillへ条件を渡し、最後に`verify_runtime_evidence`で有効な証拠を確認します。

`ready`、終了コード0、AIの自己申告だけでは完了としません。上流参照の欠落、未解決事項、mode不一致、古いruntime結果、`invalid_input`を成功として扱いません。17個のmetadata key、15個の条件入力key、fingerprintなどの内部契約を受講者が暗記する必要はありません。エージェントとruntimeが生成したJSON・実行結果を本人が根拠に照らして判断します。

## 演習：条件からCaseへ

1. M02から引き継いだ検証責務を1つ選び、仕様根拠とScopeを確認します。
2. 同値分割、境界値、条件組合せ、状態遷移のどれが必要かを本人が説明します。
3. M02の例と異なる条件を与え、代表値、期待結果、適用限界を記録します。
4. Skillが生成した条件・Caseに、仕様にない期待動作、欠けた上流参照、矛盾がないか確認します。
5. CaseごとにID、前提、操作、期待結果、観測方法、BR/AC根拠を対応させます。

## 評価基準

Level 2では、条件の異なる課題で本人が導出し、AI案とruntime証拠を照合できることを確認します。

| 観点 | 到達を示す証拠 | 到達しない例 |
| --- | --- | --- |
| 技法の適用 | 同値分割、境界値、条件表、状態遷移から必要なものを選び、選択理由と限界を説明する | 例題の表を写す、全条件へ無理由に全技法を適用する |
| 条件とCaseの導出 | 初見条件からID、前提、操作、期待結果、観測方法を作り、Risk→Condition→Caseを追跡する | 期待結果にBR/ACの根拠がない |
| 上流参照 | 実在するAuthority、Product Risk、Scopeを確認し、TCN・CI・Caseまで欠落や誤modeがない | IDらしい文字列や`ready`だけで参照確認済みとする |
| runtimeの証拠 | 固定Skill revisionで選択技法を実行し、`materialize_coverage(artifact)`、Case、最終`verify_runtime_evidence valid=true`まで同一artifact群で確認する | 終了コード0、AIの自己申告、古い結果を成功扱いする |
| 意味上の妥当性 | 仕様に合う期待結果、正しい別解、未決事項、実行不能な条件を根拠とともに説明する | 技術検証PASSだけで設計の正しさもPASSとする |

runtime証拠の有効性と、テスト設計の意味上の妥当性は別々に判定します。片方が未実施・無効なら、M03のLevel 2を認定しません。

## 次へ進む条件

M04へ進む前に、本人が条件とCaseの追跡関係を示し、AI案の採否、未決事項、正しいテスト層を説明します。最終artifactやCIが作られていない場合、その工程を完了扱いにしません。
