# M10：GitHub・CIを使った総合実践

## この章でできるようになること

この章（M10）は、これまで学んできた自動テストと開発運用の知識を一つにつなぎ合わせる**Phase 3の総合演習**です。

ここまでに学んだ内容を振り返ってみましょう。

- **M07**：Playwrightを使ったテストコード（specファイル）の読み解きと、期待値（アサーション：`expect`）の修正
- **M08**：Gitを使ったバージョン管理（変更履歴の記録、ブランチの作成、コミットの管理）
- **M09**：CI（継続的インテグレーション：プログラムの変更時にテストやビルドを自動実行する仕組み）の設計とワークフロー定義の読み解き

本章の最終目標は、**受講者本人専用の非公開リポジトリ（Private Repository）上で変更内容を整理してプルリクエスト（PR）を作成し、専用のCIワークフローを安全に動かして、その実行結果が「現在のPRの最新コード（PR head）」と完全に一致していることを、客観的な証拠（ログやハッシュ値）に基づいて確認・報告できるようになること**です。

### なぜこの演習が重要なのか？

テスト自動化の現場では、「テストコードを書いて動かした」だけでは仕事の半分しか終わっていません。実務で最も恐れられているのは、次のような**証拠の不整合や確認不足**による事故です。

1. **古い結果を見て安心してしまう失敗**：
   GitHubの画面上に緑色のチェックマーク（成功マーク）が表示されていたため、「テストが通った」と思い込んでプルリクエストを本番環境へ統合（マージ）したところ、実は数時間前の古いコードに対するテスト結果であり、直前に追加した最新の修正コードでバグが発生してシステムが停止した。
2. **テストがスキップされたことに気づかない失敗**：
   CIが緑色（成功）で終了していたが、実行ログをよく読むと、途中でブラウザのインストールやサーバーの起動に失敗しており、テストステップ自体が「スキップ（未実行）」されたままジョブが正常終了扱いになっていた。
3. **AIの報告を鵜呑みにしてしまう失敗**：
   AIエージェントにCI結果の確認を依頼したところ、「すべてのテストに合格し、アプリケーションは完全に安全です」と回答された。しかし実際には、指定された学習用テストとは無関係なサンプルテストが動いていただけだった。

この章の目的は、テストコードをゼロから大量に書き直すことではありません。\
**「ローカル環境（Codespacesなど）ですでに動作確認を終えたテストコードを、安全にクラウド環境へ共有し、対象のプログラムとテスト結果が完全に一致していることを、誰が見ても疑いようのない客観的な証拠（コミットSHAや成果物ファイル）に基づいて証明する」**という、プロのQAエンジニアとして最も重要とされる品質保証の証拠管理スキルを習得します。

## 1. 最初にCIを実行してよい「安全条件」を確認する

### 1.1 なぜいきなりCIを動かしてはいけないのか？

M09では、無効化されたワークフロー設定ファイル（ファイル名の末尾に `.disabled` という拡張子が付いたファイル）を読み解く演習を行いました。
「早くクラウド上でテストを自動実行してみたい！」と思うかもしれませんが、**手元の設定ファイルから `.disabled` を削除して、いきなりGitHubへ送信（push）してはいけません**。

GitHub ActionsのようなクラウドCIサービスは、自分のパソコンの中ではなく、**GitHubが管理するクラウド上のサーバー（仮想マシン：Runnerと呼びます）を一時的に借りてプログラムを実行する仕組み**です。自分のパソコンでスクリプトを動かすときとは異なり、クラウド上で自動処理を動かす際には、常に次の3つの重大なリスクが伴います。

```text
クラウドCIを実行する際のリスク
├── 1. 費用のリスク（意図しない自動実行による課金・無料枠の枯渇）
├── 2. セキュリティのリスク（権限の過剰付与、APIキーやパスワードの漏洩）
└── 3. 影響範囲のリスク（他人のブランチや本番環境への予期せぬ干渉）
```

1. **費用のリスク（課金問題）**：
   GitHub Actionsの実行時間や、実行結果のファイルを保存するストレージ領域には、無料枠と有料枠が設定されています。もし設定を誤り、ファイルが1回変更されるたびに何十回も重いテストが自動起動するような設定にしてしまうと、あっという間に無料枠を使い果たし、高額な利用料金が発生する危険があります。
2. **セキュリティのリスク（秘密情報の漏洩と権限の乱用）**：
   ワークフロー設定ファイルの中に、リポジトリに対する広範な書き込み権限（`permissions: write-all` など）を与えてしまったり、外部サービスのAPIキーやパスワード（Secret）を誤って画面ログに出力するような処理が含まれていると、第三者に重大な権限を奪われる恐れがあります。
3. **影響範囲のリスク（他人の作業環境への干渉）**：
   学習用のリポジトリではなく、チームの共有リポジトリや他人の作業ブランチで不用意にCIを起動すると、他者の作業を妨害したり、意図しないデプロイ（公開処理）を実行してしまったりするリスクがあります。

### 1.2 実行前の6つのチェックリスト

ワークフローを有効化（`.disabled` を外してGitHubへpush）する前に、必ず**受講者本人のリポジトリ**において、以下の6つの安全条件を1項目ずつ自分の目で確認してください。

| チェック項目 | 確認内容と安全の基準 | なぜこれを確認するのか？ |
| --- | --- | --- |
| **1. リポジトリの種類** | 操作対象のリポジトリが、受講案内で指定された本人専用の**非公開（Private）リポジトリ**になっているか。 | 公開（Public）リポジトリで作業すると、誤ってコミットした情報が世界中に公開されてしまうため。 |
| **2. 利用枠と費用** | リポジトリの支払責任者（Billing設定）、利用する実行環境（標準の `ubuntu-latest` などのGitHub-hosted runner）、Actionsの無料実行枠の残り状況を確認できているか。 | 有料の大型Runner（Larger Runner）を無断で使用したり、利用枠を超過して意図しない課金が発生することを防ぐため。 |
| **3. 権限と秘密情報** | ワークフロー定義内に、不要な書き込み権限（`write`）が含まれておらず、必要最小限の読み取り権限（`permissions: contents: read`）になっているか。外部へのデプロイ処理やSecretの埋め込みがないか。 | 最小権限の原則（Principle of Least Privilege）を守り、万が一外部から不正なコードが混入してもリポジトリが改ざんされないようにするため。 |
| **4. 起動イベントと回数** | ワークフローがどの操作（PRの作成、コミットの追加など）をトリガー（起動条件）として、何回実行される設定になっているか。 | 意図しないイベント（ブランチ作成やタグ打ちなど）で無駄にジョブが大量起動することを防ぐため。 |
| **5. テスト対象の限定** | 実行コマンドが、今回の学習課題で指定された特定のspecファイル（テストファイル）だけに限定されているか。 | リポジトリ全体にある重い全テストスイートや、環境構築が未完了の別機能テストを動かしてエラーになるのを防ぐため。 |
| **6. 停止手順の把握** | テストが終了した後、または問題が発生した際に、不要な自動実行を確実にキャンセル・停止できる手順を把握しているか。 | 万が一無限ループや長時間の待機が発生した際に、即座にクラウドの実行を止めてリソース消費を防ぐため。 |

> **最重要：安全の判断ルール（BLOCKEDの原則）**\
> 上記の6項目のうち、**1つでも確認できない項目、あるいは不安や疑問が残る項目がある場合は、絶対にワークフローを有効化（push）してはいけません**。\
> その場合は、作業状態を「**BLOCKED（安全未確認のため作業停止）**」として学習記録に残してください。「たぶん無料枠があるだろう」「権限はよくわからないけれど動かしてみよう」といった推測での実行は、エンジニアリングの世界では重大な規約違反となります。安全が客観的に確認できるまで立ち止まることは、恥ずかしいことではなく、最も称賛されるべき正しい判断です。

### 段階練習：公開してよい差分を選び、AIに確認させる（M10-01）

#### 目的

Gitでコミットやプルリクエストを作成する前に、手元の作業ディレクトリ内にある変更差分を1ファイルずつ精査し、「リポジトリにコミット・共有してよいファイル」と「絶対に含めてはならない危険なファイル」を正しく分類できるようになる。

#### 背景：なぜ差分の精査が必要なのか？

プログラムを書いたりテストを実行したりしていると、作業ディレクトリの中には様々なファイルが自動生成されます。たとえば、テストの実行ログ、画面の録画動画、外部サービスに接続するための認証トークンが書かれた設定ファイルなどです。
これらを何も考えずにまとめてGitに追加してしまうと、**「クラウド上にパスワードを世界公開してしまう」「リポジトリのサイズが巨大化して開けなくなる」**といった重大なトラブルを引き起こします。

#### 手順

**ステップ1：specファイルの依存関係を確認する**\
選択したテストファイル（`workspace/M07/repaired-assertion.spec.ts` など）をエディタで開き、以下の構成を確認します。

- 冒頭で読み込んでいるライブラリや関数（`import { test, expect } from '@playwright/test'` など）
- テスト実行前のデータ初期化（データベースの状態を初期状態に戻すReset処理の呼び出し）
- テストケース本体（`test(...)` ブロック）と、期待される検証条件（`expect(...)` アサーション）
- 参照しているPlaywrightの設定ファイル（`playwright.ai-assisted-qa.config.ts`）

**ステップ2：Gitで現在の変更一覧を確認する**\
ターミナルを開き、以下のコマンドを実行して、作業ディレクトリ内で変更・追加されたファイルの一覧を表示します。

```bash
git status --short
git diff --cached --name-only
```

- `git status --short`：手元の作業ツリー内で「変更されたファイル」や「新しく作られた未追跡ファイル」が簡潔に一覧表示されます。
- `git diff --cached --name-only`：すでにステージングエリア（コミット準備領域）に追加されているファイルの名前だけが表示されます。

> **警告：安易なファイル消去の禁止**\
> M08で学んだ通り、不要に見えるファイルがあるからといって、理由も分からずに `git restore .` や `git clean -fd` などの強制削除コマンドを実行してはいけません。過去の重要な学習記録や設定ファイルまで消えてしまい、元に戻せなくなる危険があります。

**ステップ3：差分を「含める候補」と「除外する候補」に分類する**\
ターミナルに表示されたファイル名をエディタで1つずつ開き、内容を直接読んだうえで、以下のような分類表を作成します。

| ファイル分類 | 該当するファイル例 | PRに含めるか | 理由と判断基準 |
| --- | --- | :---: | --- |
| **学習用テストコード** | `repaired-assertion.spec.ts` | 〇 | 今回の課題で検証したいテストコード本体そのものであるため。 |
| **必要な設定ファイル** | 学習専用の `playwright.ai-assisted-qa.config.ts` | 〇 | CI上の仮想マシンでテストを実行するために不可欠な最小限の設定であるため。 |
| **環境変数・秘密情報** | `.env`, `.env.local`, `*.token`, 各種パスワード | × | 外部のクラウドや第三者に漏洩すると重大なセキュリティ事故になるため（最重要）。 |
| **重い実行生成物** | `test-results/`, `trace.zip`, 巨大なログファイル | × | Gitはテキストの履歴管理用であり、巨大な生成物を含めるとリポジトリが極端に肥大化するため。 |
| **無関係な作業ファイル** | 他のモジュールのメモ、私的な学習ノート | × | 今回のプルリクエストの目的（テストコードの検証）と関係のない変更を混入させないため。 |

**ステップ4：AIエージェントに分類の妥当性をレビューさせる**\
AIエージェント（OpenCodeなど）が利用可能な環境であれば、分類の妥当性を第三者視点でレビューさせます。このとき、**指示の範囲を明確に限定し、秘密情報やファイル本文を無防備に渡さない**ように注意します。

```text
以下のファイル一覧は、テスト自動化教材M10のプルリクエストに含める候補として受講者が分類したものです。
セキュリティ上危険なファイル（APIキー、トークン、秘密情報、不要なログ、巨大なバイナリ生成物）が含まれていないか、
学習用テストの共有として範囲が適切かを客観的にレビューしてください。
なお、ファイル自体の編集、git commit、git push、PRの作成などのコマンド操作は絶対に行わないでください。

【含める候補】
- workspace/M07/repaired-assertion.spec.ts
- .github/workflows/course-m10-test.yml（学習専用・read権限のみ）

【除外する候補】
- .env.local
- test-results/trace.zip
- personal-notes.txt
```

**ステップ5：AIの指摘と自分の分類を照合する**\
AIからの回答を確認し、自分が「含める候補」に入れたファイルの中に、うっかり秘密情報や生成バイナリが紛れ込んでいないかを再確認します。すべて安全であると確信できるまで、コミットやプッシュ、ワークフローの有効化を行ってはいけません。

#### 練習問題

**問題**：\
作業ディレクトリ内に、テストコード本体である `workspace/M07/repaired-assertion.spec.ts` と、外部サービスの認証Tokenが記載された `.env` ファイルがあります。ここで何も確認せずにターミナルで `git add -A` を実行してコミットした場合、どのような危険が生じますか？ また、安全に作業を進めるためにはどのように操作すべきですか？

#### 解答と解説

- **知識と着目点**：Gitのステージング操作（`git add`）の対象範囲と、`.gitignore`（除外設定ファイル）の役割に着目します。
- **思考の順序**：
  1. `git add -A` は、現在のディレクトリ以下にある「変更されたファイル」や「新しく作られた未追跡ファイル」を、すべて漏れなくステージング（コミット対象に登録）する非常に強力なコマンドです。
  2. もし `.env` ファイルが `.gitignore`（Gitの管理から意図的に外すファイル一覧）に登録されていなかった場合、認証Tokenが含まれた `.env` がそのままコミット対象として登録されてしまいます。
  3. そのままコミットしてGitHubへpushすると、クラウド上のリポジトリに秘密情報が送信され、リポジトリにアクセスできる人（公開リポジトリなら全世界）にTokenを盗み出される危険が生じます。
- **正解の対応**：\
  一括追加コマンド（`git add -A` や `git add .`）は使わず、**共有してよい対象ファイルだけを個別に追加**します。M07配下は配布 `.gitignore` で除外されるため、まず `git check-ignore -v -- workspace/M07/repaired-assertion.spec.ts` で除外理由を確認し、必要なspecの内容・import先・秘密情報の有無を点検してから `git add -f -- workspace/M07/repaired-assertion.spec.ts` を使います。`git add -A` で範囲を広げてはいけません。追加した後は、必ず `git diff --cached --name-only` を実行し、ステージングされたファイル一覧に `.env` などの秘密ファイルが混ざっていないことを自分の目で確認してからコミットします。

## 3. Gitの差分を確認してPR（プルリクエスト）を作る

### 3.1 差分の最終確認とコミット

#### diffと公開対象を確認する

M08で習得したGitの基本手順に沿って、プルリクエストを作成するためのコミットを準備します。

1. **作業ツリーの確認**：`git status` を実行し、どのファイルが変更されているかを把握します。
2. **個別のステージング**：共有するテストコードとCIに必要なファイルだけを指定します。M07のspecは学習用 `.gitignore` で除外されるため、 `git check-ignore -v -- workspace/M07/repaired-assertion.spec.ts` の結果を先に確認します。提出が許可されたファイルだけ `git add -f -- workspace/M07/repaired-assertion.spec.ts` で追加し、`git diff --cached --name-only` と `git diff --cached` で変更範囲を確認します。import先や実行に必要な設定は、すでに追跡されているか個別に確認し、不要なファイルは含めません。
3. **行単位の差分レビュー**：`git diff --cached` を実行し、コミットに含まれる「追加・変更された行」を上から下まで丁寧に読み通します。
   - 意図しない改行コードの変更が入っていないか。
   - デバッグ用に一時的に書き込んだ `console.log(...)` やコメントアウトが残っていないか。
   - パスワードやトークンなどの文字列が紛れ込んでいないか。
4. **コミットの実行**：差分が完全にクリーンであることを確認したうえで、変更内容が第三者に伝わる明確なコミットメッセージを添えて `git commit` を実行します。

**絶対にコミットに含めてはならないものの例**：

- APIキー、認証Token、パスワード、秘密鍵、個人情報
- PlaywrightのTraceファイル（`trace.zip`）、テスト実行時のスクリーンショット、動画ファイルなどの生成バイナリ
- 他の学習モジュールの作業成果物や、今回の課題と関係のない別機能のコード

### 3.2 プルリクエストに記録すべき6つの項目

コミットを作成し、自分の作業ブランチから非公開学習リポジトリへpushしたら、GitHub上でプルリクエスト（PR）を作成します。\
プルリクエストの説明文（Description）には、後から第三者のエンジニアやAIエージェントがレビューできるように、以下の6項目を客観的事実に基づいて記載します。

| 記録項目 | 記載内容の目的 | 具体的な記載例 |
| --- | --- | --- |
| **1. 変更の目的** | なぜこの変更を行うのか（背景とゴール） | M07で修正したカート数量バリデーションのテストをCI環境で自動検証可能にするため |
| **2. 仕様の根拠** | どの仕様書・業務要件に基づくテストなのか | 対象specのテストケースから確認した `docs/spec/features/cart.md` の該当要件（例：数量上限の確認なら `BR-CART-001`、`AC-CART-001`） |
| **3. 対象ファイルのパス** | 実際にコミットした正確なファイルパス | `workspace/M07/repaired-assertion.spec.ts` |
| **4. ローカルでの検証結果** | 自分のCodespaceやローカルPCでどう動いたか | `pnpm course:run M07 repaired-assertion.spec.ts --label after` など、**実際に実行した**新課程専用コマンド、Run ID、検証済み結果（PASS/FAIL）を記載する。実行前なら正直に「未実行」と記載する |
| **5. CIで確認すること** | クラウドCIに何を期待しているのか | 指定した作業ブランチの最新コミット（HEAD）において、指定specがUbuntu/Chromium環境でPASSすること |
| **6. 未確認事項** | 現時点で「何がまだ言えないか」（品質の限界） | クラウド上の実際のRunは未取得。FirefoxやWebKitなど他ブラウザ環境での動作は未検証 |

> **注意：PRの作成と品質証明の混同を防ぐ**\
> プルリクエストを作成した時点では、まだCIによるテストは実行中か、あるいは開始すらされていません。「PRを作成した」という事実と、「CIによって品質が客観的に証明された」という事実は全く別物です。PRを作っただけで満足して作業を完了扱いにしないよう注意してください。

## 4. 専用ワークフローを安全に有効化する

### 4.1 なぜ`.disabled`がついているのか？

この課程のM09で修正した無効なworkflow案は `workspace/M09/course-e2e.workflow.yml.disabled`、完成見本は `course/templates/phase3/course-e2e.workflow.yml.disabled` です。M09の案またはM10公開fallbackを参照し、**本人の学習用リポジトリ**で必要事項を確認してから利用します。Template側の `.github/workflows/` へ自動的に配置・有効化されるものではありません。

GitHub Actionsは、リポジトリ内の `.github/workflows/` ディレクトリ配下に置かれた `.yml` または `.yaml` ファイルを正規のワークフロー定義として自動認識します。ファイル名の末尾に `.disabled` を付けておくことで、GitHub Actionsの検知システムから一時的に隠し、意図しない自動起動を防いでいるのです。

手元で `.disabled` を外して `.github/workflows/` にファイルを置いただけでは、GitHub側のCIは起動しません。正しいブランチへ変更をcommit・pushし、GitHubで `pull_request` など設定されたイベントが成立し、Actionsが許可されて初めてRunの作成対象になります。イベントと権限を確認し、実際にRunが存在するか確認してください。

有効化する前に、変更前後の差分（diff）を開き、以下の**6つの機械契約**が満たされていることを確認してください。

```text
ワークフロー有効化前の「6つの機械契約」チェック
├── 1. 最小権限の指定（permissions: contents: read が明示されているか）
├── 2. 外部依存の排除（デプロイ処理やSecret要求が含まれていないか）
├── 3. テスト対象の限定（学習用の指定specのみを実行するコマンドか）
├── 4. コミットの取得方法（PRの最新コミットを正しくcheckoutしているか）
├── 5. SHAの記録と保存（target-sha.txt を書き出してArtifactに保存しているか）
└── 6. レポートの保存（PlaywrightのJSONレポートをArtifactに保存しているか）
```

1. **最小権限の指定**：`permissions: contents: read` が明示されており、不要な `write` 権限が含まれていないこと。
2. **外部依存の排除**：外部サーバーへのデプロイ（deploy）処理や、Secret変数の入力を要求していないこと。
3. **テスト対象の限定**：実行コマンドが、学習対象の専用specファイルのみをターゲットにしていること。
4. **コミットのチェックアウト方法**：対象PRの先端コミット（head SHA）を正しく取得（checkout）する設定になっていること。
5. **SHAの記録と保存**：チェックアウトした正確なコミットSHAを `target-sha.txt` として書き出し、Artifactに保存するステップが存在すること。
6. **レポートの保存**：PlaywrightのJSON実行結果レポートを同じRunからArtifactとしてダウンロードできること。

### M09から引き継ぐ完成見本の確認

M09の公開完成見本は、M10の正式評価器と同じ契約に従う必要があります。次の条件を実ファイルで確認してください。

- テストコマンド：`pnpm run training:ai-assisted-qa:test -- workspace/M07/repaired-assertion.spec.ts`。`PLAYWRIGHT_TEST_ROOT` は `workspace/M07` です。M07の故意FAIL用specを含むディレクトリ全体を実行しません。

## 5. PR headとRunの対象を照合する

### 5.1 なぜコミットSHA（ハッシュ値）が必要なのか？

Gitのコミットは、その時点のファイル内容や履歴を識別するための40桁の英数字（**コミットSHA**、またはハッシュ値）を持ちます（例: `44b9e214a765a0ee4f25ec996d801ea046199a60`）。

プルリクエスト（PR）を作成したあとも、コードを修正して新しくpushするたびに、PRの先端コミット（**PR head SHA**）は新しい値へと更新されます。

ここに、初心者が見落としやすい最大の落とし穴があります。
**「以前のCI実行（Run）が緑色（成功）だったとしても、それは現在の最新コミット（PR head）で成功した証拠とは限らない」**ということです。

さらに、GitHub Actionsの `pull_request` イベントでは、PRの先端コミット（head SHA）をそのままテストする場合と、GitHubが自動生成したマージ用コミット（merge SHA）をテストする場合があります。そのため、画面に表示されているSHAの意味を正しく理解し、区別する必要があります。

### 5.2 整合性を証明するための「6点セット」

#### 対象shaとrunの証拠を照合する

![PR・head SHA・Run・Check・Artifactの対応](../../assets/figures/M10/01-pr-evidence-map.svg)

本カリキュラムでは、CIの成功を客観的に証明するために、次の6つの情報がすべて1本の線でつながっていることを確認します。

```text
[1. 現在のPR head SHA]
        │ 一致しているか？
        ▼
[2. 該当PRから起動したActions RunのIDとステータス]
        │
        ├─► [3. 同じRunのCheck結果（PASS / FAIL）]
        │
        └─► [4. ワークフローが実際にチェックアウトした target SHA]
                │ 一致しているか？
                ▼
        [5. Artifact内の target-sha.txt に記録されたSHA]
                │ 同じRunの成果物か？
                ▼
        [6. Artifact内の Playwright JSONレポート（テスト対象specと結果）]
```

> **最重要ルール**\
> **現在のPR head SHAと、ダウンロードしたArtifact内の `target-sha.txt` に記録されたSHAが一致しない場合、そのArtifactを「現在のコードが成功した証拠」として扱ってはいけません。**\
> 古いコミットに対する成功ログは、最新コミットの品質を何も保証していないためです。

### 5.3 古いRunを使えない具体例（時系列で考える）

理解を深めるために、時系列で起きた出来事を追ってみましょう。

- **10:00**：受講者がコミット `AAA` をpushし、PRを作成した。CIが走り、テストが**PASS（成功）**した（Run 101）。
- **10:15**：コードのタイポに気づき、微修正したコミット `BBB` をpushした。PRのheadは `BBB` に変わった。
- **10:20**：受講者がGitHubのPR画面を開いたところ、画面には先ほどの「Run 101の緑色のチェック（PASS）」がまだ残っていた。

この10:20の時点で、「CIが成功しているから大丈夫です！」と報告してよいでしょうか？

**答えは「×（ダメ）」です。**\
成功しているRun 101は、古いコミット `AAA` に対する結果です。新しくpushされたコミット `BBB` に対してCIがまだ完了していないのであれば、現在の状態は「**現在HEADに対するCIは未確認**」と報告しなければなりません。「画面に緑のマークが見えた」という主観的な印象と、「最新のコミットに対する検証結果が存在する」という客観的な証拠は、明確に区別してください。

## 6. 失敗・未実行・環境差を正確に切り分ける

### 6.1 最初の失敗ステップから調べる原則

#### ci失敗の最初の段階を分類する

CIが赤色（FAIL）になったとき、慌ててテストコードの `expect(...)` を書き換えたり、製品コードをあてずっぽうで直したりしてはいけません。
CIの実行ログを開き、**「どのステップで最初に失敗したか」**を上から順に確認します。

| 失敗した段階 | ログの兆候 | 正しい状況報告 | 次に調べるべき原因 | やってはいけない誤った対応 |
| --- | --- | --- | --- | --- |
| **依存関係の導入** | `pnpm install` でエラー、テスト未開始 | 依存ライブラリの導入失敗により、テストは未実行 | Node.jsやpnpmのバージョン、ネットワーク、`pnpm-lock.yaml` の不整合 | テストコードのアサーションを疑う、製品コードを書き換える |
| **ブラウザの準備** | `playwright install` で失敗、ブラウザ起動エラー | 実行環境の構築失敗、テストは未実行 | 必要なブラウザバイナリの不足、OS環境依存 | テストのタイムアウト時間を無暗に延ばす |
| **テストの実行** | Playwrightの `expect` でエラー | 対象テストケースがFAIL、原因調査中 | 画面仕様、セレクタ（Locator）、データ初期化（Reset）、期待値の誤り | 仕様の根拠なしにアサーションを削って無理やり通す |
| **成果物の保存** | テストはPASSしたが `upload-artifact` でエラー | テスト自体は成功、ただし証拠の保全に失敗 | 保存対象パスの誤り、ワークフローの権限不足 | 証拠ファイルが保存できていないのに完了扱いにする |
| **ワークフロー未起動** | ActionsタブにRun自体が現れない | CI未実行 | トリガーイベントの設定ミス、ブランチ名やパスの不一致 | 存在しない成功画面を想像で報告する |
| **SHAの不一致** | CheckはPASSだが、ArtifactのSHAが古い | 現在の最新コミットに対する検証証拠なし | 最新コミットに対する再実行の有無、チェックアウト設定 | 古いコミットの成功ログを最新の証拠として提出する |

### 6.2 「ローカルでは通るのにCIで落ちる」ときの考え方

「自分のPCでは成功したのに、GitHubのCIでは失敗する」という現象は、テスト自動化で非常によく発生します。
このとき、「CIがおかしい」「たまたま運が悪かった」と片付けてはいけません。必ず**実行環境の差**が存在します。

比較すべき主なポイント：

- **Node.jsやパッケージのバージョン差**（ローカルとCIのRunnerでバージョンがずれていないか）
- **画面描画とタイムゾーン・言語設定の差**（ヘッドレスブラウザの解像度や日本語フォントの有無）
- **待機条件（非同期処理）の差**（クラウドの非力なマシンでは通信や画面描画に時間がかかるため、適切なLocator待機ができているか）
- **テストデータの初期状態**（ローカルのブラウザに残ったCookieやストレージ、前回のテストデータが影響していないか）

M07で学んだ通り、原因を突き止めずに安易に `page.waitForTimeout(5000)` を追加したり、リトライ回数を増やしたりして一時的に成功させても、本質的な品質保証にはなりません。

## 7. 実行を止める・後片付けをする

### 7.1 なぜ後片付けが必要なのか？

学習用のワークフローを動かしたあと、不要になった自動実行設定を放置してはいけません。
ブラウザのタブを閉じても、GitHubのサーバー上で動いているCIや、今後のpushを待ち受けているトリガー設定は消えません。

不要なコミットやブランチの更新があるたびにCIが動き続けると、貴重な実行可能時間を消費し続けます。

### 7.2 安全な停止と運用のルール

1. **実行中の不要なRunの停止**：誤って大量のジョブを起動してしまった場合は、Actions画面から「Cancel run」を選択して停止します。
2. **トリガーの停止**：学習演習が完了した後は、ワークフローファイルを削除するか、再度 `.disabled` などの無効化状態に戻す運用ルールを確認します。
3. **操作範囲の厳守**：停止や設定変更を行う対象は、**受講者本人の学習用リポジトリのみ**です。チームの共有リポジトリや他人の作業を勝手に停止・変更してはいけません。
4. **未実行状態の記録**：リソース節約のために一部のテスト実行を意図的に停止した場合は、「どの検証が未実行のままであるか」とその理由を学習記録に必ず残します。**節約を理由に必要な品質確認を無断で省き、すべて完了したかのように報告することは禁止**されています。

## 8. AIの提案を客観的にレビューする

### 8.1 AIの誤った提案を見抜く

AIエージェント（OpenCodeなど）と協働していると、AIが非常に魅力的に見える提案をしてくることがあります。しかし、その提案が品質保証の原則やセキュリティ規約に違反していないかを判断するのは、人間のエンジニアの役割です。

よくあるAIの危険な提案例と、その対処法：

| AIの危険な提案 | AIが主張する理由 | なぜ却下すべきか（リスク） | エンジニアの正しい判断 |
| --- | --- | --- | --- |
| 「CIを高速化するため、ブラウザのインストールを省きましょう」 | 実行時間が短縮されます | ブラウザが存在しないためテストが起動できず、テスト未実行のまま終了してしまう | 却下。テスト実行に必要な依存関係のセットアップは必須 |
| 「権限エラーが出ないよう、permissionsを `write-all` に変更しましょう」 | 権限不足によるエラーを防げます | リポジトリに対する過剰な書き込み権限を与えてしまい、セキュリティ事故の元凶になる | 却下。必要最小限の `contents: read` を維持する |
| 「Artifactのダウンロード確認は手間なので、Actions画面の緑色のCheckだけを成功の証拠にしましょう」 | 手順が簡単になります | 画面のCheckが古いコミットやmergeコミットの結果である可能性を排除できず、証拠能力を失う | 却下。Artifact内の `target-sha.txt` とPlaywrightレポートを照合して初めて証明となる |
| 「テスト対象を絞るため、指定された学習specだけを直接実行するコマンドに変更しましょう」 | 不要なテストをスキップして効率化できます | カリキュラムの学習契約および検証範囲と完全に一致している | **採用**。安全・迅速に必要な対象だけを検証する適切な提案 |

### 8.1.1 Artifactを取得して中身を確認する

ここでいうArtifactは、GitHub Actionsの実行結果として保存されたファイル群です。「Runが成功した」と「必要なArtifactが存在し、現在のPR headの証拠である」は別です。

1. 本人のリポジトリのGitHubで**Actions**を開き、対象の専用workflowとRunを選びます。Run IDとworkflow名を控えます。
2. Run詳細で、そのRunに紐付いた**Artifacts**を探します。画面表示はGitHubのUI更新や権限で変わるため、名称が見当たらない場合はRunとアクセス権を先に確認します。
3. 正式演習で指定されたArtifactをダウンロードできる場合は、Zipをローカルまたは許可された演習環境内で展開します。Secretを含むファイルを外部のAIサービスへ送らないでください。
4. `target-sha.txt` を開き、記録されているSHAの値をコピーして、**現在のPR head SHA（原則40桁）**と完全一致するか照合します。
5. PlaywrightのJSON reportや必要な証拠ファイルがあるか、対象spec・結果・失敗情報を確認します。Checkが別のRunを指していないかも調べます。
6. Artifactが見つからない、権限がない、ダウンロードができない場合は**未確認**として記録します。別RunのArtifactで代用してはいけません。

**解答付き練習**：Run 501のCheckが成功でも、ダウンロードしたArtifactの `target-sha.txt` が現在のPR headと異なる場合は修了証拠として使えますか？\
**解答**：使えません。対象SHAが一致しないことが確認できています。次に現在headに対するRun/Check/Artifactを探し、存在しなければ未確認と記録します。

### 8.2 実践：実Runの証拠を照合し、AI報告と比較する（M10-03〜M10-05）

#### 結果と未確認事項を報告する

![PRと実CI証拠を照合する手順](../../assets/figures/M10/02-handoff.svg)

#### 手順

1. **証拠対照表の作成**：\
   GitHubの画面とダウンロードした成果物を開き、以下の表を埋めます。

   | 項目 | 確認した値 / 状態 | 確認元 |
   | --- | --- | --- |
   | PR番号 | #〇 | GitHub PR画面 |
   | 現在のPR head SHA | 40桁の英数字（例: `abc123...`） | GitログまたはPR先端コミット表示 |
   | Actions Run ID | 数値（例: `1234567890`） | Actionsの実行URL・画面 |
   | Checkの最終結果 | PASS または FAIL | Actionsジョブのステータス |
   | チェックアウトされた target SHA | 40桁の英数字 | ワークフローのCheckoutステップのログ |
   | Artifact内の `target-sha.txt` | 40桁の英数字 | ダウンロードしたファイルの中身 |
   | Playwright JSONレポート結果 | PASS または FAIL、対象テスト名 | ダウンロードしたJSONファイルの中身 |

2. **整合性の判定**：\
   - 「現在のPR head SHA」と「Artifact内の `target-sha.txt`」が**完全一致**しているか。
   - PlaywrightのJSONレポートで、指定されたspecファイルが実際に実行され、PASSしているか。
   - 両方が満たされて初めて、「現在のコミットに対するCI検証成功」と判定します。
3. **AIへの事実確認依頼**：\
   AIエージェントに分析を依頼する場合は、秘密情報を含めず、推測による補完を禁止する指示を与えます。

   ```text
   以下の確認結果の表に基づいて、客観的な事実のみを分析してください。
   確認できている事項、まだ確認できていない未確認事項、および不一致があれば具体的に指摘してください。
   不明なハッシュ値やRun IDを推測で補完しないでください。

   【確認結果】
   - PR番号: #12
   - 現在のPR head SHA: e5f6a7b...
   - Actions Run ID: 987654321
   - Check結果: 成功（緑色）
   - Artifact内の target-sha.txt: c1d2e3f...（前回のコミットのSHA）
   - Playwright実行結果: 1 passed
   ```

4. **AIの回答の検証**：\
   AIが「すべて成功しているので問題ありません」と回答した場合、それは**誤り**です。\
   受講者本人が「Checkは成功しているが、ArtifactのSHAが古いコミット（`c1d2e3f...`）のままであり、現在のhead（`e5f6a7b...`）に対する成功証拠ではない」と正しく看破し、AIの誤りを却下しなければなりません。
5. **記録の保存**：\
   正式な証拠識別情報を `workspace/M10/ci-run-evidence.json` へ正しく記録します。

### 別条件で考える練習問題

#### 別条件問題A

**状況**：\
PRに修正コミットを追加したため、PRのhead SHAが `AAA` に更新されました。しかし、手元にあるCIのArtifactに含まれる `target-sha.txt` を開くと、更新前の古いコミット `BBB` の値が記載されていました。GitHub上のCheck表示は緑色（成功）のままです。このとき、受講者としてどのような報告を行うべきですか？

#### 解答と解説：別条件問題B

- **着目すべき条件**：PR headが最新の `AAA` であるのに対し、手元の証拠が旧コミット `BBB` のものである点に着目します。
- **思考の順序**：
  1. Check表示が緑色なのは、旧コミット `BBB` に対して実行された過去のRunが成功したためです。
  2. 新しいコミット `AAA` でコードが変わっている以上、`BBB` での成功は `AAA` でも動く保証にはなりません。
  3. `AAA` に対する新たなRunがまだ完了していない、あるいはArtifactを取得していない状態です。
- **正解の報告**：\
  「旧コミット `BBB` での成功記録はありますが、現在のPR head `AAA` に対するCI検証結果は**未確認**です。」と報告します。`AAA` に対応する新しいRunを起動・取得できるか、リポジトリの利用条件と費用を確認して再実行を判断します。（※なお、`AAA` や `BBB` は説明用の仮の表記です）

#### 別条件問題B

**状況**：\
CIの実行が途中で赤色（FAIL）になりました。ログを見ると「依存関係のセットアップ（`pnpm install`）」のステップでネットワークエラーが発生して停止しており、Playwrightのテストステップは開始されていませんでした。しかし、AIエージェントに状況を要約させたところ、「カート機能の数量アサーションが失敗しました。テストコードのアサーションを修正しましょう」と提案してきました。この提案をどう扱いますか？

#### 解答と解説：別条件問題C

- **着目すべき条件**：CIの失敗ステップが「依存関係の導入」であり、テスト実行ステップにそもそも到達していない点に着目します。
- **思考の順序**：
  1. ログ上の客観的事実は、`pnpm install` が失敗したことです。
  2. テストコマンド自体が1行も実行されていないため、カートの数量アサーションが成功したか失敗したかは誰にもわかりません。
  3. AIは「テスト自動化の課題だからアサーションが落ちたのだろう」と、ログを読まずに推測で嘘の理由をもっともらしく作成してしまっています（ハルシネーション）。
- **正解の対応**：\
  AIの提案は根拠のない誤りであるため**即座に却下**します。「確認された事実は依存関係インストールの失敗であり、テストは未実行である」と報告します。調査すべき対象はテストコードではなく、Node.js/pnpmの環境設定、通信状態、または `pnpm-lock.yaml` の状態です。

#### 別条件問題C

**状況**：\
専用ワークフローのCIが正常に完了し、最新のコミットSHAと一致するArtifact（PlaywrightのPASSレポート）も無事に取得できました。この証拠をもって、「ECサイトの購入機能は、すべてのブラウザや実機スマートフォンにおいて完全に不具合がないと保証された」と報告してよいでしょうか？

#### 解答と解説

- **着目すべき条件**：自動テストが保証できる「対象範囲（スコープ）」の限界に着目します。
- **思考の順序**：
  1. 今回の専用CIで実行したのは、特定のブラウザ（例: Chromium）上で、指定された一部のテストケース（spec）のみです。
  2. FirefoxやSafari（WebKit）、実機のスマートフォン（Android/iOS）での動作は今回のCIジョブには含まれていません。
  3. テストがPASSしたことは、「そのテストケースに書かれた操作と検証の範囲において期待通り動いた」という事実を示すのみであり、未テストの条件（別のユーザー権限、極端な通信遅延、画面レイアウト崩れなど）まで保証するものではありません。
- **正解**：\
  **断定してはいけません。**\
  「今回実行した環境（Ubuntu / Chromium）および指定されたテストケース（カート数量バリデーション）の範囲においてPASSしたことを確認した。ただし、未検証のブラウザ環境や別機能、実機端末における動作は未確認であり、残リスクとして別途検証が必要である」と、**確認できた範囲と未確認の範囲を明確に分けて報告**するのが正しい品質保証の姿勢です。

## 9. さらに理解を深める：実際のCI証拠から何を言えるか

### 9.1 「緑のマークを探すこと」がゴールではない

テスト自動化の学習を始めたばかりの受講者が最も陥りやすい誤解は、「GitHubの画面で緑のチェックマーク（PASS）が出れば、それでテスト自動化は成功だ」と考えてしまうことです。

しかし、現場の開発・運用において問われるのは、緑のマークそのものではなく、**「その緑のマークは、誰が、どのコードの版に対して、どういう環境で実行させた結果なのか？」というトレーサビリティ（追跡可能性）**です。

- 別のブランチで動いた結果ではないか？
- 1つ前のコミットで動いた結果ではないか？
- テストコードの一部がコメントアウトされて、アサーションを通らないままPASSになっていないか？

M10の総合演習を通じて、「緑色だからOK」という直感的な判断から脱却し、「コミットSHA、実行ID、テスト対象、ログ内容の4点が揃っているから品質が証明できている」と根拠を持って語れるエンジニアになりましょう。

### 9.2 CIの実行ステップとトラブルシューティング詳細

CIワークフローが失敗した際は、以下のフローに従って原因を切り分けます。

```text
[CI失敗の発生]
       │
       ├─► 1. checkout で失敗しているか？
       │      └─► 原因: ブランチ名・コミットSHAの指定ミス、権限不足
       │      └─► 対策: ref指定の見直し、permissionsの確認
       │
       ├─► 2. 依存関係のセットアップ（Node/pnpm）で失敗しているか？
       │      └─► 原因: lockfileの不整合、ネットワーク切断、キャッシュ破損
       │      └─► 対策: lockfileの更新、環境変数の確認
       │
       ├─► 3. ブラウザのセットアップで失敗しているか？
       │      └─► 原因: Playwrightのブラウザインストールコマンド（playwright install）の欠落
       │      └─► 対策: ワークフローへのステップ追加、OS依存パッケージの確認
       │
       ├─► 4. ローカルサーバーの起動（Serve）で失敗しているか？
       │      └─► 原因: ポートの競合、起動待機時間の不足、モックデータの読み込み失敗
       │      └─► 対策: ポート番号の確認、wait-on等の待機ステップ確認
       │
       ├─► 5. テストのアサーション（expect）で失敗しているか？
       │      └─► 原因: アサーションの期待値と画面仕様の不一致、セレクタ変更、タイミング問題
       │      └─► 対策: Traceログやスクリーンショットの確認、M07の仕様書照合
       │
       └─► 6. Artifactのアップロードで失敗しているか？
              └─► 原因: 出力パスの指定ミス、テスト失敗による後続ステップの中断
              └─► 対策: if: always() の指定、アップロード対象ディレクトリの確認
```

## 10. 理解度を確認する章末問題（全12問・詳細解説付き）

### 問題1

**問題**：PRの最新のコミットSHAが `B` です。GitHubのActions画面を探したところ、1つ前のコミット `A` で成功（緑色）したCheckしか見つかりませんでした。このとき、受講者としてレビュー担当者にどのような状態を報告すべきですか？

#### 解説

- **着目点**：最新の変更点 `B` に対するテスト証拠が存在するかどうか。
- **思考順序**：コミット `A` から `B` にコードが変更されている以上、`A` の成功結果をそのまま `B` に流用することはできません。`B` に対するRunが未実行、あるいは実行中であるため、`B` の品質は現時点では保証されていません。
- **解答**：最新コミット `B` に対するCI結果は「**未確認**」と報告します。`A` の成功結果を `B` の成功証拠として代用することはできません。`B` で再実行が可能かどうか、リポジトリの利用枠や費用を確認したうえで再実行を判断します。

### 問題2

**問題**：CIの実行ログからダウンロードしたArtifact内の `target-sha.txt` は、現在のPR head SHAと完全に一致していました。しかし、同じArtifactに含まれるPlaywrightのテストレポート（JSON）を開くと、1件のアサーションが `failed` になっていました。この状態を「CIによる品質確認の成功」と言えますか？

#### 解説

- **着目点**：検証対象のバージョン一致と、テスト結果自体の合否を区別できるか。
- **思考順序**：コミットSHAが一致しているため、「最新のコードに対してテストが実行された」という対象の対応関係は証明されています。しかし、テストの結果自体がFAIL（失敗）しているため、品質基準を満たしていません。
- **解答**：**成功とは言えません。** 検証対象のコミットは最新のものであると確認できましたが、テスト結果自体は「失敗（FAIL）」です。ログやTraceを確認し、最初に失敗したテストステップとアサーションの原因を調査する必要があります。

### 問題3

**問題**：GitHubのPR画面上で、CIジョブのCheckマークが緑色（成功）になりました。しかし、成果物（Artifact）のダウンロードを試みたところ、保存期間切れまたは設定ミスにより、Artifactファイルが保存されていませんでした。正式な評価課題の提出証拠として十分ですか？

#### 解説

- **着目点**：客観的な証拠（Artifact内のレポートやSHAファイル）の必要性。
- **思考順序**：本カリキュラムの学習契約では、画面のマークだけでなく、ダウンロード可能なArtifact内に「対象SHA（`target-sha.txt`）」と「Playwright実行結果（JSON）」が存在し、それらが一致していることを修了要件としています。証拠ファイルが手元に保全できなければ、第三者による再現検証ができません。
- **解答**：**不十分です（そろっていません）。** 正式評価においてRun、Check、Artifactの一致と提出を要求している場合、Artifactが存在しない状態では完了扱いにはできません。ワークフローのアップロードステップ、保存先パス、保存期間、実行権限を確認し、正しくArtifactが取得できる状態で再実行する必要があります。

### 問題4

**問題**：PRの画面上で確認したコミットSHAと、ActionsのRun画面に表示されているSHAの文字列が異なっていました。この事実だけで、直ちに「このRunは全く関係のない不正な実行である」と断定してよいでしょうか？

#### 解説

- **着目点**：GitHub Actionsの `pull_request` イベントにおける内部仕様（merge commit）。
- **思考順序**：GitHubの `pull_request` イベントでは、ブランチの先端コミット（head SHA）のほかに、ベースブランチ（mainなど）とマージした結果をシミュレーションするためのマージ用コミット（`refs/pull/:id/merge`）がGitHubによって自動作成され、そのSHAでRunが動く仕様があります。
- **解答**：**直ちには断定できません。** 単に文字列が異なるからといって直ちに不正と決めつけるのではなく、ワークフローが実際にチェックアウトした対象refと、Artifact内の `target-sha.txt` に記録されたSHAを確認します。その実行がPRの先端コミットを正しく検証したものであるかどうかを、ログと設定から客観的に判断します。

### 問題5

**問題**：CIの実行ログを確認したところ、テスト実行前の `pnpm run build` ステップがエラー（FAIL）で終了し、後続の `playwright test` ステップには「Skipped」と表示されていました。このとき、報告書に「Playwrightのテストが失敗した」と書くのはなぜ誤りですか？

#### 解説

- **着目点**：パイプラインにおけるステップの依存関係と、テスト実行の有無。
- **思考順序**：ビルドステップが失敗したため、CIはそこで異常終了し、後続のテストコマンドは実行すらされていません（未実行）。テストが実行されていない以上、テスト自体が成功したか失敗したかは不明です。
- **解答**：**テスト自体は1件も実行されていないためです。** 正しくは「ビルドステップの失敗により、テストは未実行のまま終了した」と報告します。テストコードに原因があるかのように誤認させる報告を避け、ビルドエラーのログを調査する必要があります。

### 問題6

**問題**：Actionsの最新のRunはすべて緑色（成功）で終了しており、Artifactも取得できました。しかし、実行ログをよく読むと、実行されたspecファイルは `sample-hello.spec.ts` という別のサンプルファイルであり、今回提出すべき学習用specではありませんでした。この課題を確認済みとして完了してよいですか？

#### 解説

- **着目点**：CIの成否だけでなく、「検証対象のテストケースが正しいか」の確認。
- **思考順序**：CIがどれほど綺麗に緑色になっていても、実行された内容が指定の学習課題と無関係であれば、課題を達成した証拠にはなりません。
- **解答**：**完了にはできません。** CIが実行したテスト対象ファイルが学習課題と異なるため、今回提出すべき正式なspecファイル（M07本人成果物またはM10公開fallback）を対象として実行したRunを改めて取得する必要があります。

### 問題7

**問題**：AIエージェントにCIの最適化を相談したところ、「テスト時間を30秒短縮するために、セキュリティ脆弱性を検査するステップ（lintやsecurity check）を削除しましょう」と提案されました。この提案をどのように判断すべきですか？

#### 解説

- **着目点**：高速化と品質ゲート（Quality Gate）のトレードオフ。
- **思考順序**：CIの目的は単に速く終わらせることではなく、必要な品質や安全基準を自動的に保証することです。速度向上のために必要なセキュリティ検査を無断で削ることは、品質保証の目的に反します。
- **解答**：**提案を却下します。** 単に実行速度が速くなるからといって、安全性を担保するための品質ゲートを削除することは認められません。セキュリティ検証やリンターはリポジトリの安全を守るための必須ゲートであるため維持し、高速化が必要な場合はキャッシュの活用など安全な手段を検討します。

### 問題8

**問題**：作成した自動テストがすべてPASS（100%成功）しました。この結果をもって、「このECサイトを利用するあらゆるユーザーの全操作において、不具合は絶対に起きない」と断定できますか？

#### 解説

- **着目点**：ソフトウェアテストの基本原則（テストは欠陥があることは示せるが、欠陥がないことは証明できない）。
- **思考順序**：自動テストは、テストコードとしてあらかじめ記述された「特定の操作手順」「特定のデータ」「特定の検証条件」に合致する範囲のみを機械的に確認するものです。未知の操作順序、未検証のブラウザ・端末、想定外の通信エラーなど、テストコードに含まれていない無数の条件下での正常性を保証することは不可能です。
- **解答**：**断定できません。** テストが成功したことは、「テストコードが対象とした特定のケースとアサーションの範囲内において期待通り動作した」という事実を示すのみです。未検証の端末、異なるユーザー権限、極端な通信環境、未確認の境界値など、潜在的なリスクが依然として存在することを前提として報告する必要があります。

### 問題9

**問題**：クラウドの実行時間を短縮したいと考えました。受講者の自己判断で、リポジトリの管理者に無断でより高性能な有料の大型Runner（Larger Runner）を選択してCIを実行してもよいでしょうか？

#### 解説

- **着目点**：クラウドリソースの利用権限と費用の管理規約。
- **思考順序**：高性能なRunnerは追加の利用料金が発生します。リポジトリの支払い責任者（組織や管理者）の承認を得ずに有料リソースを消費することは、重大なコンプライアンス違反・規約違反となります。
- **解答**：**いけません（禁止です）。** クラウドサービスの利用条件、支払責任者、課金ルールを遵守し、管理者の明示的な承認や事前の合意がない限り、有料リソースや大型Runnerを勝手に選択して実行してはいけません。

### 問題10

**問題**：演習がすべて終了し、必要なログや成果物の取得も完了しました。しかし、その後もブランチへのコミットやPRの更新を行うたびに、学習用ワークフローが自動的に何度も起動し続けています。次に取るべき適切な対応は何ですか？

#### 解説

- **着目点**：リソースの節約とワークフローの適切な後片付け手順。
- **思考順序**：演習が完了した後に不要な自動実行が続くと、無料枠を無駄に消費し、他の作業の妨げになります。リポジトリの運用手順に従い、自動トリガーを止める対応が必要です。
- **解答**：学習用リポジトリの運用手順を確認し、ワークフローファイルを削除するか、再度 `.disabled` などの無効化状態に変更して、不要な自動実行を停止します。変更内容と今後の影響を記録に残します。

### 問題11

**問題**：ある受講者が提出した報告書に「すべてのテストケースに成功しました」と書かれていました。しかし添付された実行ログを詳細に確認すると、定義されていた全4件のテストのうち、実行されたのは3件だけで、残る1件は条件分岐により未実行（スキップ）になっていました。この報告書をどのように修正すべきですか？

#### 解説

- **着目点**：部分成功と未実行の正確な分離、事実に基づいた報告。
- **思考順序**：未実行のテストケースは「成功」ではありません。実行された3件がPASSした事実と、1件が未実行である事実を正確に区別して報告する必要があります。
- **解答**：「実行した3件のテストケースは成功、残る1件は未実行（スキップ）」と明確に事実を分離して記載を修正します。さらに、なぜ1件が未実行になったのかの理由と、それによる残存リスクを報告書に追記します。

### 問題12

**問題**：AIエージェントが作成した報告書の中に、「Actions Run ID: 12345678」という実行結果へのリンクが記載されていました。しかし受講者がGitHubのActionsタブでそのIDを検索したところ、該当する実行記録はリポジトリ内に一切存在しませんでした。この報告書をどう扱いますか？

#### 解説

- **着目点**：AIが生成する架空の数値やハッシュ値（ハルシネーション）の検証。
- **思考順序**：AIは時として、実在しないURLやIDをもっともらしく捏造して出力することがあります。実在しないIDを根拠にした報告書は、品質保証の証拠としての価値を持ちません。
- **解答**：**実在しない架空の証拠として扱い、報告書を採用しません。** 対象リポジトリの実際のActions画面を自分の目で確認し、本人が実際に実行して取得した正しいRun URLおよびRun IDに差し替えて報告書を修正します。実在が確認できないデータは「未確認」として扱います。

## 11. Phase 3の提出と正式修了評価

### 11.1 正式提出用ファイル `ci-run-evidence.json` の仕様

Phase 3の正式修了評価を受ける受講者は、取得した客観的な検証証拠を `workspace/M10/ci-run-evidence.json` に正確に記録して提出します。

このファイルには、以下のキーを含む指定の契約フォーマットに従って値を設定します（※実際の提出値は受講者本人のリポジトリの値を記録してください）。

- 本人の非公開リポジトリ識別子
- プルリクエスト番号
- 最新のPR head SHA
- 該当するActions Run ID
- 選択したspecのファイルパス

> **セキュリティの厳格な制約**\
> GitHub APIを利用するためにアクセストークン（PAT等）を取り扱う場合、対象リポジトリへの**必要最小限の読み取り権限（Read-only）**に限定し、環境変数経由でのみツールに渡してください。\
> **トークン文字列をファイル本文、提出用JSON、Gitのコミット、またはAIへのプロンプトの中に直接書き込むことは固く禁止されています。**

### 11.2 公開評価基準（ルーブリック）に沿った最終報告

受講者は、公開されている [Phase 3評価基準](../../../../../training/ai-assisted-qa-course/assessment/phase-3-rubric.md) に照らし合わせて、以下の6つの観点から自分の成果物を論理的に説明できる状態を目指します。

| 報告の観点 | 具体的に説明・証明すべき内容 |
| --- | --- |
| **1. 変更内容と差分** | どのテストケース（BR/AC）を対象とし、どのファイルをコミット・PRに含めたか（不要なファイルを除外できたか） |
| **2. 検証環境** | 使用したOS（Ubuntu等）、Node.js/pnpmのバージョン、テストサーバーの起動条件 |
| **3. 実行対象の一致** | PRの先端コミット（head SHA）と、実際にCIがチェックアウトした target SHAが一致していることの証明 |
| **4. 実行結果の証拠** | 該当RunのID、Checkのステータス、PlaywrightのJSONレポート、Artifact内の `target-sha.txt` の完全一致 |
| **5. 未確認事項** | 今回の検証では確認できていない範囲（別ブラウザ、未実行の条件など）とその理由 |
| **6. 残るリスクと提言** | CIのPASSだけでは保証できない品質リスクと、今後リリースに向けて必要となる追加テスト |

### 11.3 正式評価の実行コマンド

準備が整ったら、受講者本人の手で以下の評価コマンドを実行して修了判定を行います。

```bash
pnpm course:assess M10 --model provider/model-id
```

評価では、以下の状態を**修了の成功証拠として採用しません**。未実行、入力不足、環境による実行不能、実行済みの失敗をすべて同じ `FAIL` と決めつけず、評価システムが返した状態をそのまま記録してください。

- 提出された証拠のSHAやRun IDに不一致がある場合
- ワークフローが未実行、または途中で失敗している場合
- 必要なファイル（`target-sha.txt` 等）の保全が不十分な場合
- ワークフローに過剰な権限や危険な設定が含まれている場合

### 確認問題

**問題**：\
PRに新しいコミットを追加した直後、GitHubの画面を開いたところ、1つ前のコミットで成功した「緑色のCheckマーク」がまだ表示されていました。このとき、最新のコードに対して「CI検証PASS」と報告できますか？

#### 解説

- **思考順序**：
  1. コミットが新しく追加された時点で、最新コードに対する検証はまだ行われていません。
  2. 画面に残っている緑色のマークは、以前の古いコミットに対する実行記録です。
  3. コードが1文字でも変わっていれば、前回のテスト結果を引き継ぐことはできません。
- **解答**：\
  **報告できません。**\
  必ず最新のコミットSHAに対応する新しいRunが完了するのを待ち、そのRunから出力されたArtifactのSHAとレポートを確認したうえで報告します。最新のRunが存在しない場合は「未確認」と報告するのが唯一の正しい対応です。

M10を修了したときに受講者が自信を持って説明できるようになるべきなのは、単に「CIが緑色でした」という一言ではありません。\
**「このコミット版（SHA）のこのテストコードを、この実行環境のCIで検証し、この実行結果と保存成果物の一致を確認した。ただし、この範囲は未確認であり、次の検証が必要である」**と、根拠と限界を正確に切り分けて報告できることこそが、プロフェッショナルなQAエンジニアの真の証です。
