# M02：仕様とリスク分析

## この章でできるようになること

前章の M01 では、ソフトウェアテストの基本である「期待結果（本来こう動くべきという正しい姿）」と「観測結果（実際に画面を操作して起きたこと）」を明確に切り離して記録する重要性を学びました。

では、そもそも**「期待結果」は何を手がかりにして決めればよいのでしょうか？**

開発者や利用者の「きっとこう動くだろう」という思い込みや勘に頼ってしまうと、重大な不具合を見落としてしまいます。M02 では、システムの公式な設計図である**「仕様書（Specification）」を根拠にして正しい期待結果を導き出し**、テストに必要な条件を漏れなく整理する技術を身につけます。

さらに、限られた時間の中でどこから重点的にテストすべきかを決める「リスク分析」の手法や、近年利用が広がる AI アシスタントが出してきた分析案を鵜呑みにせず、正確にレビューして誤りを見抜く力を養います。

| 学習目標ID | この章で確認すること | 身につくスキル |
| --- | --- | --- |
| M02-01 | 仕様、実装、観測、AIの推測を分ける | 思い込みを排除し、公式の仕様書を根拠として期待結果を論理的に導き出せる |
| M02-02 | Role・State・Data・Journeyを操作前提に結び付ける | 単なる入力値だけでなく、操作者・初期状態・データ・画面経路を揃えた厳密なテスト条件を整理できる |
| M02-03 | Seed/Resetが保証することと保証しないことを把握する | テスト環境の初期化の仕組みを理解し、未確認の前提を勝手に決めつけない慎重な判断ができる |
| M02-04 | Impact・Likelihood・Priorityの根拠を説明する | 不具合が起きた際の影響度と発生可能性を切り分け、テスト優先順位の理由を論理的に説明できる |
| M02-05 | AIの誤読や未決事項を見つけ、質問・保留・影響を残す | AIの誤った推測を見抜いて指摘し、仕様に明記されていない事柄を確認事項として記録できる |

## 1. 仕様を調べる理由 — 「動いていること」と「正しいこと」は違う

### 1.1 なぜ「画面を動かすだけ」ではテストにならないのか？

オンラインショップの画面で、商品の購入数量入力欄に「999個」と入力して「カートに追加」ボタンを押したとします。画面にはエラーも出ず、「カートに999個追加しました」という案内が表示されました。

さて、この動作は正常でしょうか？ それとも不具合（バグ）でしょうか？

プログラミングやテストの経験がない初学者の場合、「ボタンを押してエラーメッセージも出ずに画面が切り替わったのだから、システムは正常に動いているのだろう」と考えてしまいがちです。

しかし、もしお店のルールとして「転売を防止するため、お一人様最大5個まで」と決められていたとしたらどうでしょうか。999個も買えてしまう現在の動作は、**コンピュータープログラムとしてはエラーなく動いていても、ビジネスとしては大失敗（重大な不具合）**です。

このように、画面を操作して起きたこと（観測結果）を見ただけでは、それが本当に正しい動作かどうかは絶対に判断できません。

テストを行うエンジニアは、必ず**「本来はどう動くべきと定められているのか」という公式の基準**を事前に確認しておく必要があります。その基準が書かれた文書を**「仕様書（Specification / スペック）」**と呼びます。

仕様書は、建築でいえば「設計図」、お料理でいえば「レシピ」にあたるものです。テストとは、「画面を適当に触ってみること」ではなく、**「設計図（仕様書）通りに作られているかを照合して確かめる検査」**なのです。

### 1.2 正式仕様書とBR・ACの読み方

#### 用語と根拠

![仕様をテスト条件とCaseへつなげる流れ](../../assets/figures/M02/01-spec-to-case.svg)

本カリキュラムの学習対象システムである EC サイト「Scenario Shop（シナリオ・ショップ）」では、リポジトリ内の `docs/spec/` フォルダ配下に正式な仕様書が Markdown 形式のファイルとして保管されています。

仕様書を読むとき、次の2つの用語が頻繁に登場します。英単語を暗記する必要はありませんが、それぞれの役割の違いをしっかりと理解しておきましょう。

```text
┌─────────────────────────────────────────────────────────────────┐
│                    仕様書を構成する2つの柱                      │
├───────────────────┬─────────────────────────────────────────────┤
│ 1. BR             │ システムが守るべき「ビジネス・業務上の決まり事」│
│ (Business Rule)   │ 例: 在庫数や購入上限を超えて売ってはならない │
├───────────────────┼─────────────────────────────────────────────┤
│ 2. AC             │ システムが合格かを判定する「具体的な動作基準」  │
│ (Acceptance       │ 例: 上限を超える要求が来たら拒否し、        │
│  Criteria)        │     カート内の数量を変更前の値のまま維持する │
└───────────────────┴─────────────────────────────────────────────┘
```

#### 1. BR（Business Rule：ビジネスルール / 業務ルール）

- **意味**：システムが実現すべき、ビジネス上・業務上の決まり事です。「会社としてどういう商売をしたいか」「法律や契約を守るためにどんな制約が必要か」という方針を表します。
- **具体例**：「同じ商品は最大でも在庫数までしか購入できない」「未成年には酒類を販売しない」「会員ランクに応じて割引率を変える」など。
- **見分け方**：Scenario Shop の仕様書では、`BR-CART-001` のように、「BR-機能名-通し番号」という形式の識別子（ID）が振られています。

#### 2. AC（Acceptance Criteria：受入基準 / アクセプタンス・クライテリア）

- **意味**：システムがそのビジネスルールを正しく満たしているかを判定するための、客観的な合格条件です。「こういう操作をされたとき、システム画面やデータはどう反応すべきか」という具体的な振る舞いが定義されます。
- **具体例**：「上限を超える数量を指定された場合、システムは要求を拒否し、カート内の数量を変更前の値のまま維持すること」。
- **見分け方**：Scenario Shop の仕様書では、`AC-CART-001` のように、「AC-機能名-通し番号」という形式の識別子（ID）が振られています。

テストエンジニアの仕事は、仕様書に書かれている BR や AC の文章を一文ずつ正確に読み取り、「この条件で操作したとき、システムはどう答えるべきか」という期待結果を論理的に組み立てることです。

### 1.3 扱う情報の「4つの分類」

テストの現場では、性質の異なる情報が飛び交います。これらを頭の中でごちゃ混ぜにしてしまうと、「動いているから正しいはず」「AIが言っているから仕様なのだろう」という誤ったテスト結果を出してしまいます。

次の4つの分類を常に意識して、情報の出所を区別してください。

| 情報の種類 | 内容の定義 | 初学者が陥りやすい誤解 | テストでの正しい扱い方 |
| --- | --- | --- | --- |
| **正式仕様** | 仕様書（`docs/spec/`）に明記されている公式のルール | 「仕様書は古いかもしれないから読まなくてもいい」 | **期待結果を決める唯一の絶対的な根拠**にする |
| **実装** | 実際にプログラミングされたコードの記述 | 「プログラムがこう書かれているのだから、これが正しい仕様だ」 | プログラム自体がバグを含んでいる可能性があるため、**仕様書と照合・比較する対象**にする |
| **観測** | 実際にブラウザを操作して画面上に現れた事実 | 「エラーが出ずに画面が更新されたから合格だ」 | 正常か異常かは関係なく、**実際に起きた事実**としてありのまま記録する |
| **AIの推測** | AIツールが「こうであるはず」と推測・要約した内容 | 「AIが自信満々に言っているのだから正しい仕様だろう」 | 仕様書に原文の裏付けが取れるまで**絶対に期待結果として採用しない** |

> **注意**：「実装」が仕様と食い違っている状態こそが「バグ（不具合）」です。プログラムのコードを読んで「こう動くように書かれているから、これが期待結果だ」と決めてしまうと、プログラムのバグをそのまま正解として追認してしまうことになります。正解の基準は、あくまで「正式仕様（仕様書）」にあります。

### 【理解確認ミニクイズ】

**問い**：ブラウザでカート画面を操作したところ、在庫が3個しかない商品に対して数量「5」を指定でき、エラーメッセージも出ずに画面の合計金額が更新されて注文手続きに進めました。このとき、テスターとしての正しい判断はどれでしょうか？

1. 画面がエラーを出さずにスムーズに動いたので、システムは正常であると判断してテストを合格（PASS）にする。
2. 「親切な開発者やAIが気を利かせて、裏で在庫を自動補充してくれたのだろう」と考え、特に記録を残さず終了する。
3. 画面の挙動を「観測結果」として記録し、仕様書の `BR-CART-001` や `AC-CART-001` と照らし合わせて仕様違反（不具合）がないか検証する。

**解答・解説**：
正解は **3** です。
画面が動いたこと（1）は単なる「観測」に過ぎず、「仕様（本来あるべき姿）」ではありません。また、もっともらしい推測（2）を勝手に作ってはいけません。仕様書を確認し、上限超過が拒否されるべきルールになっているかを照合して初めて不具合かどうかを判断できます。

## 2. Cart（カート）の正式仕様を使って考える

ここからは、実際の Scenario Shop のカート仕様を例にして、仕様書から期待結果を導く具体的な手順を学びます。

### 2.1 ルール：上限数量はどう決まるか？（`BR-CART-001`）

#### 例カート数量の上限

仕様書 `docs/spec/features/cart.md` に定義されている `BR-CART-001` では、同一SKU（商品の最小管理単位）について、カートに入れられる有効上限を次のように定めています。

**有効上限 ＝ 在庫数・1人あたりの購入上限数・システム上限99のうち、最も小さい数**（式：`min(在庫数, 購入上限数, 99)`）

#### 専門用語の整理

- **SKU（Stock Keeping Unit：エス・ケー・ユー）**：
  - 在庫管理を行うときの「最小の単位」のことです。
  - 例えば「同じデザインのTシャツ」であっても、「白のSサイズ」と「黒のLサイズ」では管理上の商品が異なります。この「白・S」「黒・L」の1つひとつを別のSKUとして扱います。
- **`min(A, B, C)`（ミニマム関数）**：
  - 数学やプログラミングで使われる記号で、「かっこ内の数値 `A, B, C` の中で、**最も小さい数値を選ぶ**」という計算を意味します。

#### 具体例で計算してみましょう

テスト対象の商品バリエーション（variant）が、次のような設定だったとします。

- 在庫数：3個（お店の倉庫に3個しかない）
- 1人あたりの購入上限数：5個（転売防止ルールとしては5個まで許可されている）
- システム上限：99個（システム全体で固定されている技術的な最大値）

この3つの数値を公式に当てはめます。
`min(3, 5, 99) = 3`（在庫3個、購入上限5個、システム上限99個の中で、最も小さい3個が有効上限です）

3、5、99 の中で最も小さい数値は「3」です。
したがって、有効上限は **3個** になります。

購入上限が5個であっても、お店の倉庫に商品が3個しか存在しないため、物理的に3個までしか購入できないという論理的な結果になります。

### 2.2 受入基準：上限を超えたらどう動くべきか？（`AC-CART-001`）

では、有効上限が3個と決まった商品に対して、利用者が「4個」を指定してきたらシステムはどう動くべきでしょうか？

仕様書 `docs/spec/features/cart.md` の受入基準 `AC-CART-001` には、次のように明確に記されています。

> **上限超過の指定は拒否し、変更前の数量を維持する。自動で上限値に丸める補正は行わない。**

この一文から、テストにおける厳密な期待結果が導かれます。

#### ケース1：数量変更（更新）の場合

- **操作前の状態**：現在のカートに商品が「2個」入っている。
- **利用者の操作**：カート画面の数量変更欄で「4個」を指定して更新ボタンを押す。
- **仕様に基づく期待結果**：
  - 要求はシステムによって**拒否**される。
  - カートの数量は、**変更前の「2個」のまま維持**される。
  - 「上限が3個だから、気を利かせて3個に自動的に書き換えてあげる」という動作は、親切に見えても**完全な仕様違反（バグ）**です。

#### ケース2：数量追加の場合

- **操作前の状態**：現在のカートに商品が「2個」入っている。
- **利用者の操作**：商品詳細ページを開き、さらに「2個」を選んで「カートに追加」ボタンを押す。
- **仕様に基づく期待結果**：
  - 追加後の合計要求数は `2 + 2 = 4` 個となり、有効上限の3個を超過する。
  - したがって追加要求は**拒否**され、カート内の数量は**変更前の「2個」のまま維持**される。

### 2.3 操作の違いに注目する：「数量を更新する」と「数量を追加する」

テスト条件を設計するとき、次の2つの操作を絶対に混同してはいけません。

```text
【数量の直接更新】（カート画面など）
[ 現在数量: 2個 ] ──( 4個に変更 )──> 要求数量は「4個」（絶対値の指定）

【数量の追加】（商品詳細画面など）
[ 現在数量: 2個 ] ──( 2個を追加 )──> 要求数量は 2 + 2 =「4個」（差分の加算）
```

どちらの操作も、利用者が最終的に手に入れようとしている合計数量は「4個」です。

しかし、利用する画面、押すボタン、内部のプログラムが実行する処理経路（Journey）は全く異なります。「更新処理にはバグがあるが、追加処理にはバグがない」といった実装の食い違いが頻繁に起こるため、テストを記録する際は「どちらの操作経路で実行したのか」を明確に区別してください。

また、同じSKUの商品がカート一覧の画面上で複数の行に分かれて表示されていたとしても、上限判定は**カート内の同一SKUの合計数量**で計算されます。見た目の行数に惑わされないように注意しましょう。

### 2.4 仕様から「分かること」と「分からないこと」を仕分ける

仕様書を読むときは、「何が書かれているか」を理解するのと同じくらい、**「何が書かれていないか」に敏感になる**必要があります。

#### 仕様書から100%分かること（確定事項）

- 在庫3、購入上限5、システム上限99 の場合、有効上限は3であること。
- 上限3を超える要求が来た場合、システムは要求を拒否し、元の数量を維持すること。
- 自動補正（数値を勝手に3に丸めること）をしてはならないこと。

#### 仕様書からは分からないこと（勝手に決めてはいけないこと）

- **現在ブラウザを開いたとき、カートに最初から何個入っているか**：
  - これは仕様書には書かれていません。テスト環境の初期データ設定を確認しなければ分かりません。
- **拒否されたときのエラーメッセージの正確な文言や文字色、表示位置**：
  - 仕様書に「画面上部に赤色の文字で『上限を超えています』と表示する」と書かれていなければ、赤色であることもその文言であることも決めつけることはできません。

仕様書に書かれていない事柄について、「普通はこうだろう」「赤い文字で出るはずだ」と推測でテストの合否基準を作ってはいけません。分からない仕様は**「未決事項（確認質問）」**としてメモに残し、仕様の担当者に確認するのが正しい手順です。

### 【手順付き実習】仕様書を読み、AIの要約を検査する（学習目標：M02-01）

#### 目的

仕様書の原文を自分の目で確認し、AIツールが作成した要約に誤読やもっともらしい嘘（ハルシネーション）が混ざっていないかを厳密に照合・検査する手順を学びます。

#### 準備

1. VS Code を起動します。
2. 画面左側の Explorer（エクスプローラー）ツリーを展開し、`docs/spec/features/cart.md` をクリックして開きます。

#### 手順

1. `docs/spec/features/cart.md` のファイル内を検索（`Ctrl + F` または `Cmd + F`）し、`BR-CART-001` と `AC-CART-001` のセクションを探します。
2. 原文を一文ずつゆっくり読み、ノートや作業用テキストファイルに次の3つの項目を書き出します。
   - **【仕様書に明記されていること】**：有効上限の計算ルール、上限超過時のシステムの振る舞い（拒否と数量維持）。
   - **【仕様書だけでは分からないこと】**：エラー表示のデザイン、文字色、ポップアップの有無など。
   - **【仕様担当者への確認質問】**：エラー表示のデザインや文言を定めた共通仕様書が別途存在するか。
3. AI アシスタント（OpenCode 等）が利用できる環境であれば、対象ファイルを限定して次のように指示を出してみます。
   > **プロンプト入力例**：
   > `docs/spec/features/cart.md` を参照し、Cart機能の上限超過時の期待動作を要約してください。仕様書に書かれていない警告文の文言や自動補正などの動作を勝手に推測しないでください。根拠となるBRおよびACの識別子を示し、ファイルは変更しないでください。
4. AI から返ってきた回答を、仕様書の原文と一文ずつ突き合わせます。
   - 仕様書通りの「拒否・変更前の数量維持」になっているか？
   - 「利用者の利便性を考慮して自動的に上限値に丸める」といった、仕様書に反する余計な親切（推測）が混ざっていないか？

#### 条件を変えて考えてみよう

もし AI が次のように回答してきたら、あなたはその回答をテストの期待結果として採用できますか？
> 「在庫3・上限5の商品に対して利用者が4個を注文しようとした場合、システムは利便性を考慮して自動的に購入可能最大数である3個へと数値を丸めてカートを更新します。」

#### 解答・解説

**採用できません（不合格と判定します）。**
`AC-CART-001` には「上限超過の指定は拒否し、変更前の数量を維持する。自動で上限値に丸める補正は行わない」と明確に書かれています。AI が述べた「利便性を考慮した自動調整」は、一見親切でもっともらしく聞こえますが、完全な**仕様違反（AIの誤読・でっち上げ）**です。AI の出力をそのまま信じるのではなく、必ず公式仕様書の原文を自力で確認する習慣をつけてください。

## 3. 条件を4つの観点で整理する — Role・State・Data・Journey

テストを実行するとき、「数量4を入力する」という操作内容だけを決めても、正しいテストはできません。なぜなら、**操作する前の前提条件が1つでも違えば、実行結果も変わってしまうから**です。

テスト条件の抜け漏れを防ぎ、誰が実行しても同じ結果を再現できるようにするため、本カリキュラムでは次の**4つの観点**で前提条件を整理します。

```text
┌─────────────────────────────────────────────────────────────┐
│                 テスト条件を支える4つの観点                  │
├──────────────┬──────────────────────────────────────────────┤
│ 1. Role      │ 操作するのは誰か？（ユーザーの権限・役割）    │
│ 2. State     │ 操作する直前、システムはどんな状態か？        │
│ 3. Data      │ テストに使用するデータは何か？（在庫、属性等）│
│ 4. Journey   │ どの画面や経路を通って操作を実行するか？      │
└──────────────┴──────────────────────────────────────────────┘
```

### 3.1 各観点の内容と具体例

1. **Role（ロール：役割・権限）**
   - **問い**：誰が操作していますか？
   - **具体例**：ログインしていない「ゲスト（guest）」か、一般の「購入者（customer）」か、特別な権限を持つ「管理者（admin）」か。
   - **なぜ重要か**：権限によって、表示されるボタン、利用できる割引、操作の可否が根本から異なるためです。

2. **State（ステート：状態）**
   - **問い**：操作を開始する直前、システムや画面はどんな状態ですか？
   - **具体例**：「カートに対象商品がすでに2個入っている」「カートが完全に空である」「ログイン直後のトップ画面にいる」など。
   - **なぜ重要か**：開始時の状態が違えば、同じ「2個追加する」という操作でも、合計が2個になるのか4個になるのか結果が変わってしまうためです。

3. **Data（データ：テスト対象データ）**
   - **問い**：具体的にどのデータを使ってテストしますか？
   - **具体例**：「対象商品のSKU番号」「在庫数3」「1人あたりの購入上限数5」など。
   - **なぜ重要か**：データの数値が変われば、数式によって計算される有効上限値そのものが変わるためです。

4. **Journey（ジャーニー：操作経路）**
   - **問い**：どの画面を経由して、どういう操作手順で実行しますか？
   - **具体例**：「商品一覧 `→` 商品詳細画面 `→` カート追加ボタンを押す」のか、「カート画面を開いて直接数量入力欄を書き換える」のか。
   - **なぜ重要か**：経由する画面や操作方法が異なれば、内部で呼び出されるプログラムや表示されるメッセージが異なるためです。

### 3.2 条件整理の記入例

数量超過テストの前提条件を4観点で整理すると、次のようになります。

| 観点 | 今回の確認条件（例） | 条件の確認先・根拠 |
| --- | --- | --- |
| **Role** | ゲスト（guest：未ログインの一般訪問者） | 使用するテストセッションの設定・シナリオ仕様 |
| **State** | 対象商品がすでにカートに**2個**入っている状態 | リセット実行後のカート画面での実際の観測結果 |
| **Data** | 対象商品：在庫数3、購入上限数5（有効上限＝3） | Seedデータ定義および正式仕様書（`BR-CART-001`） |
| **Journey** | カート画面を開き、数量変更欄で「4」を選択して更新を要求 | テストケースで指定された操作手順 |

4つの観点のうち、**1つでも曖昧なものや準備できていないものがあれば、そのテストを正しく実行したとは言えません**。「なんとなく動かしてみた」という曖昧なテストをなくすために、常にこの4観点をセットで書き出すようにしてください。

## 4. SeedとResetを読む — テストの出発点を理解する

### 4.1 SeedとResetって何？

自動テストでも手動テストでも、テストを何回も繰り返す現場では、前に行ったテストの影響が環境に残ってしまうトラブルが多発します。

例えば、「商品Aをカートに入れるテスト」を実行したあと、片付けをせずにそのまま次の「カートが空のときのテスト」を実行したらどうなるでしょうか？ カートに商品Aが残っているため、テストは当然失敗してしまいます。

テストを毎回まったく同じ条件からやり直すための仕組みが **Seed（シード）** と **Reset（リセット）** です。

- **Seed（シード）**：
  - テストや練習用に用意された、データベースの「初期データ」のことです。植物の「種」をあらかじめ畑に蒔いておくことに由来します。
  - 例：テスト用に最初から登録されている商品名、価格、在庫数、ユーザーアカウント情報など。
- **Reset（リセット）**：
  - テスト環境を、指定した決まった状態（シナリオ）へと巻き戻す操作のことです。ゲームの「リセットボタン」を押してセーブデータの初期位置に戻すことと同じです。

### 4.2 名前の響きだけで「中身」を推測してはいけない

Scenario Shop のテスト環境には、例えば `low-stock`（在庫僅少：在庫が少ない状態）という名前のシナリオデータが用意されています。

ここで未経験者が最も陥りやすい罠が、**「`low-stock` という名前なんだから、きっとカートは空っぽで、特定商品の在庫だけが少なくなっている状態だろう」と勝手に頭の中で決めつけること**です。

名前に惑わされてはいけません。必ず仕様書 `docs/spec/state-and-scenarios.md` を開き、そのシナリオが具体的に何を保証していて、何を保証していないのかを確認します。

#### `low-stock` シナリオの仕様書の読み解き方

仕様書を確認すると、データは次のような構造で定義されています。

1. **基準（default dataset）**：標準となる基本データ一式が存在する。
2. **上書き（override）**：`low-stock` では、対象商品の在庫数が「3」に書き換えられる。
3. **引き継ぎ（inherit）**：1人あたりの購入上限数「5」などは、標準データからそのまま引き継がれる。

ここから、次の事実が分かります。

- **保証されている事実（仕様書から確定できること）**：
  - 対象商品の在庫数が3、購入上限数が5、システム上限が99であり、有効上限が3であること。
- **保証されていないこと（仕様書からは決まらないこと）**：
  - **今ブラウザを開いたとき、カートに最初から何個入っているか**。

もし「カートに商品が2個入った状態から、さらに追加して上限を超えるテスト」を行いたいのであれば、「Resetを実行したあと、画面上でカート数量が本当に2になっているか」を実際に確認するか、あるいは「商品詳細ページからカートに2個入れる」という前提作成の操作を自分自身の手順に組み込まなければなりません。

### 【手順付き実習】SeedとResetの「保証範囲」を調べる（学習目標：M02-02, M02-03）

#### 目的

仕様書からシナリオの初期データ保証範囲を読み取り、確認できていない不確実な前提を勝手に決めつけない分析手法を習得します。

#### 準備

- エクスプローラーから `docs/spec/state-and-scenarios.md` を開きます。
- 合わせて `docs/spec/features/cart.md` も開いておきます。

#### 手順

1. `docs/spec/state-and-scenarios.md` の中から `low-stock` のセクションを探します。
2. 標準データから引き継がれる項目（購入上限数など）と、`low-stock` 固有で上書きされる項目（在庫数など）を確認します。
3. 対象商品の有効数量上限を計算します（`min(3, 5, 99) = 3`）。
4. 4つの観点（Role, State, Data, Journey）のメモを作成し、各項目の根拠を記録します。
   - Role の根拠：シナリオのセッション定義（ゲストセッション）
   - Data の根拠：`low-stock` の仕様定義（在庫3、購入上限5）
   - State の注意点：「カート現在数量はシナリオ定義単体からは決まらないため、実行後の実際の画面観測で確認する」と明記する。
5. AI に「`low-stock` シナリオを適用すれば、カートの中身は必ず2個になっているよね？」と質問したと想定し、その主張のどこに根拠が不足しているかを文章で説明してみます。

#### 解答・解説

- 対象商品の許可上限が `min(3, 5, 99) = 3` であることは、仕様書と Seed 定義から論理的に100%確定できます。
- しかし、Reset 直後の「カートの現在数量」は、仕様書で明確に定義されていない限り、名前のイメージだけで勝手に確定することはできません。
- したがって、「カート数量2」を前提とするテストを行う場合は、Reset 後に画面上で数量を観測して記録するか、あるいは「商品詳細ページからカートに2個入れる」という前提作成の操作をテスト手順に明示的に組み込む必要があります。

## 5. リスクと優先順位 — Impact・Likelihood・Priority

ソフトウェアテストの現場では、時間も人員も常に限られています。すべての画面のすべてのボタンや入力欄を、同じ時間と深さでテストすることは物理的に不可能です。

そこで必要になるのが、**「どこに重大な危険（リスク）が潜んでいて、どこから優先してテストすべきか」を見極める判断力**です。

### 5.1 リスクを測る3つの要素

#### riskを仮説として評価する

![仕様とリスクを対応付ける手順](../../assets/figures/M02/02-risk-priority.svg)

```text
┌─────────────────────────────────────────────────────────────┐
│ 1. Impact（影響の大きさ）                                   │
│    「もしそこにバグがあったら、どれくらい被害が大きいか？」 │
│                           ×                                 │
│ 2. Likelihood（起こる可能性）                               │
│    「そのバグは、どれくらいの確率で発生しそうか？」         │
│                           ∥                                 │
│ 3. Priority（優先度）                                       │
│    「限られた時間の中で、どれから順番にテストすべきか？」   │
└─────────────────────────────────────────────────────────────┘
```

1. **Impact（インパクト：影響度 / 被害の大きさ）**
   - その機能が故障したとき、利用者やお店（ビジネス）に与える損害の深刻さです。
   - **影響が大きい例**：お金の決済で二重請求が起きる、在庫がないのに注文が完了してしまう、他人の個人情報やクレジットカード番号が見えてしまう、など。
   - **影響が比較的小さい例**：特定のスマートフォン画面で余白が数ピクセルずれている、お知らせ欄に誤字脱字がある（法的な重要事項を除く）、など。

2. **Likelihood（ライクリフッド：発生可能性 / 起こりやすさ）**
   - その不具合が実際に発生する確率や頻度です。
   - 直前に大幅なプログラム書き換えが入った複雑な機能、過去に何度もバグが出ている機能、利用者の9割以上が必ず通る注文確定フローなどは、発生可能性が高くなります。

3. **Priority（プライオリティ：優先度 / 実施順序）**
   - Impact と Likelihood を掛け合わせ、さらに「今回のリリースで絶対に外せないビジネス目標」や「テストにかかる手間」を総合的に考慮して決める、**実際のテスト実施順序**です。

### 5.2 「事実」と「不確実性（仮説）」を分ける

リスクを分析するときに最も大切なのは、**「分かっている事実」と「まだ分かっていない推測」をごちゃ混ぜにしないこと**です。

根拠もないのに「発生確率は80%です！」などと数字を作って計算したふりをしてはいけません。「カートの超過注文はお店に金銭的損害を与えるため影響度は重大（事実に基づく評価）」だが、「このプログラムの改修頻度はまだ不明なので発生可能性は未確認（不確実性の認識）」というように、根拠の有無を正直に分けて記録します。

### 【練習問題】優先順位の根拠を説明する

次の2つの不具合の候補について、テストの優先度を比較し、その理由を説明してください。

- **候補A**：カートの数量上限チェックが壊れ、在庫数を超えた注文が完了してしまう可能性。
- **候補B**：スマートフォンの特定画面幅で見たときに、商品検索結果のカードの余白が数ピクセルずれる可能性。

どちらの発生頻度も、現時点ではまだ詳しく調査できていません。

#### 解答・解説

**候補Aを高い優先度（高Priority）として調査・テストすべきです。**

- **理由（Impactの比較）**：
  - 候補A（在庫超過）が起きると、在庫がないのに注文を受け付けてしまい、商品の発送不能、顧客への個別謝罪・返金対応、お店の信頼失墜など、ビジネス上の重大な損害（極めて高い Impact）を引き起こします。
  - 候補B（余白のズレ）は利用者の見た目に違和感を与えますが、商品の購入そのものは可能であり、金銭的・法的な直接被害は限定的です（低い Impact）。
- **次のアクション（不確実性の解消）**：
  - 発生可能性（Likelihood）は両者とも未確認であるため、まずは Impact が圧倒的に大きい候補Aについて、仕様書の受入基準（`AC-CART-001`）と実際のプログラム・画面動作を最優先で確認します。

## 6. AIの分析案をレビューする — 誤読・推測・未決事項の扱い方

現在では、テスト分析や仕様書の要約に AI アシスタントを活用する機会が増えています。しかし、AI はもっともらしい文章で「仕様書に書いていない嘘」をつくことが珍しくありません。AI が出してきた分析案をそのまま鵜呑みにすると、テスト全体が破綻してしまいます。

### 6.1 AIのよくある間違いパターン

#### パターン1：仕様書の明確なルールを誤読する
>
> **AIの提案**：「在庫3、購入上限5のとき、利用者が数量4を指定したら、システムは親切心から自動的に数値を3に補正してカートを更新する。」

- **分析**：これは明確な**仕様違反**です。`AC-CART-001` には「要求を拒否し、変更前の数値を維持する。自動補正は行わない」と明記されています。AI は世の中の一般的な親切なWebサイトの知識から勝手に推測してルールを曲げてしまいました。
- **テスターの対応**：AI の案を却下し、正しい仕様ID（`AC-CART-001`）を根拠として指摘します。

#### パターン2：仕様書にない情報を勝手に創作する（ハルシネーション）
>
> **AIの提案**：「上限超過エラーが発生したとき、画面上部に赤いバナーが表示され、警告ブザー音が鳴る。」

- **分析**：仕様書を見直しても、バナーの色が「赤」であることや「ブザー音」についての記述は一切ありません。正しいとも間違っているとも断定できません。
- **テスターの対応**：これをテストの合格基準にしてはいけません。**「未決事項（確認質問）」**として記録し、仕様担当者に問い合わせます。

### 6.2 「未決事項」は恥ずかしいことではない

#### 答えがない仕様から質問を作る

仕様を調べた結果、「仕様書に書かれていないから分からない」という結論になることがあります。

初学者は「自分の勉強不足ではないか」と不安になりがちですが、それは違います。**「仕様として確定していない曖昧な事実を白日の下に晒した」という、テスターとしての立派なファインプレー**です。

未決事項を見つけたら、次のような表に整理して記録します。

| 整理項目 | 記入例 | 項目が持つ意味 |
| --- | --- | --- |
| **未決事項** | 上限超過時のエラーメッセージ文言・表示色・表示形式が仕様書に定義されているか | 何が確定していないのか |
| **確認した事実** | `AC-CART-001` では「拒否」と「数量維持」のみが必須要件として定められている | どこまでは仕様書で確認できたのか |
| **必要な質問** | メッセージの文言や表示デザインを定めた別の共通仕様書が存在しますか？ | 誰に何を聞けば解決するのか |
| **テスト設計への影響** | エラーの「文字色（赤）」や「特定の文言」をテストの必須合格条件に設定しない | 回答が出るまでどう安全に対処するか |
| **次のアクション** | 仕様書の担当者に質問を送り、正式な回答があるまで結果判定を保留する | 次に取るべき具体的な行動 |

このように整理しておけば、仕様が曖昧なままで無駄なテストを作成してしまったり、誤った不具合報告を出してしまうリスクを未然に防ぐことができます。

### 【手順付き実習】AIが分析したリスク・未決事項をレビューする（学習目標：M02-04, M02-05）

#### 目的

AI が作成したリスク分析案を査読し、仕様に根拠があるもの、推測に過ぎないもの、確認質問が必要な未決事項を正確に分類する技術を学びます。

#### 手順

1. `BR-CART-001` の上限チェックが壊れた場合、利用者とお店（ビジネス）にそれぞれどのような悪影響が出るかをノートに書き出します。
   - 【確認した事実】：数量上限を超えて注文が通ってしまう。
   - 【影響に関する推定】：在庫切れによる発送遅延、返金手数料の発生、顧客の不信感など。
2. AI アシスタントが利用できる場合は、次のように指示を出してみます。
   > **プロンプト入力例**：
   > Cart機能の上限超過仕様について、不具合が起きた場合のリスク分析案と確認質問を提案してください。Impact（影響度）とLikelihood（発生可能性）の根拠を分けて説明してください。正式仕様書に記載がない振る舞いは「未決事項」として分類してください。ファイルの変更は禁止です。
3. AI が返してきた提案を、次の3つのカテゴリに仕分けします。
   - **〇 仕様に根拠がある妥当な指摘**
   - **△ 影響度や発生可能性が根拠なく過大に主張されている推測**
   - **？ 仕様書に書かれておらず確認質問が必要な未決事項**
4. 故意に情報の足りない「架空の仕様」（例：「割引クーポンは適切に適用されること」など）を読んだと想定し、「何を質問すべきか」「回答が出るまで保留すべき期待結果」「そのまま進めた場合のリスク」を文章で書き出してみます。

#### 解答・解説

- 機能が仕様通りに動かない場合の「業務上の影響（ルール違反）」は仕様書から読み取れますが、「被害額が数千万円になる」「発生確率が90%である」といった具体的な数値は、仕様書単体からは分かりません。AI がそうした根拠のない数値を返してきた場合は、事実ではなく「仮説・推定」であると明記して扱う必要があります。
- 仕様にない挙動（メッセージの細かな言い回しなど）は、独断でテストケースに書かず、担当者からの回答が得られるまで「判定保留」にしておくのが最も安全な品質管理アプローチです。

## 7. さらに理解を深める：仕様分析を一つずつ練習する

この章で学んだ重要な考え方を、例題と解説を通じて確実に定着させましょう。

### 7.1 「画面の観測」から仕様を逆算してはいけない

あるテスターが、画面上で購入数量のプルダウンメニューを開いたところ、「4」が選択できるようになっていました。そこでこのテスターは、テスト結果シートに「この画面は数量4を選択できる仕様である」と書きました。

**解説**：
これは重大な間違いです。「画面で数量4が選べた」というのは、**現在そのようにプログラムされているという単なる「観測結果」**に過ぎません。もしかしたら、プルダウンの選択肢を有効上限の3までに絞り込むプログラムが実装漏れしているバグかもしれないのです。

正しいアプローチは、まず仕様書の `BR-CART-001` を見て「有効上限は3である」という期待結果を確認し、画面で4が選べて注文が通ってしまうなら「仕様と実装が食い違っている（バグの疑い）」と報告することです。画面の挙動から仕様を逆算してはいけません。

### 7.2 例題：異なる制約で有効上限を計算する

**問題**：
ある商品の設定が変更され、**「在庫数：8個、購入上限数：3個、システム上限：99個」**になりました。このときの有効上限は何個になるでしょうか？

**考え方のプロセス**：

1. 有効上限の計算ルール `BR-CART-001` を思い出します。
2. 計算式は `min(在庫数, 購入上限数, 99)` です。
3. 数値を当てはめます：`min(8, 3, 99)`。
4. 8、3、99 の中で最も小さい数値を選びます。

**解答**：
有効上限は **3個** です。

前の例題と同じ「3」という数値ですが、今度は「在庫数」ではなく**「1人あたりの購入上限数」**がブレーキとなって上限が決まっています。「在庫が3だったから上限も3」と暗記するのではなく、毎回3つの制約を比べて最小値を計算してください。これは仕様上の計算例であり、現在のカート数量を実環境で観測した証拠にはなりません。

### 7.2.1 条件が変わっても仕様から上限を導けるか

次章の M03 では、テストすべき入力値を系統的に選ぶ「境界値分析」を学びます。M02 ではその準備として、**3つの数字のうち最小値を見つけること**と、**拒否時の変更前数量を取り違えないこと**を確認します。数字はすべて学習用の仮定です。

| 問題 | 在庫数 | 購入上限数 | システム上限 | 操作前のカート数量 | 更新したい数量 | 有効上限（予測） | 更新の可否（予測） | 操作後のカート数量（予測） |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | :---: | ---: |
| A | 12 | 4 | 99 | 2 | 5 | 4 | ×（拒否） | 2 |
| B | 120 | 150 | 99 | 10 | 100 | 99 | ×（拒否） | 10 |
| C | 6 | 10 | 99 | 2 | 6 | 6 | 〇（許可） | 6 |

各行について、実際のアプリがこの在庫を持っていると決めつけないでください。

#### 解答と理由

- **問題A**：
  - 有効上限は `min(12, 4, 99) = 4` です。
  - 更新値「5」は上限4を超過しているため、要求は拒否され、変更前の数量「2」を維持します。
- **問題B**：
  - 有効上限は `min(120, 150, 99) = 99` です。
  - 在庫も購入上限も100個以上ありますが、システム上限の「99」がブレーキになります。
  - 更新値「100」は上限99を超過しているため、要求は拒否され、変更前の数量「10」を維持します。
- **問題C**：
  - 有効上限は `min(6, 10, 99) = 6` です。
  - 更新値「6」はちょうど上限値ぴったりであるため許可され、カート数量は「6」に更新されます。

#### 別条件の確認

もし問題Aで、「更新したい数量」が「4」に変わったらどうなりますか？

- **解答**：4は有効上限（4）の範囲内であるため許可され、操作後の数量は「4」になります。
- **注意**：これが「数量を4に設定する操作（更新）」ではなく、「商品ページからさらに4個追加する操作（追加）」だった場合は、合計が `2 + 4 = 6` となり上限を超えるため拒否されます。問題文の操作種別（更新か追加か）を必ず先に読んでください。

### 7.3 理解度チェック問題（全6問）

学習した内容を自分で説明できるか試してみましょう。すべての問題に詳しい解答と解説が付いています。

#### 【第1問】

`low-stock` シナリオ（在庫3、購入上限5、システム上限99）において、カートの現在数量が「2」であることを確認しました。ここから「2個追加」のボタンを押した場合、仕様書（`BR-CART-001`, `AC-CART-001`）に基づく正しい期待結果はどうなるでしょうか？

- **解答**：追加要求は拒否され、カート数量は変更前の「2」のまま維持される。
- **解説**：有効上限は `min(3, 5, 99) = 3` です。現在数量2に2個を追加すると合計数量は4になり、上限の3を超過します。`AC-CART-001` では上限超過の要求は拒否して変更前数量を維持することになっているため、2個のまま維持されるのが正しい期待結果です。「上限に合わせて3個にしてあげる」という自動補正は仕様違反です。

#### 【第2問】

同じ初期データ（Seed）を使用する2つのテストケースがあります。テストAが先に実行されて商品をカートに追加しました。その直後に実行されるテストBは、「カートは空である」という前提を期待してテストを始めてもよいでしょうか？

- **解答**：期待してはいけない（そのまま始めてはいけない）。
- **解説**：テストAが操作した影響（副作用）が環境に残っている可能性があります。テストBを始める前には、テストごとの環境初期化（Reset）が保証されているかを確認し、実際に開始時の状態が空になっていることを確かめる必要があります。Seed の名前が同じであることは、実行時に前テストの影響がないことの証明にはなりません。

#### 【第3問】

AIアシスタントが作成したテスト分析案に、「仕様書には書かれていないが、利用者の利便性を考えて、上限超過時には確認ダイアログを表示して注意を促す」と書かれていました。テスターとしてどう対処すべきでしょうか？

- **解答**：ダイアログの表示を確定した期待結果に含めず、「未決事項（確認質問）」として記録する。
- **解説**：仕様書に書かれていない動作を、AI の推測や親切心で勝手に正式な仕様に格上げしてはいけません。業務ルール通りの「拒否・数量維持」だけを確定した期待結果とし、ダイアログの有無は仕様担当者へ確認質問を出して回答を待ちます。

#### 【第4問】

商品検索機能のテストで、カテゴリAとカテゴリBを同時に選択するテストを行いたいと考えました。しかし、用意された初期データ（Seed）の中には、両方のカテゴリを同時に満たす商品が1件も存在しませんでした。このとき、「このシステムではカテゴリAとBの同時選択は仕様上禁止されている」と断定してよいでしょうか？

- **解答**：断定できない。
- **解説**：初期データ（Seed）に対象データが登録されていないことと、システムの仕様として組み合わせが禁止されていることは全く別の問題です。データがないだけで仕様上は許可されている可能性があります。仕様書の検索ルールを確認し、安全にテスト用データを作成できるか検討するか、未確認事項として記録します。

#### 【第5問】

テスト実行者が不具合報告書に「実際の上限は5個であるべきなのに、3個でエラーになった」と記載しました。しかし正式仕様書には「在庫3、購入上限5」と書かれています。レビュー担当者は何を指摘すべきでしょうか？

- **解答**：購入上限の5だけを見て在庫数の制約を見落としていることを指摘し、有効上限の計算式 `min(3, 5, 99) = 3` を示して3個制限が正しい仕様動作であることを説明する。
- **解説**：テスト実行者が `BR-CART-001` の「在庫数・購入上限数・99の最小値」というルールを正しく理解せず、購入上限の「5」だけを仕様だと誤認しています。仕様書の根拠を示して認識を正す必要があります。

#### 【第6問】

ビジネスルール（BR）だけを読んで受入基準（AC）を読まない、あるいは受入基準だけを読んでビジネスルールを読まずにテストを作成すると、どのような問題が起きるでしょうか？

- **解答・解説**：
  - **BRだけを読んだ場合**：「上限は3個である」というルールは分かりますが、「上限を超えたときにエラーメッセージが出るのか、元の数値を維持するのか、自動補正するのか」というシステムの実装・画面動作の合格基準が分からず、正しい期待結果が書けません。
  - **ACだけを読んだ場合**：「上限を超えたら拒否する」という動作は分かりますが、その上限値が「在庫」「購入上限」「システム上限」のどれによって決まったのかという根拠を見落とし、別のデータ条件になったときに正しく上限を計算できなくなります。
  - したがって、両方を必ずセットで照合してテストを設計する必要があります。

### 8.3 最終チェック問題

**問い**：在庫3、購入上限5、カートの初期状態が未確認のシナリオにおいて、資料（仕様書とSeed定義）だけで事前に100%確定できるのは「上限3」と「現在数量2」のどちらでしょうか？

**解説**：
確定できるのは**「上限3」**のみです。仕様書の計算ルール `min(3, 5, 99) = 3` によって有効上限は論理的に確定します。一方、「現在数量2」は実際の画面やセッションを観測するまで確定しません。未確認の前提を勝手に確定事項として扱わない姿勢が大切です。

### 次の章（M03）へのつながり

M02 では、仕様書を正しく読み解いて前提条件とリスクを整理する方法を学びました。

しかし、「数量4を指定する」以外にも、数量0、数量1、数量3、マイナスの数量、文字の入力など、試すべき入力値は無数に存在します。これらをすべて闇雲にテストすることはできません。

次章の **M03** では、今回整理した仕様とリスク分析の結果を入力として受け取り、**「同値分割法」「境界値分析」「状態遷移テスト」「デシジョンテーブル」** というソフトウェアテストの代表的な4大設計技法を使って、無駄のない最小限のテストケースを論理的に設計する手法を学びます。
