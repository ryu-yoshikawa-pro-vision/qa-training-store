# M01：QAとソフトウェアテストの基礎

## この章でできるようになること

この章では、ソフトウェアテストやプログラミングの学習を初めて行う方でも、「何を確認するのか」「どうなれば正しいのか」「実際に何が起きたのか」を明確に区別し、自分の言葉で論理的に説明できるようになることを目指します。

また、手動で自由に触って不具合や違和感を探す「探索的テスト」、プログラムの変更後に以前の機能が壊れていないかを確かめる「回帰テスト」、コンピューターに手順を実行させる「自動テスト」それぞれの役割と限界を理解し、目的に応じた適切な確認方法を選べるようになります。

| 学習目標ID | 本章を終えたときに確認できる具体的な行動 |
| --- | --- |
| M01-01 | テストの目的・確認対象・仕様書に基づく期待結果を明確に区別して説明できる |
| M01-02 | 手動探索・回帰確認・テスト自動化をそれぞれの目的と限界に基づいて区別できる |
| M01-03 | テスト活動の5工程（分析・設計・実行・評価・改善）と、AIおよび人間の責務の違いを説明できる |
| M01-04 | 適切なテスト層（Unit、Integration、Component、Web E2E）を選び、すべてのテストをE2Eにしない理由を説明できる |

## 1. テストは何のために行うのか

### 1.1 身近な例から考える「確認したつもり」の罠

普段、スマートフォンやパソコンでインターネット通販（ネットショップ）を利用するときの場面を想像してみてください。

買い物カゴ（カート）の画面で、商品の数量を「1」から「2」に変更するために、数量変更ボタン（または「+」ボタン）を押したとします。画面上の数字が「2」に変わりました。

このとき、多くの方は次のように直感的に思ってしまうのではないでしょうか。

> 「画面の数字が2に変わったのだから、正しく注文数量も2個になったはずだ。」

しかし、ソフトウェアの内部構造を知ると、必ずしも画面の表示どおりに裏側の処理が進んでいるとは限らないことが分かります。

私たちが普段見ているWebサイトは、大きく分けて次の3つの要素が連携して動いています。

1. **画面（フロントエンド / クライアント）**：利用者のブラウザ上に文字や画像を描画し、ボタンのクリックや文字入力を受け付けます。
2. **通信（ネットワーク / API）**：画面で起きた操作内容を、インターネットを通じて裏側のサーバーへ届けます。
3. **サーバーとデータベース（バックエンド）**：届いた注文データを受け取り、数量の計算や在庫の引き当てを行い、確実な保存場所（データベース）に記録します。

もし、ボタンを押して画面上の数字が「2」に書き換わったとしても、通信が途中で失敗していたらどうなるでしょうか。あるいは、画面上は「2」と見えていても、サーバー側のデータベースへの保存処理に不具合があり、実際には「1個」のまま記録されていたらどうなるでしょうか。その場合、注文を確定した瞬間に「1個」として決済されてしまい、利用者は困惑することになります。

逆に、ボタンを押しても画面上の数字が「2」に変わらなかったとします。このとき、「システムが故障している！」とすぐに断定できるでしょうか。
もしかすると、その商品は「限定品のため、お一人様1点限り」という業務ルールが定められており、2個目の追加要求がシステムによって**正しく拒否された**結果なのかもしれません。あるいは、通信環境が極端に遅く、反映に数秒の時間がかかっているだけかもしれません。

このように、画面の表面だけを眺めたり、思いつきでボタンを押してみるだけでは、システムが本当に正しく動いているのかを客観的に判断することはできません。

### 1.2 「試すこと」と「テストすること」の違い

日常生活における「ちょっと操作してみる（試す）」ことと、技術としての「テスト」には明確な境界線があります。

- **試すこと（感覚的な操作・アドホックな操作）**：
  事前に明確な基準や判定ルールを決めず、思いつきでボタンを押したり画面を眺めたりして、「なんとなく動いた」「動かなかった」と感覚的に判断することです。
- **テストすること（体系的な検証活動）**：
  操作を行う**前**に、「どのような前提条件の状態で」「どのような入力や操作を行えば」「どのような結果になるのが正しい状態なのか（仕様）」をあらかじめ定義しておき、実際に動かした結果と照らし合わせて品質に関する客観的な情報を得る活動です。

料理に例えるなら、「なんとなくスプーンで味見をして、美味しい気がする」と判断するのが「試すこと」です。一方、「レシピ（仕様書）に定められた分量どおりに調味料を入れ、塩分濃度計で測って1.0%になっているかを確認する」のが「テストすること」にあたります。

テストを行う最大の目的は、単に「バグ（不具合）を見つけて開発者を責めること」ではありません。**「作られたシステムが、あらかじめ定められた要求や仕様書どおりに正しく動くかを確認し、利用者が安心して使える品質になっているかどうかの確かな事実と情報を関係者に届けること」**です。

### 1.3 QA（品質保証）とは何か

「テスト」とよく似た文脈で使われる言葉に「QA（Quality Assurance：品質保証）」があります。この2つは現場で混同されることもありますが、活動の範囲と責任の大きさが異なります。

- **テスト（Test）**：
  完成した、あるいは開発中のソフトウェアを実際に動かしたり、設計内容を調べたりして、期待どおりに動くかどうかを確かめる「具体的な検証作業」です。
- **QA（品質保証：Quality Assurance）**：
  利用者が真に満足する品質を届けるための「開発プロセス全体の仕組みづくりや活動全般」を指します。

QAの活動範囲は、テストの実行だけにとどまりません。プログラミングが始まる前の「要求や仕様書のレビュー（矛盾や漏れがないかの確認）」、開発現場の手順やツールの改善、どのようなテストをどの順番で行うかという「テスト計画・設計」、不具合が発見されたときの「原因分析と再発防止策の策定」など、開発の最初から最後まで深く関わります。

テストは、QAを実現するための強力な手段の一つですが、テストを大量に実行してすべて合格させたからといって、それだけで「品質が100%保証された」とは言えません。

例えば、ネットショップの購入ボタンのテストがすべて合格したとしても、次のような品質上の問題は残り得ます。

- 画面の文字色が背景と同化していて、視力の弱い方には文字が読めない（アクセシビリティ・使いやすさの問題）。
- 特定の通信キャリアや古いスマートフォン機種で開くと、購入ボタンが画面外に見切れて押せない（環境互換性の問題）。
- 注文処理自体は成功するが、クレジットカード情報の暗号化が不十分で、悪意ある第三者に盗まれる危険がある（セキュリティ・プライバシーの問題）。

ソフトウェア工学の有名な原則に、**「テストは欠陥が存在することは示せるが、欠陥が存在しないことは証明できない」**という言葉があります。

テストが合格したという事実は、あくまで**「そのとき確認した特定の条件と手順において、期待どおりに動いた」**ことを客観的に証明しているにすぎません。「あらゆる環境、あらゆる操作順序、あらゆる利用者の入力において、絶対に不具合が起きない」という完全な保証ではないのです。

この「テストの持つ力と限界」を正しく弁え、過信せず、客観的な事実に基づいて品質を語る姿勢こそが、プロフェッショナルなQAエンジニアとしての第一歩となります。

## 2. 期待結果と観測結果を分ける

### 2.1 テストの基本原則：先に「期待結果」を決める

#### 期待結果と観測事実

![期待結果と実際の観測を分けるQAの流れ](../../assets/figures/M01/01-qa-loop.svg)

テストという作業を行ううえで最も重要であり、未経験者が最も混同しやすい落とし穴が**「期待結果」**と**「観測結果」**の混同です。

- **期待結果（Expected Result）**：
  実際に操作を行う**前**に、仕様書や設計書、業務ルールなどの確かな根拠に基づいて「この前提条件のもとでこの操作を行えば、システムはこうなるべきである」とあらかじめ定めた結果です。
- **観測結果（Actual Result / Observed Result）**：
  実際に操作を行ったり、ログや画面、データベースの記録を確認したりして、**現実に発生した客観的な事実**をありのままに記録した結果です。

次の会員登録画面の例を見てみましょう。

| 項目 | 内容 |
| --- | --- |
| 前提条件 | 新規会員登録画面（`/signup`）を開いている状態 |
| 実施操作 | 必須入力項目である「メールアドレス」欄を空欄のまま、「登録する」ボタンをクリックする |
| **期待結果** | 会員登録は完了せず、メールアドレス欄の直下に「メールアドレスを入力してください」というエラーメッセージが表示され、画面遷移しないこと（仕様書の受入基準に基づく結果） |
| **観測結果** | 画面遷移は発生せず、メールアドレス欄の直下に赤文字で「メールアドレスを入力してください」と表示されたことを目視確認した |

もし、期待結果を操作前に決めずに操作してしまうと、どうなるでしょうか。
例えば、メールアドレスを空欄にしてボタンを押したとき、何の警告も出ずに「登録完了画面」が表示されたとします。仕様を知らない人は「ボタンを押したらスムーズに次の画面に進んだから、正常に動いた」と思い込んで合格と判定してしまうかもしれません。

「あらかじめ正しいルール（仕様）を調べ、何が起きるべきかを決めておく」からこそ、現実に起きた現象が正常なのか異常なのかを正しく見極めることができるのです。

また、画面上にエラーが出たという観測結果が得られたとしても、それだけで「裏側のデータベースに空文字の不正な会員レコードが作成されていないか」まで確認できたわけではありません。**「自分はどこまでを目やログで観測し、どこから先はまだ確認していないのか」**を厳密に切り分ける姿勢が不可欠です。

### 2.2 練習用アプリ「Scenario Shop」とCart（カート）の仕様例

本カリキュラムでは、学習用の本格的なWebアプリケーションである**「Scenario Shop（シナリオショップ）」**を題材として使用します。Scenario Shopは、商品の検索、カートへの追加、注文、配送先指定、決済などが行えるEC（ネット通販）サイトです。

ここで、ショッピングカート（Cart）機能に関する実際の仕様を確認してみましょう。
Scenario Shopの仕様書には、商品の数量変更に関して次のようなルールが定められています。

- **`BR-CART-001`（ビジネスルール：業務規則）**：
  同一商品（SKU：受発注の最小単位となる商品識別コード）をカートへ追加・変更できる上限数は、以下の3つの値のうち「最も小さい値（最小値）」を採用する。
  1. 商品の現在庫数（現在倉庫にある実際の在庫数）
  2. 1回の注文で購入できる購入上限数（商品ごとに設定された個数制限）
  3. システム共通の上限値である「99」
- **`AC-CART-001`（受入基準：合格とみなす具体的なシステム挙動）**：
  カート内の商品数量を変更する際、有効上限数を超える数量の指定は**システム側で要求を拒否し、変更前の数量をそのまま維持**する。

この仕様をもとに、テストの記録欄を次のように整理します。

【具体例：商品の現在庫数が「3個」、購入上限数が「5個」の場合】

- 有効上限数の計算：`min(在庫数: 3, 購入上限数: 5, システム上限: 99)` → 最も小さい値は **`3`** となります。
- 現在カートには、この商品が **`2個`** 入っているとします。
- ここで、カート画面の数量欄に **`4個`**（上限3を超える数量）を指定して更新を試みたとします。

| 記録項目 | 記入内容 |
| --- | --- |
| 確認したいこと（目的） | 有効上限数を超える数量変更を要求したとき、システムが要求を正しく拒否し、操作前の数量が維持されるかを検証する |
| 操作前の条件（前提条件） | 対象商品の有効上限数が「3」、現在のカート内数量が「2」であること |
| 実施する操作 | カート画面の数量入力欄に「4」を指定し、「更新」ボタンを押す |
| **期待結果** | 数量変更の要求は拒否され、カート内の数量表示は変更前の「2」のまま維持されること |
| **観測結果** | 実際に画面を操作して確認できた事実をありのままに記入する。 ／ **※まだ画面を操作していない準備段階では、必ず「未実行」と記入する。** |
| 仕様上の根拠 | `BR-CART-001`、`AC-CART-001` |

もし実際に操作した結果、画面の数量表示が「3」に変わってしまったとします。
このとき、観測結果欄に書くべき客観的事実は「画面の数量表示が3に変化した」です。

期待結果は「変更前の2のまま維持されること」だったので、期待と観測が食い違っています。しかし、**この瞬間に「製品プログラムのバグを見つけた！」と性急に決めつけてはいけません。**
「自分が操作前に準備した商品の在庫数は本当に3個だったか」「仕様書の解釈を誤っていないか」「テスト環境のデータが壊れていないか」など、冷静に原因の可能性を検証する姿勢が求められます。

### 2.3 テストが失敗したとき、どう考えるべきか？

テストを実行した結果、期待結果と観測結果が一致しなかった場合、そのテストは「失敗（FAIL）」となります。
しかし、「テストの失敗」が意味する原因は、プログラム本体の不具合（バグ）だけとは限りません。

テスト失敗の原因には、大きく分けて次の4つの可能性が存在します。

1. **製品コードの実装ミス（真のバグ）**：プログラムが仕様書どおりに作られておらず、間違った処理を行っている。
2. **テスト側のミス（テストの不備）**：テスト手順の解釈ミス、入力した値の間違い、あるいは自動テストコード側の記述ミス。
3. **テストデータの不備**：操作を開始する前に揃えておくべき前提データ（対象商品の初期在庫数やログインユーザーの権限など）が、設計どおりに準備されていなかった。
4. **テスト環境の不具合**：ネットワークの一時的な通信障害、検証用サーバーの停止、ブラウザのキャッシュ残りなどによる環境起因の失敗。

したがって、期待と異なる挙動に直面したときは、**「現実に何が起きたか（客観的事実）」**と**「なぜそうなったのか（テスターの推測や仮説）」**を明確に切り離して報告しなければなりません。

プロフェッショナルな不具合報告書に最低限含めるべき項目は次のとおりです。

- **操作前の状態（前提条件）**：どのアカウントでログインし、どの商品がどのような初期状態（在庫数や数量）だったか。
- **再現手順**：誰が読んでも1行ずつ同じ操作を再現できるよう、ボタンの名前や入力値を順序立てて記述した手順。
- **仕様上の期待結果**：仕様書のどの条項（`BR-*` や `AC-*`）に基づき、システムがどう振る舞うべきだったか。
- **実際の観測結果**：画面に表示された文言、変化した数値、コンソールログやエラーメッセージなど、確認できた客観的事実（画面キャプチャを含む）。
- **確認環境**：使用したOS、ブラウザの種類とバージョン、検証環境のURLなど。
- **未確認事項**：画面上の数値変化は確認したが、データベースの保存値やAPIの通信内容まではまだ調査していない、という調査の限界点。

まだ実行していないテストについて、想像や願望で「仕様どおり動くだろうから合格」と記録したり、起きていない現象を観測したかのように記録することは、QA業務において最も信頼を損なう禁止事項です。

### 実習1：最初の観測記録表を作成する（M01-01）

#### 1. 目的

「操作を行う前に決めるべきこと（目的・前提・操作・期待結果・根拠）」と、「実際に動かして初めて得られる事実（観測結果）」を一切混同せずに整理する基本スキルを習得します。

#### 2. 準備するもの

- テキストエディタまたは学習用メモ
- 仕様書：`docs/spec/features/cart.md`

#### 3. 実施手順

##### ステップ1：仕様書を確認する

`docs/spec/features/cart.md` を開き、`BR-CART-001` と `AC-CART-001` の記述を探してください。
「上限超過の指定は拒否され、操作前の数量が維持される」という文言があることを自分の目で確認します。

##### ステップ2：操作を行う前に表を作成する

**この段階では、まだScenario Shopの画面を開いて操作してはいけません。**
以下の5項目を手元の学習メモに書き出します。

- 【確認したいこと（テストの目的）】
- 【操作前の条件（前提条件）】
- 【実施する操作（入力値とアクション）】
- 【仕様上の期待結果】
- 【根拠（出典となる仕様書条項ID）】

※数量の数値は、教材の例（上限3、変更前数量2、変更要求4）を使用して構いません。

##### ステップ3：操作を実施し、観測結果を記入する

もしScenario Shopの実画面を起動できる環境にある場合は、実際にログインして指定の条件（上限3、変更前2）を整えたうえで操作を行います。
実画面が起動できない環境の場合、観測結果欄には必ず **`未実行`** と記入してください。

##### ステップ4：事実を記録し、確認済みと未確認を整理する

画面を動かせた場合は、見えた数字やエラーメッセージを「見えたまま」記録します。
最後に、「今回の確認で何が分かって、何がまだ分かっていないのか」をそれぞれ1行で記述してください。

#### 4. 条件を変えた練習（練習課題）

ある新人テスターが、次のような不具合報告を提出してきました。

> 「カート画面で数量4を指定したら、画面の数字が3になりました。上限が3個なので、システムが親切に自動調整してくれたのだと思います。問題ありません（合格）。」

この報告には重大な問題があります。この報告を、「前提条件」「実施操作」「仕様上の期待結果」「実際の観測結果」「客観的事実」「推測（根拠のない思い込み）」の要素に正しく分解し、QAとして適切な記録に書き直してください。

#### 練習課題の解答と解説

##### 解答例：適切な記録への書き直し

| 項目 | 修正後の記録 |
| --- | --- |
| 対象機能 | カート画面（数量変更機能） |
| 前提条件 | 対象商品の有効上限数が「3」、変更前のカート内数量が「2」である状態 |
| 実施操作 | 数量入力欄に「4」を指定し、「更新」ボタンをクリックした |
| 仕様上の期待結果 | 変更要求は拒否され、変更前の数量「2」が維持されること（根拠：`BR-CART-001`、`AC-CART-001`） |
| 実際の観測結果 | 画面上の数量表示が「3」に変化した |
| 結果判定 | **不一致（テスト失敗 / 不具合の疑いあり）** |
| 客観的事実 | 画面上の表示が「2」から「3」へ書き換わったことまでが確認できた事実である。 |
| 未確認事項・推測 | 「システムが自動補正した」というのは根拠のない推測である。仕様書（`AC-CART-001`）上は自動補正ではなく「拒否して元の2を維持」が要求されているため、製品コードの不具合か仕様解釈の齟齬の可能性がある。サーバー通信ログおよびデータベース内部の保存値は未確認。 |

##### 解説

新人の報告の最大の問題点は、**「仕様書を確認せず、画面の現実に合わせて勝手に期待結果を作り出したこと」**です。
「上限が3だから、3になったのは親切な自動調整だろう」というのは単なる個人の推測（思い込み）にすぎません。仕様書（`AC-CART-001`）には明確に「拒否し、現在の数量を維持する」と書かれているため、画面が「3」になったのであれば、それは仕様と一致していない危険な挙動（不具合の候補）です。
「期待結果は操作前に仕様書から決める」「観測結果には事実だけを書く」「理由や推測は事実と明確に切り離す」という基本原則を徹底しましょう。

## 3. 探索、回帰、自動化を選ぶ

テストと一口に言っても、すべての確認を同じやり方で行うわけではありません。確認したい目的や開発の状況に応じて、主に**「探索的テスト」「回帰テスト」「自動テスト」**の3つのアプローチを適切に使い分ける必要があります。

### 3.1 探索的テスト（Exploratory Testing）

**探索的テスト**とは、あらかじめ細かく決められた手順書（テストケース）に縛られず、テスター自身の知識、直感、経験、そして画面から得られたフィードバックを手がかりに、探索するようにソフトウェアを触りながら未知の不具合や使いにくさを探していくテスト手法です。

- **どんなときに使うか**：
  新しく開発された画面を初めて触るときや、仕様書がまだ十分に固まっていない開発の初期段階で威力を発揮します。
- **具体例**：
  新しく作られた商品購入画面を触りながら、「もし商品が購入手続きの途中で売り切れたらどうなるだろう？」「ブラウザの『戻る』ボタンを素早く連打したらどうなるだろう？」「極端に長い名前を入力したら画面が崩れないか？」など、画面の反応を見ながら次の確認アイデアを思いつき、深掘りしていきます。
- **ポイント**：
  ただの「適当な操作（気まぐれな操作）」ではありません。自分が試した手順や気付いた挙動をメモ（チャーターやログ）としてしっかり残し、仕様が曖昧な部分を見つけたら開発チームに質問して仕様の確定を促します。

### 3.2 回帰テスト（リグレッションテスト：Regression Testing）

**回帰テスト（退行テストやデグレ確認とも呼ばれます）**とは、プログラムの一部を変更・修正したときに、「以前まで正常に動いていた別の機能が巻き添えで壊れていないか（先祖返りやデグレが起きていないか）」を確認するテストです。

- **どんなときに使うか**：
  不具合を修正したあとや、新しい機能を追加したあとに、関連する既存機能が今までどおり動き続けているかを確かめるために行います。
- **具体例**：
  カートの「数量上限の計算式」を修正したとします。修正した数量変更機能だけでなく、「商品の新規追加」「商品の削除」「購入手続きへの遷移」といった、以前から動いていた周囲の機能が巻き添えで壊れていないかを再度確認します。
- **ポイント**：
  回帰テストは、ソフトウェアを変更するたびに「まったく同じ確認」を何度も繰り返すことになります。そのため、後述する「自動テスト」と非常に相性が良い領域です。

### 3.3 自動テスト（Test Automation）

**自動テスト**とは、これまで人間が手作業で行っていたテストの操作や結果確認を、プログラム（テストスクリプト）に代行させる手法です。

- **どんなときに使うか**：
  毎回同じ手順で、同じ前提条件と期待結果を何度も繰り返し確認したい場合に適しています。
- **具体例**：
  「ログイン機能が壊れていないこと」や「カートの計算式が正しいこと」を、プログラムの変更があるたびに自動で実行して数分でチェックします。
- **誤解してはいけない限界**：
  「自動テストがあれば、人間のテスターはいらなくなるのか？」というと、絶対にそんなことはありません。
  自動テストは、「あらかじめ指示されたとおりに動いたか（指定した文字が表示されたか、計算結果が一致したか）」を機械的に判定することしかできません。「画面のデザインがなんとなく崩れていて押しにくい」「文言のニュアンスが不自然で利用者が戸惑いそうだ」といった**人間の感覚や違和感に基づく発見は、人間にしかできません。**

### 3.4 手動と自動を選ぶ基準

テストを自動化するかどうかは、「自動化できる技術があるか」だけで決めてはいけません。以下の要素を総合的に考えて判断します。

1. **実行頻度**：毎週、毎日のように何度も繰り返すテストか？（1回しかやらない使い捨てのテストなら、手動のほうが圧倒的に早くて安上がりです）
2. **期待結果の明確さ**：「こうなれば成功」という正解が厳密に決まっているか？（結果の正否判定が曖昧なものは自動化できません）
3. **作成・保守のコスト**：自動テストのコードを書く時間や、画面が変わったときにテストコードを直す手間に見合うだけの価値（時間短縮効果）があるか？
4. **不具合の見つけやすさ**：コンピューターの機械的な一致判定で見つけられる種類の不具合か？

### 通常練習：テスト手法の分類

次の3つのテスト作業について、「まず人間が探索すべき」「自動化の有力な候補」「テスト前に仕様の確認が必要」のどれに当てはまるかを考え、その理由をそれぞれ説明してください。

1. 初めて一般公開されたばかりの購入画面について、利用者が迷ったり使いにくさを感じたりする部分がないかを調べる。
2. 仕様書で厳密に計算式が定義されている「カートの数量上限ルール」について、プログラムを更新するたびに同じ条件で正しく動作するかを確かめる。
3. 仕様書にエラー時の挙動が何も書かれていない入力欄について、画面に表示された注意文言が正しいかどうかを判定する。

#### 解答と解説

1. **まず人間が探索すべき**：
   「使いやすさ」や「利用者の迷い」は主観的な体験であり、あらかじめプログラムで正否を判定することができません。人間が実際に操作しながら違和感を探す「探索的テスト」が最適です。
2. **自動化の有力な候補**：
   前提条件（上限値と現在数量）と期待結果（拒否されて元の数量を維持）が仕様書で明確に定まっており、かつプログラム更新のたびに何度も繰り返し確認する価値があるため、自動テストに最も向いています。
3. **テスト前に仕様の確認が必要**：
   仕様書に挙動が定義されていない以上、何が正しい状態（期待結果）なのかを誰も判断できません。この状態でテストを実施したり自動化したりしても意味がないため、まずは仕様担当者への確認・起票が必要です。

### 実習2：同じ題材で探索・回帰・自動化を比較する（M01-02）

#### 1. 目的

カート画面という1つの題材を通じて、探索的テスト、回帰テスト、自動テストの観点の違いを体験し、さらにAIエージェントを活用する際の指示方法と注意点を学びます。

#### 2. 準備するもの

- Scenario Shopのカート機能の概要（前述の `BR-CART-001`、`AC-CART-001`）
- 学習用メモ
- （利用可能な場合）AIプログラミング支援環境（OpenCode等）

#### 3. 実施手順

##### ステップ1：探索的テストの観点を考える

自分が「初めてこのカート画面を触るテスター」になったつもりで、仕様書には細かく書かれていないけれど、触って確かめてみたい疑問点や気になる操作を3点挙げてください。

- （ヒント例：数量を極端に大きな数字にしたらどうなるか？ 数量変更ボタンを素早く2回連続で押したらどうなるか？ 商品を削除した直後にブラウザの戻るボタンを押したらどうなるか？ など）

##### ステップ2：回帰テストの観点を考える

開発者が「数量上限の計算ロジック」を修正しました。この修正によって、**「以前は正常に動いていたはずの周辺機能」**が壊れていないかを再確認するため、確認すべき既存の機能を3点選んでください。

- （ヒント例：カートへの新規追加、カートからの商品削除、注文画面への進むボタン など）

##### ステップ3：自動テストの候補を選定する

ステップ2で挙げた回帰確認のうち、特に「自動テストとしてコード化して、毎回機械に実行させる価値が高いもの」を1点選び、なぜそれを自動化すべきなのか理由を説明してください。

##### ステップ4：AIエージェントに観点を提案させて比較する（AI協働実習）

もしAIエージェントツールが利用できる環境であれば、以下のプロンプト（指示文）を入力してAIに相談してみましょう。

```text
私たちはScenario ShopというECサイトのカート機能をテストしています。
カートの数量上限については以下の仕様があります。
- BR-CART-001: 数量上限は在庫数、購入上限数、99の最小値。
- AC-CART-001: 上限超過の変更要求は拒否され、操作前の数量が維持される。

このカート機能について、以下の条件でテスト観点を提案してください。
1. 探索的テストの観点を3点
2. 数量上限修正に伴う回帰テストの観点を3点
※仕様書に書かれていない挙動については勝手に決めつけず、「仕様確認が必要な事項」として明示してください。
※リポジトリ内のファイル変更やコードの生成は行わず、テキストでの提案のみを行ってください。
```

AIから回答が得られたら、次の基準で分類・点検します。

- **採用**：仕様に沿っており、具体的で妥当な観点。
- **保留**：アイデアとしては面白いが、仕様書に根拠がないため確認が必要な観点。
- **却下**：仕様と矛盾していたり、AIが勝手に「こう動くはずだ」と期待結果を捏造している観点。

#### 実習2の解答例と解説

##### 探索的テストの観点例（3点）

1. 在庫が残り1点しかない商品をカートに入れた状態で、別のタブで同じ商品をさらに追加しようとしたらどうなるか？
2. 数量欄に「-1」や「0」、「あいうえお」などの不正な文字を直接キーボードで打ち込んだらどうなるか？
3. カートに商品を入れたまま数日間放置し、その間に商品が販売終了（非公開）になった場合、カート画面を再読み込みするとどう表示されるか？

##### 回帰テストの観点例（3点）

1. 【商品の新規追加】：商品一覧画面からカートに新しい商品が正常に追加できること。
2. 【商品の削除】：カート内の「削除」ボタンを押したとき、対象の商品明細が正しく消えること。
3. 【画面遷移】：カート画面から「レジへ進む（チェックアウト）」ボタンを押したとき、注文手続き画面へ正しく遷移できること。

##### 自動テスト候補の選定と理由

- **選定**：「ログインして商品をカートに入れ、上限を超える数量を指定したとき、拒否されて元の数量が維持されること」の正常系・異常系の一連の流れ。
- **理由**：前提条件（初期数量）と入力値（上限超え）、期待結果（元の数量維持）が完全に明確であり、今後の開発でもカート周りのコードに手が入るたびに壊れていないかを即座に検証したい重要なビジネスルールだからです。

##### AI協働のポイント解説

AIは豊富な知識を持っているため、テストの観点出しを依頼すると非常にたくさんのアイデアを出してくれます。
しかし、**AIは「仕様書に書かれていないこと」を、あたかも確定した仕様であるかのように自然な文章で創作してしまう（ハルシネーションを起こす）傾向があります。**
例えば、AIが「数量を0にしたら確認ダイアログが出るはずです」と提案してきたとしても、仕様書に「確認ダイアログを出す」と書かれていなければ、それを期待結果としてテストケースに採用してはいけません。必ず人間が仕様の正本（ドキュメント）と突き合わせ、「これは仕様の範囲内か、それとも確認が必要な推測か」を判定してください。

## 4. テスト活動はどうつながるか

### テスト工程と役割

![仕様の期待と実際の観測を確認する手順](../../assets/figures/M01/02-expected-observed.svg)

テストという仕事は、画面を触ってボタンを押す（テスト実行）だけではありません。テストは、以下の5つの活動が一本の鎖のようにつながって成り立っています。

```text
分析 → 設計 → 実行 → 評価 → 改善
            （必要に応じて分析・設計に戻る）
```

上の順序は代表的な学習用の流れです。実務では、評価結果を受けて分析や設計へ戻り、テスト条件とケースを見直します。

| 活動フェーズ | 主な問い（何を考えるか） | 作成・更新するもの（成果物） |
| --- | --- | --- |
| **1. 分析** | 対象の機能において、何を確認すべきか？ どこに重大なリスクがあるか？ | 仕様の確認メモ、リスク一覧、テスト対象となる条件の候補 |
| **2. 設計** | その条件を、具体的にどのような手順・データ・期待結果で確かめるか？ | 具体的なテストケース、テスト用データ、合否判定基準 |
| **3. 実行** | 実際に動かしてみて、何が起きたか？ | 観測結果の記録、実行ログ、画面キャプチャ、実行証拠 |
| **4. 評価** | 得られた結果から何が分かったか？ テストしていない残余リスクは何か？ | テスト合否判定、不具合報告書、未実行・未解決事項のまとめ |
| **5. 改善** | 見つかった問題に対して次は何を直し、どのように再テストするか？ | バグ修正案、テストケースの見直し、再テスト計画 |

### AIと人間の責務分担

![QAの期待結果と観測結果の対応関係](../../assets/m01-expected-observed.png)

近年の開発現場では、AIエージェントにテストの設計やコード作成を支援させることが増えています。しかし、どこまでをAIに任せてよく、どこから先は人間が責任を持たなければならないのでしょうか。

- **AIに任せてもよい領域（アイデア出しと下書き）**：
  - 仕様書を読み込ませて、テストすべき観点や**条件が変わる境目の値（境界値）**の候補をリストアップさせる。境界値を系統的に選ぶ方法はM03で学びます。
  - テストケースの記述形式に沿った下書き（ドラフト）を作成させる。
  - 観測されたエラーログから、考えられる原因の仮説を複数挙げさせる。
- **人間が責任を持って判断・実行すべき領域（意思決定と検証）**：
  - AIが出してきた観点が、正式な製品仕様と合致しているかの検証（AIの嘘を見抜く）。
  - 実際のテスト環境で操作を行い、現実に何が起きたかを目とログで確認すること。
  - 「このテスト結果をもって、本番環境にリリースしてよいか」という最終的な品質の評価と責任の引き受け。

**AIが画面を見ずに「すべてのテストが正常にパスしました」と報告してきたとしても、実際の環境で動かした証拠（ログや実行結果）がなければ、テストは「未実行」と同じです。**

## 5. テスト層と確認できる範囲

### 5.1 テストのピラミッド（4つのテスト層）

同じ「カートの数量上限」という機能を確かめる場合でも、**「どの深さ（階層）でテストするか」**によって、確認できる範囲や実行にかかる費用・時間が大きく変わります。

一般的に、ソフトウェアのテストは以下の4つの層（レベル）に分かれます。

```text
      / \
     /   \       Web E2E（ブラウザを通した利用者全体の導線確認）
    /-----\
   /       \     Component（画面部品単体の表示や挙動の確認）
  /---------\
 /           \   Integration（複数の部品やAPI・データベースの連携確認）
/-------------\
/               \ Unit（関数や計算処理など、最小単位のロジック確認）
-----------------
```

自動車の製造に例えてみましょう。

1. **Unit（単体テスト）**：
   プログラムの最も小さな処理単位（関数や計算式）を直接テストします。自動車で言えば、エンジン単体やブレーキパッド単体が規定どおりの出力を出すかを検査する段階です。
   - *例*：`min(stock, purchaseLimit, 99)` という上限計算を行う関数に、在庫3・購入上限5を渡して「3」が返ってくるかを検証する。
2. **Integration（統合テスト）**：
   複数のプログラム部品や、API（サーバーとの通信窓口）、データベースなどが正しく連携できるかを検証します。自動車で言えば、エンジンとトランスミッションを繋いだときに、動力が正しくタイヤの軸へ伝わるかを検査する段階です。
   - *例*：カートAPIに数量変更リクエストを送信したとき、データベースの注文明細テーブルが正しく更新されるかを検証する。
3. **Component（コンポーネントテスト）**：
   画面全体ではなく、ボタンや入力欄といった特定の画面部品（コンポーネント）単体に焦点を当てて表示や動作を検証します。自動車で言えば、ダッシュボードのスピードメーター単体に通電し、針が正しく振れるかを検査する段階です。
   - *例*：数量入力欄の部品に「4」と入力したとき、エラーメッセージの枠が赤く描画されるかを部品単位で検証する。
4. **Web E2E（End-to-End：エンドツーエンドテスト）**：
   実際のブラウザ（ChromiumやWebKitなど）を起動し、本物の利用者が操作するのと同じように、画面遷移やクリック、入力を通して一連の流れ全体を検証します。自動車で言えば、完成車をテストコースで実際に走らせて、ドライバーが快適に運転できるかを総合確認する段階です。
   - *例*：トップページから商品を探し、カートに入れ、数量を上限より大きく変更しようとしたときに要求が拒否され、変更前数量が維持されるまでをブラウザで確認する。注文完了まで確認する場合は、別途チェックアウトの仕様とテストデータが必要です。

### 5.2 なぜ「すべてをE2Eテスト」にしてはいけないのか？

初心者の方が自動テストを学び始めると、次のように考えがちです。

> 「ブラウザを自動で動かすE2Eテストが一番本物のユーザーに近いのだから、すべての入力パターンのテストをE2Eで自動化すれば完璧なのではないか？」

しかし、現場でこれをやってしまうと、ほぼ確実に自動テストの運用は破綻します。理由は以下のとおりです。

- **実行時間が非常に遅い**：
  Unitテストはブラウザを起動せず、純粋な計算処理だけをメモリ上で動かすため、一般に数百〜数千の計算条件を数秒で検証できます。一方、E2Eテストは本物のブラウザを起動し、ページを読み込み、アニメーションを待ちながら画面を操作するため、1つのテストを動かすだけでも数秒から数十秒かかります。すべての組み合わせをE2Eに集めると、テスト完了までに何時間もかかり、開発のスピードを著しく阻害します。
- **不安定になりやすい（フレイキーテスト：Flaky Test）**：
  ブラウザの描画タイミング、ネットワークの通信遅延、画面アニメーションの完了待ちなど、プログラム本体のバグとは関係のない理由で「たまに成功し、たまに失敗する」という不安定なテスト（フレイキーテスト）が発生しやすくなります。テスト結果が信用できなくなると、開発者はテスト結果を見なくなってしまいます。
- **原因の特定が難しい**：
  E2Eテストが失敗したとき、画面の表示ミスなのか、サーバーAPIのエラーなのか、データベースの不整合なのか、ネットワークの遅延なのか、どこに問題の原因があるのかを突き止めるために長い調査時間が必要になります。
- **保守のコストが高い**：
  画面のデザインが少し変わったり、ボタンの文言や配置が変更されただけでE2Eテストコードは壊れやすく、日々のメンテナンスに追われて新しいテストを書く余裕がなくなります。

したがって、**「計算や複雑な条件の組み合わせは、下層のUnitテストで高速・大量に検証し、画面全体のつながりや利用者の主要なシナリオだけをE2Eテストで厳選して確認する」**という役割分担が極めて重要になります。

### 実習3：AIと人間の担当を決めてテスト計画表を作る（M01-03・M01-04）

#### 1. 目的

「カートの数量上限ルール」を題材に、テスト活動の各工程における人間とAIの役割分担を明確にし、適切なテスト層を選定する判断基準を身につけます。

#### 2. 実施手順

1. 手元の学習メモに、テストの5工程（分析・設計・実行・評価・改善）を縦軸に取った表を作成します。
2. 各工程について、「AIに支援・下書きさせてもよい作業」と「人間が自分の目と責任で決定・検証すべき作業」を書き分けます。
3. 次の2つの検証対象について、それぞれ「Unitテスト」と「Web E2Eテスト」のどちらが最初の候補として適しているかを理由とともに説明します。
   - 対象A：`min(在庫数, 購入上限数, 99)` の計算処理
   - 対象B：カート画面で数量を変更し、購入手続きを完了するまでの一連の画面導線

#### 実習3の解答例と解説

##### 1. 工程別の役割分担表

| 工程 | AIに支援させてもよい作業 | 人間が決定・検証すべき作業 |
| --- | --- | --- |
| **分析** | 仕様書テキストから、条件が変わる境目の値（境界値）やリスクの候補をリストアップさせる。 | 仕様書の意図を確認し、今回のテストで本当に検証すべき対象範囲と優先度を決定する。 |
| **設計** | テストケースの記述形式に沿って、テスト手順や期待結果の下書きを作成させる。 | AIの作った期待結果が仕様の正本と一致しているか確認し、テストデータを確定する。 |
| **実行** | 自動テストスクリプトのコード生成や実行コマンドの組み立てを行わせる。 | 実際の実行環境を立ち上げ、テストが本当に実行された証拠（ログや画面）を確認する。 |
| **評価** | テスト結果のログを要約させ、失敗原因の候補を推測させる。 | その失敗が製品バグか環境要因かを調査して特定し、リリース可否の最終判断を下す。 |
| **改善** | 失敗したテストコードの修正案や、追加で確認すべきテストケース案を提案させる。 | 修正案の妥当性をレビューし、今後の再発防止策と再テストの計画を確定する。 |

##### 2. テスト層の選定と理由

- **対象A（計算処理）**：**Unitテストが最適**
  - *理由*：画面やネットワーク、データベースを動かす必要がまったくなく、入力値（在庫数、購入上限数）と出力値（最小値）の組み合わせだけを検証すればよいためです。Unitテストであれば、境界値（0、1、98、99、100など）の多数のパターンを1秒未満で瞬時にテストできます。
- **対象B（購入導線）**：**Web E2Eテストが最適**
  - *理由*：画面上の入力、ボタンのクリック、ページ間のデータ引き継ぎ、サーバーとの通信がすべて連携して初めて成立する機能だからです。計算ロジックが合っていても画面遷移が壊れていれば買い物はできないため、実際のブラウザを通したE2Eテストで確認する価値があります。

## 6. さらに理解を深める集中演習

テストの基本的な考え方を定着させるために、5つの演習問題に取り組みましょう。

### 演習A：前提・操作・期待・観測・推測の分類

次のA〜Eの文章は、テストに関わる記録の一部です。それぞれ「前提条件」「実施操作」「仕様上の期待結果」「実際の観測結果」「推測」のどれに該当するか分類してください。

- **A**：対象商品の在庫数は3個、購入上限数は5個、現在のカート内数量は2個である。
- **B**：数量入力欄に「4」と入力し、「更新」ボタンをクリックした。
- **C**：画面上の数量表示が「3」になり、「在庫の上限です」という赤いメッセージが表示された。
- **D**：きっとサーバー側のプログラムが、在庫上限に合わせて自動的に数値を丸めてくれたのだろう。
- **E**：仕様書（`AC-CART-001`）によれば、上限を超える変更要求は拒否され、元の数量「2」が維持されるべきである。

#### 解答と解説

- **A**：**前提条件**（テストを開始する前に整えておくべき状態やデータ）
- **B**：**実施操作**（テスターまたはプログラムが対象に対して実際に行ったアクション）
- **C**：**実際の観測結果**（操作を行った結果、画面やログに現れた客観的な事実）
- **D**：**推測**（観測結果を見て個人が頭の中で考えた推論であり、確定した事実ではない）
- **E**：**仕様上の期待結果**（仕様書などの正本を根拠とした、あらかじめあるべき正しい状態）

C（観測結果）とE（期待結果）を比べると、「3」と「2」で食い違いが発生しています。このとき、Dのように推測を事実と混ぜて納得してしまうのではなく、「期待結果と観測結果が不一致である」という事実を正確に記録することがQAの役割です。

### 演習B：仕様書に書かれていない場合の対処法

会員登録画面のテストを設計しています。「メールアドレス欄に `@` マークを含まない不正な文字列を入力して登録ボタンを押した場合」についてテストしようとしましたが、手元の仕様書には「入力チェックを行うこと」としか書かれておらず、具体的にどんなエラーメッセージを出すか、赤字で表示するのかポップアップを出すのかが一切書かれていませんでした。

このとき、テスターとしてどのように行動すべきでしょうか。考える順序を整理したうえで、仕様担当者（開発者やプロダクトマネージャー）への質問文を作成してください。

#### 解答と解説

##### 考える順序

1. **入力条件の整理**：どのような不正な入力値（@マークなし等）を想定しているかを明確にする。
2. **仕様の現状確認**：仕様書のどこまでが決まっていて、何が未定義なのかを特定する。
3. **推測での作業停止**：「たぶん赤文字でエラーが出るはずだ」と勝手に正解を決めてテストを作らない。
4. **具体的な質問の作成**：相手が「はい/いいえ」や具体的な文言で答えられるように論点を絞って質問する。

##### 質問文の作成例
>
> 「会員登録機能の仕様について確認させてください。
> 仕様書には『メールアドレスの入力チェックを行うこと』と記載されていますが、不正な形式（例：@マークが含まれない文字列）が入力された場合の具体的な受入基準について確認があります。
>
> 1. 不正な形式の場合、画面遷移を中断して登録を拒否する認識で合っていますでしょうか。
> 2. その際、画面上に表示すべき特定のエラー文言や表示位置（入力欄直下に赤字表示など）の指定はありますでしょうか。
> テストケースの期待結果を確定させたいため、ご教示いただけますと幸いです。」

このように、勝手に期待結果を想像せず、仕様の空白を見つけて関係者に確認を取ることも、テスト設計における極めて重要な業務です。

### 演習C：探索的テストと回帰テストの使い分け

ネットショップのカート機能で、「ある特定の順番でボタンを素早く連打すると、数量がおかしな値に戻ってしまう」という噂がありますが、開発チームもまだ正確な再現手順を掴めていません。

1. この問題の再現手順や発生条件を突き止めたいとき、最初に行うべきなのは「探索的テスト」と「回帰テスト」のどちらでしょうか。理由とともに答えてください。
2. 原因が判明してプログラムが修正された後、同じ不具合が二度と再発しないことを確かめるために定期的に行うべきなのはどちらでしょうか。

#### 解答と解説

1. **最初に行うべきは「探索的テスト」**：
   決まった手順書がない未知の問題であるため、テスターが画面の挙動を注意深く観察しながら、ボタンを押すタイミングや操作順序を様々に変えて試行錯誤する「探索的テスト」が適しています。
2. **修正後に行うべきは「回帰テスト」**：
   一度発生条件と修正内容が確定した後は、「その条件で二度と壊れないこと」をプログラム変更のたびに繰り返し確認する必要があるため、「回帰テスト」としてテストケースを固定化（あるいは自動化）して実行します。

### 演習D：テスト層の選択

以下の3つのテスト観点（A〜C）について、最初に検討すべきテスト層（Unit、Integration、Web E2E）をそれぞれ選んでください。

- **観点A**：商品価格が1,000円、消費税率が10%のとき、税込価格として1,100円が正しく計算されるか、端数処理のパターン（切り捨て・四捨五入など）を含めて100通りの数値で検証したい。
- **観点B**：カートに商品を追加した状態で決済画面へ進み、クレジットカード決済代行サービスと通信して注文完了画面が表示されるか、本番に近い導線で確認したい。
- **観点C**：注文APIに対して「存在しない商品ID」を送信したとき、APIが適切なエラーコード（404 Not Foundなど）を返すかを確認したい。

#### 解答と解説

- **観点A**：**Unitテスト**
  - *解説*：画面やネットワークは無関係で、純粋な価格計算関数のロジック検証だからです。100通りの計算パターンをWeb E2Eでやると時間がかかりすぎますが、Unitテストなら一瞬で終わります。
- **観点B**：**Web E2Eテスト**
  - *解説*：利用者の実際の画面操作、画面間のデータ受け渡し、外部決済サービス連携など、システム全体を通した体験を確認したいからです。
- **観点C**：**Integrationテスト（APIテスト）**
  - *解説*：ブラウザのUIを介さず、APIサーバーとデータベースや内部ロジックの境界における通信契約を確認するのに最も適しているからです。

### 演習E：客観的な欠陥報告書の作成

次の悪い不具合報告を読んで、QAエンジニアとして関係者がすぐに調査できる客観的な報告書に書き直してください。

【悪い報告の例】
> タイトル：カートがおかしい
> 本文：カートの数量変更を試したら動きがおかしいです。たぶんサーバーのAPIがバグってます。早く直してください。

#### 解答と解説

##### 改善後の報告書例

- **タイトル**：【カート】上限を超える数量変更時に元の数量が維持されず上限値が表示される
- **対象画面**：カート画面（`/cart`）
- **前提条件**：
  - テスト用ユーザー（`customer@example.com`）でログイン済み
  - 商品「シナリオマグカップ」（SKU: `MUG-001`、在庫数: 3、購入上限数: 5）をカートに2個投入した状態
- **再現手順**：
  1. カート画面を開く。
  2. 商品「シナリオマグカップ」の数量入力欄の数値を「2」から「4」に書き換える。
  3. 「更新」ボタンをクリックする。
- **仕様上の期待結果**：
  - 要求が拒否され、数量は「2」のまま維持されること（根拠：`BR-CART-001`、`AC-CART-001`）。
- **実際の観測結果**：
  - 画面上の数量表示が「3」に更新された（添付スクリーンショット `cart_error_20261028.png` 参照）。
- **確認環境**：
  - OS: Windows 11 / ブラウザ: Google Chrome 最新版 / テスト環境: ローカル検証環境
- **備考・未確認事項**：
  - 画面表示上の不一致を確認した段階であり、データベース内部に保存された値およびAPIのレスポンス詳細については未調査です。

##### 解説

悪い報告は「感情的」「主語や条件がない」「推測でバグを決めつけている」という三重苦でした。
改善後の報告書のように、前提条件、具体的な数値、手順、仕様書の根拠、画面のキャプチャ、環境を揃えることで、開発者は迷わず調査に入ることができます。

## 7. 理解度自己点検チェック

本章の学習内容を理解できたか、以下の5つの問いに自力で答えてみましょう。

1. テストケースがすべて合格（PASS）したとき、「この機能にはもう不具合が一切ない」と断定してよいでしょうか。理由とともに答えてください。
2. 仕様書に書かれていない挙動について、AIに質問したところ「通常はこう動くはずです」と回答されました。この回答をそのままテストの期待結果として採用してよいでしょうか。
3. 画面上に「数量が3個に変更されました」と表示された場合、それだけで「データベースにも正しく3個と保存された」と断定してよいでしょうか。
4. ログイン機能のテストを、プログラムを修正するたびに何度も繰り返し実行する理由は何でしょうか。
5. 「UnitテストよりもWeb E2Eテストのほうが実際の画面を動かすから、常に高級で優れている」という考え方は正しいでしょうか。

### 理解度チェックの解説

1. **断定できません。** テストの合格は「テストケースで確認した特定の条件において期待どおり動いた」ことを証明しているだけであり、未実行の条件や異なる利用環境、セキュリティや使いやすさといったあらゆる品質特性まで保証するものではないからです。
2. **採用してはいけません。** AIの回答は一般的な推測にすぎず、対象システムの正式な仕様ではないからです。仕様書に書かれていない事項は、必ず仕様担当者（開発者や設計者）に確認して正式な受入基準を確定させる必要があります。
3. **断定できません。** 画面表示が変わったことと、裏側のデータベースが正しく更新されたことは別の事象だからです。画面表示だけを確認した場合は、観測結果欄にも「画面上に3と表示されたことまでを確認した（データベース保存値は未確認）」と正確に記録すべきです。
4. **回帰（デグレ）を防ぐためです。** 新しい機能の追加や他の箇所の不具合修正によって、これまで正常に動いていたログイン機能が思わぬ影響を受けて壊れていないかを確かめるために繰り返し実行します。
5. **正しくありません。** それぞれのテスト層には得意・不得意があり、優劣の関係ではないからです。Unitテストは高速で網羅的な計算確認に適しており、Web E2Eテストは利用者の実際の導線確認に適しています。目的に応じて組み合わせて使うことが正解です。

## 8. 通常演習の模範解答例と判断理由の総まとめ

### 演習1：数量「0」への変更時の整理

【シナリオ】：カート内の明細について、数量を「0」に変更したときの挙動を確認する。仕様書には「数量0への変更は、カートからの明細削除として扱う」と定められている。現在数量2の商品に対して数量0を指定する場合の整理。

| 記入欄 | 適切な解答例 | なぜこの答えになるのか（判断理由） |
| --- | --- | --- |
| 確認目的 | 数量0の指定により、対象商品の明細がカートから正しく削除されるかを確認する | 仕様書に定められた「数量0＝削除」という機能ルールを検証するため。 |
| 操作前条件 | 対象商品の明細が数量2でカート内に存在することを確認している | 操作前の数量が分からないと、削除されたのか最初からなかったのか区別がつかないため。 |
| 実施操作 | 数量欄に「0」を入力し、更新を実行する | 仕様に定められた操作を正確に行う。 |
| 期待結果 | 対象商品の明細がカート画面から消去され、カートから削除されること | 仕様書の規定に基づく正しい状態。 |
| 観測結果 | **未実行**（まだ動かしていない場合） | まだ操作していない段階で「削除された」と書くことは虚偽の記録になるため。 |
| 次の確認事項 | カートを再読み込みしても該当商品が復活しないかを確かめる | 一時的な画面消去ではなく、データの永続化まで確認するため。 |

### 次の章（M02）で学ぶこと

本章では、テストの最も重要な土台である「期待結果と観測結果の分離」「テスト手法の選び方」「テスト層の考え方」を学びました。

しかし、テストを行うためには、そもそも「期待結果の根拠となる仕様書」を正しく読み解けなければなりません。
次の **M02** では、Scenario Shopの正式な仕様書（機能要件、ビジネスルール、受入基準、画面カタログ）を実際に読み解き、漏れや矛盾のないテストケースを組み立てる「テスト分析とテスト設計の技術」を本格的に学んでいきます。
