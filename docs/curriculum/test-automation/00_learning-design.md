# 学習方針と進め方

## このカリキュラムの考え方

本カリキュラムでは、テスト自動化を単なる「ツールの操作」ではなく、継続的な品質保証活動として捉えます。

学習の中心となるのは、次のサイクルです。

```text
テスト対象を理解する
↓
テストを分析・設計する
↓
自動化対象を選定する
↓
自動テストを実装する
↓
実行する
↓
結果を分析する
↓
改善する
↓
運用・保守する
```

Playwright、Maestro、GitHub Actionsは、このサイクルを実現するための手段として学びます。

## 教材

**すべての説明や演習では、本リポジトリのScenario Shopを使用します。**

別のサンプルアプリは使用しません。受講者は同じアプリを一貫して観察し、Web、ネイティブアプリ、テストデータ、テストコード、CI/CDを段階的に理解していきます。

## この文書群と教材実装の関係

このディレクトリでは、学習の順序、教材内容、演習、到達目標を定義します。リポジトリ側には、これらを実行可能にするTraining Web / Nativeの入口、CSV形式のワークブック、バリデータ、TypeScriptのチェックゲート、CIテンプレートなどが、同じ計画のもとであらかじめ実装されています。

各Lessonでは、次の2つの境界を明確に区別します。

- **正式な仕様を読む学習**: [`docs/spec/README.md`](../../spec/README.md)および各FeatureのBR / AC（ビジネスルール／受け入れ基準）を起点とします。
- **Training境界で行う演習**: `training/` ディレクトリと `playwright.training.config.ts` を使用し、正式なリグレッションテストや本番ワークフローに変更を混入させないようにします。

既存の `e2e/web/` や `maestro/`、正式なCIは比較教材および正式なリグレッション検証用であり、受講者のテストコードの保存先ではありません。また、本番環境のシークレット、OIDC、デプロイ権限などはTraining環境には持ち込みません。

リポジトリ内に存在することを検証するための資材と、受講者が必ず通る学習経路で扱う内容・演習・自己確認・修了条件・評価成果物とは明確に区別されます。`03_instructor-reference.md` はリポジトリ上で必要な支援資料ですが、受講者必須の学習経路や共通課程の修了条件を定義する正本ではありません。

## Lesson共通契約

本カリキュラムは、講師による口頭説明がなくても進められるよう設計されています。17のCanonical Lesson（`P1-01`〜`P1-09`、`P2-01`〜`P2-08`）は、本文を読んだ受講者が以下の項目に沿って自立して一巡できるように構成されています。なお、`P1-07`（Native）と`P2-06`（Native CI）は選択課程です。

| 項目 | Lesson本文で明示する内容 |
| --- | --- |
| 目的 | 何を理解し、どのような判断ができるようになるか |
| Input | 配布済みの資材、前のLessonの成果物、受講者自身が準備するものを区別し、出所・参照先・準備完了の確認方法を明記する |
| Activity | 読む、観察する、設計する、実装する、実行する、比較するなど、受講者が進める手順 |
| Observation | 画面、ログ、差分、実行結果、アーティファクトなど、作業後に何を確認し、その理由をどう説明するか |
| Output | 何を残すか、形式の自由度、評価担当へ渡す場所、次のLessonでの用途 |
| Self-check | 質問項目と、回答に最低限含めるべき要素。理解度は受講者自身の言葉による説明で確認する |
| Completion | ファイル、実行ログ、自己確認など、第三者が客観的に確認できる完了条件。単なる操作回数やスイート全体のPASSとは区別する |
| Recovery | 学習上のつまずき、テスト／プロダクトの失敗（Failure）、環境の不備を区別し、それぞれの復帰手順を明記する |
| Handoff | 次の担当者、テストケースIDやLesson ID、ファイル、エビデンス、次へ進むための開始条件 |

### InputとOutputの受け渡し場所

受講者は、ワークブックやメモの編集をGoogle スプレッドシートやローカルフォルダなど、任意の環境で行えます。編集ツールの指定は学習目標ではありません。ただし、Part 1からPart 2の最終確認へ引き渡す評価用の正本は、次の `handoff-root/` ディレクトリに集約します。

```text
handoff-root/
  workbook/
    01_target-risk.csv
    02_test-cases.csv
    03_automation-mapping.csv
    04_execution-improvement.csv
  code/
  evidence/
  receipts/
  self-check/
```

`code/` にはリポジトリの相対パスを維持した受講者のコードを配置します（例: `training/playwright/exercises/my-cart.spec.ts` は `code/training/playwright/exercises/my-cart.spec.ts`）。`evidence/` にはTrace、スクリーンショット、動画、HTMLレポートなどを配置し、`receipts/` には実行の事実を記録したExecution Receiptを、`self-check/` には既存のLesson IDごとの自己確認メモを配置します。評価用のCompletion Receiptはこのルート直下に出力し、`receipts/` 内のExecution Receiptと混同しないようにします。

Lesson本文が指定するInputには、単に「前のLessonで作成済み」と書くのではなく、具体的にどのファイル・列・ID・実行結果が揃っているべきかを明記します。たとえばPlaywrightの実装を行うLessonでは、実装対象のテストケースID、条件、前提、期待結果、初期化（Reset）手順が事前に準備されていることをInputの条件に含めます。Outputには、受講者が作業した場所にかかわらず、評価へ渡すために上記ルートへどのように集約すべきかを記載します。

## AIエージェントによる学習

OpenCodeをAIエージェントの実習環境として利用し、`qa-workflow-skills`をテスト分析・設計・自動化・結果分析を支援するSkill群として活用します。特定のモデルや料金プラン、Skillの内部実装を学ぶことは目的ではありません。

受講者は最初にテスト対象と最低限のテスト条件を自分で考え、その後でAIに分析・設計・実装を依頼します。AIの提案を仕様・リスク・実行結果と照合し、採用・修正・不採用を判断します。AIによるコード生成は認めますが、期待結果の捏造、未実行を成功とする報告、根拠のない仕様変更は認めません。

詳細な実施手順は[AIエージェント活用演習](./05_ai-agent-workflow.md)を参照します。各工程では既存のLesson ID、4つのワークブック、Training Playwright実行入口、修了レシートを使用します。AIを導入するために別の成果物形式や新たなテスト実行基盤を作りません。

**演習環境**: Part 1の学習にGitHubアカウントを要求しない既存方針は維持します。OpenCodeやSkill群の環境構築は講師・運営側が支援できます。AIの無料利用枠が使えないことを理由に、受講者の能力を不合格としません。

## 対象者

コース開始時点の受講者像は、「テスト自動化の目的や基本概念を理解しており、ノーコード／ローコードツールの経験や概要の知識があってもよいが、Playwrightなどのコードベースの自動化は未経験であり、事前のプログラミング経験は必須としない方」です。

主な対象者は次のとおりです。

- 手動テストの経験があり、テスト自動化へステップアップしたい方
- AutifyやMagicPodなどのノーコード／ローコード自動化ツールの経験がある方
- Playwrightなどのコードベースツールは未経験だが、テスト設計や運用の基礎を学びたい方
- モバイルアプリのUIテスト自動化を選択して学び、Web自動化からネイティブアプリ自動化へ幅を広げたい方
- Part 2でCI環境における自動テストの実行を学びたい方
- 修了後に実際のプロジェクトで自動化基盤を設計・導入したい方

プログラミング経験は前提条件としません。Playwrightの演習に入る前に、テストコードの読み書きに必要なJavaScript / TypeScriptの最小限の知識をPart 1で学習します。

プログラミング言語の全体を網羅することは目的とせず、Scenario Shopの自動テストを作成するために必要な範囲に絞って学びます。

### 共通課程の既習知識に関するルール

共通課程で前提とできる知識は、上記の受講者像と、それ以前に必須の学習経路で明示的に学んだ内容のみです。モバイルアプリ自動化の選択課程、発展課題、参考資料、教材外でのPlaywright / TypeScript / Git / CIなどの実務経験を前提にしてカリキュラムを進めることはしません。

## 用語の使い分け

自動化の領域では同じ単語が異なる意味で使われがちなため、本カリキュラムでは以下の呼称を標準とします。

| 用語 | 本カリキュラムでの意味 |
| --- | --- |
| Test Case ID | `TC-CART-001` など、スプレッドシート上で管理するテストケースの識別子 |
| UI Test ID / `testId` | PlaywrightやMaestroからUI要素を安定して特定するための識別子 |
| Seed Scenario | Scenario Shopを確定的な初期状態へリセットするためのシナリオ |
| テストシナリオ / 利用者の操作経路 | 複数の条件や画面をまたいで検証する業務上のシナリオ |
| Maestro Flow | MaestroのYAML形式で記述する実行単位 |
| 共通操作 / Helper | 複数ページにまたがる操作を、必要に応じてまとめたコード上の関数や構造 |

教材本文では原則として上記の呼称を用い、単に「Test ID」「Scenario」「Flow」と略記して意味を混同させないようにします。

テストケースIDの形式とワークブックの列定義については、[Training Workbook README](../../../training/workbook/README.md)を正本として参照します。

なお、既存コードのAPI名や変数名、外部ツール固有の名称を引用する場合は、実装上の名称をそのまま使用します。その場合も、教材上でどの概念に該当するのかを明確に区別します。

特に、**テストケースID（Test Case ID）とUIテストID（UI Test ID）、初期状態リセット（Seed Scenario）と利用者経路（User Journey）、Maestro Flowとコード上の共通操作（Helper）は別物である**点に留意してください。

### 安定表記ルール

- 受講者向けの一般的な解説文は、自然な日本語を中心に記述する。
- ツール名、製品名、API名、コマンド、パス、識別子は、公式のリテラル表記を維持する。
- `Locator` や `Fixture` などの公式用語は、必要に応じて初出時に日本語の解説を補足する。
- 共通課程、モバイルアプリ自動化の選択課程、発展課題、参考資料の役割の違いは、本文中で明記する。
- `BR`、`AC`、IDの命名規則（grammar）、機械処理用の見出し（machine-consumed heading）は、定義されたリテラルを変更しない。
- アプリケーション上の判断に必要なUIの文言（UI copy）は、画面に表示されるリテラルをそのまま扱う。

## Part 1の前提

Part 1ではGitHubアカウントの取得を必須としません。

受講者に必要なのは、Scenario ShopとPlaywrightをローカル環境で動作させられる状態です。リポジトリの取得方法は `git clone` に限定せず、必要に応じて配布ZIPファイルなどを利用しても構いません。

Maestroの演習に進む段階では、ネイティブアプリの実行環境が追加で必要になります。準備完了の確認は、リポジトリ内のAndroid手順書（runbook）、Trainingベースライン、Native CIの定義に基づいて行います。

### Web / Playwright 開始ゲート

- 対応するバージョンの Node.js / pnpm を利用できること。
- 依存パッケージをインストールできること。
- Scenario Shop Webを、作業ツリー（worktree）専用の `PLAYWRIGHT_BASE_URL` で起動できること。
- `pnpm run training:web:baseline` を実行し、`training-chromium` で正常終了すること。

モバイルWebの基準確認は、P1-05でビューポートと `training-mobile-chromium` を学んだ後に行います。P1-04の開始ゲートではデスクトップブラウザでの基準確認までを対象とします。

### モバイルアプリ自動化の選択課程 / Maestro 開始条件

Native / MaestroはPart 1共通課程の必須前提ではありません。共通課程の必須要件はP1-06までであり、モバイルアプリ自動化の選択課程を希望する受講者のみが以下のMaestro開始条件を満たす必要があります。選択しない受講者はP1-07をスキップしてP1-08へ進み、P1-07を修了した受講者もP1-08で合流します。

Windowsローカル環境での標準ハンズオンは、USB接続された実機のAndroid端末を基準とします。Androidエミュレータ / AVDは任意の補助的な手段であり、Part 1の必須修了条件ではありません。

- JDKおよびAndroid SDKを利用できること。
- Android端末側で開発者向けオプション、USBデバッグ、ADBの接続許可を設定できること。
- `adb devices -l` を実行し、対象端末のシリアル番号のステータスが `device` になっていることを確認できること。
- 端末を起動して画面ロックを解除し、Maestroから操作可能な状態にできること。
- Scenario Shopのネイティブアプリをビルドし、端末にインストールできること。
- Maestroから最小限のFlowを実行できること。

ネイティブアプリの標準学習経路としてはAndroid環境を採用します。iOSについては現在のリポジトリ上での保証がビルドのみ（Build-only）であるため、Part 1およびPart 2における実行完了条件には含めません。iOSシミュレータを説明や比較のために利用する場合でも、テストのPASS実績として記録することはしません。

Git、GitHub、プルリクエスト、GitHub ActionsはPart 2で扱います。

## Part 2の前提

Part 2ではGitHubを利用するため、有効なGitHubアカウントを所持していることを前提とします。

Part 2の選択課程を開始する前に必要な共通課程の前提はP2-05までであり、P2-06のNative CIとMaestroは選択式の課程です。P2-06を選択しない受講者はスキップしてP2-07へ進み、選択して完了した受講者もP2-07で合流します。P2-06を選択する場合は、Part 1の選択課程で身につけたMaestroの実行能力を、選択課程内の前提条件としてあらかじめ満たしておく必要があります。Part 1の選択課程を受講せずにPart 2のNative課程を選択する場合も、同様にこの前提要件を事前に満たしてください。

ただし、受講者が本リポジトリ本体へのプッシュ権限を持つことは前提としません。Part 2のGitHub操作では、受講開始前に用意された、受講者が書き込み可能な演習用リポジトリ（Training Copy）を使用します。

Git / GitHubの基礎演習では、次のいずれかの標準的な方法を利用できます。

- 自身のアカウントにリポジトリをフォーク（Fork）する。
- 運営側が事前学習の開始前に用意したTraining Copyを使用する。

既存リポジトリの本番向けCI/CD設定やCloudflareのシークレットを直接使用することは、演習の前提に含めません。既存のワークフローは完成例として参照するにとどめ、演習用のワークフローは安全に分離された環境で扱います。

**CIのハンズオン、C12の評価、およびPart 2の最終確認では、事前準備済みのTraining Copyを正式な作業経路とします。** フォーク環境はP2-01〜P2-03のGit / GitHubの基礎学習でのみ利用可能です。フォーク環境での実行ログ、チェック結果、成果物は、C12やPart 2の最終修了のエビデンスとしては認められません。Training Copy上では、受講者がブランチ作成、コミット、プッシュ、プルリクエスト、GitHub Actionsの実行結果やアーティファクトの確認までを行いますが、リポジトリ管理者権限、シークレット管理、ブランチ保護ルールの変更、ワークフロー権限の変更、GitHub Appsの設定などは求められません。

本番環境のシークレットを受講者に配布し、既存の本番ワークフローを無理にパスさせるような運用は行いません。

## 共通課程の修了条件

共通課程の修了時に目指す姿は、「現場に入りたての汎用的なテスト自動化エンジニア」です。評価の詳細と必須成果物は[習熟度評価基準](./02_competency-rubric.md)を正本とし、共通課程の修了にネイティブアプリ環境の実行結果は求められません。

- Part 1 共通課程: `C01〜C07 + C09〜C10`、対象範囲を限定したレベル2
- Part 2 / 最終共通課程: `C01〜C07 + C09〜C12`、対象範囲を限定したレベル2
- `C08` はモバイルアプリ自動化の選択課程であり、共通課程の修了条件には含みません。

成果物や実行記録はリポジトリ内に正しく保存・記録されていれば成立し、外部への提出は共通課程の修了条件とはしません。

### 自習と講師支援の境界

学習内容、演習における判断基準、自己確認、つまずきからの復帰手順、完了条件、評価観点は、受講者向け教材を正本とします。講師や運営担当は、環境のセットアップ、アカウントや権限の付与、端末の準備、演習用リポジトリ（Training Copy）の払い出し、インフラやツールチェーンの障害対応などを支援しますが、非公開の情報や属人的な個別判断を修了条件に組み込むことはありません。

### Part 1からPart 2への移行

Part 1を配布ZIPなどのGit管理されていない環境で進めた受講者もいるため、Part 2の開始時に作業環境を明確に切り替えます。

標準的な移行の流れは以下のとおりです。

```text
Part 1
Scenario ShopのZIP / ローカルコピーで学習
↓
Part 2開始
Git管理されたqa-training-storeの演習用コピーを用意
↓
Part 1で作成したテストコードや学習成果物を引き継ぐ
↓
Gitで変更履歴を管理する
↓
準備済みのTraining Copyのリモート／プルリクエストへ進む
```

ここで別のサンプルアプリに切り替えるわけではありません。**コードベースとテスト対象は同じScenario Shopのまま、変更管理が可能な作業環境へ移行します。**

Part 1の作業フォルダ内で単に `git init` を実行し、教材本来のコミット履歴を失ってしまう方法は標準経路としません。Gitのコミット履歴を保持した使い捨て可能な演習用リポジトリ（Training Copy）に対して、Part 1の成果物を安全に引き継ぎます。元コミットのSHAの特定、許可リストの適用、ファイルの複製手順の検証などは、あらかじめ用意された配布手順に従って運営側が実施し、受講者必須の学習内容に隠れた前提として上乗せすることはありません。受講者は、提供されたTraining Copy上でブランチ作成、コミット、プッシュ、プルリクエスト、実行結果や成果物の確認を行います。

## ノーコード・ローコード経験との接続

AutifyやMagicPodなどのツールで培った経験を無駄にせず、共通する概念に対応づけて整理します。

| 共通概念 | ノーコード・ローコード | Playwright / Maestro |
| --- | --- | --- |
| テストシナリオ | GUI上のシナリオ | spec / Maestro Flow |
| 操作 | ステップ（Step） | アクション（Action） |
| 要素指定 | 要素（Element）指定 | Locator / UI Test ID |
| 検証 | アサーションステップ | `expect` / `assertVisible` |
| 前提状態 | 初期化設定 | Seed / Seed Scenario / Reset |
| 共通処理 | グループ / 共有ステップ | Helper / POM / Fixture |
| 実行結果 | ダッシュボード | Report / Trace / JUnit / Artifact |

ツールや記述スタイルが変わっても、「テスト対象」「前提条件」「操作」「期待結果」「テストデータ」「実行結果」という基本的な構造は変わらないことを理解します。

## 学習順序

### Part 1

Part 1では、まずテスト自動化の一連のサイクルを最後まで体験します。

POM（Page Object Model）やFixtureなどの保守性を高める設計手法は、カリキュラムの後半に配置しています。最初から高度な共通化を導入すると、受講者が「なぜそれが必要なのか」を理解しないまま、コードのパターンだけを形骸的に模倣してしまうためです。

基本的な学習順序は以下のとおりです。

1. テスト自動化の基本概念を理解する。
2. Scenario Shopの画面や仕様を探索する。
3. スプレッドシートを用いてテストを分析・設計する。
4. 自動化の対象を選定する。
5. Playwrightのテスト作成に必要なJavaScript / TypeScriptの最小限の知識を学ぶ。
6. Playwrightでテストを実装する。
7. 実行結果を分析する。
8. モバイルアプリ自動化の選択課程を選んだ受講者は、P1-07でMaestroによるネイティブアプリの自動化を実施する。
9. 共通課程の受講者はP1-06完了後にP1-07をスキップしてP1-08へ進み、選択課程の受講者もP1-07完了後にP1-08へ合流する。P1-08では共通課程としてPlaywrightテストの保守課題を扱い、選択受講者のみネイティブアプリの成果物が追加される。
10. テスト管理や保守上の課題を洗い出す。
11. Helper、POM、Fixture、Seed Scenarioなどを活用してテストコードを改善する。
12. 総合演習を実施する。

Part 1の前半では、Seed Scenarioによるリセットや実行記録の収集の仕組みは教材側が提供するテスト基盤（Test Harness）として利用し、Fixture内部の責務の分離や共通化設計そのものには踏み込みません。リポジトリ既存の `e2e/web/fixtures.ts` の内部設計を教材として読み解くのは、P1-06までの共通課程を完了し、P1-07をスキップまたは完了してP1-08に到達した後の段階です。

### Part 2

Part 2では、Part 1で作成したテストを一般的なソフトウェア開発プロセスへと接続します。

1. ソフトウェア開発における変更管理を理解する。
2. Gitを用いて変更履歴を管理する。
3. GitHub上でプルリクエストを作成し、レビューを行う。
4. 継続的インテグレーション（CI）の必要性を理解する。
5. GitHub Actionsを用いてテストを自動実行する。
6. Playwrightのレポートや成果物（アーティファクト）を管理する。
7. モバイルアプリ自動化の選択課程を選んだ受講者は、P2-06でAndroidのビルド＋実行時E2Eテストと、iOSのビルド検証のみ（Build-only）の保証境界について学ぶ。
8. 共通課程ではP2-06をスキップし、P2-07でWebの品質ゲート、ビルド／テスト成果物、失敗時の記録、フェイルクローズ（fail-closed）の条件を設計する。デプロイやスモークテストなどは、発展課題・参考資料として比較検討する。
9. Scenario Shopを題材に、テスト自動化の導入設計演習を行う。

## 教材の進め方

各モジュールは、原則として以下の構成になっています。

1. 学習目標
2. 背景・考え方
3. Scenario Shopで確認する対象
4. ハンズオン
5. 考察
6. 確認問題
7. 完了条件

受講者には「手順書どおりに操作して終わり」にするのではなく、自分がその設計や実装を選んだ理由を言語化して残すことを求めます。

## 完成済みの実装を最初から見せすぎない

Scenario Shopには、すでに高度な自動化の実装例が用意されています。

たとえば以下のファイル群です。

- `e2e/web/fixtures.ts`
- `e2e/web/phase1-required.spec.ts`
- `playwright.config.ts`
- `maestro/`
- `.github/workflows/ci.yml`
- `.github/workflows/native-ci.yml`

これらは貴重な学習材料ですが、演習の前に正解コードとしてそのままコピーさせることはしません。

まずは受講者自身が小さな設計と実装を自力で行い、その後にリポジトリ既存の実装を読んで、以下の観点で比較・検討します。

- 自身の設計とリポジトリの実装とで、何が異なっているか。
- なぜリポジトリ側の実装はそのような構造を採用しているのか。
- 自身の実装のまま進めた場合、どのような条件下で問題が生じるか。
- リポジトリの実装が必ずしも唯一の正解とは限らない点はどこか。

特に `e2e/web/fixtures.ts` については、Part 1前半では模範解答として読ませず、後半の保守設計のモジュールに入ってから初めてその責務と構造を分析します。

## 「唯一の正解」よりも判断基準を学ぶ

特に以下の項目については、カリキュラムとして単一の正解を提示しません。

- E2Eテストに含めるべき検証スコープ
- 自動化すべきテストと手動に残すべきテストの線引き
- Page Object Model（POM）を採用するかどうか
- Helper関数による共通化で十分か
- 前提状態のセットアップをFixtureにどこまで組み込むか
- 複数画面にまたがる操作をどの粒度で切り出すか
- UI Test IDをどの要素に付与するか
- リトライ（Retry）設定を導入するかどうか
- プルリクエスト（PR）の時点でどこまでテストを実行するか
- Nightly（夜間バッチ）実行に何を回すか
- CIの並列実行をどの程度まで拡張するか

Scenario Shopの具体的な要件やコンテキストを踏まえ、メリット、デメリット、保守コスト、品質リスクを天秤にかけて受講者自身が判断できるように導きます。

## 到達度の評価

知識を問う確認テストだけでなく、作成した成果物と、その設計意図を論理的に説明できる能力を重視して評価します。

受講者が以下の問いに対して自身の判断理由を論理的に説明できれば、単なるツールの操作習得を超えた、実践的な理解に到達していると判断します。

- なぜそのテストケースを自動化の対象として選んだのか。
- なぜその初期状態（Seed Scenario）を採用したのか。
- なぜそのLocator（要素特定手法）を選定したのか。
- テスト失敗時に、どのログやアーティファクトを確認して原因を切り分けたか。
- なぜその共通化のアプローチ（Helper / POM / Fixture）を選択したのか。
- なぜそのテストをPR、mainブランチ、Nightlyのいずれのタイミングで実行する設計にしたのか。
- なぜそのJobを品質ゲート（Quality Gate）のブロッキング条件に含めたのか。
