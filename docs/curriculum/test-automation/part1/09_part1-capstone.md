# Part 1-9: 総合演習

この総合演習では、既存の正式な回帰テストを答えとして丸写しするのではなく、現在の正式な仕様書をもとにカート機能における最小限のリスクを一通り検証します。Part 1の共通課程は共通の学習経路のみで修了でき、モバイルアプリ自動化の選択課程は追加の選択肢となります。また、発展課題はさらなる挑戦のための追加課題です。

## 学習目標

- Part 1共通課程の C01〜C07 および C09〜C10 を、一連の明確な対応関係として結び付ける。
- ゲストカート、ログイン、チェックアウトのうち、どこまでをWeb E2Eテストの対象とするかを根拠とともに判断する。
- トレーニングのベースライン、演習、実行記録、失敗分類について自力で説明できるようにする。

## 中核: カートジャーニー（共通課程の必須範囲・Web）

中核課題は、Playwrightを用いたWebカートジャーニーの自動化によって修了できます。モバイルアプリ自動化の選択や、Android / iOSでの実行は共通課程の前提条件には含まれません。

1. [`cart.md`](../../../spec/features/cart.md) のビジネスルール（BR）および受入基準（AC）を読み込み、ゲスト、会員、状態、データの関係を整理する。
2. 受講者用の作業表にリスク、条件、境界値、期待結果を記録し、完了時には4つのCSVファイルを`handoff-root/workbook/`へ集約する。リポジトリ内のサンプルCSVファイルに回答を直接追記しないこと。
3. [`state-and-scenarios.md`](../../../spec/state-and-scenarios.md)で必要な初期状態を確認し、該当する箇所のみ[`seed_catalog.md`](../../../07_testability/seed_catalog.md)や`/guide`画面で確認する。実装段階でのみ、実行可能なソースコードから具体的なIDを照合する。
4. `pnpm run training:web:baseline`でベースラインテストを実行し、必要なカートの検証条件を`exercises/`配下に実装した上で、P1-6で整備したレシート出力付きの実行入口からデスクトップ向けの演習テストを実行する。
5. `training-mobile-chromium`を実行し、レスポンシブ表示に関するリスクを1件検証する。
6. 受講者用ワークブックに設計判断、実行記録、失敗分類を記録し、`03_automation-mapping.csv`と`04_execution-improvement.csv`を`handoff-root/workbook/`へ集約する。

P1-6のC09診断演習で作成した失敗時の実行記録、原因、対策、修正後の再実行記録は、同一の`test_case_id`における異なる`run_context`として再利用します。P1-9のために診断用の失敗ケースを改めて作り直す必要はありません。

## モバイルアプリ自動化の選択課程（選択時）

P1-7を選択した受講者は、P1-6までの共通課程における前提条件を満たした上で、P1-7のネイティブ開始条件とC08に求められる最低限の成果物を確認します。実機Android、ネイティブビルド成果物、Maestroの実行記録は選択課程の対象であり、Part 1共通課程の修了要件には含まれません。詳細はP1-7および [習熟度評価基準](../02_competency-rubric.md) を参照してください。

選択課程を受講しない場合やネイティブ環境を利用できない場合でも、共通課程における「未着手（`blocked`）」や「未完了（`not_completed`）」としては扱いません。

ネイティブ課程を選択した場合に限り、P1-7で作成した演習コードの差分とMaestroの実行成功ログなどの成果物を、中核課題の成果物とは個別に確認します。なお、ベースラインの成功結果（PASS）やiOSのビルド確認のみをもって、これらの成果物の代わりとすることはできません。

## 発展課題

本課題は、中核課題の代替ではなく、さらなる習熟を目指す受講者向けの追加課題です。

- 購入ジャーニー: ゲストカート → ログイン → カート統合 → 配送先住所入力 → チェックアウト → 決済 → 注文完了
- 失敗と回復: 決済失敗 → 再試行 → 決済完了
- ロール間ライフサイクル: 顧客の購入 → 管理者・運用者の発送処理 → 顧客のレビュー投稿

発展課題に取り組む場合も、仕様のBR／AC、シナリオのリセット手順、テストレイヤーの選定理由、実行記録を中核課題と同様の形式でリポジトリ内に記録・保存してください。外部への提出は必須ではありません。

## 自己確認

自身の成果物を参照しながら以下の項目を確認できれば、Part 1共通課程の修了を自己判定できます。

- `cart.md`のBR／ACから抽出したリスク、テストケース、テストレイヤー、使用ツール、および実行記録の対応関係を説明できること。
- ゲスト／会員、状態／データ、シナリオ／リセットの境界について、信頼できる唯一の情報源（SSOT）である仕様書に戻って確認できること。
- Webのベースラインテストと自身で作成した失敗演習を明確に区別し、失敗分類、原因の仮説、実行記録、未確定の範囲を説明できること。
- C10において、実在する保守上の問題を用いたか、該当する問題がなければ決定的な教材演習に切り替えたかを明示し、改善前後の別実行の記録と、テスト目的が維持されていることを提示できること。
- 自動化対象外とした条件や後回しと判断した条件について、そのリスクと判断理由を併せて説明できること。
- ネイティブ課程を選択しない共通課程のみでも修了判定が可能であり、ネイティブ課程を選択した場合にのみその成果物を個別判定できること。

## 修了確認コマンド

Part 1の成果物を`<handoff-root>`へ集約したら、受講者自身で以下の正式な確認コマンドを実行します。なお、`<handoff-root>`の部分は、ワークブック、受講者コード、エビデンス、レシート、自己確認結果を集約した固定ディレクトリパスに置き換えてください。

```bash
pnpm run training:completion:check -- --mode common --root <handoff-root>
```

実行後に生成される`<handoff-root>/completion-receipt.json`を開き、少なくとも以下の項目を確認します。

- `status`: 完了条件を満たしているかの機械的な判定結果。
- `missing_requirements` および `reasons`: 不足している要件と、最初の手順に戻るべき理由。
- `checked_outputs`: 引継ぎ成果物、ワークブック、実行記録、受講者コード、エビデンス、自己確認結果などの検査結果。
- `semantic_understanding`: 自動判定の対象外となっている理解度項目（通常は`NOT_EVALUATED`と表示されます）。

このレシートにおける`PASS`の表示は、成果物のディレクトリ構成、トレーサビリティ、実行記録が所定の規約を満たしていることを示す機械的な検証に過ぎず、設計の妥当性や受講者の理解度を自動採点したものではありません。Part 1の完了は、レシートの`PASS`判定、自己確認の記述内容、および自身の成果物に基づいた評価ルーブリックの確認をすべて揃えた上で、受講者自身が総合的に自己判定してください。`PASS`とならなかった場合は、`reasons`や`missing_requirements`に示された最初の指摘項目に戻って修正を行い、確認コマンドを再実行してください。

### 復旧手順

成果物の対応関係や失敗分析の整合性が取れない場合は、まず対象のBR／AC、リスク、テストケース、実行条件、実行記録を順に照合し、不足が生じた最初の工程まで戻って見直してください。テストを実行できない場合は、ブラウザ、初期データ投入やリセット、テスト制御、実行環境の要因に切り分けて記録します。なお、ネイティブ実行環境の不備は共通課程の未達理由には当たらないため、ネイティブ課程を選択している場合に限りP1-7の復旧手順に戻って対処してください。

## 完了条件

- Part 1共通課程: 対象範囲を限定したレベル2基準（C01〜C07 および C09〜C10）を達成していること。各習熟項目に求められる最低限の成果物については [習熟度評価基準](../02_competency-rubric.md) を参照すること。なお、C08、実機Android環境、およびネイティブ成果物は共通課程の修了要件に含まれない。
- 仕様、リスク、テストケース、テストレイヤー、ツール、実行記録の一連の対応関係を説明できること。
- 自動化を行わないと判断した条件、または後回しとした条件を少なくとも1つ挙げ、その理由を説明できること。
- ベースラインのテストコード・実行結果と、失敗演習の内容を混同せず明確に分離していること。
- 共通課程の成果物が、Webカートジャーニー、各種対応関係、失敗分析として独立して完結しており、ネイティブ課程やベースラインの実行記録と混在していないこと。
