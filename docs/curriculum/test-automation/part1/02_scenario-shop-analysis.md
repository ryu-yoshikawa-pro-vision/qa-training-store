# Part 1-2: Scenario Shopの探索とテスト対象分析

## 学習目標

- 自動化コードを実装する前に、テスト対象を十分に調査・分析できる。
- 画面、ロール、状態、データ、業務ルール、境界条件を体系的に整理できる。
- リスクの影響度（Impact）、発生確率（Likelihood）、優先度（Priority）を、単なるラベルの割り当てではなく判断理由とともに説明できる。
- `/guide` やシードシナリオ（Seed Scenario）を、仕様と観察結果を結び付ける補助情報として活用できる。
- 単一の画面単位にとどまらず、ユーザージャーニーと状態遷移の観点からテスト対象を捉えられる。

- ホーム（Home）

### Customer（顧客向け機能）

- お届け先住所（Address）
- 購入手続き（Checkout）
- 決済（Payment）
- 注文履歴・詳細（Order）

### Admin / Operator（管理・運用向け機能）

- 商品管理
- 在庫管理
- 注文管理
- レビュー管理
- ユーザー管理

すべての画面を暗記する必要はありません。どの機能がどのロールや内部状態に依存しているのかを大まかに掴むことが目的です。

## Lesson 2: ロールを整理する

Scenario Shop には以下の4つのロール（Role）が存在します。

- Guest（ゲスト）
- customer（一般顧客）
- operator（運用担当者）
- admin（システム管理者）

ロールによって許可されている操作が異なるため、同じURLにアクセスした場合でも期待される結果が変わる可能性があります。

スプレッドシートやメモに、以下のように整理してみましょう。

| ロール | 主な操作 | アクセス制約 | 重点的なテスト観点 |
| --- | --- | --- | --- |
| Guest | 商品閲覧、カートへの追加 | アカウント機能の利用不可 | カート操作、ログインへの導線 |
| customer | 商品購入、注文履歴の確認、レビュー投稿 | 管理画面へのアクセス不可 | 購入手続き（Checkout）、決済処理（Payment） |
| operator | 日常の運用管理業務 | ユーザー管理機能の一部制限 | 在庫管理、配送管理 |
| admin | すべての管理機能 | 最後の管理者を削除・無効化させない保護 | ユーザー管理、商品管理 |

## Lesson 3: 状態を整理する

UIテストは、画面の見た目や要素の配置だけを見ていては十分に設計できません。

たとえば同じ商品詳細画面であっても、商品の「状態」によって期待される動作は大きく異なります。

- 在庫あり
- 在庫切れ
- 残りわずか（低在庫）
- セール中
- セール終了
- 1人あたりの購入上限数に達している

同様に購入手続き（Checkout）画面でも、以下のような状態のバリエーションが存在します。

- 通常状態
- カートのバージョン不一致（編集中に他で変更が発生）
- 商品価格の変更
- 在庫状況の変動
- 決済成功
- 決済拒否（エラー）
- 決済処理中

## Lesson 3.5: リスクの優先度を検討する

テストにおけるリスクとは、単に「何かが起きるかもしれない」という漠然とした不安ではありません。「問題が発生した際にどのような影響が出るか」「その問題はどれくらい発生しやすいか」を具体的に捉える必要があります。以下の3つの要素を個別に検討します。

- **影響度（Impact）**: そのリスクが実際に顕在化した際、誰にどのような不利益が生じるかを評価します。売上金額、在庫数、決済処理の整合性、あるいはユーザーの購買体験の中断などへの影響度合いを考えます。
- **発生確率（Likelihood）**: そのリスクの状況にどれほど到達しやすいかを評価します。日常的な通常操作だけで起こり得るのか、あるいは特定のタイミングや複雑な前提条件が重なって初めて起こるのかを確認します。
- **優先度（Priority）**: どのリスクから優先して確認・対策すべきかを判断するために設定します。影響度と発生確率を機械的に掛け算して数値を出すこと自体が目的ではなく、その優先順位付けにした明確な理由を第三者に論理的に説明できることが重要です。

### カート機能における具体例

「購入上限数を超えた状態でカートが成立してしまう」というリスクを考えてみましょう。

1. **影響度（Impact）**: 購入者への誤った案内にとどまらず、注文合計金額、在庫引き当て数、受注処理全体の整合性に深刻な不整合をもたらす可能性があります。この不具合が発生した際、どの業務プロセスが破綻するかを言語化します。
2. **発生確率（Likelihood）**: 通常の数量変更や追加操作だけで簡単に上限を超えられてしまうのか、それとも在庫の増減や特殊なシードシナリオの適用といった特定の条件下でのみ発生するのかを確認します。
3. **優先度（Priority）**: 被害の大きさと到達のしやすさを総合的に勘案し、早期に対策・確認すべきかを判断してその根拠を記述します。たとえば「影響度は極めて大きいが、上限を超えるシチュエーション自体は境界値操作で確実に押さえる必要があるため、評価を `高 / 中 / 高` とする」といった説明が成り立ちます。

これは評価の数値を暗記するための例ではありません。自身が観察したカートや購入手続きのリスクについて、「誰にどんな影響があり」「どのような条件で発生し」「なぜその優先度で確認するのか」を筋道立てて説明できるようにしてください。

仕様書から状態と期待結果を整理した後は、`docs/spec/state-and-scenarios.md` および `docs/07_testability/seed_catalog.md` の該当箇所を確認し、各シナリオの目的と初期状態を把握します。続けて `/guide` 画面を開き、実際のUIや操作の起点、観察対象の状態を確認しましょう。なお、このレッスンでは TypeScript の実装コードを読む必要はありません。

## Lesson 4: ユーザージャーニーの視点で捉える

単一の画面一覧だけでなく、ユーザーの業務や行動の一連の流れ（User Journey）としてテスト対象を整理します。

例:

```text
Guest（未ログイン）
↓
商品を探す
↓
商品詳細を見る
↓
カートに追加する
↓
ログインする
↓
ゲスト時のカート内容を統合する
↓
購入手続きへ進む
↓
決済を行う
↓
注文を完了する
↓
配送状況を確認する
↓
レビューを投稿する
```

このように一連のジャーニーとして捉えることで、1画面だけのテストでは見落としがちな「機能間の連携時に潜むリスク」を洗い出すことができます。

## Lesson 5: データと状態遷移に着目する

Scenario Shop では、ユーザーのUI操作に伴ってシステム内部のデータや状態が遷移します。

例:

- カート内の商品数量が変わる。
- チェックアウトセッション（Checkout Session）が発行される。
- 決済ステータスが更新される。
- 注文レコードが作成される。
- 在庫数（Inventory）が減算される。
- 配送ステータス（Shipment）が進行する。
- 商品のレビュー集計（Review Summary）が再計算される。

「ボタンがクリックできるか」という表面的な確認にとどまらず、「操作の実行後に、内部の何がどう変わるべきか」を分析します。

## Lesson 6: `/guide` とシナリオの照合

`/guide` 画面では、検証用の固定アカウント、ロール、シナリオ、確認用画面、安全に初期化できるリセット先などを一覧で確認できます。

仕様と状態の分析を終えたら、`docs/spec/state-and-scenarios.md` と `docs/07_testability/seed_catalog.md` の必要な節を読み、`/guide` で現在の画面を観察しながら、以下の項目を受講者用のメモとして整理します。

- そのシナリオの目的は何か。
- 開始時の初期状態はどのような状態か。
- 初期のログイン状態はどうなっているか。
- 推奨される利用アカウントはどれか。
- どのルート（URL / 画面）を確認すべきか。
- リセットを実行した場合、どこに戻るか。

ここで重要なのは、「シードシナリオは単なる便利なテストデータ」ではなく、「テスト前提となる状態を確実に再現可能にするための自動化設計の一部である」と理解することです。具体的なシナリオID、シード値、固定時刻（Fixed Clock）など、実行ファイルやソースコードに直接定義されている値は、このレッスンでは深追いしません。後の Playwright 実装フェーズに進んでから、必要な値だけを実行コード側で確認します。

## ハンズオン1: カート機能の分析

カート機能について、以下の観点を網羅的に洗い出します。

- 実行ロール
- 初期状態
- 入力値
- 実行する操作
- 内部および画面の状態変化
- 正常系
- 異常系
- 境界値
- 関連する画面

最低限、「在庫切れ」と「購入上限数」に関するパターンは必ず含めてください。

分析が完了したら、受講者自身の作業表に次の2つの識別子を作成します。`TARGET-CART-101` は調査対象となる機能・観点、`RISK-CART-101` はその対象において発生し得る影響の大きいリスクです。既存の `TARGET-CART-001` や `RISK-CART-001` を上書きしたり、模範解答として丸写ししたりせず、自身が実際に観察した条件と、根拠とした仕様書（Spec / BR / AC）を記録してください。後続の P1-03 では、このリスクだけに絞るのではなく、さらに別のリスクも追加してテストケースへと細分化していきます。

`RISK-CART-101` には、影響度（Impact）、発生確率（Likelihood）、優先度（Priority）のラベルに加え、それぞれの評価理由を明記してください。もし値を決めきれない場合は、影響を受けるユーザーや業務範囲、通常操作での再現性、追加で確認すべき事項を書き出してから最終評価を下します。

## ハンズオン2: チェックアウトジャーニーの分析

ゲスト（未ログイン）状態から購入完了に至るまでのプロセスを図として整理します。

以下のポイントを明確に表現してください。

- どのタイミングでログインが必要になるか
- ゲストカートの統合処理
- お届け先住所の指定
- 決済情報の入力
- 決済処理中（Processing）
- 完了（Complete）と失敗（Failed）の分岐
- 失敗時の再試行（Retry）

図を作成した上で、「どのステップが破綻したときに、最もビジネス影響が大きいか」を考察します。

## AIエージェントによる仕様分析

[AI活用演習のテスト対象](../../../training/ai-assisted-qa/README.md)を参照して、カート機能を対象に次を実施します。

## 確認問題

1. 画面一覧だけをベースにE2Eテストを設計すると、どのような重大な要素を見落としやすくなるか。
2. ロールと状態をそれぞれ独立した軸として整理すべき理由は何か。
3. `out-of-stock`（在庫切れ）のようなシードシナリオを用意することは、テスト自動化にどのような価値をもたらすか。
4. 決済処理において「決済成功」のパターンだけを確認するのでは不十分な理由は何か。
5. UI操作の実行後に、画面の見た目だけでなく内部状態の変化まで考慮しなければならないのはなぜか。
6. 影響度（Impact）と発生確率（Likelihood）を別々の指標として評価すべきなのはなぜか。
7. 優先度（Priority）を単なる機械的な計算結果（掛け算など）で機械的に決定してはならない理由は何か。

## 自己確認

### 回答の最低判定基準

- 画面一覧の確認だけでは、ロール、状態（State）、データ、状態遷移、機能間の連携リスクを見落としてしまう理由を説明できていること。
- ロールと状態を別軸として整理し、アクセスするURLが同じであっても期待結果が変化する具体例を1つ以上示せていること。
- `out-of-stock` などのシードシナリオを「テストを決定論的な初期状態に戻す仕組み」として説明し、テストデータを手作業で都度作成し続ける運用の破綻と結び付けて語れていること。
- 決済の成功系だけでなく、拒否・処理中・再試行、あるいは在庫数やカートバージョンの競合状態を挙げ、一連のジャーニーに及ぼす影響を説明できていること。
- UI操作後に検証すべき内部状態を1つ挙げ、それが `docs/spec` 内のどの BR / AC や状態・シナリオ仕様に基づいているかを明示できていること。
- 「購入上限を超えたカートが成立してしまう」などのリスクを1つ取り上げ、影響度・発生確率・優先度を、被害範囲・到達条件・検証の緊急度といった具体的根拠とともに説明できていること（単なる掛け算の数値を理由にしていないこと）。

### リカバリー

ロール、状態、シードシナリオのいずれかの概念について明確に説明できない場合は、レッスン2〜6を読み直し、カートまたは購入手続きの1つの条件を「ロール → 初期状態 → アクション → 期待結果 → 変化する内部状態」のフォーマットで書き直してください。固定値や設定値が見当たらない場合は前述のSSOT（仕様書）に立ち返り、万一リンク先が開けない・権限がないといった事象があれば、環境起因の問題として分けて記録してください。

## 完了条件

- Scenario Shop における主要なロールの権限と役割を説明できる。
- 1つ以上のユーザージャーニーを図として表現できる。
- カートまたは購入手続きについて、正常系・異常系・境界条件を整理できる。
- 少なくとも1つのリスクについて、影響度・発生確率・優先度を客観的な根拠とともに記録できる。
- シードシナリオがテスト自動化の安定運用に不可欠である理由を説明できる。
