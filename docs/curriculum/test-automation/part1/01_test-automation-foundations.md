# Part 1-1: テスト自動化の基礎

## 学習目標

- テスト自動化の目的を説明できる。
- 手動テストと自動テストの役割の違いを説明できる。
- 自動化が有効な場面と、自動化しない方がよい場面を判断するための観点を持てる。
- テスト自動化を「分析 → 設計 → 実装 → 実行 → 結果分析 → 改善」のプロセスとして捉えられる。
- AutifyやMagicPodなどの経験を、Playwright / Maestroへ共通概念として接続できる。

## 教材

**このモジュールでは、このリポジトリのScenario Shopを使用します。**

期待動作の確認は [`docs/spec/README.md`](../../../spec/README.md) とNormative Feature（例: [`cart.md`](../../../spec/features/cart.md)）のBR / ACから始めます。画面で観察した結果はObserved Evidenceとして記録し、Specの代わりにしません。

最初はテストコードを読み込むのではなく、Scenario Shopを「テスト対象」として観察します。

## Lesson 1: テスト自動化とは

テスト自動化は、単に人間のクリック操作を置き換えることではありません。

自動化によって主に狙うものは次です。

- 繰り返し確認の高速化
- Regressionの再現性向上
- 人間が行う単純反復作業の削減
- 複数環境・条件の継続確認
- 変更に対する早いFeedback
- 失敗時のEvidence確保

一方で、自動テスト自体にも実装・保守コストがあります。

そのため、「自動化率を高くすること」ではなく、「自動化によって得られる価値がコストを上回るか」を考えます。

## Lesson 2: 手動テストと自動テスト

Scenario Shopを使って、同じ確認を手動と自動で比較します。

例:

- 商品詳細を開く。
- Variationを選ぶ。
- Cartへ追加する。
- Cartへ追加されたことを確認する。

手動では、人間が画面を見ながら柔軟に判断できます。

自動では、前提条件、操作対象、期待結果を明確に定義する必要があります。

### 考えること

- 1回だけの確認なら自動化する価値はあるか。
- 毎回同じRegressionで確認するならどうか。
- 見た目の「なんとなく違和感」を完全に自動判定できるか。
- Human Exploratory Testと自動テストは競合するのか、補完するのか。

## Lesson 3: 自動化しやすいテスト

一般に次の特徴があるテストは自動化候補になりやすいです。

- 繰り返し実行される。
- 前提状態を再現できる。
- Pass / Failを明確に判定できる。
- Business Riskが高い。
- Regressionとして継続的に価値がある。
- 人間が繰り返すと時間がかかる。

Scenario Shopでは、Cart、Login、Checkout、Payment、Role制御、在庫境界などが教材になります。

## Lesson 4: 自動化しにくいテスト

次は慎重に判断します。

- 一度しか確認しない。
- UIが頻繁に変わる試作段階。
- 人間の感覚的評価が中心。
- 外部サービスやCAPTCHAなどの制御不能な依存が大きい。
- 自動化のための準備コストが確認価値を上回る。

自動化できることと、自動化すべきことは同じではありません。

## Lesson 5: テスト自動化プロセス

このカリキュラムでは次の流れを繰り返します。

```text
1. テスト対象を理解する
2. Riskとテスト観点を整理する
3. テストケースを設計する
4. 自動化対象を選定する
5. 自動テストを実装する
6. 実行する
7. 結果を分析する
8. 改善する
9. 運用する
```

PlaywrightやMaestroは4以降で登場します。

## Lesson 6: ノーコード・ローコード経験との対応

AutifyやMagicPodで経験している概念は、コードベースでも多くが共通します。

例:

```text
Scenario
↓
Action
↓
Assertion
↓
Result
```

Playwrightでは、これをTypeScriptコードとして明示的に管理します。

MaestroではYAML FlowとしてNative操作を記述します。

重要なのはSyntaxの違いより、前提条件・操作・期待結果を明確にする考え方です。

## ハンズオン

Scenario Shopで次を手動実行します。

1. Homeを開く。
2. 商品一覧へ進む。
3. 商品詳細を開く。
4. Variationを選ぶ。
5. Cartへ追加する。
6. Cartを確認する。

その後、次を記録します。

- 前提条件
- 操作
- 期待結果
- 手動で確認しやすい点
- 自動化しやすい点
- 自動化すると難しそうな点

## 確認問題

1. テスト自動化の目的は「人間のテストをなくすこと」か。
2. 100%自動化を目標にすると、どんな問題が起きるか。
3. Scenario ShopのCart確認はなぜ自動化候補になりやすいか。
4. Exploratory Testを完全にE2Eへ置き換えるべきでない理由は何か。
5. Autify / MagicPodとPlaywrightに共通する概念を3つ挙げる。

## 自己確認とRecovery

完了前に、ハンズオンで記録した候補から「自動化するもの」1件と「自動化しないもの」1件を選び、対象・期待結果・理由を説明します。説明が「重要だから」「人間が必要だから」だけになる場合は、Lesson 2〜4へ戻り、Risk、再現性、観察の価値を具体化します。

次はPart 1-2でScenario Shopを分析します。まだPlaywright、Git、CI、Maestroの操作を前提にしません。

## 完了条件

- テスト自動化の目的と限界を自分の言葉で説明できる。
- Scenario Shopから自動化候補を3件以上挙げ、その理由を説明できる。
- 自動化しない候補も1件以上挙げ、その理由を説明できる。
- テスト自動化プロセスを説明できる。
