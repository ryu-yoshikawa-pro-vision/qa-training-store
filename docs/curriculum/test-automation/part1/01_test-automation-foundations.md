# Part 1-1: テスト自動化の基礎

## 学習目標

- テスト自動化の目的を説明できる。
- 手動テストと自動テストの役割の違いを説明できる。
- 自動化が有効な場面と、自動化しない方がよい場面を判断するための観点を持てる。
- テスト自動化を「分析 → 設計 → 実装 → 実行 → 結果分析 → 改善」という一連のプロセスとして捉えられる。
- AutifyやMagicPodなどで培った経験を、PlaywrightやMaestroへ共通概念として接続できる。

## 教材

**このモジュールでは、本リポジトリの「Scenario Shop」を使用します。**

期待動作の確認は、[`docs/spec/README.md`](../../../spec/README.md) および正式な機能仕様書（例: [`cart.md`](../../../spec/features/cart.md)）に記載されたビジネスルール（BR）や受入基準（AC）から始めます。画面を操作して得られた挙動はあくまで「観測記録」として扱い、仕様そのものの代わりにはしません。

最初はテストコードを読み解くのではなく、Scenario Shopを1つの「テスト対象」として観察していきます。

## Lesson 1: テスト自動化とは

テスト自動化は、単に人間が行うクリック操作を機械に置き換えるだけのものではありません。

テストを自動化する主な狙いは、以下の点にあります。

- 繰り返し行う確認作業の高速化
- リグレッション（回帰テスト）における再現性の向上
- 人間が担当する単純な反復作業の削減
- 複数の環境や条件下での継続的な品質確認
- コード変更に対する素早いフィードバックの獲得
- テスト失敗時における客観的な実行記録の確保

一方で、自動テストの導入には実装コストや継続的な保守コストが伴います。

そのため、単に「自動化率の最大化」を目指すのではなく、「自動化によって得られる価値が投じるコストを上回っているか」を常に意識することが重要です。

## Lesson 2: 手動テストと自動テスト

Scenario Shopを題材に、同じ確認作業を手動と自動の両面から比較してみましょう。

例：

- 商品詳細画面を開く。
- バリエーションを選択する。
- カートへ追加する。
- カートに追加されたことを確認する。

手動テストでは、人間が画面上の細かな変化を見ながら、状況に応じて柔軟に判断できます。

対して自動テストでは、テストの前提条件、操作対象の要素、そして検証すべき期待結果をあらかじめ厳密に定義しておく必要があります。

### 考えること

- 1回きりの確認であれば、わざわざ自動化する価値はあるか。
- リグレッションテストとして毎回同じ手順を繰り返す場合はどうか。
- 画面を見て直感的に感じる「なんとなくおかしい」という違和感を、自動テストで完全に判定できるか。
- 人間による探索的テストと自動テストは、互いに競合するものなのか、それとも補完し合うものなのか。

## Lesson 3: 自動化しやすいテスト

一般的に、以下のような特徴を持つテストは自動化の有力な候補となります。

- 繰り返し実行される頻度が高い。
- 前提となるデータや画面状態を正確に再現できる。
- 成功（Pass）／失敗（Fail）の判定基準が明確である。
- 不具合が発生した際のビジネスリスクが高い。
- リグレッションテストとして継続的な価値を発揮する。
- 人手で繰り返し実行すると多大な時間がかかる。

Scenario Shopにおいては、カート、ログイン、チェックアウト、決済、権限（ロール）制御、在庫の境界値確認などが代表的な学習用題材となります。

## Lesson 4: 自動化しにくいテスト

一方で、以下のようなテストを自動化するかどうかは慎重に判断する必要があります。

- 1回しか確認しないもの。
- UIの変更が頻繁に発生する初期のプロトタイプ段階。
- 人間の主観や感覚的な評価に依存する確認。
- 外部サービスやCAPTCHAなど、テスト側で制御できない依存要素が大きいもの。
- 自動化の環境構築や実装にかかるコストが、得られる確認価値を上回るもの。

「技術的に自動化できること」と「業務として自動化すべきこと」は必ずしも一致しません。

## Lesson 5: テスト自動化プロセス

本カリキュラムでは、以下のプロセスを一連のサイクルとして繰り返し学びます。

```text
1. テスト対象を理解する
2. リスクとテスト観点を整理する
3. テストケースを設計する
4. 自動化対象を選定する
5. 自動テストを実装する
6. 実行する
7. 結果を分析する
8. 改善する
9. 運用する
```

PlaywrightやMaestroといったツールのコード実装は、ステップ4以降で登場します。

## Lesson 6: ノーコード・ローコード経験との対応

AutifyやMagicPodなどのツールで扱ってきた概念の多くは、コードベースのテスト自動化でもそのまま共通して活かせます。

例：

```text
Scenario（シナリオ）
↓
Action（操作）
↓
Assertion（検証）
↓
Result（結果）
```

Playwrightでは、上記の流れをTypeScriptのコードとして明示的に管理します。

Maestroでは、YAMLで記述したフロー（Flow）としてネイティブアプリの操作を定義します。

ここで最も重要なのは、ツールの記法（シンタックス）の違いではなく、「前提条件・操作手順・期待結果を論理的かつ明確に定義する」という共通の思考プロセスです。

## ハンズオン

Scenario Shopを使って、以下の手順を手動で実行してみましょう。

1. ホーム画面を開く。
2. 商品一覧画面へ進む。
3. 商品詳細画面を開く。
4. バリエーションを選択する。
5. カートへ追加する。
6. カート画面で追加内容を確認する。

確認後、以下の項目を記録・整理します。

- 前提条件
- 操作手順
- 期待結果
- 手動で確認しやすい点
- 自動化に向いている点
- 自動化すると難易度が高そうな点

## 確認問題

1. テスト自動化の究極的な目的は「人間のテストを完全にゼロにすること」でしょうか。
2. 自動化率100%を目標に掲げた場合、どのような問題が発生しますか。
3. Scenario Shopのカート機能の確認が、自動化の候補として適しているのはなぜでしょうか。
4. 探索的テストをすべてE2E自動テストに置き換えるべきではない理由は何ですか。
5. AutifyやMagicPodとPlaywrightに共通するテスト自動化の基本概念を3点挙げてください。

## 自己確認

### 回答の最低判定基準

- 自動化の目的に関する回答に、「反復性・再現性・フィードバックの早さ・実行記録の価値」と「人間の判断が不可欠な領域との境界」が含まれていること。
- 100%自動化の弊害として、「実装・保守コストの増大」「機械判定できない品質観点の存在」「過信による誤った安心感（False Confidence）」のいずれかが具体的に述べられていること。
- カート機能を自動化候補とする理由として、「明確な期待結果（Expected）があること」「前提状態を再現可能であること」「リグレッションテストとしての価値が高いこと」が含まれていること。
- 探索的テストに関して、「未知のリスクを人間が柔軟に探索する役割」と「自動テストによる既存機能の保証」が補完関係にあることを説明できていること。
- 共通概念として、「前提条件 / シナリオ」「操作（Action）」「検証（Assertion）」「結果（Result）」の中から3点以上挙げられていること。

### リカバリー（復習手順）

各質問の根拠をうまく説明できない場合はLesson 1〜6に戻り、同じカート確認の手順を振り返りながら「何を自動化し、何を人間に委ねるべきか」を1行ずつ整理し直してください。なお、ローカルアプリの起動可否自体はこのLessonの修了必須条件ではないため、アプリが動かない場合でも学習上の判断・考察の記録を優先して完了させることができます。

## 完了条件

- テスト自動化の目的と限界を、自分の言葉で説明できる。
- Scenario Shopの中から自動化すべき候補を3件以上挙げ、その理由を論理的に説明できる。
- 自動化すべきではない候補を1件以上挙げ、その理由を論理的に説明できる。
- テスト自動化の一連のプロセス（分析〜運用）を説明できる。
