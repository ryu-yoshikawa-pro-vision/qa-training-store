# Part 2-6: ネイティブCIとMaestro

> **モバイルアプリ自動化の選択課程:** 本レッスンはPart 2共通課程における必須レッスンではありません。開始前に必要な共通課程の前提条件はP2-5までです。Part 1の選択課程で習得するMaestroの実行能力をネイティブ側の前提条件とし、Part 1の選択課程が未修了の状態でPart 2ネイティブを選択する場合は、先にそのスキルを習得してください。本レッスンを選択しない受講者はP2-6をスキップしてP2-7へ進み、本レッスン完了後はP2-7へ合流します。

## 学習目標

- MaestroをCIで実行するために必要なネイティブ実行環境を説明できる。
- Androidの最小構成の研修用ワークフローで、ビルド、エミュレータ起動、インストール、Maestro実行までを一連で体験できる。
- AndroidビルドとAndroidエミュレータ実行のジョブを分離する理由を理解できる。
- APK成果物をビルドジョブからランタイムジョブへ受け渡す構成を説明できる。
- iOSのビルド専用CIにおいて、ビルド時のメタデータ、本番ガード、成果物を検証する流れを理解できる。
- ネイティブコードの変更がない場合に、高コストなジョブをスキップする設計を理解できる。
- JUnitレポート、スクリーンショット、logcat、シミュレータ診断など、ネイティブテスト失敗時の記録を適切に扱える。
- Web CIとネイティブCIにおけるコスト、不安定さ（フレーキネス）、実行時間の違いを考慮できる。

## 現在のリポジトリにおけるAndroid／iOS CIの位置づけ（参考・現在の構成）

2026年8月時点のリポジトリでは、AndroidとiOSで実行トリガーが異なります。

### Android

`.github/workflows/native-ci.yml` は `pull_request` と `workflow_dispatch` で起動します。

ネイティブコードの変更検知、静的チェック、本番バンドル検証（Production Bundle Guard）、Androidビルド、Androidランタイム／Maestroテスト、最終検証（verify）までを含む、プルリクエスト連動型のネイティブCIです。

### iOS

`.github/workflows/native-ios-ci.yml` は、単体では `workflow_dispatch` により手動起動できるビルド専用のエントリポイントです。ネイティブ関連の変更時は、`.github/workflows/native-ci.yml` が `native_changed=true` を検出した際にこの再利用可能ワークフローを呼び出します。

単体実行時は、iOS自動化・本番向けの署名なしRelease `iphonesimulator` ビルドとその成果物を確認するための、**手動実行によるビルド検証のベースライン**となります。ネイティブ変更時は、最上位の `native-ci` によるPR連動ルートでiOSビルドが実行され、`native-ci / verify` ジョブにおいてiOSビルドの成功が必須条件となります。なお、シミュレータへのインストール、アプリ起動、Maestro実行は現行の正式ゲートでは保証対象外です。

この現状の境界線を前提として、後続の演習では「iOSのテストをPR、main、夜間定期実行（Nightly）、手動実行（Manual）のどこに配置すべきか」をリスクとコストの観点から検討します。

## 研修用ネイティブワークフローの前提

受講者が最初から現行の `native-ci.yml` をそのまま複製して構築することは想定していません。ソースリポジトリにある `training/github-actions/*.yml` はリポジトリ管理用のテンプレートおよび参考資料であり、研修用コピー側の `.github/workflows/*.yml` が実際に実行されるアクティブなワークフローです。モバイルアプリ自動化の選択課程を開始する時点ですでにアクティブワークフローは準備されています。

- 本番デプロイや本番用シークレットには依存しない。
- Androidを標準の実行プラットフォームとする。
- Part 1で作成したMaestro Flowを1本以上CI上で実行できる。
- ビルド、エミュレータ起動、インストール、Maestro実行、実行記録の保存という一連の関係性を確認できる。
- 現在の高度な正式版ネイティブCIは、最小構成を実際に動かした後に比較対象として確認する。

研修用ネイティブワークフローは `permissions: contents: read` のみを付与し、Secret、OIDC、Environment、Deployには依存しません。対象パスの変更または手動実行（workflow_dispatch）をトリガーとして、GitHubホストのUbuntuランナー上で以下の順に処理を実行します：
ビルド → API 34エミュレータ起動 → アプリインストール → `training:native:baseline` → `training:native:exercise` → 実行ログ・記録の取得。
なお、ベースラインと演習のJUnitレポートおよび成果物は分離されており、失敗時に保存される診断用成果物とも明確に区別されます。ここでのエミュレータ実行はGitHub上のネイティブCIにおける標準経路であり、Windowsローカル環境で初学者が実機を接続して行う手順とは役割が異なります。また、正式なネイティブCIの必須ゲートを置き換えるものではなく、共通課程のファイルのみを変更した場合には、この研修用ワークフローは起動しません。

研修用ベースライン（training baseline）は、実行環境と動作経路を確認するための出発点です。P2-6選択課程の修了条件は、ベースラインを単に再実行することではなく、受講者自身が作成したネイティブ演習の差分、研修用ネイティブCIで取得したMaestro演習の成功成果物、およびトリガー・失敗ステージ・成果物・コストに関するCI設計上の判断提示です。テスト失敗時に保存される成果物はあくまで原因診断用であり、演習ステップの失敗や演習のJUnitレポートを欠いた成果物だけでは、正常終了の証跡とはみなされません。

## レッスン1: ネイティブCIがWeb CIより重い理由

Playwrightを用いたブラウザテストと比べ、ネイティブアプリのCIでは追加で以下の要素が必要になります。

### Android

- JDK
- Android SDK
- ネイティブプロジェクト生成
- Gradleビルド
- APK
- エミュレータ
- APKインストール
- アプリ起動
- Maestro

### iOS

- macOSランナー
- Xcode
- CocoaPods
- `iphonesimulator` ビルド
- ビルド時メタデータ／本番ガードの検証
- `.app` 成果物の保存

そのため、ネイティブCIの設計では、実行時間とランナーコスト（特に高額なmacOSランナーなど）を強く意識する必要があります。

## レッスン2: まず単一ジョブで全体を動かす

学習の初期段階からビルドとランタイムのジョブ分離を採用するわけではありません。

研修用ワークフローでは、まず概念を把握するため、単一ジョブ（1ジョブ）で以下のステップを一気通貫で動かします。

```text
チェックアウト
↓
依存関係・SDKセットアップ
↓
Androidビルド
↓
エミュレータ起動
↓
APKインストール
↓
アプリ起動
↓
Maestro 1 Flow実行
↓
JUnit／スクリーンショット保存
```

最初にエンドツーエンド（E2E）で動作させることで、ネイティブCIに必要な構成要素と、どこで失敗が起きやすいか（失敗ポイント）を把握します。

そのうえで、実行時間や失敗時の再実行コストという課題を体験し、実際のリポジトリでビルドとランタイムを分けている理由の学習へと進みます。

## レッスン3: Androidビルドとランタイム

単純な構成であれば、1つのジョブ内で以下をすべて実行できます。

```text
ビルド
↓
エミュレータ起動
↓
インストール
↓
Maestro実行
```

しかし、Maestroのテストだけが失敗した場合でも、ビルド処理からすべてやり直すことになってしまいます。

Scenario Shopの現行ネイティブCIでは、責務を以下のように分割しています。

```text
Androidビルド
↓
APK成果物
↓
Androidランタイム／Maestro
```

## レッスン4: APK成果物

ビルドジョブで生成したAPKをGitHub Actionsの成果物（Artifact）として保存し、後続のランタイムジョブでダウンロードして利用します。

これにより、以下の運用が可能になります。

- ビルドとランタイムの責務分離
- テスト失敗（ランタイム失敗）時の原因箇所の切り分け
- ビルド済み成果物（APK）の再利用と再実行の効率化
- APKメタデータを用いた実行記録の検証

ただし、成果物のアップロード／ダウンロード自体にもオーバーヘッドが生じるため、どこでジョブを分割するのが適切かを考える必要があります。

## レッスン5: CIエミュレータ

GitHub上のAndroidランタイムジョブでは、APKをインストールして実行するために、API 34 / `google_apis` / `x86_64` のエミュレータを起動します。なお、Windowsローカル環境で進める受講者は、本レッスンでエミュレータを起動するのではなく、Part 1の実機用ランブックを参照して実行します。

確認観点:

- APIレベル
- アーキテクチャ
- 起動完了
- adb接続
- APKインストール
- アプリプロセス

一見するとMaestroのテスト失敗に見える事象でも、実際にはエミュレータの起動遅延やAPKのインストール失敗が原因である場合があります。

## レッスン6: ネイティブテスト制御

CI環境では、テストを実行するたびに初期状態へ確実にリセットできる仕組みが必要です。

Scenario Shopではディープリンク（Deep Link）を用いたテスト制御（Test Control）機能を活用し、Maestroのテストフローからシードシナリオのリセットを実行できます。

Webテストにおけるフィクスチャ（Fixture）と目的は共通していますが、実現方法はプラットフォームの特性に合わせて設計されています。

## レッスン7: Maestro Flow単位の実行結果

すべてのMaestro Flowを1つのコマンドにまとめて実行してしまうと、どのFlowで失敗したのかをCI上で判別しづらくなることがあります。

Scenario ShopのAndroid CIでは、同一のエミュレータジョブの中で、Flowごとにステップを分けて実行しています。

ここで重要なのは、Flowごとにエミュレータ起動ジョブを細かく分割しすぎて、起動にかかる待機時間やランナーコストを肥大化させないことです。

## レッスン8: JUnitと実行記録

Maestroの実行結果はJUnit XML形式で保存・出力できます。

ネイティブアプリのテスト失敗時には、以下の記録も原因究明に有効です。

- Maestroのスクリーンショット／成果物
- JUnitレポート
- logcatログ
- エミュレータ情報
- APKメタデータ
- Gradleビルドログ

失敗が発生したフェーズ（ビルド、起動、テスト実行など）によって、参照すべきログや証跡が異なります。

## レッスン9: ネイティブ変更判定

ドキュメントの修正などネイティブコードと無関係な変更でも、毎回Androidビルドとエミュレータテストを実行してしまうと、ランナーコストや実行時間がかさみます。

Scenario Shopでは変更されたファイルパスを判定し、ネイティブ関連の変更が含まれない場合は高コストなジョブをスキップします。

ただし、変更検知の対象パスを過剰に絞り込みすぎると、本来ネイティブアプリに影響する変更を見落とすリスクが生じます。

コスト最適化と安全策（フェイルセーフ）のバランスを考慮することが大切です。

## レッスン10: iOSのビルド専用CI

`native-ios-ci.yml` を読み、次の流れを確認します。

```text
macOSランナー
↓
Xcode選択
↓
pnpm install
↓
expo prebuild
↓
pod install
↓
xcodebuild
↓
ビルド時メタデータ／本番ガードの検証
↓
`.app` 成果物のアップロード
```

iOSのビルドにはmacOSランナーが必須であり、Linuxランナーを用いるAndroidとはコスト特性（課金レートや並列実行制限）が大きく異なります。

単体では `workflow_dispatch` による手動ビルド検証のベースラインとして機能し、ネイティブコード変更時には最上位の `native-ci` から呼び出される必須のビルド専用ルートとなります。「ビルド成果物が生成・検証されること」と「シミュレータ上でランタイム／Maestroテストが実行されること」は別の段階として明確に区別します。

## レッスン11: AndroidとiOSを独立して考える

片方のプラットフォームで障害が発生した際、それに依存関係のない他方のプラットフォームの検証まで中断すべきかどうかを検討します。

Scenario ShopのPhase 2方針では、AndroidとiOSを独立して実行し、実行可能な検証は継続してフィードバックを得るアプローチを採用しています。

一方で、将来の最終品質ゲートにおいて両プラットフォームの成功を必須とするかどうかは、プロダクトの品質要件、ランナーコスト、フィードバック速度、テストの安定性を踏まえて慎重に判断する必要があります。

## ハンズオン1: Android Maestroを研修用CIで実行する

準備済みの研修用コピーにあるアクティブワークフローを、選択課程に関連するパスの変更、または手動実行（workflow_dispatch）によって実行します。受講者自身でワークフローのYAMLファイルを新規作成・編集することは必須ではありません。ワークフロー内では `pnpm run training:native:baseline` の後に `pnpm run training:native:exercise` が順次実行されます。

最低限、以下の工程を含めます。

1. リポジトリのチェックアウト
2. Node / Java / Android SDKのセットアップ
3. 依存関係のインストール
4. Scenario ShopのAndroidビルド
5. Androidエミュレータ起動
6. APKインストール
7. アプリ起動
8. Maestro Flow実行
9. JUnitレポートまたはスクリーンショットを成果物として保存

目的は、現行の `native-ci.yml` を完全に再現することではありません。

**ローカル環境で動作していたMaestro Flowを、GitHub Actionsのランナー環境上でも自動実行できる**ことを体験するのが本演習の目的です。

## ハンズオン2: ネイティブCIの失敗を1件分析する

研修用ネイティブワークフローにおいて、意図的な設定ミスまたは実際に発生した失敗を1件確認します。

次のプロセスのどこで失敗したかを分類します。

- Gradleビルド
- エミュレータ起動
- APKインストール
- アプリ起動
- Maestroアサーション失敗

失敗した箇所に応じて、原因特定のために最初に確認すべきログや成果物を記録します。

## ハンズオン3: 現在のAndroidネイティブCI構成を図にする

研修用ワークフローを動かした後、現行リポジトリの正式版AndroidネイティブCIのジョブ依存関係を図示します。

最低限、以下の要素を含めます。

- Detect（変更検知）
- Native Static（静的解析）
- Production Bundle Guard（本番バンドル検証）
- Android Build（ビルド）
- APK Artifact（成果物保存）
- Android Runtime / Maestro（テスト実行）
- Verify（総合検証）

準備済み研修用ワークフロー（単一ジョブ構成）と比較し、なぜ現行リポジトリではジョブの責務を分割しているのかを説明します。

## ハンズオン4: ビルドとランタイムの分離を設計する

研修用ワークフローの実行結果をもとに、次のポイントを考察します。

- ビルドに何分かかったか。
- Maestroテストだけを再実行したい場合に、何を再利用できるか。
- APKを成果物化する価値があるか。
- ジョブを分割することで新たに発生するオーバーヘッドやコストは何か。

実際に高度な分割ワークフローを一から作り直すことは必須ではありません。設計上のトレードオフと判断基準を論理的に説明できることを重視します。

## ハンズオン5: iOS構成の比較

現行の `native-ios-ci.yml` を読み、AndroidとiOSで共通する工程と異なる工程を表へ整理します。

さらに、現在iOSに単体手動実行のエントリポイントがあり、ネイティブ変更時には必須のビルド専用ルートへ組み込まれる構成を踏まえ、自分ならどこに配置するかを次の候補から選択します。

- PRで必須
- PRでは任意
- main
- 夜間定期実行（Nightly）
- 手動実行（Manual）

macOSランナーのコスト、フィードバック速度、対象となる品質リスクを理由として添えて記録します。

## ハンズオン6: ネイティブテストの実行頻度を考える

Part 1で作成したMaestro Flowについて、次の候補から適切な実行タイミングを検討します。

- PR
- main
- 夜間定期実行（Nightly）
- 手動実行（Manual）

AndroidとiOSを同一の頻度で実行すべきかどうかも含め、ランナーコストと機能の重要度を根拠として記録します。

## 確認問題

1. 初期の研修用ネイティブCIを単一ジョブ（1ジョブ）で構成・実行することのメリットは何か。
2. Androidのビルドとテスト実行（ランタイム）を別ジョブに分離するメリットは何か。
3. Maestro Flowごとにエミュレータジョブを過剰に細分化しない方がよい理由は何か。
4. ネイティブ変更検知（パスフィルタリング）を過度に最適化（厳格化）しすぎるリスクは何か。
5. Maestroのテスト失敗とエミュレータ起因の失敗をどのように切り分けるか。
6. iOS CIが現時点で `workflow_dispatch` による手動実行であることと、プルリクエストで必須の品質ゲートであることの違いは何か。
7. iOS CIにmacOSランナーが必要であることは、CIの全体設計（実行頻度やコスト）にどのような影響を与えるか。

## 自己確認

受講者自身が作成した演習差分、研修用ネイティブCIの実行結果（Run）、または成果物を具体的に示しながら以下を確認できれば、選択課程の到達度を自己評価できます。

- ベースラインと自身が作成したネイティブ演習差分を区別し、`training:native:exercise` ステップの成功と、同一Run内で出力された演習用JUnit成果物を確認できる。
- 選択課程に関連するパスのトリガー条件、失敗ステージ、成果物、およびコストの判断理由を説明できる。また、共通課程のみのファイル変更では研修用ネイティブワークフローが起動しないことを確認できる。
- Androidのビルド、エミュレータ起動、APKインストール、アプリ起動、Maestroアサーションの各失敗ステージと、初動で確認すべきログ・記録を対応付けられる。
- APK成果物を再利用する価値と、Flowごとにジョブを細分化しすぎない理由を、コストと対応の容易さ（アクション性）の観点から説明できる。
- ネイティブ変更判定によりジョブをスキップする場合のリスクと、安全策（フェイルセーフ）としての再確認手段を説明できる。
- iOSにおけるビルド時メタデータ／ガード／成果物の検証と、シミュレータ上でのランタイム／Maestro未保証の違いを区別できる（現行リポジトリの構成詳細は参考比較として扱う）。

### 復旧

ネイティブCIが失敗した場合は、ワークフロー起動、SDK／依存関係セットアップ、Gradleビルド、エミュレータ起動、APKインストール、アプリ起動、Maestroアサーションの順に確認し、該当箇所の成果物を保存します。ランナーやSDK、端末エミュレーション起因の不具合は環境トラブルとして切り分け、CI設計の理解不足と混同しないようにしてください。なお、ベースラインのみの実行記録、演習ステップの失敗、あるいは演習のJUnitレポートが欠落している成果物は原因診断用として扱い、修了に必要な「演習の成功記録」とはみなしません。修了確認においては、ワークフローYAMLの差分を求めるのではなく、演習コードの差分およびトリガー／失敗ステージ／成果物／コストに関する設計判断を確認します。

## 完了条件

本完了条件は、モバイルアプリ自動化の選択課程を履修する受講者に適用されます。Part 2共通課程のみを履修する場合はP2-6は必須ではなく、P2-5からP2-7へ直接進みます。

- 受講者自身が作成したネイティブ演習差分と、研修用ネイティブCIで取得したMaestro演習の成功成果物が正しく対応付けられていること。
- 準備済みの研修用ネイティブワークフローを選択課程関連パスの変更または手動実行（workflow_dispatch）で起動し、API 34エミュレータ上でベースライン → 演習の順に実行され、成果物が分離して保存されていることを確認していること。
- ネイティブCIの失敗要因を工程別に分類し、各失敗ステージに対応する確認ログや記録を特定できていること。
- トリガー、失敗ステージ、成果物、コストに関するCI設計上の判断を、コスト・リスク・再実行範囲の根拠とともに説明できること（研修用ワークフローYAML自体の編集は必須としません）。
- iOS CIのビルド専用境界を参考比較として理解しており、ネイティブランタイムやベースラインの成功のみを選択課程の修了実績と取り違えていないこと。
