# Part 2-2: Gitによるバージョン管理

## 学習目標

- Gitが何を管理するための仕組みなのかを説明できる。
- ワークツリー（Working Tree）、ステージング（Staging）、コミット（Commit）の関係を理解できる。
- ブランチ（Branch）を活用して作業ごとの変更を安全に分離できる。
- 差分（Diff）から変更内容を的確に確認できる。
- コミットを単なる「一時保存ボタン」ではなく、意味のある変更単位として扱える。
- Scenario Shopに加えた変更をGitを使って安全に管理できる。

## 教材

**このモジュールでは、本リポジトリ `qa-training-store` をGitの教材として使用します。**

別の教材アプリや異なるコードベースへ切り替えることはありません。Part 1で使用したScenario Shopと、Part 1で作成したPlaywrightテストおよび学習成果物を引き続き使用します。

フォーク（Fork）や演習用コピーを利用する場合も、中身は同一の `qa-training-store` をベースとします。

## Part 1からの作業環境移行

Part 1ではGitHubアカウントの作成を必須としていなかったため、配布ZIPファイルなどGitのコミット履歴を持たないフォルダで学習を進めていた受講者もいます。

その場合は、Part 2の開始時に**Gitの履歴を保持した `qa-training-store` の演習用コピーへ移行**します。

標準的な流れ:

```text
Part 1のZIP / ローカルコピー
├ 演習用Playwrightテスト
├ Maestroフロー
└ 学習成果物
        ↓ 必要な成果物だけを引き継ぐ
Git管理されたqa-training-store
├ mainブランチとリポジトリ履歴
├ Part 2用作業ブランチ
├ Part 1の成果物
└ 以降のGit演習
```

### 移行時の安全な手順（開始前の準備）

演習用コピーの準備と成果物の引き継ぎは、受講開始前にあらかじめ完了させておく環境準備作業です。共通課程の修了基準は、準備済みのGit管理コピー上でブランチ、差分（Diff）、ステージング、コミットを正しく扱えるようになることにあります。そのため、Source SHAの確認やallowlistの保守、コピー自体のセットアップ作業を受講者自身が単独で行うことは求めていません。

演習開始時には、Git管理されたコピー、Part 1の成果物、教材元のGit履歴、および既存のワークフローと分離されたトレーニング用ワークフローがそろっていることを確認します。受講者は、準備済みコピー上で自分のPart 1成果物とリポジトリ既存の資産とを差分から明確に区別し、必要な変更のみを作業ブランチに取り込んで作業を進めます。

作業ブランチの作成や、`git status`、`git diff`、`git diff --staged` などのローカルGit操作は、本モジュールの共通課程における学習対象です。コピー準備の不備や成果物の不足が発生した場合は、Gitの理解不足ではなく環境・準備面の問題として扱い、準備手順を確認した上で作業を再開します。

Part 1のZIPフォルダ内で単に `git init` を実行し、教材元のGit履歴が存在しない状態のまま進めることは、標準的な学習経路とはしません。

本モジュールでは、まずローカル環境でのGit操作を学びます。GitHub上でのフォーク（Fork）、リモートリポジトリ（Remote）、プッシュ（Push）、プルリクエスト（Pull Request）の操作は、続くPart 2-3で扱います。

## Lesson 1: Gitとは

Gitは、ソースコードやドキュメントなどの変更履歴を記録・管理する分散型バージョン管理システム（VCS）です。

主に以下の情報を正確に追跡できます。

- どのファイルが変更されたか。
- どの行が変更されたか。
- いつコミット（記録）されたか。
- どのコミットを起点としてブランチが分岐したか。

## Lesson 2: ワークツリー（Working Tree）

エディタ等でファイルを編集・保存しただけでは、まだGitにはコミットされていません。

まずは現在のワークツリーの状態を確認します。

```bash
git status
```

具体的な変更内容は、差分（Diff）を表示して確認します。

```bash
git diff
```

作業時には、意図していない不要な変更が混ざっていないかを必ず確認する習慣を身につけます。

## Lesson 3: ステージング（Staging）

コミットに含める変更対象を選択してインデックス（ステージングエリア）に登録します。

```bash
git add path/to/file
```

何でも機械的に `git add -A` でまとめて追加するのではなく、今回のコミットに含める変更範囲を正しく理解した上でステージングすることを学びます。

## Lesson 4: コミット（Commit）

コミットは、意味のある1つの変更単位として作成します。

良いコミットメッセージの例:

```text
test: add cart out-of-stock E2E
```

避けるべきコミットメッセージの例:

```text
fix
update
work
```

コミットメッセージを読んだだけで、変更の目的や意図がおおむね把握できる状態を目指します。

## Lesson 5: ブランチ（Branch）

製品や基準となる既存の `main` ブランチに直接変更を積み重ねるのではなく、作業専用のブランチを作成して変更を分離します。

```bash
git switch -c training/cart-e2e
```

ブランチを活用することで、現在安定している状態と、作業途中の変更内容を切り離して安全に扱うことができます。

本Git演習においても、最初の変更やコミットを `main` 上で行ってから後追いでブランチを切るような手順はとりません。Part 1からの移行時点で作業ブランチを作成し、そのブランチ上で変更の確認、ステージング、コミットを行います。

## Lesson 6: 差分（Diff）を読む

コミットを実行する前には、必ず差分を確認します。

確認の観点:

- 意図したファイルだけが含まれているか。
- デバッグ用のコードや一時的な記述が残っていないか。
- テストの検証内容を意図せず弱めて（緩めて）いないか。
- 認証情報や個人情報などの機密情報が含まれていないか。
- 本質的でない大量のフォーマット変更（自動整形による差分など）が混入していないか。

テスト自動化においては、ロケーター（Locator）やアサーション（Assertion）を誤って削除・変更していないかも重要な確認観点となります。

## Lesson 7: 変更履歴（History）

代表的な履歴の確認方法:

```bash
git log --oneline
```

コミット履歴を辿ることで、「いつこのテストが追加されたのか」「どの変更によってアプリケーションの挙動が変わったのか」を正確に追跡できることを理解します。

Part 1をZIPファイルで進めていた受講者は、ここで「自分が受け取った1時点のスナップショット」と「リポジトリ全体が保持している変更履歴」の違いを具体的に確認します。

## Lesson 8: コンフリクト（競合）の考え方

複数の変更が同一ファイルの同じ箇所に加わると、コンフリクト（競合・Conflict）が発生することがあります。

コンフリクトはGitの動作不良やエラーではなく、「どちらの変更を採用すべきか、人間による判断が必要になった状態」を指します。

自動テストのファイルはチーム開発で複数人が同時に編集する可能性が高いため、1つの巨大なファイルに変更を集中させすぎるとコンフリクトが起きやすくなる、という点も考慮して設計します。

## ハンズオン1: Part 1の成果物をGit管理下で確認する

Part 1から引き継いだ演習用テストまたは学習成果物を1つ選びます。

以下の点を確認します。

- 自分が追加・変更したファイルはどれか。
- `main` ブランチの状態とどのような差分があるか。
- Gitの履歴に含まれている既存ファイルと、自身が追加した成果物を区別できているか。
- `.git` フォルダや既存のリグレッションテストなど、引き継ぎ対象外のファイルを誤って上書きしていないか。

ZIPファイルから移行した場合は、成果物を引き継いだ直後の差分を確認します。

この時点ではまだコミットしません。まずは「現在どのような変更が存在しているか」を把握します。

## ハンズオン2: 作業ブランチとmainの境界を確認する

Part 1の成果物移行時に作成した作業ブランチを確認します。

```bash
git branch --show-current
```

以下の点を確認します。

- 現在チェックアウトされているブランチが `main` ではないこと。
- Part 1から引き継いだワークツリー上の変更が、作業ブランチ上に正しく存在すること。
- `main` を安定した基準点として残したまま演習を進められる状態であること。
- `main` と現在のワークツリー／ブランチとの差分を説明できること。

ブランチを作ること自体が目的ではなく、**変更やコミットをどの作業単位に属させるかを事前に決定しておくこと**の重要性を学びます。

## ハンズオン3: Playwrightテストの変更をコミットする

作業ブランチ上で、Part 1で作成したテストに小さな改善を加えます。

改善例:

- テストタイトルの改善
- ロケーターの改善
- アサーションの追加

編集後、以下の順序で確認とコミットを行います。

```text
status（状態確認）
↓
diff（変更内容の確認）
↓
add（ステージング）
↓
diff --staged（コミット対象の差分確認）
↓
commit（意味のある単位で記録）
```

最初の演習コミットを誤って `main` ブランチへ直接作成していないことも併せて確認します。

## ハンズオン4: 意図しない変更を除外する

演習用として、別のファイルに無関係な変更をあえて加えます。

`git status` と `git diff` を使って全体の変更を確認した後、今回のコミットに必要なファイルだけを選択してステージングします。

ここでの目的は、「すべての変更を無差別に一括コミットする」のではなく、意味のある変更単位を自身で選択してコミットできるようになることです。

## ハンズオン5: mainとの差分と履歴を確認する

作業ブランチ上でコミットを作成した後、以下を確認します。

- `main` ブランチと作業ブランチの差分
- 新しく作成されたコミット
- Part 1の成果物と今回の改善内容との関係

自身の変更がどのブランチ・どのコミットに属しているかを説明できるようにします。

## 確認問題

1. ファイルを保存した状態と、Gitにコミットした状態の違いは何か。
2. ステージングエリア（インデックス）が存在することで、どのような操作が可能になるか。
3. ブランチを使用する目的は何か。
4. 最初の変更やコミットを行う前に、あらかじめ作業ブランチを作成しておく理由は何か。
5. コミットを実行する前に差分（Diff）を確認すべき理由は何か。
6. テストファイルを1つの巨大なファイルにしてしまうと、Git運用上どのような問題が発生しやすくなるか。
7. Part 1をZIPファイルで進めた受講者が、Part 2の開始時にGit履歴を持つ演習用コピーへ移行する理由は何か。
8. Part 1のフォルダ内で単に `git init` を実行するだけでは、教材リポジトリの履歴を学べないのはなぜか。
9. Part 1のフォルダ内容を丸ごとGit管理済みコピーへ無差別に上書きしてはいけない理由は何か。

## 自己確認

自身のブランチと差分を実際に指し示しながら、以下の項目を説明できれば共通課程修了の判断材料となります。

- ワークツリー、ステージング、コミットのそれぞれの違いを説明できる。
- Part 1の成果物、教材元の履歴、および自分自身の変更を差分から区別できる。
- 最初の演習変更やコミットを `main` 上で行わず、先立って作業ブランチを用意した理由を説明できる。
- 意図したファイルのみをステージングし、ステージ済み差分（Staged Diff）を確認した上で、意味の通じるコミットメッセージでコミットできる。
- 演習用コピーのSource SHAの確認、allowlist、コピーの事前準備は開始前の環境準備であり、準備済みコピーを利用する共通課程の修了要件に内在する学習課題ではないと説明できる。

### リカバリ手順

ブランチや差分の状態が分からなくなった場合は、一度作業を止め、`git status` → `git branch --show-current` → `git diff` → `git diff --staged` の順に現在の状態を確認します。準備済みコピーやPart 1の成果物が手元に見当たらない場合は、受講者のGit理解不足と決めつけず、環境・準備上の課題として記録した上で準備手順を再確認して再開します。

## 完了条件

- 準備済みのGit管理された `qa-training-store` コピー上で、Part 1の成果物と自身の変更を区別できる。
- 教材元のGit履歴と自身の変更を区別できる。
- Part 1の成果物を扱う前に作業ブランチを作成し、`.git` フォルダや既存のリグレッションテストを無差別に上書きしない境界を説明できる。
- `main` ブランチへ直接演習コミットを作らず、作業ブランチ上で変更を適切に管理できる。
- 変更内容を `git diff` で確認できる。
- 意図したファイルのみをステージングできる。
- ステージ済み差分を確認してから、意図が明確に伝わるメッセージでコミットできる。
- `main` との差分、および自身のコミットが保持している変更内容を説明できる。
