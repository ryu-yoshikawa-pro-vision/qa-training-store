# スプレッドシートによるテスト分析・設計

## 学習目標

- テストコードの実装に着手する前に、テスト対象とテスト条件を論理的に整理できる。
- Google スプレッドシートなどを活用し、実際のプロジェクト現場にも展開しやすい形式でテスト設計を管理できる。
- 単なる操作手順書ではなく、テスト条件・期待結果・リスク・自動化の要否判断を軸として管理できる。
- 同値分割法、境界値分析、デシジョンテーブル、状態遷移テストなどの設計技法を用いて、テスト条件を体系的に導出できる。
- テストケースID、テスト階層、使用ツール、実装コードを正しく紐付けられる。

## 標準CSVと段階的な入力手順

4つのCSVファイルは、以下の順序に沿って使用します。最初からすべての列を埋めようとするのではなく、各レッスンで必要になった列のみを順次確認し、記録していきます。

| CSVファイル | 役割 | 必須トレーサビリティ |
| --- | --- | --- |
| `01_target-risk.csv` | テスト対象、仕様参照、リスク | `target_id` → `spec_ref` / `br_ids` / `ac_ids` → `risk_id` |
| `02_test-cases.csv` | テスト条件、前提条件、期待結果、テスト設計技法 | `risk_id` → `test_case_id` |
| `03_automation-mapping.csv` | 自動化判断（Automate / Later / Do not automate）とテスト階層 | `test_case_id` → `implementation_path` |
| `04_execution-improvement.csv` | 実行結果、実行記録、失敗分類、改善策 | `test_case_id` → `evidence` |

複数のBRやACを紐付ける場合は、`;`（セミコロン）で区切ります。テスト対象、リスク、テストケースを繋ぐ主キーとなるID列は必ず入力し、BR / ACなど直接対応する識別子が存在しない項目についてのみ空欄を許容します。

なお、`implementation_path` は未実装の場合や「Do not automate（自動化しない）」と判断して実装パスが存在しない場合、`evidence` は未実行の場合、`failure_category` はPassまたは未実行の場合に空欄とすることができます。`cause`（原因）、`action`（対応）、`improvement`（改善策）は、調査の進捗に応じて追記していきます。実在しないファイルパスや架空の実行記録でセルを埋めることは避けてください。

テストケースIDの命名形式については、[ワークブックのREADME](../../../training/workbook/README.md)を正本とし、本文書では具体例の提示にとどめます。

成果物の正本となるのはこれら4つのファイルです。後述する8つのシート風の設計ビューは、4つのCSVを設計観点ごとに見やすく整理した**概念上の設計ビュー**であり、8つの独立したCSVや成果物の提出を求めるものではありません。

| 設計ビュー | 対応する標準CSV |
| --- | --- |
| `01_テスト対象分析` / `02_リスク分析` | `01_target-risk.csv` |
| `03_テスト観点` / `04_テストケース` | `02_test-cases.csv` |
| `05_自動化候補` / `06_自動化対応表` | `03_automation-mapping.csv` |
| `07_実行結果` / `08_改善管理` | `04_execution-improvement.csv` |

## なぜスプレッドシートを使うのか

本カリキュラムでは、テスト分析・設計の基本ツールとしてGoogle スプレッドシートを想定しています。

その主な理由は以下のとおりです。

- Google Workspaceなどの業務環境ですぐに利用しやすい。
- QA担当者だけでなく、開発者、プロダクトマネージャー（PdM）、運用担当者も手軽に閲覧・共有できる。
- 特定の商用テスト管理ツール固有の操作に知識を依存させない。
- 別のプロジェクトや現場へ移っても、設計の考え方やフォーマットをそのまま持ち運べる。
- フィルタ、ソート、入力規則、条件付き書式など、テスト管理に必要な最小限の機能を網羅している。

ただし、スプレッドシートの利用自体が目的ではありません。プロジェクトの規模が拡大し、専用のテスト管理ツールを導入することになった場合でも、ここで学ぶ分析・設計の思考法はそのまま活用できます。

## 詳細な操作手順を過剰に書き出さない

次のように、画面の細かな操作手順だけをひたすら列挙する管理方法は、本カリキュラムの主眼ではありません。

```text
1. 商品一覧を開く
2. 商品Aをクリックする
3. サイズMをクリックする
4. カートに追加をクリックする
5. メッセージを確認する
```

自動テストへ繋げるテスト設計において、より重要なのは以下の観点です。

- 何を確認したいのか（検証の目的）。
- どのような条件で確認するのか（入力値や環境条件）。
- どのような初期状態が必要か（事前状態・テストデータ）。
- 何が満たされれば合格とするのか（期待結果）。
- その検証はビジネス上どの程度重要か（リスクと優先度）。
- 自動化に適しているか（自動化の採否判断）。

## 4つのCSVに記録する設計観点

本ワークブックで作成・更新する正式な成果物は4つのCSVファイルです。画面分析、リスク、テスト観点、実装、実行、改善をそれぞれ別個のシートとして提出する必要はありません。各観点は、以下の列に対応づけて記録します。

| 設計観点 | 記録先ファイル | 主な記録内容 |
| --- | --- | --- |
| 対象・リスク | `01_target-risk.csv` | テスト対象、仕様参照、BR / AC、リスク、影響度、発生確率、優先度 |
| 条件・設計 | `02_test-cases.csv` | テストケースID、リスクID、前提条件、テスト条件、期待結果、適用したテスト設計技法 |
| 自動化判断・実装 | `03_automation-mapping.csv` | 自動化判断（Automate / Later / Do not automate）、テスト階層、ツール、実装パス、判断理由 |
| 実行・改善 | `04_execution-improvement.csv` | 実行コンテキスト、実行結果、実行記録、失敗分類、原因、対応、改善策 |

テスト階層は「どの層でリスクを検証するか」、ツールは「その階層をどの手段で実行するか」を表します。Part 1ではテスト実行頻度の本格的な設計までは行わず、Part 2でCIのトリガー設計とあわせて検討します。

観点を単に箇条書きで並べて満足するのではなく、同値分割法、境界値分析、デシジョンテーブル、状態遷移テストなどを適用し、CSV上の具体的なテスト条件と期待結果へと落とし込んでください。実行時のエビデンスは後から再現可能な参照情報として残し、未実行の行に予定の参照パスを記入してはいけません。実際に存在を確認した証拠の参照先だけを記録します。

## テスト条件を導出するための技法

### 1. 同値分割法

同一の振る舞いになると想定される入力値やシステム状態をグループ（同値クラス）としてまとめ、その中から代表値を選定します。

カートの購入数量上限が5個と定められている場合の例：

| 同値クラス | 条件 | 代表値 |
| --- | --- | --- |
| 無効同値クラス | 0以下 | 0 |
| 有効同値クラス | 1から5 | 3 |
| 無効同値クラス | 6以上 | 6 |

「1個、2個、3個、4個、5個をすべて同じE2Eテストで試す」のではなく、システムが同一の処理を行う範囲を見極めてテストケースを効率化します。

### 2. 境界値分析

不具合は仕様の境界線付近で発生しやすいため、同値クラスの端にある値を重点的に検証します。

購入上限が5個の場合、例えば以下の値を検討します。

- 0（無効側の境界）
- 1（有効側の最小値）
- 5（有効側の最大値）
- 6（無効側の境界）

これらの境界値をUI E2Eテストでどこまでカバーするかは、リスクの高さと単体テストや統合テストなどの下位テストでの網羅性を考慮して判断します。

### 3. デシジョンテーブル

複数の条件が複雑に組み合わさることで動作結果が変化する場合に活用します。

条件を大雑把にまとめすぎるとビジネスルールの差異が見落とされてしまうため、購入可否の判定であれば「ログイン済みか」「ロールがcustomerか」「アカウント状態がactiveか」のように、独立した判定要素に分解して整理します。

例：

| ログイン済み | ロール = customer | アカウント状態 = active | 在庫あり | 購入上限内 | 期待結果 |
| --- | --- | --- | --- | --- | --- |
| 〇 | 〇 | 〇 | 〇 | 〇 | チェックアウト可能 |
| × | - | - | 〇 | 〇 | ログインが必要 |
| 〇 | × | - | 〇 | 〇 | ロール権限により購入不可 |
| 〇 | 〇 | × | 〇 | 〇 | アカウント状態により購入不可 |
| 〇 | 〇 | 〇 | × | 〇 | 在庫切れにより購入不可 |
| 〇 | 〇 | 〇 | 〇 | × | 数量上限超過により購入不可 |

※ `-` は、そのルールにおいて結果に影響を与えない条件を表します。

ゲスト、停止中の顧客、オペレーター、管理者を単に「有効な一般顧客ではない」とひとくくりにするのではなく、**拒否される理由や表示されるエラーメッセージが異なる条件は明確に分離して整理する**ことが重要です。

すべての組み合わせを機械的にUI E2Eテスト化するのではなく、ビジネスルールとそれに付随するリスクを正確に理解するために活用します。

### 4. 状態遷移テスト

チェックアウト、決済処理、注文確定、配送手配などのように、時間の経過やイベントによって変化する振る舞いは状態遷移として整理します。

```text
決済処理中
├ 成功 → 注文決済完了
└ 失敗 → 決済失敗 → 再試行 → 成功
```

単に「各状態が存在するか」だけでなく、以下の観点を確認します。

- 許可されている正常な遷移
- 許可されてはならない不正な遷移
- 再試行（リトライ）が可能な状態
- 画面のリロードやアプリ再起動後も正しく保持されるべき状態

### 5. ロール／権限マトリクス

ユーザーのロール（役割）に応じて操作の可否が切り替わる場合は、ロール × 操作の対照表を作成します。

| 操作 | ゲスト | 顧客（customer） | オペレーター（operator） | 管理者（admin） |
| --- | --- | --- | --- | --- |
| 商品閲覧 | 〇 | 〇 | 〇 | 〇 |
| 商品購入 | × | 〇 | × | × |
| 在庫運用 | × | × | 〇 | 〇 |
| ユーザー管理 | × | × | 制限あり | 〇 |

こちらも全組み合わせを自動テスト化するのではなく、権限の境界線となる操作や、権限漏れのリスクが大きい箇所を重点的に選定します。

### 6. シナリオ／ユースケーステスト

複数の画面をまたいで進行する一連の業務フローは、単一画面の機能テストとは切り離し、テストシナリオやユーザージャーニーとして整理します。

例：

```text
ゲスト状態で商品をカートに追加
→ ログインを実行
→ ゲストカートの商品を会員カートへ統合
→ チェックアウトへ進行
→ 決済を完了
→ 注文履歴画面で内容を確認
```

ビジネス上きわめて重要となる機能間・画面間の連携リスクを検証するために用います。

なお、ここで扱う「テストシナリオ／ユーザージャーニー」は、アプリケーションを確定的な初期状態へと巻き戻す「初期状態リセットシナリオ（Seedシナリオ）」とは異なる概念であることに留意してください。

### 発展課題: 組み合わせテスト技法（ペアワイズ法など）

条件やパラメータが膨大に存在する場合、ペアワイズ法などを用いて組み合わせ数を最小限に絞り込むアプローチがあります。

ただし、これはPart 1の必須要件ではありません。まずは同値分割法、境界値分析、デシジョンテーブル、状態遷移テストを確実に使いこなせるようになることを優先してください。

## 演習1: カート機能を分析する

Scenario Shopのカート機能について、実装コードを見る前に実際の画面を探索・操作してみます。

最低限、以下の挙動を確認してください。

- ゲスト状態で商品をカートに追加できること。
- 数量の変更ができること。
- 商品の削除ができること。
- カートが空の状態の表示があること。
- 在庫切れ商品の扱いが存在すること。
- 残りわずかな在庫（低在庫）の表示があること。
- 購入数量の上限が設定されていること。
- ログイン時にゲストカートの内容が統合されること。

探索を終えたら、`01_target-risk.csv` に対応するテスト対象分析とリスク分析、および `02_test-cases.csv` に繋がるテスト観点を整理します。

## 演習2: テストケースへ落とし込む

導出した観点をもとに、以下のようなテストケースを定義します。

| テストケースID | テスト条件 | 初期状態（Seed） | 設計根拠 | 期待結果 |
| --- | --- | --- | --- | --- |
| TC-CART-001 | 同一SKUを上限まで追加した後、さらに追加を試みる | default | 境界値分析 / 状態遷移 | 追加が拒否され、既存の数量が維持される |
| TC-CART-002 | 購入不可明細を含むカートからチェックアウトへ進む | cart-with-invalid-items + customerログイン | 状態再検証 | 購入不可の理由が表示され、チェックアウトへ進行できない |

上記の `TC-CART-001` および `TC-CART-002` は、設計の考え方を示すためのサンプルです。これらをそのまま課題の成果物としてコピーするのではなく、受講者自身のケースには `TC-CART-101`、`TC-CART-102` などの固有のIDを付与してください。サンプルの条件を参考にする場合でも、対象リスク、前提条件、期待結果、選定理由は、自分自身の画面観察と仕様書の記述をもとに言語化してください。

ケース数をやみくもに増やすことよりも、「なぜそのテスト条件が必要なのか」を論理的に説明できることを重視します。

## 演習3: 自動化対象を選定する

作成したテストケースのそれぞれについて、以下の観点から自動化の可否を判断します。

判断結果は、`03_automation-mapping.csv` の `automation_decision` 列に、`Automate`、`Later`、`Do not automate` のいずれかで記録してください。なお、デシジョンテーブルやロール／権限マトリクスで使用した `〇` / `×` は条件判定の例であり、この列に入力する値ではありません。

- 繰り返し頻繁に実行するテストか。
- 合否の判定を機械的・確知的に行えるか。
- 前提となる初期状態を安定的・確定的に再現できるか。
- リグレッション（先祖返り）の検知として重要度が高いか。
- 実行時間やメンテナンスにかかるコストと、得られる品質効果が見合っているか。
- コストの高いUI E2Eテストとして実装する価値があるか。
- より下位の単体テストや統合テストで検証すべき内容ではないか。

## トレーサビリティの確保

実装したテストコードには、可能な限りテストケースIDを対応づけておきます。

例:

```ts
// TC-CART-002
test("在庫切れ商品はカートへ追加できない", async ({ page }) => {
  // ...
});
```

テストケースIDをコメントとしてコード内に記載する方式、テストタイトルに含める方式、Playwrightのアノテーション機能を活用する方式など、プロジェクトの運用方針に合わせて選択できます。

一方で、画面上のUI要素を特定するためのUIテストID（`testId`）は、テストケースIDとはまったく異なる識別子です。両者を混同しないよう注意してください。

最も重要なのは、**スプレッドシート上の設計内容と、実際の自動テストコードとの対応関係を双方向に追跡できる状態を作ること**です。

## 確認問題

1. 詳細な操作手順を過剰に書きすぎると、自動テストの設計や運用においてどのような問題が生じるか。
2. 同値分割法と境界値分析にはどのような目的・性質の違いがあるか。
3. 複数のビジネスルールが複雑に組み合わさる場合、なぜデシジョンテーブルが有効なのか。
4. ログイン状態、ユーザーロール、アカウント状態をひとつの条件にまとめてしまうと、どのようなルールの見落としが発生しやすいか。
5. `out-of-stock`（在庫切れ）の初期状態シナリオ（Seedシナリオ）は、どのようなテスト条件を安定して再現するために活用できるか。
6. ビジネス上きわめて重要なテストであっても、「自動化しない（Do not automate）」という判断が妥当になるのはどのような場合か。
7. UI E2Eテストではなく、単体テストや統合テストなどの下位レイヤーに任せるべき検証条件にはどのようなものがあるか。
8. テストケースIDと実装コードを紐付けてトレーサビリティを維持することのメリットは何か。

## 自己確認

### 回答の評価基準

確認問題への回答には、以下の要素が過不足なく含まれているか確認してください。

- 操作手順を細かく書きすぎることのリスク、同値分割法と境界値分析の違い、デシジョンテーブルが有効となる条件を、カートやチェックアウトの具体的な挙動と結びつけて説明できていること。
- ログイン有無・ロール・アカウント状態を分離して整理すべき理由と、異なる拒否理由やエラーを別ケースとして切り出すべき理由を説明できていること。
- `out-of-stock` が前提状態を再現するためのSeedシナリオであること、およびUI E2Eテストから外す判断の背景にテスト階層・保守コスト・再現性の観点があることを論理的に説明できていること。
- テストケースID、リスク、BR / AC、テスト階層・ツール、実装パス、実行記録のトレーサビリティが、1行のデータとして破綻なく追跡可能であること。

### つまずいたときの復帰手順

- 回答の根拠となる「理由」をうまく言語化できない場合は、対象機能のBR / ACおよび[状態とシナリオ](../../spec/state-and-scenarios.md)へ立ち返り、ひとつのテストケースについて「リスク → テスト条件 → 期待結果 → テスト階層／ツール」の順序で再構成してみてください。
- CSVの各列の意味やIDの付け方が曖昧な場合は、[ワークブックのREADME](../../../training/workbook/README.md)と標準CSVのヘッダー定義を確認してください。なお、ツールの不具合等でCSVが開けない問題は、学習上の理解度不足ではなく、作業環境上のトラブルとして切り分けて記録してください。

## 完了条件

- Scenario Shopの1機能以上を対象として、テスト対象分析を作成していること。
- 潜在するリスクとテスト観点が論理的に整理されていること。
- 選定したテスト設計技法をScenario ShopのリスクやBR / ACに適用し、その技法を選んだ意図を説明できること。
- テストケースID、リスク、仕様参照、テスト条件、期待結果、テスト階層／ツール、実行記録の相互関係を説明できること。
- 複数条件が絡むルールを、デシジョンテーブル等を用いて適切に分解・説明できること。
- 各テストケースについて自動化の可否判断とその理由が明確に記述されていること。
- 少なくとも1件のテストケースについて、PlaywrightまたはMaestroで自動化するための前提条件を説明できること。

※演習の目安として5件以上のテストケース作成や複数の設計技法の適用が推奨されますが、単に作成した件数や使った技法の数だけで完了とはみなしません。
