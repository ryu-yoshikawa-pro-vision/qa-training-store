# カリキュラムの自主学習レビュー確認項目

この文書は、カリキュラムの自主学習における品質を確認するための基準のみを定めたチェックリストです。個別のレビュー結果、レビュー担当者、日付、合否（PASS）履歴、指摘事項（Finding）、エビデンス、進捗状況などを記録・保存する欄は設けていません。

## 対象者 / 前提知識の深さ

- 対象となる受講者、受講条件、前提知識、使用するリポジトリやツールが、受講者向けの教材だけで明確に把握できる。
- 共通課程の必須範囲、モバイルアプリ自動化の選択課程、拡張課題（Extension）、参考資料（Reference）、発展課題（Advanced）の前提条件を明示し、選択しなかった内容を共通課程の修了要件における隠れた前提にしていない。
- リポジトリに同梱すべき支援用アセット、講師によるサポート、受講者自身が果たすべき必須の責務が明確に切り分けられている。

## ナビゲーション / スキップ / 分岐 / 合流

- 共通の入り口（Shared entry）から各レッスンへと進む順序が一意に定まっている。
- 共通課程の次の手順、モバイルアプリ自動化の選択課程における分岐、スキップ条件、合流先が、受講者向けの必須教材のみで把握できる。
- 次に行うべき行動の案内が、演習、自己確認、復旧、修了の各ステップよりも前に配置されていない。
- 任意課題、過去の資産（Legacy）、講師用資材へのリンクが、必須の学習経路に見えないよう配慮されている。

## 目標 → 説明 → 演習 → 成果物 → 自己確認 → 修了

- 学習目標と解説が、実際の演習（Practice）で確認する判断基準へとしっかり結びついている。
- 演習の対象、具体的な操作手順や設計作業、期待される成果物が明確に示されている。
- 自己確認（セルフチェック）において、知識問題であれば必須となる最低限の回答要素が、トレードオフを伴う問題であれば最低限考慮すべき事項と許容される理由の範囲が示されている。
- 修了判定において、単なる件数、適用したテクニックの数、ベースラインや既存テストの通過（Baseline / stock PASS）のみに依存せず、判断の質と成果物の対応関係を確認している。
- 受講者が自己確認から修了要件の達成を判断し、次に取るべき行動を自分で決定できる。

## 講師の非公開情報に依存しない回答可能性

- 確認問題への回答に必要な仕様（Spec）、業務ルールや受入基準（BR / AC）、リポジトリ内のアセット、用語、期待される判断の範囲が、公開資料から追跡できる。
- 単一の模範解答を求めるトレードオフ問題において、最低限考慮すべき事項と、回答として許容される理由の範囲が明確に示されている。
- 模範解答（Answer Key）、講師だけが把握している判断基準、未公開の環境状態などを、修了（Completion）の判定根拠にしていない。

## 復旧

- 学習上の未理解と、コマンド、パーミッション、アカウント、デバイス、ツールチェーン、ワークフローなどの環境トラブルによる問題とを切り分けるための確認手順（入口）が用意されている。
- 失敗した際に立ち戻るべき最初の確認箇所、再確認すべきエビデンス、学習を再開するレッスンや演習（Exercise）が有限かつ明確に示されている。
- ベースラインの再実行、リトライ、既存成果物の存在確認だけで、受講者自身が作成した成果物による修了の代替としていない。

## 共通課程 / 発展課題 / 参考資料 / 選択課程の境界

- 共通課程の範囲のみで、定義された能力基準（Competency）と必要最低限の成果物を満たすことができる。
- モバイルアプリ自動化の選択課程、プラットフォーム固有事項、リポジトリ固有事項、役割横断（Cross-role）の要素、アクセシビリティテストの実行、Preview / Production環境の差異、発展的な内容（Advanced）が、共通課程の必須範囲に混入・逆流していない。
- ネイティブ（Native）を選択しない場合のスキップ手順と、選択した場合に必要となる追加エビデンスおよび共通フローへの合流（rejoin）手順が明示されている。
- 参考資料（Reference）は最新の設定値や運用支援への案内として扱い、受講者向けの学習・自己確認・修了判定における不要な第3の信頼できる情報源（SSOT）にしていない。

## コマンド / 成果物 / 環境上の問題

- コマンド、テスト、成果物ごとに、成功、学習上の失敗、環境トラブルによる問題の意味合いが明確に区別されている。
- 成果物（Artifact）は対象、操作、事象、取得元が正しく対応しており、ベースラインのものと受講者作成の演習成果物とを混同していない。
- 現在のコマンド、ワークフロー、初期シードデータ、時刻（Clock）、アドレス、プラットフォーム固有の値を教材内へ複製（二重管理）せず、既存のSSOTを参照する経路が用意されている。
- 外部サービス、シークレット（秘密情報）、利用枠（Quota）、実機デバイスなどが必要な場合、受講者自身が準備すべきか講師側が支援するかが明記されている。

## 用語

- 一般的な解説は日本語を中心とし、ツール名、製品名、API、コマンド、パス、識別子（identifier）などは公式のリテラル表記を維持している。
- 共通課程、モバイルアプリ自動化の選択課程、Extension、Referenceなどの分類用識別値が一貫している。
- 業務ルール（BR）、受入基準（AC）、IDの命名規則（grammar）、ツールで機械処理される見出し、UI上の文言を、不用意に翻訳したり別表記に変えたりしていない。

## 仕様参照の安全性

- 基本仕様（Normative Specification）、補助資料（Supporting Source）、実行可能な正準実装（Executable Canonical Source）の責務を区別している。
- 仕様の曖昧な箇所やプロダクト判断（Product Decision）が必要な部分を、教材側の推測や「観測された実際の挙動（Observed Behavior）」だけで安易に埋めていない。
- 仕様への参照から該当する機能（Feature）、業務ルール/受入基準（BR / AC）、状態遷移/シナリオ（State / Scenario）の各セクションへ確実に到達でき、仕様値における第3のSSOTを作っていない。

## 専門的な指摘の成立条件とエビデンス

- 専門的な指摘事項（Finding）は、対象ファイル、見出し・セクション、観測された問題と影響、最小限の修正案、対応方針（Disposition）、解決を確認するための検証手順（Validation）が一意に特定できる。
- 指摘の重要度（Severity）や優先度が、対象となる規約・契約、学習経路、ユーザーへの影響と適切に対応付けられている。
- 結果分類: 観測した事象を「Bug」「UX」「Suggestion」「未確定」に明確に区別する。現行の基本仕様（Normative Specification）の業務ルール・受入基準（BR / AC）に反することが再現手順とエビデンスで確認できる場合は「Bug」、仕様違反とまでは断定できない利用上の懸念は「UX」、現行仕様への違反ではなく新しい振る舞いや機能追加を求めるものは「Suggestion」、再現条件・仕様根拠・エビデンスが不足している場合は「未確定」として扱う。
- 解決済み（resolved）の根拠は、該当レッスンの自己確認（Self-check）、修了判定（Completion）、導線（Navigation）、仕様参照、または実行時の成果物（Artifact）など、対象に適したエビデンスで確認できる。
- 過去の候補ブランチ（Candidate）、別のプルリクエスト、ベースラインの状態のみを根拠に、現在のリポジトリに対する指摘事項を確定していない。
- 独自の指摘事項データベース、エビデンス管理台帳、スコアリングシステム、個別結果の保存欄を勝手に新設せず、既存の実行成果物（Run Artifact）や対象ドキュメント本来の管理領域を活用している。

## 確認項目の境界

- 本チェックリストは基準の再利用に限定し、特定の実行（Run）結果や個別の受講者（Learner）に対する判定結果を記録しない。
- 実際の確認手順では、本基準を用いて共通課程の共通区間を一度確認したうえで、ネイティブ（Native）や発展課題（Advanced）の差分項目のみを追加で確認する。
