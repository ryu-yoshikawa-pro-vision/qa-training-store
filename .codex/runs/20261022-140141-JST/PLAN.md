## Approach（進め方）
1. 指定Planと現行コードを基準に、最小の実行経路を先行検証する。
2. M02→M03、M05→M06の代表教材・クイズ・実技・公開状態契約を作成し、正式仕様照合、コード/教材レビュー、自動・静的・契約検証を開発中に行って結果を反映する。
3. 上記の開発受入が通過したら、代表教材の実地受入を待たずに残る全モジュール・全機能へ展開する。
4. Web、同期/ロード、状態・知識グラフ検証、回帰テストを実装する。
5. 全11モジュールと関連機能の実装完了後に、実受講者/評価者・2コアCodespacesでの実地検証を行う。これは実装完了の条件ではなく、結果を運用開始判断へ渡す。
6. 旧課程の境界を検証し、Run成果物・差分・ローカルゲートを確定してからcommit/pushする。
7. 最新PR headでWeb CI/Mobile App CIを待機し、PR本文の実装・検証・未完了・実地検証の位置づけを同期する。merge等はしない。

## Definition of Done（完了条件）
- Plan修正タスクDoD: 全体Plan/関連詳細Plan/決定事項の達成基準と実地検証順序を整合し、実装完了・実地検証・運用開始判断を分ける。代表教材の仕様/コード/教材レビューと自動検証を全量展開条件に残し、人間の実地受入を移す。文書lint/link/format検証を行い、PR本文を更新する。
- Curriculum implementation DoD: 全体Planと対象詳細Planで定義した全11モジュールのWeb教材・クイズ・実技・開始終了データ・評価基準・非公開模範/採点資料、51学習目標/知識・教材・評価対応、版付き再開、1問ずつのクイズ、非公開境界、同期/ロード、M02→M03固定Skill統合検証などを完成し、必須自動/契約/静的/CI検証と正式仕様照合を通過する。
- 実地検証は全実装後に別途行う。未実施/不合格だけで実装完了を未完了扱いせず、BLOCKEDにも分類しない。実地で実装欠陥が判明した場合は別の修正として開発ゲートを再実行する。
- 旧課程/製品/正式回帰への非回帰を確認する。外部Template名/権限、非公開保管先/アクセス権、評価者、費用条件は指定されるまで推測しない。
- local HEAD・remote branch・PR head整合、通常push、最新SHAの必須CI成功とPR本文更新を確認する。

## Risks / Unknowns（リスク・未知点）
- 人間による初心者試行/独立採点と2コアCodespaces実測は全量実装後の実地検証。未実施は現在の開発ゲートをBLOCKEDにしない。
- 外部Template名称・権限、非公開保存先・評価担当者、個人費用は運用開始判断まで未指定のまま維持する。
- M02→M03の実データ固定Skill通し検証と、M05→M06の必要な実技/開始データは開発時に残る受入項目であり、実地検証へ移さない。
- .gitへの書込はsandboxで拒否された。Git commit/push/fetchは明示承認済みだが、通常経路での実行可否を安全に確認する。
- 静的なソース依存調査だけでは学習用リポジトリ単体でBuild/Serve/Reset/Playwrightが成立した証拠にならない。
